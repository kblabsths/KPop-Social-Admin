Two read kinds. Pick deliberately; do not blur them.

1. **Complete read — `readComplete(missing, run, db?)`, new in `src/lib/db/result.ts`.** Use it whenever the surface presents the result as the whole set: a list the page shows in full, a count, an oldest age, an "exactly the matching items" claim. The `run` callback passes `{ count: "exact" }`, a total `.order()` ending in the primary key, and `.range(0, cap - 1)` with the cap handed in. If the exact count exceeds the rows returned, it returns `kind: "error"` naming the object, the count and the cap. **An `ok` array from a complete read is the whole matching set** — that property is what every figure in this app rests on, and it is why no caller needs a "was this all of it?" flag.
2. **Window read — `readRows`, unchanged.** The caller's own `.order()` + `.limit()` define a named window, and the surface says which window it is showing. This is section 8's gauge contract and TASK-0007's landed gauges use it correctly. A window read's rows must never become a figure presented as a total.

- 2026-09-02T12:35:40Z [architect] Architect ruling, 2026-09-02 — the four data-surface states are now a TYPED contract (TASK-0030, ARCHITECTURE section 7, DECISIONS same date). Code against these signatures; do not work around them.

1. **`reading` is REQUIRED on `ErrorLine` and on `GaugeState`'s error arm.** QA's residual on BUG-0016 was right: an optional prop is a rule TypeScript cannot enforce, and the omission it permits is a red line that names none of the page's reads. `DbResult`'s error arm carries `reading: string` already (`src/lib/db/result.ts:14`), so pass `result.reading` straight through on every error arm you render. Do NOT invent a string, do not pass `""` to satisfy the compiler, and do not trim the message: a transport failure's account runs ~900 chars including stack frames, and whether that is too long is the designer's call at the walk, not yours.

2. **A state card that replaces a labelled surface keeps its eyebrow.** `Empty` and `NotProvisioned` take an optional `micro` eyebrow; the three gauge components always pass their own `label`, so an unprovisioned gauge still says which knob it is and not just which table is missing. On your page's own `Empty`/`NotProvisioned` the eyebrow is optional — the `Section` heading above it already names the surface — so only pass it where there is no heading.

3. **A rows surface has no headers-only rendering.** `TrendTable` and `Distribution` take a REQUIRED `empty: { holds, filledBy }` and render it themselves when there are no rows and no other state. The ruling on who owns the empty state: **the component owns WHEN, you own THE WORDS.** Write them in the app's voice, naming what the series holds and the one thing that fills it (LOOK_AND_FEEL Voice bar 4) — never "No data". An explicit `state` still wins, so pass your own empty state where the emptiness has a REASON (a filter that matched nothing) rather than being simply no rows yet.

For you specifically: the resolution-latency gauge's rows are the trap BUG-0012 found — render the AGGREGATE's counts, never `rows.applies.length` (now in your description, with the file:lines). Both gauges here are empty against a database whose resolver has not run, which is the state your reviewer will see first.

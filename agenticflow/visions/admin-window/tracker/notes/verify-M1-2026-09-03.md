## The designer's routed question — does `groups.updated_at` move?

**Observed:** it does not. Same value before the edit, after the edit, and after
the restore (`2026-04-06T14:10:47.251155+00:00`, equal to `created_at`).

**What the spec requires: nothing.** The string `updated_at` appears in no
contract snapshot (`grep -n updated_at contracts/*.md` → zero hits). Spec §8
mentions timestamps once, and only to forbid them at the surface: the map holds
"user-facing fields only, **never ids, keys, or timestamps**". A pre-cutover
edit is defined there as "directly, legal and **unprovenanced**, as the
ownership rules allow", and SPEC.md named gap 3 already records that no
`field_provenance` row exists for a groups/idols edit. No M1 criterion (EC10 or
otherwise) names `updated_at`.

**So it is not a defect, and it is also not the build's to fix.** The two ways
to make it move are both closed in M1: Admin writing the column itself would be
writing a column absent from the map — exactly what EC10 requires be refused
server-side (and it is: see the forged-request table below, `updated_at` → 403)
— and a database trigger is schema, which this repo may not carry (M1 "carries
zero schema") and which the scraper repo owns. **Graded: PASS on the criterion,
and a contract gap if anyone wants the behaviour** — a blocked question for Ben
routed to the ecosystem, never a silent build judgment (SPEC rules of
engagement 2).

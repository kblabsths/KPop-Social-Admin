# /claims reads the whole claim population on every request: ~14 sequential round trips, 2.9-3.8 s warm

## Description
Found by **Ben, walking the M2 endgame instance himself**, 2026-09-09. Warm server times he measured on the walk instance: `/claims` **2.9-3.8 s** and `/sources` 2.0-2.3 s, against `/` 0.2 s and `/queues` 0.3 s.

**Where the time goes: the read chain, not the render.** `src/app/claims/page.tsx` (~562-620) awaits four things one after another, and the first of them is O(the whole view):

1. `listClaims()` (`src/lib/db/claims.ts:190-231`) — `readComplete` over `pending_claims` (`claimsQuery`: six columns, `neq bucket in_window`, `order bucket, observation_id`, `.range(0, cap - 1)`, `count: "exact"`), then a SECOND leg `readClaimInstants` over every `observation_id` it returned. That leg is `readRowsByIds` at `ID_CHUNK = 100` and **its chunks are sequential by design** (`src/lib/db/result.ts:592`).
2. `readSourceNames(asFound.source_id)` — one more, and it cannot start until leg 1 finishes, because the ids it asks for come from the population.
3. the tab's gauge (`readPendingClaims` / `readStandingDisagreements`) — itself two sequential legs, the second chunked.

MEASURED read-only against staging today (architect; script and output in `agenticflow/tracker/evidence/architect-perf-M2/perf-probe.mjs` / `perf-probe.tsv`):

- `pending_claims` holds **877** rows; the page's own complete read returns them in **379 ms**.
- the instants leg is therefore **9 sequential requests** (877 / 100), each a `.in()` over 100 ids.
- head counts on the same view: all-buckets **1039 ms** cold / ~210 ms warm (measured 2026-09-03), per bucket **262-355 ms** (`standing_disagreement` 0, `awaiting_link` 108, `awaiting_row` 769, `escalated` 0, `agreeing` 0).

~14 sequential round trips at 200-380 ms each is the 2.9-3.8 s. Nothing here is a slow query; it is depth.

## Ben's ruled fix shape (2026-09-09)

- the page **must not read the claim population**;
- bucket counts (total, per bucket, and whatever the standing tab counts) come from **`readCount` head requests the row cap cannot touch**;
- the list is **ONE named-window read of the 50 longest-waiting, ordered in the database** (`limit 50`, the existing `DrawnWindow` contract with `scope`, held/limit/truncated taken from the count, `oldest` per BUG-0109);
- the registry and both gauge reads run **concurrently** with it (`Promise.all` over independent reads, each still reporting its own refusal per ARCHITECTURE §4.3);
- **page cost invariant to table size** — the stub's call log shows no `.range(0, cap - 1)` over claims and at most N reads however many rows the stub holds;
- the rendered numbers and words stay **byte-identical** on the same fixtures (BUG-0118 / 0123 / 0127 / 0136 pins green);
- and no json, no RPC, no view.

## What I measured about that shape, and why this ticket is BLOCKED

**Decided, and not in question — the bucket counts are one `readCount` per bucket, not a grouped read.** PostgREST refuses aggregates on this deployment: `select=bucket,count()` answers **PGRST123 "Use of aggregate functions is not allowed"** (measured today, 84 ms). There is no grouped read to choose. So: one `readCount` for the renderable total (`neq bucket in_window`) plus one per renderable bucket, each carrying the page's source/domain narrowing as `.eq()`, all issued together. Six head requests, ~300 ms wall, and `ROW_CAP` cannot reach any of them.

**Not decided, and not decidable from this repo — the ORDER.** `pending_claims` carries no age (ARCHITECTURE §6 trap 3) and PostgREST exposes **no relationship** between it and `observations`. Measured three ways today, all **PGRST200 "Could not find a relationship ... in the schema cache"**:

    pending_claims.select("…, observations!inner(observed_at)").order(observed_at, {referencedTable:"observations"}).limit(50)   PGRST200  183 ms
    observations.select("observed_at, pending_claims!inner(…)").order(observed_at).limit(50)                                     PGRST200   88 ms
    pending_claims.select("…, observations(observed_at)").limit(5)                                                               PGRST200   98 ms

So **no Admin-side read can order claims by wait time in the database**, and "the 50 longest-waiting, ordered in the database" is not expressible today. The only orders the view can be read in are over columns it carries (`bucket`, `observation_id`, `source_id`, `domain`, `field`) — and `observation_id` is not a wait order: the page's own order is `observed_at asc`, nulls last (`claimOrder`).

Two further figures on this page are computed from the population and have no bounded substitute:

- the bucket table's **`sources` column** (distinct sources holding a claim in that bucket, `src/components/claims/bucket-table.tsx`) — distinct counts need aggregates, refused above (PGRST123);
- the **filter-chip vocabularies** (`facetOptions`): which sources and which domains actually carry claims. `domain_target` is a function taking a domain name, not an enumerable registry, so Admin has no bounded read of "the domains in play". Source chips could come from the registry read the page already makes, but that offers every REGISTERED source rather than every source with a claim, which changes the chip row.

Ben's two requirements — *no population read* and *byte-identical rendering* — are therefore jointly unsatisfiable as stated, and the gap is one column wide. I am not guessing which half gives.

## Acceptance criteria
**These criteria are written for Answer A + A2 of the question in the Description** (the scraper carries `observed_at` through `pending_claims`; the bucket table's `sources` column and the domain chip row go). If Ben rules B, the architect amends criteria and checks in one pass before this ticket is dispatched — a builder never resolves that fork.

1. **The page reads no claim population.** `src/lib/db/claims.ts` no longer exposes a complete read of the view: `claimsQuery` / `readComplete` over `pending_claims` are gone, and no read this page makes carries `.range(0, cap - 1)` over the view. The offline pin is the stub's own call log, named `page cost is invariant to the size of the view`: rendering `/claims` against a stub scripted with 20 claims and against one scripted with 2,000 claims records **the same number of calls**, and no recorded step over `pending_claims` is a `range`. Both fixtures are stated, and the 2,000-row one is the fixture that would have caught this: it must not add a single request.

2. **Every count is a `readCount` head request.** The renderable total (`neq bucket = in_window`) and each renderable bucket's count are `readCount` (`{ head: true, count: "exact" }`), one per bucket, five buckets plus the total — **not a grouped read**, which PostgREST refuses (PGRST123, measured; see Description). The standing tab's count is the `standing_disagreement` count read the same way. Each count carries the page's active source/domain narrowing as `.eq()` on the query, never as a filter over rows. A null count is a refusal, never a zero (§4.3, common violations row 2): a scripted `{count: null, error: null}` renders that bucket's refusal, not `0`, and the offline suite states both fixtures — the count that is a real `0` (rendered as a real zero, the bucket row still present) and the count that is absent (rendered as the refusal).

3. **The list is ONE named-window read, ordered in the database.** `pending_claims` selected with `observed_at`, `neq bucket in_window`, the page's narrowing as `.eq()`, `.order("observed_at", asc, nullsFirst: false)`, `.order("observation_id", asc)`, `.limit(50)` — one request, no second leg, no TypeScript re-sort of a set larger than the window. `CLAIM_WINDOW` stays 50 and stays the one place the number is spelled. The rows render in exactly the order the database returned them, and a claim whose `observed_at` is null still sorts last and still renders with the dash for its age — never "now", never dropped.

4. **The window line is unchanged in every clause.** `DrawnWindow` keeps `scope`; `held`, `limit` and `truncated` come from the COUNT read (held = the count under the same narrowing, truncated = count > rows returned), not from the rows; `oldest` stays `null` for the reason BUG-0109 gives (the window is drawn longest-waiting first, so its bottom row is the newest it holds). The four landed sentence pins stay green to the byte: BUG-0118 (the filled/truncated clauses name the tab's narrowing, not "these filters"), BUG-0123 (the bucket caption's two arms, and the dropped-parameter line), BUG-0127 and BUG-0136 (a dropped parameter is named or counted, never a hole). An `ok` read with **no rows** still publishes the window line with `data-window-held="0"` beside the `Empty` card, and a **refused** read publishes no line at all (§4.3, common violations row 11) — both cases graded, as today, in `tests/offline/absence/pages.test.ts`.

5. **The independent reads run concurrently, and each still reports its own refusal.** The list read, the six count reads, the source registry read and the tab's gauge read are issued together (`Promise.all` over independent reads) — none of them waits on another's ids. Each keeps its own `DbResult` and its own rendering: a refused registry costs the LABELS and nothing else (every claim still renders, named by its id verbatim, with the refusal reported beside the rows naming `sources` — the landed practice at `src/app/claims/page.tsx` ~723-728); a refused gauge renders its own state card in its own Section; a refused count renders that bucket's refusal without touching the list. `not_provisioned` from any leg still names THAT object.

6. **The bucket table loses its `sources` column and keeps everything else** (Answer A2). One row per renderable bucket, always, in the view's own precedence order; `claims` from the count read; `oldest` from a `limit 1` window read per bucket ordered `observed_at asc` (five reads, issued with the rest), rendered relative with the absolute instant in the title, and rendered as the table's dash when the bucket holds nothing or nothing in it has an instant. `in_window` appears nowhere — not a row, not a chip, not a zero, not a URL parameter carried forward (§6 trap 4).

7. **The chips say only what the page read** (Answer A2). The source chips are the registry read's rows — every registered source, sorted by label with the id breaking the tie, exactly as today — and a source with no claims is a real chip with a real zero, not a hidden one. The domain chip row goes; `?domain=<value>` stays a real narrowing, applied by `.eq("domain", ...)` on every count and on the window read, named in the window line's scope and in the bucket caption's narrowed arm. A `?domain=` value that matches nothing renders the NOTHING_MATCHED card and a window line holding 0 — the narrowing happened, and the page says where it looked. `droppedParams` continues to name genuinely unapplied parameters and continues to count rather than spell a name this app may not render.

8. **The live oracle grades the surface the page now claims.** `tests/live/claims.live.test.ts` counts the SAME narrowing each surface renders (common violations row 7): the bucket figures against per-bucket counts it issues itself, the list against the 50-row window and not against the view's 877. It reads state kind from `data-state` before comparing any number — `empty` is a pass with a 0, `error` is always a FAIL (row 6) — and it addresses every surface by `data-surface`, never by position (row 8).

9. **The page is measurably faster on the walk instance, and the number is recorded.** Warm server time for `/claims` on the walk instance, same recipe as STACK.md's, is stated in the handoff with the before (2.9-3.8 s, Ben's own measurement) and the after. The bar is the shape, not a threshold: at most 8 requests per render, none of them over more than 50 claim rows, whatever the view holds.

## Interface contract
(architect ruling, 2026-09-09; shapes for Answer A of the Description's question)

`src/lib/db/claims.ts` — the module keeps its job as the ONE place the view is
queried (§6 trap 4: the parked bucket is excluded here, once, in every query and
in the predicate) and stops being the place the population is transported.

    /** The view's columns plus the instant the handoff carries through. */
    export interface ClaimRow extends PendingClaimRow {
      observed_at: string | null;
    }

    /** The N longest-waiting claims under a narrowing — ONE request, ordered in
     *  the database (`observed_at asc nullsFirst:false`, then `observation_id`),
     *  `.limit(n)`. A WINDOW read (§4.3 kind 2): its rows never become a total. */
    export function readClaimWindow(
      options: { filter?: ClaimsFilter; limit: number },
      db?: SupabaseClient,
    ): Promise<DbResult<ClaimRow[]>>;

    /** How many claims a narrowing holds. `head: true, count: "exact"` through
     *  `readCount`, so ROW_CAP cannot reach it and a null count is a refusal,
     *  never a zero (§4.3; common violations row 2). `filter.bucket` undefined
     *  means every RENDERABLE bucket (`neq bucket = in_window`). */
    export function readClaimCount(
      filter?: ClaimsFilter,
      db?: SupabaseClient,
    ): Promise<DbResult<number>>;

    /** The oldest instant in one bucket under a narrowing: a `limit 1` window
     *  read ordered `observed_at asc`. `ok` carries null when the bucket holds
     *  nothing — an absence, never "now". */
    export function readBucketOldest(
      bucket: PendingClaimBucket,
      filter?: ClaimsFilter,
      db?: SupabaseClient,
    ): Promise<DbResult<string | null>>;

    // GONE: claimsQuery, listClaims, readClaimInstants, facetOptions, claimOrder
    //       (the database owns the order now; nothing re-sorts a window).
    // KEPT: CLAIMS_OBJECT, PENDING_CLAIM_BUCKETS, RENDERABLE_BUCKETS,
    //       UNRENDERABLE_BUCKET, isRenderableBucket, readPendingClaims
    //       (the gauges' id-set leg), selectClaims only if a caller remains.

`src/app/claims/page.tsx` — one composition, every leg independent:

    const [rows, total, perBucket, oldest, registry, gauge] = await Promise.all([
      readClaimWindow({ filter, limit: CLAIM_WINDOW }),   // DbResult<ClaimRow[]>
      readClaimCount(withFacet(filter, "bucket", undefined)),
      Promise.all(RENDERABLE_BUCKETS.map((b) => readClaimCount({ ...filter, bucket: b }))),
      Promise.all(RENDERABLE_BUCKETS.map((b) => readBucketOldest(b, filter))),
      readSources(),                       // the chip vocabulary AND the labels
      tab === "standing" ? readStandingDisagreements(...) : readPendingClaims(...),
    ]);

Each element stays its own `DbResult` and is rendered by its own branch: no leg
is cast into another's shape, and no leg's refusal removes another leg's rows
(§4.1, §4.3, common violations row 14 — the shape a builder does not recognise
as a composed read at all). The window line follows the LIST read only.

Two hazards the offline suite will hit, named so nobody rediscovers them:

  1. the stub scripts one queue of responses PER OBJECT, and all six count
     reads plus the window read name `pending_claims` — so the queue is
     consumed in the order the `Promise.all` array builds its promises
     (`.from()` runs synchronously up to the first await). Script the queue in
     that order and assert on `calls`, not on interleaving between objects.
  2. `readSources()` replaces `readSourceNames(ids)` here: the page can no
     longer know which ids to ask for before the list read returns, and asking
     afterwards would put the sequential round trip back.

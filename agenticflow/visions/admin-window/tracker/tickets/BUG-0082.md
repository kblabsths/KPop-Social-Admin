# the verdicts handoff grants service_role SELECT but never revokes the ALL it inherits, so the table installs writable by the Admin key

## Description
**Expected** (the artifact's own stated guarantee): after Ben applies `M2-handoff-verdicts.md`, `service_role` holds SELECT on `public.verdicts` and nothing else. The SQL comment says it in the file — `agenticflow/tracker/for-human/M2-handoff-verdicts.md:64-72`: "service_role holds SELECT and nothing else", "Handing service_role INSERT would leave a second write path open to every holder of that key, including the Admin dashboard, which is exactly the door this design closes" — and note §4 item 1 (lines 169-176) stakes the FEAT-0009 coupling on it: "the deferred proof run's 'grant introspection proving verdicts is written by settle_review_item alone' only passes if service_role holds no write here".

**Found**: the block revokes only the two client roles and then adds a grant, never narrowing service_role —

    agenticflow/tracker/for-human/M2-handoff-verdicts.md:142  revoke all on table public.verdicts from anon, authenticated;
    agenticflow/tracker/for-human/M2-handoff-verdicts.md:143  grant select on table public.verdicts to service_role;

On this Supabase project a newly created public table is born with ALL already granted to service_role:

    /Users/ben-m4/Desktop/Coding/KPOP/kspace Scraper/supabase/migrations/20260818000000_the_schema_arrives_as_one_snapshot.sql:6850
      ALTER DEFAULT PRIVILEGES FOR ROLE "postgres" IN SCHEMA "public" GRANT ALL ON TABLES TO "service_role";

so `grant select` is a no-op on top of privileges that are already there. A GRANT cannot narrow; only a REVOKE can. The sibling repo measured this exact ACL and wrote the number down:

    /Users/ben-m4/Desktop/Coding/KPOP/kspace Scraper/supabase/migrations/20260821000001_the_gate_becomes_the_only_write_path.sql:30
      -- file: `service_role=arwdDxtm/postgres` on each of the three; target:
      -- `service_role=r/postgres`.

and its fix for the identical design ("the gate is the only write path") is an explicit revoke, at the same file lines 44-46:

      revoke insert, update, delete, truncate, references, trigger, maintain on table public.observations from service_role;

As authored, `verdicts` installs as `service_role=arwdDxtm/postgres`, not `r`. Consequences:
1. The Admin dashboard holds that key and already touches this table (`src/lib/db/verdict.ts:210-211`, `db.from(T.verdicts).select("*")`), so the second write path the design closes is open — including TRUNCATE on the verdict log, which the file's own §4 comment (lines 129-133) names as the reason the revoke is "necessary rather than decorative", while omitting it for the very role that ends up holding it.
2. FEAT-0009's second half is being authored against a false coupling: `settle_review_item` is not the only writer, and the deferred grant-introspection proof would fail on the installed table.
3. It is silent: `supabase db push` succeeds, nothing errors, and the divergence is only visible in `pg_class.relacl`.

**Repro (no SQL executed anywhere):**
1. `grep -n 'service_role' 'agenticflow/tracker/for-human/M2-handoff-verdicts.md'` — the only statement naming service_role is the GRANT on line 143; no REVOKE names it.
2. `grep -n 'GRANT ALL ON TABLES TO "service_role"' '/Users/ben-m4/Desktop/Coding/KPOP/kspace Scraper/supabase/migrations/20260818000000_the_schema_arrives_as_one_snapshot.sql'` — line 6850, the inherited grant.
3. Run the check below: the pin in `tests/offline/handoff/verdicts.test.ts` asserts a revoke on `public.verdicts` names `service_role`, and it is red on `ba26a22` (verified: 1 failed | 17 passed).

**The grader shares the blind spot.** `gradeVerdicts`'s `service_role_write_grant` finding (`tests/offline/handoff/verdicts.test.ts:239-241`) only inspects GRANT statements, so it certifies an artifact whose installed ACL is the opposite of what it grades. The fix must move the assertion from "no write is granted" to "the write privileges are revoked", or the same hole recurs in the `settle_review_item` artifact.

**Suggested shape** (architect/builder's call, not mine): add before the grant, in the sibling's own house wording —
`revoke insert, update, delete, truncate, references, trigger, maintain on table public.verdicts from service_role;`
— and widen §4 item 1 and the SQL comment to say the revoke, not the grant, is what makes the posture true. `--as qa` did not touch the artifact.

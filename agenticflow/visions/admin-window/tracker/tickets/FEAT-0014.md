# F16 — the second leg of a two-step join runs its chunks concurrently

## Description
The unbuilt half of BUG-0138's Answer B — a decision already taken and half shipped. `readRowsByIds` (`src/lib/db/result.ts`) walks its chunks of 100 SEQUENTIALLY and is shared by /claims, /queues and the review item. The built half of Answer B, plus Ben's own install of `pending_claims.observed_at` on staging (2026-09-10), took /claims from 2.9-3.8 s warm to ~2.4 s; making the chunks concurrent is estimated to take it to ~1 s. Ben's original complaint on that page was wall-clock, and it is not paid yet.

Behavior: SPEC F16. NOTHING the app says changes — only the clock.

The one way this can be wrong: concurrency turning a refusal into a partial answer. Every guarantee the function makes today must survive. No ids means ZERO round trips. The first non-ok result comes back unchanged, so a missing table still reaches the page as not_provisioned naming that table. A chunk that errors never yields a half-filled ok. Bound the fan-out; do not open an unbounded number of concurrent requests at the database.

Sequenced FIRST in M3: FEAT-0014's paged fetches inherit whatever this leg costs.

vision_trace: VISION, 'Who it's for' — "Ben, the ecosystem's operator, at breakfast: did anything happen last night, what needs me, who keeps being wrong." The page that answers 'who keeps being wrong' is /claims; Ben measured it himself at 2.9-3.8 s and filed BUG-0138 on it, and this is the half of that accepted fix that was never built.

## Acceptance criteria
Chunks are issued concurrently and bounded, asserted against a stub that records issue order and observed concurrency over an id set spanning at least three chunks. All three surviving properties proved on their own fixtures (LESSONS 8: one input that must flag, one that must not): an empty id set issues zero requests; an erroring chunk yields the first non-ok result unchanged, never a half-filled ok; a missing table reaches the page as not_provisioned naming that table. /claims warm server time measured over HTTP against a production build is at or under 1.4 s, recorded as a before/after pair with the exact commands in the evidence note (human-checkable measurement, structural proxy below). /queues and the review item measured in the same pass; neither regresses. No rendered text on any of the three surfaces changes.

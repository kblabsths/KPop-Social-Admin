# Claims' dropped-parameter line is holed again by nonspacing marks, and a bidi override in a key reverses the whole sentence

## Description
Found while attacking admin-window/BUG-0136 on the LANDED tree (run/admin-window @ aede186), over HTTP against a production build (own port 8798, staging, 2026-09-09) and in Chromium via playwright (both colour schemes, measurements identical in light and dark).

BUG-0136 closed the ink-less half of "this key names nothing" by asking the app's ONE definition of blank, `hasVisibleContent` (`src/lib/verdict/decision.ts`). That definition's class is `[\p{White_Space}\p{Cf}\p{Cc}\u115F\u1160\u3164\uFFA0]` (decision.ts:83) — it does NOT include `\p{Mn}`, and it rules U+2800 BRAILLE PATTERN BLANK content on purpose. Three divergences follow, all from the one line `if (!hasVisibleContent(key)) continue;` / `neverNamed.includes(visibleContent(key))` at `src/lib/claims/filters.ts:218-228` feeding `DroppedParamsLine` at `src/app/claims/page.tsx:382-410`, which renders the key VERBATIM.

--- A. the 0px hole BUG-0127/BUG-0136 each closed, reopened by a nonspacing mark

**Expected** — BUG-0136 criterion 1 and its pin in `tests/offline/claims/page.test.ts` ("names a parameter an operator can read back, whatever the key's codepoints").
**Found** — a key of nothing but a nonspacing mark is named and spelled into the mono span, where it lays out at 0px:

    /claims?%EF%B8%8F=1   U+FE0F  span width_px=0     visible=False
    /claims?%CD%8F=1      U+034F  span width_px=0     visible=False
    /claims?%CC%81=1      U+0301  span width_px=0     visible=False
    /claims?record_id=abc (control) width_px=59.41    visible=True

Visible text, both themes: `The URL carries , which this page did not apply: nothing below is narrowed by it.` — the identical hole, one codepoint family over.

--- B. the parked bucket rendered legibly on screen (bar 3)

**Expected** — LOOK_AND_FEEL bar 3: "`in_window` appears nowhere — not as a bucket row, not as a filter option, not as a zero, on any page"; `contracts/admin-build.md` acceptance test 3 says the same. BUG-0136 made the withheld test read the key as a reader would (`visibleContent`) for exactly this reason.
**Found** — a mark that definition calls CONTENT rides through it and the word is drawn:

    /claims?in_window%EF%B8%8F=1   mono span reads `in_window`, width_px=59.41 (record_id's exact width — U+FE0F adds no ink), visible=True
    /claims?in_win%CD%8Fdow=1      mono span reads `in_window`, width_px=59.41, visible=True
    /claims?in_window%E2%A0%80=1   mono span reads `in_window` + a blank braille cell, width_px=66.92, visible=True

The literal string `in_window` is in the response body markup for the first two (`in_window` absent from the bare page's body, 67099 chars; these are 67338). Screenshot read back by eye: `The URL carries in_window, which this page did not apply: nothing below is narrowed by it.`

--- C. a URL reverses the sentence it is named in

**Expected** — bar 13 ("no screen claims a mark it did not draw") and BUG-0123's contract that the line names something the operator can read back.
**Found** — U+202E RIGHT-TO-LEFT OVERRIDE is `\p{Cf}`, so `visibleContent` strips it, the key `ab\u202Ecd` has visible content, and the override is rendered VERBATIM into the span. Its scope is the paragraph, not the span, so the rest of the sentence reverses:

    /claims?ab%E2%80%AEcd=1  ->  The URL carries ab.ti yb deworran si woleb gnihton :ylppa ton did egap siht hcihw ,dc
    /claims?%E2%80%AEabc=1   ->  The URL carries .ti yb deworran si woleb gnihton :ylppa ton did egap siht hcihw ,cba

(name span box grows 19.81px -> 371.75px as it swallows the reversed run; both themes identical). The reversal travels with the text when the sentence is copied out of the page, so it is not a styling question.

--- Two things the builder must know before choosing a fix

1. **Do not just widen `INK_LESS` to `\p{Mn}`.** `hasVisibleContent` answers a DIFFERENT question on the edit surface — "did the operator type anything?" — and `tests/offline/ui/editable-cell.test.ts:1975-2001` pins U+FE0F and U+2800 as CONTENT there (a draft of `\ufe0f` commits). Changing the shared class changes committed drafts. The claims line's question is "what ink does the reader see, in what order", which is not the same question; a second, explicitly named function beside `visibleContent` (or a screen-side rule in `filters.ts`) keeps both answers honest.
2. **This is the third codepoint slice on one sentence** (BUG-0127 whitespace, BUG-0136 Cf/Cc/fillers, this one Mn + U+2800 + bidi). A fourth blocklist is the wrong shape; the rule wanted is "the name rendered is what the reader can read back, in the order the app wrote it". Worth the architect's ruling before the next patch — recorded here rather than acted on by QA.

## Acceptance criteria
**RULED 2026-09-09 (architect). The fix is a rule, not a fourth blocklist: the
line spells a key only from a renderable allowlist, and every other key is
counted through the arm that already exists.** `src/lib/verdict/decision.ts` is
NOT touched — `hasVisibleContent` keeps answering the edit surface's question
("did the operator type anything?", pinned by `tests/offline/ui/editable-cell.test.ts`)
and keeps its `INK_LESS` class exactly as it is.

Why an allowlist and not a wider class: bar 3 ("`in_window` appears nowhere")
is not decidable against verbatim Unicode. `in_win͏dow` reads as the
parked word; so do a Cyrillic-і spelling and any number of homoglyphs
nobody has typed yet. Widening the ink-less class answers one family per bug
forever (this is the third: BUG-0127 whitespace, BUG-0136 Cf/Cc/fillers, now
Mn + U+2800 + bidi). An allowlist collapses the whole question to an exact
ASCII compare, which is total and stays true. The three defects A, B and C fall
out of it together rather than one family at a time.

**The rule, in `droppedParams` (`src/lib/claims/filters.ts`), in this order:**

1. `tab` skipped; then `hasVisibleContent(key)` false -> **ignored entirely**
   (BUG-0127/BUG-0136's gate, unchanged: a query pair carrying no name asked
   for nothing, and there is no name being withheld); then an absent or empty
   value -> ignored; then a facet that reached the filter -> ignored.
2. A key that survives is **spelled verbatim only if it matches the renderable
   allowlist `^[A-Za-z0-9_.-]{1,64}$`** — the class every name this page could
   offer satisfies (`bucket`, `source_id`, `domain`, `record_id`, `tab`), and
   the class in which a key renders as itself, carries no bidi semantics, and
   cannot read as a word it is not. The test is on the key's RAW characters,
   never on `visibleContent(key)`: what the line spells is then byte-identical
   to what the URL carried (spec §11), because the two are the same string.
3. Every other surviving key — any character outside the class, or longer than
   64 — is **counted through the existing `withheld` arm**, exactly as a
   `neverNamed` word is. The arm's sentence ("a parameter this page may not
   name") is true of both: there is a name, and the page declines to spell it.
   The `neverNamed` comparison becomes a plain string compare, since a key that
   reaches it is pure ASCII.

Where the sentence gets its words is unchanged and stays the designer's
(Voice); this ruling moves no wording.

**Criteria**

1. The allowlist is the rule and `droppedParams`' docstring states it, with
   both consequences named: no character outside `[A-Za-z0-9_.-]` reaches the
   sentence by any path, and `decision.ts` keeps its own ruling for the edit
   surface. The regex is declared ONCE, in `src/lib/claims/filters.ts`, as a
   named constant.
2. `/claims?%EF%B8%8F=1` (U+FE0F), `/claims?%CD%8F=1` (U+034F) and
   `/claims?%CC%81=1` (U+0301) spell no name: nothing with no renderable glyph
   is written into the mono span. Each is COUNTED (`{named: [], withheld: 1}`) —
   a parameter was carried and dropped, and bar 13 has the page say so without
   naming it.
3. `in_window` appears NOWHERE in the claims response body for
   `/claims?in_window%EF%B8%8F=1`, `/claims?in_win%CD%8Fdow=1` and
   `/claims?in_window%E2%A0%80=1`, and each is counted exactly as `?in_window=1`
   is (LOOK_AND_FEEL bar 3; `contracts/admin-build.md` acceptance test 3).
4. `/claims?ab%E2%80%AEcd=1`, `/claims?%E2%80%AEabc=1` and `/claims?x%E2%80%ADy=1`
   render the page's own sentence in the order the page wrote it, and it
   survives being copied out as plain text — no bidi control from a URL reaches
   the markup at all, which is stronger than isolating one.
5. The three strict pins flip from `it.fails` to `it` and pass —
   `tests/offline/claims/filters.test.ts` "ignores a key that is nothing but
   marks a reader cannot see" and "still refuses to spell the parked word when
   an inkless mark rides along"; `tests/offline/claims/page.test.ts` "cannot let
   a URL reverse the sentence its name is written into". **The first pin's
   assertion widens by one field, and only that one**: it expects
   `{named: [], withheld: 1}` rather than `withheld: 0`. Its own docstring
   offers either arm ("ignore such a key, or spell something an operator can
   read back") and this is the ruled arm — measured 2026-09-09
   (`agenticflow/tracker/evidence/BUG-0137/rule-dryrun.mjs`), the pin as
   written and its sibling B (`{named: [], withheld: 1}` for
   `in_window️`) are jointly satisfiable ONLY by a predicate that calls
   U+FE0F blank and U+2800 not — i.e. by the fourth blocklist this ticket
   exists to refuse, and by a second opinion about blankness in a module whose
   docstring forbids holding one. Nothing else in the pin moves; the docstring
   records the arm taken.
6. Three assertions in `tests/offline/claims/filters.test.ts` "names a key that
   puts any ink on the page, however little" MOVE, with their reason written
   beside them, and nothing else in that test does: `"記録"` (CJK) and
   `"⠀"` (BRAILLE PATTERN BLANK) go from `named: [key]` to
   `{named: [], withheld: 1}`, and `"record_id​"` goes from
   `named: ["record_id​"]` to `{named: [], withheld: 1}`. The test's
   purpose — that the rule cannot pass by dropping every dropped parameter —
   is kept by `"."`, `"-"`, `"_"`, `"0"`, `record_id`, `bucket` and
   `in_windows`, all still named verbatim.
7. A key of 64 allowlisted characters is named; 65 is counted. (A name spelled
   verbatim is a line the operator reads; there is no facet this page will ever
   offer longer than 12 characters, and an unbounded one is the next patch on
   this sentence.)
8. Everything else BUG-0123, BUG-0127 and BUG-0136 pinned still holds, measured
   against the ruled rule 2026-09-09 and green in the dry-run:
   `record_id` and `bucket` named verbatim and only when dropped; `tab` never
   named; an empty value, an empty key, a blank key and an ink-less key saying
   nothing and counting nothing; `in_window` and `in_window​` counted and
   never spelled; two dropped names on one line; the line standing over a
   refused read. And the edit surface's ruling is untouched:
   `tests/offline/ui/editable-cell.test.ts` still commits a draft of `️`
   and `⠀` as content, from an unchanged `decision.ts`.
9. `npm run lint` and `tsc --noEmit` clean; the offline suite green.

Optional, not required: a `dir="ltr"` / `unicode-bidi: isolate` belt on the
mono span in `DroppedParamsLine`. With criterion 4 no control can reach it, so
this is defence in depth, not the fix — and it is not the second arm of the
ARCHITECTURE rule below being claimed here.

# Review-item detail — three typed views over one anatomy, evidence resolved

## Description
Module: `src/app/queues/[reviewItemId]/page.tsx` + `src/lib/db/review-item.ts`. Authority: spec section 6 **in full**; `contracts/resolver.md` section 7 and section 11; `contracts/data-model.md` (observations, per-field provenance); SPEC F4; M1 EC7; acceptance test 5; LOOK_AND_FEEL 'The evidence pair — this app's signature' and 'Key screens — Review item detail'.

The shared anatomy (spec section 6), rendered for all three shapes:

1. **What happened** — the `summary` sentence, `severity`, age from `opened_at`, and `folded_count` rendered as 'asked again xN'.
2. **Evidence, side by side** — every observation id in `review_items.evidence` (a `uuid[]`, rendered in its stored fold order) resolved to its row: **value, source, tier, `observed_at`, payload link** — with **the fact's current canonical value and its provenance beside them**, in the `EvidencePair` primitive (contenders left, canonical rightmost and labelled current).
3. **The close slot** — present in the layout and **empty in M1**. The verdict actions and the fixed / won't-fix dispositions arrive with the verdict slice. Do not build them, do not scaffold them, do not render a disabled button.
4. **The recommendation slot** — exists in the layout and **renders nothing**; its producer is parked.

Two facts from the schema you must not guess at (ARCHITECTURE section 6):

- **A claim has no tier of its own.** The evidence row's tier is `sources.tier` (the source's *current* tier); the canonical card's tier is `field_provenance.tier_at_apply` (frozen at the apply). Label each as what it is.
- **The current canonical value** is the observation named by the **latest** `field_provenance` row for `(entity_type, entity_id, field)` ordered `applied_at desc, provenance_id desc`, and only if that observation is still live. `field_provenance` spells the domain column `entity_type`; `review_items` spells it `domain`.

**Each of the three shapes gets its own detail view** over that anatomy — the evidence block renders what that shape's evidence *is*, not one generic layout:

- `data_conflict` fact item: the contending claims.
- `entity_link` fact item: the stuck claims and the unmet requirement (`pending_claims.unmet_requirement` names it: a missing NOT NULL column by name, 'at least one linked performer', or 'curated domain').
- `entity_link` source-pattern item: the folded records **as a list**, with the per-source dial beside it — and the dial's *threshold* is the blocked question (see the stuck-pattern ASK ticket); render the trend without a threshold line until it is answered, never a hand-copied number.

**Detail links out**: to the item's claims (`/claims` filtered), to its source (`/sources`), and to the affected record (`/records/<table>/<id>`).

Every page ticket in this milestone carries the same standing rules (ARCHITECTURE sections 4, 5, 7):
- The page function is the **only** async component on the route; every child is a pure synchronous component taking plain props. That is what lets the tests render `await Page(props)` with `react-dom/server`.
- Read only through `src/lib/db/**`; never build a Supabase client in a page; never spell a table name outside `src/lib/db/tables.ts`.
- Render all four states from the `ui` primitives: loading, empty, **not provisioned** (naming the missing table, gray, never a zero), error (the database's own message). A missing backing table must not throw and must not take the rest of the app down.
- Use tokens and primitives, never raw hex, arbitrary type sizes or ad-hoc radii.
- **State lives in the URL**: every filter, sort and tab is a `searchParams` value and survives the back button.
- Voice: buttons are a verb plus their object; ages are relative with the absolute in the title attribute; scheduled times are absolute UTC with the zone stated once in the column header; machine identifiers render verbatim in mono; empty and not-provisioned states name what the surface holds and what fills it.
- **Nothing settles anything in M1.** No verdict action, no settle control, no fixed/won't-fix, no scaffolding toward them.

## Acceptance criteria
[test 5, test 2, test 9; EC7] For each of the three shapes, offline tests render the detail page against fixtures and assert: every evidence id appears as an observation row carrying value, source, tier and `observed_at`; the current canonical value and its provenance render beside them; the header carries summary, severity, age and `folded_count`; the recommendation slot renders nothing; **no settle or verdict control is present**. The three shapes render three distinct views. An evidence id that resolves to no row renders honestly rather than throwing. The links to claims, source and record are real URLs. A live-marked test opens a real staging item and asserts its evidence rows against rows the test fetches itself. (human-checkable) One close-review screenshot per shape.

# Against a real PGRST205 database /claims leaks a developer sentence: 'a count read requires { head: true, count: "exact" }'

## Description
M3 endgame verification, 2026-09-11, HEAD bed26500. Found outside the test harness — the offline absence proof cannot see it, because it never speaks HTTP.

REPRO FROM A CLEAN START:
1. Stand up a stub that answers every PostgREST request with 404 and the PGRST205 body (46 lines of python; the walk used one on 127.0.0.1:8777 answering
   {"code":"PGRST205","details":null,"hint":null,"message":"Could not find the table 'public.<t>' in the schema cache"}).
2. ( set -a && source .env && set +a && SUPABASE_URL="http://127.0.0.1:8777" SUPABASE_SERVICE_ROLE_KEY="stub" AUTH_URL="http://localhost:8776" npm run start -- --port 8776 )
3. GET /claims with a walk cookie.

EXPECTED (F2/F10, VISION 'absence is honest'): every panel renders the app's one not-provisioned clause naming its table.
OBSERVED: 200, and the page carries BOTH. The not-provisioned cards are right —
  'pending_claims isn't in this database yet — it arrives with the scraper repo's migrations.' (x3, for pending_claims, sources, observations)
— and beside them one data-state="error" line reads, verbatim:
  'pending_claims — the query returned no count, so the number of rows is unknown; a count read requires { head: true, count: "exact" }.Reload to try the read again.'
That second half is a note to a developer about this app's own call site, rendered to the operator, in the one state the campaign most cares about getting right.

MECHANISM, established against REAL staging rather than guessed:
  curl -I -X HEAD ... '<staging>/rest/v1/verdicts?select=*' with Prefer: count=exact  ->  HTTP/2 404, content-type application/json, content-length 162, and NO body on the wire (HEAD).
  curl (GET) on the same absent table -> 404 with {"code":"PGRST205", ...}.
So the COUNT leg of a read against a missing table cannot carry PGRST205 to the client: a count read is a HEAD, and a HEAD's body never arrives. The row leg classifies correctly (not_provisioned); the count leg falls through to the 'no count' arm. The offline stub client returns structured results and never exercises this, which is why the suite is green and the product is not.

REACHABILITY: any deploy pointed at a project without the ecosystem tables — which is exactly the state 'honest absence beats a crash' exists for, and the state the deployed Railway service is in whenever the scraper's migrations are behind.

## Acceptance criteria
1. Against a database answering 404+PGRST205 to every request over real HTTP, /claims renders no sentence containing 'count read requires', 'head: true' or 'count: "exact"' — the count leg's absence reaches the page as the same not-provisioned clause the row leg does, naming the same table once. 2. The same holds for every surface whose read includes a count leg, asserted over HTTP against that stub, not against an in-process stub client. 3. A count leg that fails for a reason that is NOT absence still reaches the page as an error naming the read and the database's own words — the fix narrows what absence means, it does not swallow errors. 4. The regression lives in tests/http (the tier that speaks HTTP); the offline absence proof is left as it is.

# events record page shows venue as a bare uuid with no way through: less than the Browse row the operator clicked

## Description
**Expected** (Ben's ruling 2026-09-02, the criterion TASK-0029 was written from): "a resolver-owned record page shows the columns an operator came to see" — events: title, description, poster, starts_at, **venue**. TASK-0029's own opening complaint was that /records/events/<id> "shows exactly one field line — event_id ... the operator clicks through from Browse and learns nothing they did not already have in the row they clicked."

**Found**: the `venue` line renders the raw uuid of `events.venue_id` as inert text, and `/records/venues/<id>` is linked from nowhere in `src/` (`grep -rn '/records/venues' src/` = no match; the only record link the app builds is `eventRecordHref`, src/lib/browse/rows.ts:85). So for this one field the page is STRICTLY LESS informative than the row that linked to it: Browse renders the venue's NAME (`venue_name`, read through `event_listings`, src/lib/browse/rows.ts:35/236), and clicking through replaces that name with an opaque uuid the operator can neither read nor follow.

**Repro** (offline, no database):
1. `cd 'kspace Admin'`
2. `./node_modules/.bin/vitest run tests/offline/records/page.test.ts -t 'reaches the venue record page'`
3. The case is pinned `it.fails` today. Remove `.fails` and it reports `hrefs seen: []` — the page renders an events record whose `venue_id` is `01920000-0000-7000-8000-0000000000a4` and contains no anchor at all.
Equivalently, in the app: Browse -> click any event row -> the venue line is a uuid, and there is no route from it to that venue's record.

**Not a TASK-0029 criterion failure** — that ticket met all 8 and is closed `done`. Criterion 1 required every display name to be "a real column of that table", and `venue` is not a column of `events`; `venue_id` is the only venue-bearing one (scraper migration 20260825000002:83, `\"venue_id\" \"uuid\"`), so the builder's reading was the only one the criterion permitted. The gap is what that reading COSTS the operator, and it needs an answer this ticket does not presume.

**Two answers exist; the architect/Ben should pick one.**
(a) **Link it** — the smaller, in-scope M1 answer: render `venue_id` through the landed generic helper `provenanceHref('venues', id)` (src/lib/claims/filters.ts:306, which already produces exactly `/records/venues/<id>` and is already used by src/app/queues/[reviewItemId]/page.tsx:168). The venue's name/city/country/address are then one real click away, which is what src/lib/edit/config.ts:152-154 ALREADY CLAIMS in its comment ("the venues record page, one click on from here") — the comment is true of the design and false of the code.
(b) **Show the name** — read `event_listings.venue_name` (scraper migration 20260825000004:24). This is a design change, not a build choice: it changes which relation the record read addresses, and `display` is defined as columns of `config.table`. It would also need Ben, since the map's read-only half would then carry a name that is not a column of `events`.

Answer (a) needs no new read, no map change and no contract change, and is the recommendation. It is a rendering change in `src/components/records/record-fields.tsx` driven by the existing map — NOT a second allowlist: the cell is a link when the drawn column is a foreign key the map already carries.

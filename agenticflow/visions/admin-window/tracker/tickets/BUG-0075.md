# Edit cell: a previous save's 1.5s confirmation timer erases the NEXT edit's status — the in-flight 'saving…' vanishes mid-write and a refusal self-erases after 1374ms

## Description
Expected: a status the cell shows belongs to the edit that produced it — the in-flight statement BUG-0066 just landed stands until ITS OWN write answers, and a refusal stands until the operator does something about it. src/components/EditableCell.tsx:229-230 arms `timer.current` on a SUCCESSFUL save (`setTimeout(() => setStatus({kind:"idle"}), 1500)`) and clears it in exactly one place — the next successful save. The `saving` branch (:210), the `failed` branch (:232-234) and the button's own `onClick` (:270-272) never clear it, so a timer armed by an EARLIER save later resets an UNRELATED status to idle.

Found, three measurements on the production build of the landed tree (next build && next start --port 8796, staging data, minted cookie, bundled Chromium, in-page MutationObserver + fetch wrapper for the clock), 2026-09-03, groups 15ff6af9-178a-4f44-ae11-8bdc0c11b296, field short_name:

(1) THE IN-FLIGHT STATEMENT IS ERASED MID-WRITE. Edit 1 (120ms write) lands: 'saved' at +167ms, timer armed for +1667ms. Edit 2 committed at +226ms with a 1.6s write:
    +  229ms  button 'admin-window/BUG-0066 qa p5-second' disabled=True   cell:[status] 'saving…'
    + 1671ms  button 'admin-window/BUG-0066 qa p5-second' disabled=False  cell:(no region in cell)
    + 1834ms  << PATCH answered 200 >>
  For the last 163ms of a write still in flight the cell states no work and the button is enabled again — the exact state BUG-0066 was filed to remove, reached from a second edit instead of a first. The silent window is `1500ms - (gap between the previous save and this commit)`, bounded by the write's own length: commit 200ms after the confirmation on a 3s Railway write and the cell is silent for ~1.3s of it. Re-measured at 8ms in a second run (qa-attack2.py P7), so the width is timing, not the presence of the defect.

(2) A REFUSAL SELF-ERASES, AND THE ROUTE'S OWN WORDS ARE LOST. Edit 1 writes 200 ('saved' at +211ms, timer armed for +1711ms); edit 2 at +331ms is answered 403 with the route's refusal shape `{"error":"short_name is not editable on groups"}`:
    +  341ms  button 'admin-window/BUG-0066 qa p8-A' disabled=False  cell:[alert] 'short_name is not editable on groups'
    + 1715ms  button 'admin-window/BUG-0066 qa p8-A' disabled=False  cell:(no region)
  READABLE FOR 1374ms, then gone. The field has already reverted to its pre-edit value, so what an operator who looked away sees is a cell holding the old value and NOTHING saying their edit was refused — indistinguishable from never having typed. The same refusal raised OUTSIDE a confirmation window persists indefinitely (measured, offline commit: alert still present at +3000ms), which is the correct behaviour and the reason this is a bug and not a design.

(3) It is not tied to a transport: (2) is a real 403 through the app's own client; the offline variant ('Failed to fetch') behaves identically. No lost update was reachable — the racing third commit in qa-attack2.py P7 ordered correctly (PATCHes [200,200,200], cell, database and a reload all read 'p7-C'), so this is a statement-of-work defect, not data loss. That is why it is P2 and not P1.

PRE-EXISTING, not a regression from BUG-0066: `git show a412e9e` touches only the status RENDERING (type export, EditStatus, the render swap); the timer lines are untouched and date from TASK-0004. BUG-0066 met its own bar on the single-edit path and closed on it; this is the second edit.

## Acceptance criteria
A status the cell is showing is cleared only by the edit that produced it. Concretely, both measured divergences die: (a) a second edit committed inside a previous save's 1.5s confirmation window keeps its statement of work, and keeps its button disabled, for the whole of its own write — no silent, clickable window before the PATCH answers, at any interval between the two edits; (b) a refusal raised inside that window is not erased by the earlier save's timer (measured: readable for 1374ms, then gone), and persists as long as one raised outside such a window does. The confirmation itself must still clear ~1.5s after ITS OWN save, the failure must still name the refusal and revert the field, and the in-flight statement BUG-0066 landed must still appear within 100ms of a commit. THE TIMING RULE IS RENDERED THROUGH A PURE SEAM, as EditStatus and EditField were and for the same reason (tests/offline is environment node with renderToStaticMarkup and no jsdom, STACK.md §4): a rule that lives only inside commit()'s closure is a rule no offline test can reach. Shape is the builder's — a pure reducer over (status, event), an explicit status-with-deadline unit, whatever fits — and tests/offline/ui/editable-cell.test.ts drives it directly to pin that a later status is never retired by an earlier save's clock. Watch those tests fail against today's code before you fix it. Assert the BEHAVIOUR — which status is showing, and until when — never the sentence.

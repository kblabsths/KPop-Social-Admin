# /sources reads runs once per registered source and then waits for both gauges: ~9 sequential round trips, 2.0-2.3 s warm

## Description
Found by **Ben, walking the M2 endgame instance himself**, 2026-09-09. Warm server times he measured on the walk instance: `/sources` **2.0-2.3 s** (and `/claims` 2.9-3.8 s, admin-window/BUG-0138), against `/` 0.2 s and `/queues` 0.3 s.

**Where the time goes: depth, not a slow query.** `src/app/sources/page.tsx` (~131-145) awaits three composed reads one after another, and the first of them is itself a loop:

1. `listSources()` (`src/lib/db/sources.ts:255-270`) — `readSources()`, then **one `readLastRun` per registered source, in a `for` loop, each awaited**. Three sources today is four sequential round trips; a registry of thirty is thirty-one.
2. `readAwaitingRowTrend({ filter })` — two sequential legs, the second chunked.
3. `readRejectionStampGauge()` — two more.

MEASURED read-only against staging today (architect; `agenticflow/tracker/evidence/architect-perf-M2/perf-probe.mjs` / `perf-probe.tsv`): `sources` holds **3** rows, `runs` holds **5**; one of today's per-source last-run reads takes **110 ms**. ~9 sequential round trips at 110-380 ms each is the 2.0-2.3 s. None of the three composed reads needs anything from the other two.

## Ben's ruled fix shape (2026-09-09)

`listSources` folds the per-source last-run loop into **ONE PostgREST request** ("sources with runs embedded, ordered by start time, limited to one per source, **or the equivalent single query you rule honest under §4.3; state the exact chain**"), the trend and rejection gauges run **concurrently** with it, each leg reports separately as today, and the pin is the stub's call log — exactly 1 request for the sources+runs leg regardless of source count — plus byte-identical rendering on the existing fixtures.

## The embed does not exist; here is the chain I rule instead

**Measured today: there is no relationship to embed.** `sources` and `runs` have no foreign key — deliberately, so a run against an unregistered source can still write its row (migration `20260829000001`'s own column comment; ARCHITECTURE §6 trap 6), and PostgREST refuses both spellings:

    sources.select("…, runs(run_id)").limit(5)          PGRST200  111 ms  "Could not find a relationship between 'sources' and 'runs'"
    sources.select("…, runs!source(run_id)").limit(5)   PGRST200   89 ms  same

so `runs.order=…&runs.limit=1` has nothing to hang off. Aggregates are refused as well (**PGRST123**, "Use of aggregate functions is not allowed"), so there is no `distinct on (source)` and no group-by to lean on either — which is what `readLastRun`'s own docstring already says.

**The equivalent single query, ruled honest under §4.3 — the exact chain:**

    db.from(T.runs)
      .select(LAST_RUN_COLUMNS, { count: "exact" })
      .order("source",     { ascending: true })
      .order("started_at", { ascending: false })
      .order("run_id",     { ascending: false })   // uuid v7: ties break in time's own direction
      .range(0, cap - 1)                            // through readComplete, cap = ROW_CAP

through `readComplete`, then fold in TypeScript: the newest run for a source NAME is the **first row carrying that name** in that order. Measured: **159 ms, one request, count 5 of 5**.

Why this is honest rather than a window pretending to be a total (§4.3, and the exact objection `readLastRun` was written to answer): `readComplete`'s `ok` array is the WHOLE `runs` table or the read refuses, so "this source has never run" is a real absence in a complete set and never a row that fell off the end of a window. That is the one thing the dash may not mean here, and a complete read is the only bounded shape that preserves it.

Why **unnarrowed** rather than `.in("source", names)`: the narrowed form needs the registry's names first, which puts the sequential round trip straight back, and above 100 names it would have to chunk — at which point "exactly 1 request" stops being true. Unnarrowed, the runs read depends on nothing and goes into the same `Promise.all` as the registry read. Runs belonging to no registered source are simply never matched by the fold.

## The cost of this ruling, stated plainly

`runs` is "**one row per invocation of the adapter run loop**" (migration `20260829000001`'s table comment) and **has no retention policy**. Five rows today because the crons are not yet running in anger; three sources on an hourly cron is ~72 rows/day, so `ROW_CAP` (1000) is roughly **two weeks of production cron**. On the day the log outgrows the cap this page stops rendering the registry and renders the honest refusal instead — "the database holds N rows matching this read and it is capped at 1000" — where today's per-source `limit 1` reads can never truncate. §4.3 sanctions exactly that trade ("when a table genuinely outgrows ROW_CAP the app says so with the real number, and raising the cap or narrowing the filter is then a deliberate decision with evidence behind it"), and criterion 3 below makes the refusal a tested, legible state rather than a surprise — but it is a new failure mode, it is weeks away rather than years, and the fix for it is not Admin's: either a retention policy on `runs` or a per-source seek, both in the scraper repo. **Recommended for the M3 list beside the paging ruling below**, not for this ticket.

## Acceptance criteria
1. **One runs request, whatever the registry holds.** `listSources` issues exactly two requests — `readSources()` and one `readLastRuns()` — and never a request per source. The offline pin is the stub's own call log, named `one runs request, whatever the registry holds`: rendering `/sources` against a stub scripted with 3 sources and against one scripted with 300 records **the same number of calls**, with exactly one `.from(runs)` in each. Both fixtures are stated; the 300-source one is the fixture that would have caught the loop.

2. **The fold is exact, and the dash still means what it meant.** The newest run for a source is the first row carrying its `source` NAME in the chain's order (`source asc, started_at desc, run_id desc`); `lastRun` is `null` — rendered as the table's dash — when the complete set holds no run for that name, and a run whose `source` matches no registered source is matched by nobody and renders nowhere. The offline suite states all four fixtures: a source with several runs (the newest wins, and a tie on `started_at` breaks on the uuid v7 `run_id`), a source with exactly one, a source with none (dash, never a zero, never "no runs" as a word of ours), and a run whose name is in no row of the registry (present in the read, absent from the page). A run still in flight keeps its null `ended_at` and null `outcome` and renders the dash for each.

3. **Complete-or-refuse, and the refusal is legible.** The runs read goes through `readComplete` with `{ count: "exact" }`, the total order above and `.range(0, cap - 1)`; a scripted `{ data: 1000 rows, count: 1500 }` makes the read refuse naming **`runs`** and the real number, and the page renders the error state — it must not render a registry whose last-run column is quietly wrong. Both fixtures: the complete read (`ok`, every row) and the truncated one (refusal). A null count is a refusal, never a zero (§4.3, common violations row 2).

4. **Each leg still reports separately, exactly as today.** `not_provisioned` from the registry read names `sources` and from the runs read names `runs`, so the card says which object is absent rather than blaming the other; the first refusal is returned as the read's refusal, as today — this ticket changes the number of requests, not the composed read's semantics.

5. **The three composed reads run concurrently.** `listSources()`, `readAwaitingRowTrend({ filter })` and `readRejectionStampGauge()` are issued together (`Promise.all` over independent reads) — the filter each takes is derived from `searchParams`, never from another read's rows. Each keeps its own `DbResult` and its own Section: a refused trend gauge renders its own state card with its own eyebrow and leaves the registry table and the rejection gauge untouched, and the same in every other combination. No leg's refusal removes another leg's rows (§4.1, common violations row 14).

6. **The rendering does not move.** On the existing fixtures the page is byte-identical: the same source chips in the same order, the same registry columns and cells, the same paragraph under the table ("State, not configuration…"), both gauges' window lines with their `data-window`, `data-window-held` and `data-window-truncated` hooks unchanged, and the two emptinesses still telling themselves apart — `data-empty="registry"` when the registry holds nothing and `data-empty="narrowing"` when a chip matched nothing. A null `checkpoint` or `note` still renders the dash with no qualifier. A window line stands on every `ok` read including an empty one, and on no refused read (§4.3, common violations row 11) — graded for every surface at once in `tests/offline/absence/pages.test.ts`.

7. **The live oracle grades the state before the number.** `tests/live/sources.live.test.ts` reads the state kind from `data-state` first — `empty` is a pass with a 0, `error` is always a FAIL (common violations row 6) — addresses every surface by its `data-surface` name and never by position (row 8), and counts the same narrowing the surface renders (row 7).

8. **Measurably faster, and the number is recorded.** Warm server time for `/sources` on the walk instance, by STACK.md's own launch recipe, is stated in the handoff with the before (2.0-2.3 s, Ben's measurement) and the after. The bar is the shape, not a threshold: at most 6 requests per render, and the registry+runs leg is 2 of them however many sources are registered.

## Interface contract
(architect ruling, 2026-09-09)

`src/lib/db/sources.ts` — the module keeps its job as the ONE place `sources`
and `runs` are matched by NAME (§6 trap 6: there is no key to join on, by
design) and stops doing it one source at a time.

    /** Every run the table holds, newest first within each source NAME — ONE
     *  request. A COMPLETE read (§4.3 kind 1): the `ok` array is the whole
     *  table or the read refuses naming `runs` with the real number, which is
     *  what keeps "this source has never run" an absence in a complete set
     *  rather than a row that fell off a window. Unnarrowed on purpose: it
     *  needs no name from the registry, so it runs CONCURRENTLY with it, and
     *  `.in(names)` above 100 names would have to chunk. */
    export function readLastRuns(
      db?: SupabaseClient,
    ): Promise<DbResult<LastRunRow[]>>;

    /** The newest run per source NAME, from that complete set — a pure fold,
     *  no read. `null` for a name the set holds no row for. */
    export function lastRunBySource(
      runs: readonly LastRunRow[],
    ): ReadonlyMap<string, LastRunRow>;

    /** Unchanged signature, two requests inside it now instead of 1 + N. */
    export async function listSources(
      db?: SupabaseClient,
    ): Promise<DbResult<SourceState[]>>;

    // GONE: readLastRun (the per-source `limit 1` seek and its loop).
    // KEPT unchanged: SourceRow, LastRunRow, SourceState, SourcesFilter,
    //      SourceNameRow, readSources, readSourceNames, selectSources.

The exact chain `readLastRuns` builds, which is the ruling and not a suggestion:

    client.from(T.runs)
      .select(LAST_RUN_COLUMNS, { count: "exact" })
      .order("source",     { ascending: true })
      .order("started_at", { ascending: false })
      .order("run_id",     { ascending: false })   // uuid v7 — ties break in time's direction
      .range(0, cap - 1)                            // cap handed in by readComplete

`src/app/sources/page.tsx` — one composition, three independent legs:

    const [sources, trend, rejections] = await Promise.all([
      listSources(),
      readAwaitingRowTrend({ filter }),
      readRejectionStampGauge(),
    ]);

`filter` is derived from `searchParams` and the registry's ids as today, so the
narrowing the trend gauge takes must be computed BEFORE the `Promise.all` from
the URL alone, or the concurrency is lost again. Where the URL names a
`source_id` the registry turns out not to hold, the page renders exactly what it
renders today (`data-empty="narrowing"`), and the gauge legs are unaffected —
each leg keeps its own `DbResult` and its own Section state, and no leg's
refusal removes another leg's rows (§4.1, common violations row 14).

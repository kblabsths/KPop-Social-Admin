# The two schema handoff artifacts, authored complete for Ben to install

## Description
**SPEC F9.** Author the campaign's entire database footprint as two migration files that NOBODY HERE INSTALLS: the `verdicts` table and the `settle_review_item` function. Each is filed as a blocked handoff ticket carrying the complete artifact — exact file content, target path under `kspace Scraper/supabase/migrations/`, and the apply command Ben runs there. Nothing in this repo applies them; no ticket's touch scope names a sibling path; the sibling working tree stays clean.

**`verdicts`** (spec §7's table, verbatim): `verdict_id` uuid PK default `uuid_generate_v7()`; `review_item_id` uuid nullable FK to `review_items` (null on an override from the editor); `actor` text not null; `action` text not null with a CHECK on §7's action names plus `override`; `observation_id` uuid nullable FK to `observations` (null on a settle-only verdict); `note` text nullable, required by the function on `wont_fix`; `created_at` timestamptz not null default `now()`. RLS on, ZERO policies, client roles hold nothing. No json column. No new canonical column. No `alter table` on anything vetted.

**`settle_review_item`** (spec §7's "one entry point, one transaction"): the ONLY writer of `verdicts` and the ONLY setter of `review_items.status`. It takes ONE typed decision and branches inside — a value-carrying verdict writes the admin-tier observation through the gate and applies it through `apply_resolution` with `rejected_by = 'verdict'`; a keep-current verdict carries rejections alone with canonical standing; a link verdict writes the confirmed match for the resolver's next cycle to read. Every branch ends the same way: item marked settled, `verdicts` row inserted. One transaction, so a settlement's apply and its rejections SHARE A TIMESTAMP — resolver.md §7 step 0b's strictly-newer guard assumes exactly that. `wont_fix` with a null or empty note RAISES. Overrides enter item-less. Standard revoke pair.

**Author against what is actually installed, never against what a contract implies.** The resolver campaign in the sibling closed 2026-09-03; read `kspace Scraper/supabase/migrations/*.sql` for `apply_resolution`'s real signature and arity, the gate function's real signature, and the real columns of `observations` and `review_items`. `verdicts` and `settle_review_item` exist nowhere there today — confirmed 2026-09-04. **Every identifier the artifacts call must resolve in those migration files.** One that does not is a BLOCKED QUESTION FOR BEN on the ticket — never a signature invented so the file reads well. This is the single highest-risk thing in M2: an artifact that does not apply cleanly costs Ben a debugging session in a repo this campaign cannot enter.

The bar is a REVIEW bar, not an execution bar (DECISIONS 2026-09-02, "a ticket's bar is what its own repo can decide; an external handoff gets its own gate"). Nothing here runs them; the checks are structural reads of the artifact text plus a citation-resolution scan against the sibling's migrations.

FEAT-0010 through FEAT-0013 CALL this function. The shape authored here is the shape they call, and no surface may adapt to a signature Ben has not seen.

# /sources says "nothing matched" for a REGISTERED source named in an uppercased or hyphen-less uuid spelling

## Description
Regression introduced by admin-window/BUG-0139 (landed cd6d267). `filterFrom` in `src/app/sources/page.tsx:123-126` now derives the narrowing from the URL alone, gated only by `isRecordId`, and `selectSources` (`src/lib/db/sources.ts:344-351`) then compares that raw string to `source_id` with JavaScript `===`. The same raw value goes to the awaiting-row gauge query (`src/lib/db/gauges.ts:347`, `.eq("source_id", filter.source_id)`), where Postgres compares it as a UUID.

Postgres accepts three spellings of one uuid and `isRecordId` (`src/lib/db/records.ts:109`, `/^[0-9a-f]{4}(?:-?[0-9a-f]{4}){7}$/i`) deliberately accepts all three. `/records` already honours that rule — `tests/offline/records/page.test.ts` WELL_FORMED_IDS: "Every spelling of a uuid Postgres itself accepts and a URL can carry: canonical, uppercased, and with the hyphens left out. Each names the SAME row". `/sources` no longer does.

**Repro (production build of run/admin-window @ c11c03d, staging, port 8793, warm, cookie-authed):**
1. `GET /sources?source_id=01a05782-8e7f-752c-ae60-3ce4c51962f6` (ticketmaster, canonical) -> 200, registry renders `data-source="01a05782-8e7f-752c-ae60-3ce4c51962f6"`.
2. `GET /sources?source_id=01A05782-8E7F-752C-AE60-3CE4C51962F6` (same id, uppercased) -> 200, 0 source rows, `data-empty="narrowing"`.
3. `GET /sources?source_id=01a057828e7f752cae603ce4c51962f6` (same id, hyphen-less) -> 200, 0 source rows, `data-empty="narrowing"`.

**Expected:** all three name the same registered source, so the registry table renders that source row (as `/records` does for the same three spellings).
**Found:** 2 and 3 render the "nothing matched" emptiness — the page states that the registry holds no source matching a narrowing whose source the registry demonstrably holds. Read-only staging measurement, 2026-09-09 (`agenticflow/tracker/evidence/BUG-0139-qa/probe2.mjs`): `sources` `.eq("source_id", v)` returns `count=1` for the canonical, uppercased, hyphen-less AND upper-hyphen-less spellings of one registered id — the database matches every spelling the page denies.

**Second half of the same defect (latent, no number on staging today):** the value that fails the TypeScript compare is handed unchanged to the gauge query, which DOES match it in Postgres. So the awaiting-row leg fetches that source rows and `selectClaims` (`src/lib/gauges/pending-claims.ts:219`, the same `!==` string compare) then drops every one of them, while the window line reports the rows the query returned. On a database where the narrowed source has awaiting-row claims the page renders `data-window-held="<n>"` beside a registry that says nothing matched and a trend that says none — three sections disagreeing about one narrowing. That is exactly the property BUG-0139 criterion 5/7 and the page own docstring rest on ("the gauges answer the same narrowing the table renders").

**Not pre-existing:** before BUG-0139, `filterFrom(params, offered)` matched the asked value against the registry ids it had already read, so an unmatched spelling narrowed NOTHING and the page rendered the whole registry with the "all" chip active (`git show d43b954^:src/app/sources/page.tsx:108-113`). Benign. The new false statement arrived with this fix.

**Fix shape (architect rules, not mine):** one canonicalisation of the uuid spelling where the narrowing is derived, so the JS compare and the Postgres compare agree — `filterFrom` is the one place that value is made. Nothing about BUG-0139 read shape (`readLastRuns`/`lastRunBySource`/the `Promise.all`) is implicated.

**Pin:** `tests/offline/sources/page.test.ts`, "narrows to the source the URL names, in every uuid spelling Postgres accepts" — `it.fails` (strict: it goes red the day the defect is fixed and the pin is not removed). Watched red 2026-09-09: canonical passes, the uppercased spelling renders `[]`.

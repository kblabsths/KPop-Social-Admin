# the ACL replay silently ignores a grant to PUBLIC and an owner change, so both grade clean

## Description
**Expected** (`tests/offline/handoff/extract.ts:369-375`, the instrument's own invariant): a statement that "may still change the table's ACL" and cannot be modelled is reported in `unreadable` — "NEVER ignore these: silently skipping the statement you cannot parse is how a grader certifies an ACL it never read (BUG-0082 again, one level down)". `verdicts.test.ts:366` asserts `acl.unreadable` is empty precisely so the three ACL assertions beside it are not vacuous.

**Found**: two statement forms that change who may write `public.verdicts` are neither replayed nor reported, and `gradeVerdicts` returns `[]` on both.

1. **A grant to the PUBLIC pseudo-role.** `tableAclAfter` treats `public` as an ordinary role key (`parseRoles`, `extract.ts:389-397`: "the role names one GRANT/REVOKE tail names, `public` included as itself"). In Postgres every role is a member of PUBLIC, so a privilege granted to PUBLIC is held by `anon`, `authenticated` and `service_role`. The replay files it in a `public` bucket that no assertion reads.
   Repro (measured, this checkout, commit 99b058f):
   - doctor the shipped block, inserting after `agenticflow/tracker/for-human/M2-handoff-verdicts.md:161`:
     `grant insert, update, delete on table public.verdicts to public;`
   - `privilegesHeld(acl,"service_role")` → `["select"]`; `anon` → `[]`; `authenticated` → `[]`; `acl.unreadable` → `[]`; `gradeVerdicts(doctored)` → `[]`.
   - Installed reality: every one of the three roles can INSERT/UPDATE/DELETE the verdict log. The only red in the whole suite came from an incidental `expect(grants).toHaveLength(1)` in `verdicts.test.ts:346` — a count assertion the shared instrument does not carry, so the `settle_review_item` note's own test inherits the blind spot with nothing to catch it. `revoke ... from public` is this project's own house idiom (`kspace Scraper/supabase/migrations/20260901000003_an_adjudicated_claim_carries_its_stamp.sql:125`, `20260821000000_the_new_gate_signature_gets_its_revoke.sql:17`), so `public` is a role name these artifacts do name.

2. **An ownership change.** The artifact carries `alter table public.verdicts owner to postgres;` (`M2-handoff-verdicts.md:103`). Doctor that one word to `owner to service_role` and the whole file passes 21/21: an owner holds every privilege on its table and may re-grant them, so the `revoke ... from service_role` below it narrows nothing and "settle_review_item is the only writer" is false. `alterTableTargets` sees the statement and reports only the target name; `tableAclAfter` never looks at it.

**Repro (no SQL executed anywhere)** — from the repo root, on a checkout of 99b058f:
1. In `tests/offline/handoff/verdicts.test.ts`, the two `it.fails` pins in `describe("the grader proves itself on doctored blocks")` — `does not certify a block that hands the write to the PUBLIC pseudo-role` and `does not certify a block that hands the table's ownership to service_role` — each assert `expect(gradeVerdicts(doctored)).not.toEqual([])`.
2. Flip either `it.fails` to `it` and run the check below: `expected [] to not deeply equal []`, twice (observed 2 failed | 21 passed before the pins were flipped).
3. The pins are `it.fails`, so they are green today and go RED the day the grader stops certifying these blocks — at which point delete the `.fails` and this ticket.

**Fix shape is the builder's call, not mine.** Either model the reach (a grant to `public` credits every role in `ROLES_BORN_HOLDING_ALL`; an `alter table ... owner to <role>` credits that role with everything) or refuse to grade them (`unreadable`). Refusing is enough: `unreadable` is already a finding and already asserted empty. The one thing that must not survive is `gradeVerdicts` returning `[]`.

**Why it matters beyond this file**: `extract.ts` is the shared instrument for the `settle_review_item` artifact's own test (its header says so, `extract.ts:16-18,336-338`), which is FEAT-0009's second half and is being authored now. The shipped `verdicts` block is NOT affected — it grants nothing to `public` and its owner is `postgres`. This is a hole in the gate, not a defect in what is behind it.

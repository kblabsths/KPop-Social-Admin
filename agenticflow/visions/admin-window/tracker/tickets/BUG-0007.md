# countRows fabricates 0 when PostgREST returns no count, so a parity test passes against a number the database never gave

## Description
Expected (tests/live/parity.ts:178-191 docstring, and ARCHITECTURE.md 10 'two paths to one number, or it proves nothing'): countRows() throws rather than letting a parity test 'quietly compare against 0 because its own query broke'.

Found: countRows() returns 'count ?? 0' at tests/live/parity.ts:190. A PostgREST answer with error null AND count null - which is exactly what a select written without { head: true, count: 'exact' } returns - is turned into 0 with no complaint. assertParity() then compares a page's rendered 0 with that fabricated 0 and PASSES.

Repro (offline, no database, fabricated values only), from the repo root:
1. const db = stubClient({ review_items: {} }).asSupabaseClient();   // no error, no count
2. await countRows(() => db.from('review_items').select('*'))  ->  resolves 0   (expected: throws)
3. await assertParity({ markup: <a StatCard rendering 0>, label: 'Open decisions', expected: () => countRows(() => db.from('review_items').select('*')) })  ->  RESOLVES 0 (expected: refuses)

Both steps are already written and pinned in tests/offline/live-guard.test.ts as two it.fails() cases marked 'PIN admin-window/BUG-0001' (added by QA on the run branch; the suite is green while the defect lives). The pin is strict - proven by temporarily flipping the assertion so the body passed, which turned the file red ('Tests 1 failed | 34 passed').

Why it matters: parity.ts is the mechanism EVERY M1 page's live test plugs into (acceptance test 2). The one thing it must never do is certify a page against a number it invented; a page ticket that forgets count: 'exact' gets a green parity on any page rendering 0.

Fix direction (builder): countRows must refuse when the resolved count is null/undefined and there is no error - naming that the query returned no count and that a count option is required. Then flip the two it.fails() cases back to plain it() and delete the PIN comments; the check below then genuinely verifies the fix.

Out of scope: the two residuals in QA's TASK-0003 handoff (ref-only declaration matching a foreign domain; the SERVICES.md parser not tracking code fences) - neither is this bug.

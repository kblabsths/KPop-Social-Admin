# An empty queue renders no open count: /queues drops the figure the Dashboard renders as a real 0

## Description
Found on the first live parity run against staging (QA, TASK-0010 History, 2026-09-02), ruled a defect by the architect the same day (DECISIONS.md, "a counted zero is a real figure").

## Expected vs found

Staging holds exactly one `review_item` (an `entity_link` signal), so the DECISION queue is empty and honestly so.

- **Found:** `/queues` renders the `Empty` card for that queue and **no open figure at all** — `src/app/queues/page.tsx:227-236` returns `<QueueList … card={<Empty …/>} />` and passes neither `open` nor `openDetail`, and `src/components/queues/queue-list.tsx:142` renders the `StatCard` only when `open !== undefined`. The live test's `MarkupReadError` is the symptom: nothing labelled "Open decisions" exists in the markup.
- **Expected:** the labelled figure reads `0`, and the rows region still shows the `Empty` card. The Dashboard already does exactly this in the same state (its live assertion on a real `0` is green).

## The bar it violates

- **LOOK_AND_FEEL quality bar 1** — "the question is answered above the fold … **Queues shows the open count of each queue**". With one queue empty, one of the two counts is not on the page at all.
- **The Feel, repeat use** — "counts sit in fixed positions". A figure that vanishes when it reaches zero is a figure that moves, and an operator scanning the same spot every morning cannot tell a quiet queue from a broken page.

Not in tension with the emptiness rule ("an empty bucket, a table with no rows, and an unprovisioned table are three different states and never share a rendering"): that rule is about the ROWS region, where the `Empty` card is right and stays. The figure and the card answer different questions and both belong.

## The fix (small, one branch)

In `src/app/queues/page.tsx`, the empty branch passes `open={0}` and an `openDetail` in the app's voice — the same sub-line rule the populated branch follows, including the "in this filtered view" scoping when a filter is what emptied it (`isNarrowed(filter)`), so a scoped zero still names its scope. `QueueList` needs no change: it already renders the card whenever `open` is defined, and `tone` already falls to `default` at 0. Keep the `Empty` card exactly as it is.

**Both queues keep rendering** — that is already true and is TASK-0010's equal-standing rule; this ticket must not disturb it.

## The line this ticket must NOT cross

`not_provisioned` still renders **no number**. A zero there would be a lie about a table that is not present (LOOK_AND_FEEL state 3, bar 4). The distinction this ticket makes concrete: a counted zero is data and is always shown; an absent table shows the gray card and no figure.

## Why it is scheduled with a P1 behind it

admin-window/TASK-0032 (live-oracle hardening, P1) depends on this: its rule is that an `empty` page is a pass **with a stated 0**, which is only assertable once the figure exists. Small ticket, but it gates that one — dispatch it early.

## Acceptance criteria
1. With a queue holding no items, /queues renders that queue's labelled open figure reading 0, in the position it occupies when the queue has rows, AND the Empty card in the rows region. Both queues still render, at equal standing. 2. The zero names its scope when a filter is what emptied the queue (the populated branch's 'in this filtered view' rule), so a filtered 0 never reads as a whole-queue 0. 3. A not-provisioned queue still renders NO figure — the gray card alone. 4. Offline: tests/offline/queues covers all three states' figure behaviour, and the equal-standing pins from TASK-0010 still hold.

# Adapter runs table still heads its columns with raw database names, so /cycles now speaks two vocabularies

## Description
Found attacking BUG-0044 on the landed tree (run/admin-window), real render on staging: own dev instance :8793, Chromium 1440x900, minted walk cookie, GET /cycles 200, 69 cycle rows and 5 run rows.

**Expected** (LOOK_AND_FEEL Voice bar 5 as the designer applied it in BUG-0044: "a snake_case name uppercased into a sans micro label is neither" prose nor a verbatim mono machine identifier; every table header in this app renders through the one `type-micro` class at src/components/ui/data-table.tsx:104): one page names a column one way, and the app names a column the same way everywhere.

**Found**, on one screen:

    [Cycles]       CYCLE ID | STARTED | OUTCOME | DURATION | FACTS EXAMINED | APPLIED | HELD | ESCALATED | ENTITIES CREATED | CLAIMS LINKED | CLAIMS RE-REJECTED | ERRORS | ERROR
    [Adapter runs] SOURCE | STARTED_AT | ENDED_AT | OUTCOME | ERROR_SUMMARY | RECORDS_PARSED | CLAIMS_EMITTED | RECORDS_UNLINKED | FAILURE_CLASS

`error_summary` is headed **ERROR** in the first table and **ERROR_SUMMARY** in the second, on the same page, a few thousand pixels apart — the exact self-contradiction BUG-0044 was filed for, one table over. Seven of the nine adapter-runs headers are raw column names.

And the same columns are already headed in the app's words on the Dashboard (rendered the same way, `/` 200):

    [runs on the Dashboard] SOURCE | STARTED | OUTCOME | ERROR

So `runs.started_at` reads STARTED on `/` and STARTED_AT on `/cycles`, and `runs.error_summary` reads ERROR on `/` and ERROR_SUMMARY on `/cycles`.

**Repro**
1. Launch a walk instance per STACK.md §5 on a free port, mint a cookie, GET `/cycles` with it against staging.
2. Read `table[aria-label="Adapter runs"] thead th` — the nine strings above.
3. Read `table[aria-label="runs"] thead th` on `/` — SOURCE | STARTED | OUTCOME | ERROR.

**Why this is a gap and not a ruling.** The builder of BUG-0044 recorded the carve-out as "documented as a ruling in src/lib/db/runs.ts". It is not. Ben's ruling of 2026-09-02 (agenticflow/docs/DECISIONS.md:445) settles WHICH nine columns the half shows — its one use of "verbatim" qualifies the error VALUE ("the error line (`error_summary`, inline and verbatim)"), never a header — and src/lib/db/runs.ts:18 says so itself ("settled the column set"). The only sanction for verbatim headers is a code comment authored by that half's own builder, src/app/cycles/page.tsx:967-969. Nothing a human ruled is being overturned here.

**Where the fix lands.** `runColumns()` at src/app/cycles/page.tsx:971 maps `label: column` straight off RUN_COLUMNS. Note that tests/offline/runs/page.test.ts:178 currently PINS the defect (`expect(headers(markup, RUNS_TABLE)).toEqual([...RUN_COLUMNS])`) — the fix must separate "the nine ruled columns, in order" (a real contract, keep it, read it off the cells' keys) from "headed by their machine names" (this bug). RUN_COLUMNS itself is the select list and the ruling's contract: do not rename it, and keep every `data-*` hook on its machine name so the live oracles stay valid.

Which words replace them is the designer's call; the pin asserts only that no header is a raw column name, and pins no copy.

**Pinned by** `tests/offline/runs/page.test.ts`, "heads no column with a raw database column name" — watched RED against this code (`expected [ 'started_at', 'ended_at', ...(5) ] to deeply equal []`), then marked `it.fails` so the branch stays green; when the fix lands it XPASSes and turns red, pointing here.

# the venue reference column shows no provenance: the log is queried by column name, and that fact is registered as 'venue'

## Description
Expected (TASK-0054 criterion 6; `contracts/data-model.md` Per-field provenance): on a resolver-owned record, a source-won field renders the source and the age, and only a field with NO decision renders the dash.

Found: the `venue_id` line of every `events` record renders the em dash, under the page's own `data-note="provenance-absence"` note — "A — in Provenance means no field provenance is recorded for that field: the value has no source behind it" — while `field_provenance` holds a decision for exactly that fact. The page states, in words, the opposite of what the database holds.

Location: `src/lib/db/records.ts:410`, `provenanceFor` filters `.in("field", [...mappedColumns(config)])`. `mappedColumns(EDIT_CONFIG.events)` spells the CANONICAL COLUMN names (`event_id, title, description, poster_url, starts_at, venue_id`), but `field_provenance.field` holds the REGISTRY FIELD name, and `src/lib/verdict/decision.ts` (`VerdictValue.field`) names the one place the two differ: "the registry's field names ARE the canonical columns' names, with `events.venue` (field) -> `events.venue_id` (column) the one exception, which is what makes it a reference rather than a cell". So the filter asks for `venue_id`, the log stores `venue`, and the row can never match.

Measured on staging `ubfjjqlvnpnoborczbdb` 2026-09-08, production build on 127.0.0.1:8931, walker cookie:
- `field_provenance` distinct `entity_type.field` over 1000 rows: `events.venue` 11 rows, `events.title` 21, `events.poster_url` 21, `events.starts_at` 21, `events.status/event_type/ticket_url/time_precision` 21-22 each, `venues.name/city/country/address/timezone/latitude/longitude` 114-124 each. ZERO rows anywhere spell `venue_id`.
- Event `01a03c9b-1d28-707d-9873-f73ab3add10c` carries `field=venue`, `source_id=01a05782-8e7f-752c-ae60-3ce4c51962f6` (ticketmaster), `tier_at_apply=official`, `applied_at=2026-09-02T15:41:43.234679+00:00`, `admin_locked=false`.

Repro (exact):
1. Build and start the app against staging (`STAGING_SUPABASE_URL` / `STAGING_SUPABASE_SERVICE_ROLE_KEY` mapped onto `SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY`), mint a cookie with `tests/walk/session-cookie.mts` under the same `AUTH_SECRET`.
2. GET `/records/events/01a03c9b-1d28-707d-9873-f73ab3add10c` with that cookie.
3. Read the field table. Observed verbatim:
   - `title` -> `XG` | `ticketmaster, applied 6d ago`
   - `poster_url` -> ... | `ticketmaster, applied 6d ago`
   - `starts_at` -> `2026-09-02T17:30:00+00:00` | `ticketmaster, applied 6d ago`
   - `venue_id` -> `OVO Arena Wembley 01a03c9b-1b59-7cf5-bda8-50d13f6787aa` | `—`
   Expected on that last line: `ticketmaster, applied 6d ago`.

Consequence beyond the dash: the same mismatch will hide `admin_locked` on the venue fact the day `settle_review_item` lands, so an admin-locked venue would read as unprovenanced — the exact stickiness spec section 8 asks this column to show. It is also the one column an operator most needs a source for: it is the only value on the page they cannot verify by reading it.

Not a rendering defect: `record-fields.tsx` draws whatever `readRecordProvenance` returns, and it returns nothing for this fact. The fix is the field-name mapping, and WHERE it belongs is a judgment for the builder to record — the map already knows `events.venue_id` is a reference (`EDIT_CONFIG.events.reference`), and `decision.ts` already states the exception; nothing today turns one into the other. Do not add a second allowlist and do not widen `editable`: `venue_id` stays read-only (AGENTS.md, TASK-0054 criterion 8).

Pin: `tests/offline/edit/records.test.ts`, `readRecordProvenance > carries the venue fact onto the reference column that displays it`, landed as `it.fails` (strict: it reddens the day the behaviour is fixed and the marker is left behind). Watched RED as a plain `it` before it was marked — "expected [ 'event_id', 'title', ...(4) ] to include 'venue'". The fix removes the `.fails` marker.

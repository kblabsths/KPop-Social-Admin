**Nothing here applies anything.** No agent runs either artifact, no ticket's touch scope names a sibling path, and the sibling's working tree and git log stay untouched — two of this ticket's stored checks are exactly that, by absolute path.

**The signature.** `public.settle_review_item(p_decision jsonb)` — ONE typed decision, a jsonb ARGUMENT, following the two shipped idioms next door (`apply_resolution(p_decisions jsonb)`, `ingest_observations(p_batch jsonb)`, whose own migration comment records that "the ban is on jsonb COLUMNS, and a batch argument is not a column"). The keys are `src/lib/verdict/decision.ts`'s `VerdictDecision`, exactly: `action`, `review_item_id`, `actor`, `note`, `value{domain, entity_id, field, observation_id, value, ref}`. An unaccepted key is refused, in the shape `apply_one_resolution` already uses for its own key sets.

**What every branch does, and what they share** (spec §7):
- **The ending is common to all of them, in ONE transaction**: `review_items.status` set to `settled`, and one `verdicts` row inserted. The function is the ONLY writer of `verdicts` and the ONLY setter of `review_items.status`. One transaction is not a nicety — `contracts/resolver.md` §7 step 0b's strictly-newer guard assumes the settlement's apply and its rejections share a timestamp.
- `choose_claimed_value` / `supply_value` / `override` — value-carrying: write the **admin-tier observation through the gate**, then apply it through **`apply_resolution`** with the rejections the verdict implies (`rejected_by = 'verdict'`). `override` enters **item-less**: `review_item_id` null, nothing settled, the `verdicts` row alone.
- `keep_current` — rejections alone, canonical standing; `apply_resolution`'s `adjudicate` kind is the arm that stamps without applying (read its contract in `20260901000006`).
- `link_entity` — the confirmed match: a `confirmed_matches` row for `(admin source, domain, external_ref)` with `matched_by = 'verdict'` (that value is already in the table's CHECK), which the resolver's next cycle reads to unlock the waiting claims.
- `settle`, `fixed`, `wont_fix` — no canonical write at all. **`wont_fix` with a null or blank note RAISES**, with an errcode in the sibling's `KS0xx` grammar; the form's refusal is courtesy, this one is the contract.
- **Standard revoke pair** at the end, exactly as `apply_resolution` carries it: `revoke all ... from public, anon, authenticated;` then `grant execute ... to service_role;`.

**Facts of the installed schema this artifact must honour** (read 2026-09-08; re-read them, do not trust this list):
- `apply_resolution(p_decisions jsonb)` returns a table of 13 columns and takes an ARRAY of decisions whose kinds are `apply | unset | create | adjudicate | link`; a fact object carries `{field, column, observation_id, reference_entity_id, performers, tier_at_apply, admin_locked}` and `column` defaults to `field`. **`admin_locked` is already a fact key** — that is how spec §8's `admin_locked` stamp is produced, not by a second write.

If no honest way to resolve it exists in the installed schema, that is a blocked question for Ben, not a hardcoded `3`.
- `review_items.status` admits exactly `open | settled`; a settled item never blocks a new one for the same subject.
- The admin source's name comes from TASK-0043's answer. Until that answer lands, this ticket stays blocked — the branches that need it and the branches that do not live in one file.

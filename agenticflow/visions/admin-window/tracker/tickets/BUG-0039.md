# STACK.md 5's walk launch line is not runnable from a fresh shell: the staging names it maps are unset there, so the walk instance has no database

## Description
Expected (agenticflow/docs/vision/STACK.md §5, "The walk instance: launch it, get past the gate, drive it" — "Everything below is verbatim and runnable from the repo root", step 1): a walker copies the launch line and gets a walk instance whose server-side reads reach staging.

Found: from a fresh agent shell the two mapped names arrive EMPTY, so the app's only database client cannot be constructed and no server-side read on that instance can succeed. §5 itself closes the only other door ("`.env` no longer carries `SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY` at all"), and the step never says where `$STAGING_SUPABASE_URL` / `$STAGING_SUPABASE_SERVICE_ROLE_KEY` are supposed to come from. They live only in the repo-root `.env` (names listed in `.env.example`); no doc in the repo carries a `source .env` / `set -a` / `export STAGING_*` step (grep over agenticflow/docs, agenticflow/visions/admin-window/docs, contracts: zero hits).

REPRO, measured 2026-09-03 on run/admin-window at 1a89375 (no value printed anywhere):

1. Fresh agent shell:
     bash -c 'for v in STAGING_SUPABASE_URL STAGING_SUPABASE_SERVICE_ROLE_KEY SUPABASE_URL SUPABASE_SERVICE_ROLE_KEY; do [ -n "${!v+x}" ] && echo "$v SET" || echo "$v UNSET"; done'
   -> all four UNSET.

2. Run §5's launch prefix verbatim, with Next's own env loader in place of `npm run dev` (same precedence `next dev` uses, @next/env loadEnvConfig):
     SUPABASE_URL="$STAGING_SUPABASE_URL" SUPABASE_SERVICE_ROLE_KEY="$STAGING_SUPABASE_SERVICE_ROLE_KEY" AUTH_URL="http://localhost:8771" node <probe>
   ->  SUPABASE_URL: EMPTY STRING
       SUPABASE_SERVICE_ROLE_KEY: EMPTY STRING
       AUTH_SECRET: non-empty (picked up from .env)
       AUTH_URL: non-empty
       getSupabaseAdmin() equivalent THREW: supabaseUrl is required.
   (src/lib/supabase.ts:3-4,14-16 — `createClient(process.env.SUPABASE_URL!, ...)`.)

3. Same line, prefixed with the undocumented step `set -a; . ./.env; set +a`:
   -> both names non-empty, `getSupabaseAdmin() equivalent: constructed OK`.

What was NOT measured, and why: the exact page a walker would see on such an instance. `next dev` refuses a second instance in this project dir ("⨯ Another next dev server is already running.", observed on port 8779; the pid I spawned was killed, 8779 clear, the dispatcher's 8771 untouched and still HTTP 200), and rebuilding for a production-like walk would have disturbed the live 8771 instance. The measured fact is that the client cannot be constructed; the rendering that follows is for the fix to state.

Why it matters (walker-visible, both directions): §5 is the recipe every M1 endgame walker is pointed at — designer walk, user-sims, verifier. Followed literally, a walker drives a credential-less instance and either reports app-wide breakage that does not exist, or reads whatever the surfaces do when every read fails and reports a false picture of the app. The instance currently on 8771 serves real staging rows (dashboard shows resolver cycles and ticketmaster runs), so it was demonstrably NOT launched by the recipe as written — the gap is real and is already being papered over by hand.

Fix (doc only, same scope as BUG-0038; no product code): §5 step 1 must make the launch self-sufficient from a fresh shell — name where the staging names come from (the repo-root `.env`, the one file §5 already says the DB names must not be READ from by the app) and give the runnable prefix, or map from a source the doc names. The rest of the recipe is sound: `AUTH_URL` behaviour, the mint line, the cookie descriptor and the Playwright snippet were all re-driven and work (see BUG-0038's QA note).

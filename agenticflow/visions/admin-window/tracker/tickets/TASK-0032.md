# Live oracles must name the page's state kind: an ERROR page may not pass and an EMPTY page may not fail

## Description
Module: `tests/live/**` (the oracle), `tests/offline/live-guard.test.ts` (its proof), and the four `ui` state primitives (the seam the oracle reads). Authority: ARCHITECTURE §10 (the live-oracle rule, added 2026-09-02), DECISIONS.md 2026-09-02 ("a live oracle names the page's state kind"), Common violations class 6, acceptance test 2.

## What the first staging run proved

The live suite graded three pages wrong, in both directions, and nobody could tell from the exit codes:

- `tests/live/queues.live.test.ts` — two failures. `?queue=data_conflict` matches nothing on staging, both queues render the `NOTHING_MATCHED` Empty card, `listsRendered()` (a `[data-queue] table` probe) is false, and the test falls into its **not-provisioned** branch, which demands the markup carry the table name. An honest EMPTY page is graded as an unprovisioned one and fails.
- `tests/live/sources.live.test.ts` — the same two-way branch, the same false red.
- `tests/live/claims.live.test.ts` — the opposite and worse: **4 of 6 passed on a page in its ERROR state.** The fallback branch only asks that the markup contain `pending_claims`, and the red error line carries that string exactly as well as the gray not-provisioned card does. Four vacuous passes while the page was broken.
- `tests/live/parity.ts` — a failed parity count reported an EMPTY message: a `head: true` count carries no body, so supabase-js parsed nothing out of a real `57014` (measured: `code=undefined, msg=""`). A timeout was reported as a blank.

A live suite that can be green while the page it grades is broken is the one thing this suite exists not to be.

## The oracle rule (ARCHITECTURE §10 — implement it, do not re-derive it)

Every live parity test, on every read it grades:

1. **The test decides the kind it EXPECTS from its own independent count**, then asserts the rendered kind equals it. Four kinds: `ok`, `empty`, `not_provisioned`, `error`.
2. **The kind is read structurally, never from prose.** `Empty` and `NotProvisioned` render the same container today and differ only in their words — so this ticket adds `data-state` to the four `ui` state primitives (`loading` / `empty` / `not_provisioned` / `error`) and the oracle reads that attribute. Do not grep rendered copy: copy is the designer's jurisdiction and a test that pins it will redden on a wording change (ARCHITECTURE §10, and the campaign's standing rule that behaviour lives in tests, wording in walks).
3. **`ok` compares numbers.** Unchanged: two independently written paths to one number.
4. **`empty` is a pass WITH a number** — the test's independent count is exactly 0, and the page's labelled figure reads 0. It is never an absence and never a skip. (admin-window/BUG-0027 makes `/queues` render that figure; this ticket depends on it.)
5. **`not_provisioned` is a pass only when the test's own read of that same object returns the absence code** (`PGRST205` / `42P01`). It is never inferred from "no rows rendered".
6. **`error` is a FAIL**, and the message names the read and the database's own code.

## The seam, so three test files and every later one share it

Put the classifier in `tests/live/parity.ts` beside the existing helpers (it is pure and client-free, which is what keeps it provable offline):

```ts
export type PageStateKind = "ok" | "empty" | "not_provisioned" | "error";

/** Every state card the markup carries, in document order, by `data-state`. */
export function pageStates(markup: string): PageStateKind[];

/**
 * The kind of ONE surface: the state card inside `within` (a selector), or
 * `ok` when that surface rendered rows and no state card.
 */
export function stateOf(markup: string, within: string): PageStateKind;

/** Asserts the kind, and on a mismatch says which kind was found and where. */
export function assertState(
  markup: string,
  within: string,
  expected: PageStateKind,
): void;
```

`assertParity` keeps its signature and gains the rule: it asserts `ok` (or an explicitly passed expected kind) before it reads a number, so a MarkupReadError can never again be the way a test discovers the page was in another state.

And fix the blank refusal: the helper that runs a test's own count issues a **GET-shaped** count (`select("id", { count: "exact" })` with a range, not `head: true`) so PostgREST returns a body and a real error code — or, when it genuinely cannot tell, says "the count query failed and returned no parseable error" rather than an empty string.

## The three files

Rewrite the branch logic in `queues.live.test.ts`, `sources.live.test.ts` and `claims.live.test.ts` against the rule. Concretely for each: count independently first, derive the expected kind, assert it, then compare numbers only in `ok`/`empty`.

**`claims.live.test.ts` will then FAIL on staging, and that is the correct result.** `pending_claims` cannot be read (admin-window/TASK-0031 — every shape but an unordered `limit 1` times out at ~8.1s; the fix is a scraper-repo handoff), so the page is honestly in its `error` state and rule 6 says an error is a failure naming the read. **Do not weaken the oracle to make it green, do not skip the file, and do not mark the cases `todo`.** Its red is the campaign's only honest signal that the handoff has not landed. Say so in the file, cite TASK-0031, and leave it red. The two live checks on this ticket are `queues` and `sources` for exactly that reason.

## Also record, do not paper over

Under the new rule those cases become explicit `empty` assertions with a stated 0 — which is honest, and is still not coverage. Where a live case can only compare 0 to 0, the file says so in one line beside it, so nobody reads the green as proof the decision queue renders.

## Standing rules for this ticket

- Product code changes are **only** the `data-state` attributes on `src/components/ui/{loading,empty,not-provisioned,error-line}.tsx`. Nothing else under `src/` is touched. `data-state` is additive markup in the idiom the app already uses for test seams (`data-queue`, `data-evidence`, `data-bucket-claims`) and must not change any class, token or word.
- The live suite still refuses by name when the staging names are unset, and prints no value or host.

## Acceptance criteria
1. The four ui state primitives each emit a data-state attribute (loading | empty | not_provisioned | error) and nothing else about them changes — same classes, same tokens, same words. 2. tests/live/parity.ts exports a pure state classifier (pageStates / stateOf / assertState) that reads data-state and never rendered prose, and assertParity asserts the expected kind before it reads a number. 3. The parity count helper reports a real database error code for a failed count — a head:true count's empty message is gone; measured against a query that fails. 4. queues.live.test.ts, sources.live.test.ts and claims.live.test.ts all grade against the four kinds: ok compares numbers, empty is a pass with a stated 0, not_provisioned requires the absence code from the test's own read, error FAILS naming the read. 5. tests/offline/live-guard.test.ts proves the classifier offline on markup rendered from the real primitives, including the case that regressed: a page in its error state must classify error and must NOT satisfy a not-provisioned expectation. 6. queues and sources live tests pass against staging. claims.live.test.ts is expected RED (pending_claims is unreadable — TASK-0031) and is left red, not skipped, not weakened, with the reason and the ticket cited in the file. 7. Any live case that can only compare 0 to 0 says so beside itself.

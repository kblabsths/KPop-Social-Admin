# readPendingClaims is exported twice with unrelated meanings — the same module pair DEBT-0014 just separated, one function over

## Description
Expected (ARCHITECTURE §6/§11; DEBT-0010 criterion 1, 'no identifier is exported twice from src/ with two different meanings'): a grep for a vocabulary word returns one declaration.

Found, on run/admin-window at 035fd2e — two exported `readPendingClaims`, from the SAME module pair DEBT-0014 just separated:

- `src/lib/db/claims.ts:137` — `(ids: readonly string[], db?) => Promise<DbResult<PendingClaimRow[]>>`. The rows of the classification view, by `observation_id`. Called by `src/app/queues/[reviewItemId]/page.tsx:661` and re-exported through `src/lib/db/gauges.ts:64`.
- `src/lib/gauges/pending-claims.ts:304` — `(options: GaugeOptions & {filter?: PendingClaimsFilter}, db?) => Promise<DbResult<PendingClaims>>`. Fetch + aggregate: 'what /claims calls'. Called by `src/app/claims/page.tsx:585`.

Repro (repo root, run/admin-window @ 035fd2e):

    grep -rnE '^export (async )?function readPendingClaims' src

Observed: 2 hits (the two above). Expected: 1.

Why this is worth a ticket and not a comment: the collision has ALREADY forced a rename at an import site. `src/lib/gauges/pending-claims.ts:7` imports the db one as `readPendingClaimRows` — a module that must rename its neighbour's word to use it is the §6 hazard's own symptom, and it is the sentence DEBT-0014's description was filed on, one function over. Two adjacent PAGE surfaces (`/claims`, `/queues/[reviewItemId]`) each call a different function under the one word.

Both are `async (x, db?) => Promise<DbResult<…>>`, so as with DEBT-0014 nothing but the type checker separates them, and only because the first parameter happens to be `readonly string[]` on one and an options object on the other. Nothing renders wrong today — P3, no user-visible path; a readability and wrong-import hazard.

Suggested shape (the builder's call, as in DEBT-0010/DEBT-0014, which is why the pin below does NOT name a winner): the two names could be `readPendingClaimRows` / `readPendingClaims`, which is already the vocabulary every call site of the gauge module reads. Do NOT merge them — different inputs, different return types, different layers (db read vs gauge façade).

THE PIN, already on the branch (written by QA under DEBT-0014, tests/offline/url/narrowing.test.ts): `it.fails("readPendingClaims is declared in exactly one module (admin-window/DEBT-XXXX)")`. It passes TODAY because the assertion inside it fails on two declarers; the day this ticket lands it XPASSes and the file goes RED, naming this ticket. Watched both ways before filing: as a plain `it` it reds with `expected [ 'src/lib/db/claims.ts', 'src/lib/gauges/pending-claims.ts' ] to have a length of 1`, and pointed at a single-declarer name the `it.fails` reds with 'expected test to fail'.

When it lands, the builder REPLACES that pin with two OWNER-map entries in the same file (the DEBT-0014 shape) — the `it.fails` must not survive the fix.

Not in scope: the 14 other identifiers this branch exports from more than one module (measured 2026-09-09). They are two different, benign patterns and must not be swept in with this one — `TABS`, `DEFAULT_TAB`, `TAB_PARAM`, `ANY_LABEL`, `SOURCE_FACET`, `withFacet`, `facetChips`, `filterBar`, `filterFrom`, `tabFrom`, `tabLinks` are the deliberate domain-parallel pair `lib/claims/filters.ts` ∥ `lib/review/queue-filters.ts` (one word, the SAME meaning, two domains); `FilterBar` is the same pattern in components; `dynamic` is Next's route-segment config on six pages. `newestFirst` (`lib/db/cycles.ts`, `lib/db/verdict.ts`) is the one unexamined case — same-meaning duplication if anything, not this hazard.

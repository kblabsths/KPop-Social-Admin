# The admin_locked write guard's balanced-argument scan is not string-aware: it reports a READ as a write, and misses a real WRITE

## Description
Found while attacking BUG-0028 (landed fd2ad40). BUG-0028 implemented the architect's ruled predicate correctly; this defect is in the pin the builder added BEYOND the ruling and flagged for review — `writeArguments` / `filesWritingColumn` in `tests/offline/edit/config.test.ts` (helpers at :348-:382, used by the rule at :438-:440).

The addition is worth keeping: it catches a real hole in the ruled line-wise pin (a Prettier-wrapped `.update({\n admin_locked: true,\n})` carries the name and the verb on different lines and the ruled pin misses it — measured green/red on a mirror tree). Its false-positive claim on `.update(values).select("... admin_locked ...")` also holds: the extracted argument is `"values"`, so the chained read is not reported. Verified, not taken on trust.

What is wrong is the scanner itself. `writeArguments` counts `(` / `)` in the raw code text with no string-literal awareness, so a parenthesis inside a string in a write payload moves the argument boundary. Both directions are reachable and both are wrong.

1. FALSE POSITIVE on a read (re-introduces BUG-0028's own defect class, narrowed).
   Repro: mirror tree file `src/read-after-write.ts` containing
     export const a = (db: Db) =>
       db.from("groups").update({ note: "opens ( here" }).eq("id", 1);
     export const b = (db: Db) =>
       db.from("field_provenance").select("field, admin_locked");
   Expected (BUG-0028 acceptance criterion 2: a READ of admin_locked anywhere under src/ passes the guard): `filesWritingColumn("admin_locked", base)` === [].
   Found: ["src/read-after-write.ts"] — the unclosed `(` inside the string runs the scan past the real `)`, so the argument swallows the later pure READ. The guard would forbid the spec §8 provenance display in any file that also holds such a write.

2. FAIL OPEN on a real write (the pin's whole purpose).
   Repro: mirror tree file `src/stamp.ts` containing
     export const stamp = (db: Db, id: string) =>
       db.from("field_provenance").update({
         note: "set by admin :)",
         admin_locked: true,
       }).eq("id", id);
   Expected: `filesWritingColumn("admin_locked", base)` === ["src/stamp.ts"] — this IS a forbidden write of a resolver-owned column (AGENTS.md data ownership).
   Found: [] — the `)` inside the string ends the argument early, `writeArguments` returns `["{\n    note: \"set by admin :"]`, and the payload's own `admin_locked` is never seen. The ruled LINE pin misses it too (wrapped payload), and `EDIT_CONFIG`'s value assertion does not cover it (a hand-built payload does not go through the map). A forbidden write slips every pin.

Neither shape exists on the tree today: `writeArguments(RECORDS_MODULE)` on the real tree returns exactly `["{ [field]: value }"]`, and `.update(` lives only in `src/lib/db/records.ts`. This is a latent guard soundness gap, not a live product defect — which is why it is P2 and not a bounce of BUG-0028.

Both shapes are PINNED, watched red first and now landed as strict expected failures in `tests/offline/edit/config.test.ts`, describe "the argument scan and string literals" (`it.fails`, both naming this ticket). Watched red as plain `it` against the landed code: "expected [ 'src/read-after-write.ts' ] to deeply equal []" and "expected [] to deeply equal [ 'src/stamp.ts' ]".

The fix: make the paren walk in `writeArguments` skip string literals (single, double, backtick) and their escapes, then CONVERT THE TWO `it.fails` PINS BACK TO `it` — left as `it.fails`, a correct fix turns them red as XPASS and points here. Test-only; no product code. Alternative disposition for the architect: delete the argument pin entirely (line 440 plus its probe assertion, as the builder offered) — but that restores the Prettier-wrapping hole the addition closes, so fixing the scan is the better trade.

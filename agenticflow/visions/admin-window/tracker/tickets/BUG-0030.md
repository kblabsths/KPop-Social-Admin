# The admin_locked write guard's balanced-argument scan is not string-aware: it reports a READ as a write, and misses a real WRITE

## Description
RULING (architect, 2026-09-02) on QA's churn flag — bounce 3 of 3 on one class.
The inputs are changed; the approach below is NOT the fourth tokenizer round.

## Why the last three rounds failed

`codeOnly` is a hand-rolled JavaScript lexer living in a test file. Each fix
closed the case in front of it and opened the next, because "is this `/`
division or a regex, is this backtick a template or text" is not a corner —
it is the whole of lexing TypeScript, and the three bounces were three
different facts about the grammar (parens in a payload string; an unclosable
template blanking to EOF; a backtick inside a regex literal after `=>`, where
the `/` reads as division). A fourth patch is the same bet at longer odds.

## The disposition: stop lexing, use the compiler's parser

TypeScript's own parser already ships here — `typescript` ^5 (lock 5.9.3), a
devDependency, grandfathered in `agenticflow/docs/ALLOWED_DEPS.md:72`. No DEP
ticket, no new dependency. Verified 2026-09-02 that it resolves from this repo
(`require.resolve("typescript")` → `node_modules/typescript/lib/typescript.js`,
version 5.9.3). `ts.createSourceFile` + a small AST walk answers the question
the scan actually asks — "does a write verb receive this column" — and
strings, comments, template literals, interpolations and regex literals are
handled by construction rather than by heuristic.

Prototyped before ruling, not prescribed on faith:
`agenticflow/tracker/evidence/BUG-0030/ast/proto.mjs` runs the predicate below
over the real `src/` tree and 20 mirror-tree cases — every landed case in
`describe("the argument scan and string literals")`, all four mirror probes,
all three QA pins, plus five shapes nobody has tried (regex after `return`, a
nested payload object, a computed key spelling the column, a payload built by
a helper call, a `.tsx` write). 20/20 green on the first run, no per-case
tuning. Real tree, identical to today: `filesWritingColumn("admin_locked")`
=== `[]`, `writeArguments("src/lib/db/records.ts")` === `["{ [field]: value }"]`,
zero `src/` files with a parse error. The strict-typed form
(`evidence/BUG-0030/ast/typed.ts`) exits 0 under `tsc --strict` and under the
repo tsconfig's exact flags.

## Why not the alternative (drop the argument scan)

It was on the table and it is genuinely cheap, and the residual is narrower
than this ticket implies: `.insert(` / `.upsert(` / `.rpc(` are already banned
repo-wide and `.update(` is already pinned to `records.ts` alone by "writes the
database from exactly one module", so the only shape that slips a line-only pin
is a Prettier-wrapped `admin_locked` payload inside `records.ts` itself. I keep
the guard anyway: that wrapped shape is exactly what Prettier produces, after
this ticket the pin is ~45 lines of parser calls with no bespoke logic left in
it, and the campaign has already paid for this guard three times.

**Pre-decided escalation:** if a FOURTH corner is found in the AST route, do
not patch it. Take the drop-the-scan disposition — delete `writeArguments`,
`filesWritingColumn`, the `filesWritingColumn(ADMIN_LOCKED)` line of the rule
and this whole `describe`, keeping only the ruled line pin and the
`EDIT_CONFIG` value assertion, and record the wrapped-payload gap as a
residual. This paragraph is the authorisation; nobody needs to re-litigate it.

## What to build — test-only, one file, `tests/offline/edit/config.test.ts`

1. **Delete the tokenizer whole.** `codeOnly` and every part of it: `quoted`,
   `template`, `regexLiteral`, `previousSignificant`, `REGEX_MAY_FOLLOW`,
   `scan`, `blank`. No tokenizer and no regex over code text to decide a
   literal boundary survives this ticket. `sourceText`, `codeLines`,
   `filesWhereCodeMatches`, `sourceFiles` and `WRITE_VERB` all STAY — the
   ruled line pin and the other repo-wide rules use them.

2. **Parse instead.**

       const WRITE_VERBS = new Set(["update", "upsert", "insert"]);

       function parsed(file: string, base: string): ts.SourceFile {
         return ts.createSourceFile(
           file,
           sourceText(file, base),
           ts.ScriptTarget.Latest,
           /* setParentNodes */ true,
           file.endsWith(".tsx") ? ts.ScriptKind.TSX : ts.ScriptKind.TS,
         );
       }

   `setParentNodes` must be `true` — `node.getText(source)` needs it. `.tsx`
   must use `ScriptKind.TSX`: `sourceFiles()` walks `.tsx`, and a `.tsx` parsed
   as TS produces parse errors that would over-report the whole file.

3. **A write call is structural.** A `ts.CallExpression` whose `expression` is
   a `ts.PropertyAccessExpression` whose `name.text` is in `WRITE_VERBS`;
   walked with `ts.forEachChild`. This is what makes
   `.update(values).select("… admin_locked …")` safe by construction —
   `.select(` is a different call, not an argument of the write. BUG-0028's
   read can no longer be false-positived by accident.

4. **`namesColumn(node, column, source)` — does this ARGUMENT name the column?**
   - `ObjectLiteralExpression`: each property's NAME (an identifier's or a
     string-literal key's `.text`; a `ComputedPropertyName`'s
     `expression.getText(source)`), then recurse into a `PropertyAssignment`'s
     `initializer` and a `SpreadAssignment`'s `expression`.
   - `ArrayLiteralExpression`: recurse into elements.
     `ParenthesizedExpression`: recurse into `.expression`.
   - `ts.isStringLiteralLike(node) || ts.isTemplateExpression(node)`: **false**.
     A column named in PROSE inside a payload string is not a write of it —
     the one place text is deliberately not matched, pinned by the landed case
     "does not report the column when only a payload string names it".
   - anything else (identifier, call, conditional, `as`, …):
     `node.getText(source).includes(column)`. That default is the over-report
     direction on purpose: `update(buildPayload({ admin_locked: true }))` is
     reported; `update(values)` is not, because nothing spells it.

5. **A parse error is REPORTED, never skipped.**
   `(source as unknown as { parseDiagnostics?: readonly ts.Diagnostic[] }).parseDiagnostics ?? []`
   — `parseDiagnostics` exists at runtime and is `@internal` in typescript's
   d.ts, so it needs that cast; the cast is `unknown`-based, not `any`, and the
   helper typechecks strict-clean (measured). A file with any parse diagnostic
   is reported by `filesWritingColumn` without further inspection: a file the
   scan cannot see into is a file it may not stay silent about. This is what
   keeps QA's round-2 pin (`src/unterminated.ts`) green.

6. **Re-read once before reporting a parse error.**
   `tests/offline/db/layering.test.ts` writes and deletes a probe under `src/`
   while this suite runs in a parallel worker (BUG-0020, BUG-0029). Today a
   torn read is harmless — the tokenizer gives up and reports nothing — but
   under rule 5 it would be a flaky red on the real-tree assertion. On a parse
   error, read and parse the file a second time and use the second result. No
   fail-open either way: a genuinely unparseable file fails both reads; a
   half-written one either comes back whole (correct silence) or torn again
   (correct over-report).

7. **`writeArguments` keeps its name and shape** — `string[]`, the source text
   of every argument of every write call — because "extracts the argument of
   the one real write in this repo" asserts on it and that is what keeps the
   pin non-vacuous. `filesWritingColumn` no longer decides from that text; it
   decides from `namesColumn` over the argument NODES.
   **The one assertion in this file that changes:** in "does not report the
   column when only a payload string names it", drop
   `expect(argument).not.toContain(ADMIN_LOCKED)` — its premise was that
   `codeOnly` blanked the string's text out of the extracted argument, and
   there is no blanking any more. Replace it with the assertions that carry the
   same weight without the dead premise: the write call WAS found
   (`writeArguments("src/note-about-locking.ts", base)` has length 1 and its
   one entry contains `note:`), and `filesWritingColumn` is still `[]`.
   Nothing else in the file's assertions may change.

8. **The three QA pins become plain `it()`s and pass**; no `it.fails` survives

   `describe("the admin_locked write guard itself")` and every other case in

# ASK BEN: pending_claims view times out on staging (handoff: index or view rewrite in the scraper repo)

## Description
**A handoff, not Admin work.** `public.pending_claims` is defined in the sibling scraper repo (`supabase/migrations/20260901000004_every_pending_claim_lands_in_one_bucket.sql`), a campaign is running there, and ARCHITECTURE §1.1 makes every scraper-side change a handoff for this milestone. This ticket carries the measurement, the candidate artifacts, and the ruling that **no Admin-side mitigation exists**.

## What is measured, and by whom

QA first, on the live parity pass (TASK-0012's History, 2026-09-02): the Claims page's own read times out — `57014 canceling statement due to statement timeout` at 8515 / 8099 / 8127 ms, 3 of 3 — and narrowing it did not help.

Then the architect, read-only, my own client through the staging guard, eight shapes (evidence, redacted: `agenticflow/tracker/evidence/architect/claims-probe.tsv` and `claims-probe2.tsv`). Every shape but one hits the 8s statement timeout with `57014`:

| shape | result |
| --- | --- |
| `limit 1`, no order, no filter | **852–1083 ms, 1 row** — the only shape that returns |
| `limit 2` | 8098 ms, 57014 |
| `limit 3`, `limit 5`, `limit 10` (narrow select, two columns) | 8106–8178 ms, 57014 |
| `order(observation_id) limit 1` | 8107 ms, 57014 |
| `.in("observation_id", <10 known pending ids>)` | 8118 ms, 57014 |
| `.in("observation_id", <100 known pending ids>)` — the gauges' shape | 8146 ms, 57014 |
| `head:true count exact`, whole view | 8138 ms |
| `head:true count exact` per bucket, one per bucket (5 runs) | 8137–8172 ms each |
| `eq("bucket","awaiting_row") limit 10` | 8137 ms, 57014 |

Population, same session, from the base tables (all sub-150 ms): `observations` where `status='pending'` = **859**; `field_provenance` = 1705; `observations` total = 2567.

**Read the shape of that.** A `limit 1` returns in under a second, `limit 2` does not; a filter on the view's own key over ten ids is as slow as no filter at all. Whatever the plan is, no qualifier and no limit bounds the work — the population is classified before anything narrows it.

## Where the cost plausibly is (from the SQL; the plan is yours to confirm)

Two candidates, both readable in the migration:

1. **The `incumbent` lateral has no index to use.** Per claim it runs `select provenance.observation_id from public.field_provenance where entity_type = claim.domain and entity_id = claim.entity_id and field = claim.field order by applied_at desc, provenance_id desc limit 1`. `field_provenance` carries **only its primary key** — I read every `create index` in `supabase/migrations/`: three on `review_items` (20260901000002), one on `confirmed_matches` (20260829000003), three on `observations` (rebuilt on `domain` by 20260819000002), and nothing at all on `field_provenance` beyond `field_provenance_pkey (provenance_id)`. So that lookup is a seq scan of 1705 rows plus a top-N sort, once per live pending claim, 859 times.
2. **The multiply-referenced CTEs are materialized, so nothing pushes down.** `live_pending_claim` is referenced five times and `reference_entry` three; PostgreSQL 12+ materializes a CTE referenced more than once. A materialized CTE is an unindexed tuplestore: correlated lookups into it (`record_bar`'s `missing_column` NOT EXISTS, the `performers` lateral) are full scans of it, and an outer qualifier — `observation_id in (…)`, `bucket = …` — cannot be pushed inside it. That is exactly the measurement's signature: filters do not help.

## The artifact, as precisely as I can state it from here

**Step 0 — the one thing only you can run** (scraper repo, psql; the default timeout will cancel it, so raise it for the session):

```sql
set statement_timeout = '120s';
explain (analyze, buffers, verbose)
select observation_id, bucket from public.pending_claims limit 2;
```

**Candidate A — the index. Forward-only, reversible, no semantic change.** Target file, scraper repo: `supabase/migrations/2026090300000X_the_current_provenance_row_is_one_seek.sql`

```sql
-- pending_claims' incumbent lateral (20260901000004) asks the same question
-- resolver/weighing.py's _incumbent() asks: the latest provenance row for one
-- fact identity. field_provenance carries only its primary key, so that is a
-- seq scan and a top-N sort per live pending claim. This is the seek it wants.
create index if not exists field_provenance_current_per_fact
    on public.field_provenance (entity_type, entity_id, field, applied_at desc, provenance_id desc);

comment on index public.field_provenance_current_per_fact is
  'The current provenance row for one fact identity, in one seek: pending_claims'' incumbent lateral and every "what is canonical now" read';
```

Apply: `supabase db push` from `kspace Scraper/` (the only repo that pushes migrations). Reverse: `drop index public.field_provenance_current_per_fact;`.

**Candidate B — the planner hint, if A is not enough.** In the view, `with live_pending_claim as not materialized (…)` and `reference_entry as not materialized (…)`. One word each; a CTE materialization hint changes no semantics. It is what lets an outer `observation_id in (…)` or `bucket = …` reach `observations` and use the partial indexes 20260819000002 already built. If B alone fixes it, the view stays exactly as written otherwise.

**Candidate C — the one I recommend against reaching for first: a materialized view.** It would break the property the view's own header opens with — "derived on every read and storing nothing … it can never disagree with them" — and hand the resolver a refresh cadence to own. That is a design conversation in the scraper campaign, not a fix.

**Not a fix: raising the statement timeout.** An honest read that takes 30 seconds is still a broken page, and the timeout is the only thing currently telling anyone the view is super-linear.

## Two things worth knowing before you decide

- **This is not an Admin-only symptom.** The view is `security_invoker` and Admin reads it as `service_role` — the same role the resolver reads it as. The resolver's own reads of `pending_claims`, and its parity test, pay the same cost on the same data.
- **The population is small.** 859 live pending claims, 1705 provenance rows, 2567 observations. A classification view that cannot answer over 859 rows in 8 seconds will not survive the catalog growing.

## The Admin-side ruling: there is no mitigation to build, and none may be built

I looked for an honest faster read and measured five candidates for one: a narrowed select list, a per-bucket `count: "exact"` head query instead of a complete read, an id-restricted `.in()` read (the shape `readPendingClaims` already uses for the gauges), a bucket-filtered list, and a smaller range. **All five time out.** So:

- **No mitigation TASK is filed**, and none should be invented later. `src/lib/db/claims.ts` and `src/lib/db/gauges.ts` are correct as written; `listClaims`' complete read is the right kind for a page that claims exact bucket counts (§4.3), and narrowing it would trade a true refusal for a slow one.
- **`/claims` and the Sources awaiting-row gauge render their error state**, naming `pending_claims` and the database's own words. That is the correct rendering of a database that will not answer, and it stays until this lands.
- **No workaround code** (spec §10, ARCHITECTURE §6 trap 12): no cache, no swallowed timeout, no surface hidden because it is red.
- **Admin never re-computes the buckets** from `observations` + `field_provenance` + `review_items`. That would be a second copy of the resolver's precedence rules living in this repo; the bucket of a claim is the ledger's answer or it is nothing.

## Done looks like

On staging, `select observation_id, bucket from public.pending_claims limit 10` returns, and so does the Claims page's own shape — all six columns, `neq bucket in_window`, `order bucket, observation_id`, `range(0,999)`, `count: "exact"` — both inside the 8s timeout. Then `tests/live/claims.live.test.ts` and the Sources awaiting-row assertions go green **with no change to Admin**, which is the point: if an Admin change turns out to be needed, this diagnosis was wrong and the ticket comes back here.

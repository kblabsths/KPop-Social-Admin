# Cycles: a ?cycle= link asserts the cycle is absent when resolution_runs was never read

## Description
Expected (ARCHITECTURE.md §7 / TASK-0030's four-state contract, and TASK-0014's own rule that a failed read never renders as a figure or a verdict): when the read of `resolution_runs` refuses or the object is absent, the page holds NO window, so it must not publish a verdict about whether the asked-for cycle is in one.

Found: `/cycles?cycle=<run_id>` renders the definite negative in both failure states — 'Cycle <id> is not among the 200 newest cycles, so it is not in this window - it ran earlier, or no cycle carries that id.' On the not-provisioned path that sentence sits directly ABOVE a NotProvisioned card saying `resolution_runs` is missing entirely, so the page contradicts itself on one screen.

Why it matters: the Dashboard links every cycle line to `/cycles?cycle=<run_id>` (`lineHref`, src/app/page.tsx) and an operator follows that link exactly when something is wrong. During an outage the page tells them the cycle does not exist, sending them after a phantom data problem instead of the missing/refused table the same screen already names.

Location: src/app/cycles/page.tsx:669-670 — `const rows = cycles.kind === \"ok\" ? cycles.data.rows : []` then `const found = rows.some(...)`, so a non-ok read collapses to `found === false`; :690 renders `<AskedCycle askedFor={askedFor} found={found} />` on the sole condition `askedFor !== undefined`, and AskedCycle's else branch (:366-370) states the absence as fact. The three states are not distinguished: 'read the window, it is not there' and 'never read a window' render identically.

Repro (offline, no database):
1. cd '/Users/ben-m4/Desktop/Coding/KPOP/kspace Admin'
2. Render the page with the cycles read failing and a cycle facet set — the two pins in tests/offline/cycles/page.test.ts, describe 'the ?cycle= link against a window the page could not read', do exactly this: they script `resolution_runs` to `tableNotInSchemaCache` (case 1) and to `permissionDenied` (case 2) and pass `{ cycle: SUCCEEDED.run_id }`.
3. Observed: `[data-cycle-found=\"false\"]` is present (length 1) in both cases, i.e. the page published the negative verdict. Measured 2026-09-02 on run/admin-window @ c102991: both assertions failed with 'expected 1 to be +0'.

Fix shape (builder's call): render nothing, or a line that says the window could not be read, when `cycles.kind !== \"ok\"`. The affirmative branch (`found === true`) is only reachable from an ok read and is correct as it stands.

The two pins are committed as `it.fails(...)` (vitest's strict-xfail: it goes RED the moment the page stops publishing the verdict). Flip both back to `it(...)` as part of the fix — leaving them as `it.fails` will redden the suite once the page is correct.

# Browse's error line reads only 'TypeError: fetch failed': it names no read and drops the client's own cause

## Description
Early walk of M1 against a database that refuses (the http harness's sentinel URL, exactly as tests/http/server-harness.ts sets it). /browse renders its error state, and the whole of it is: "TypeError: fetch failed   Reload to try the read again." — a red mono line above an empty seven-column table frame, in both themes (agenticflow/tracker/evidence/designer/browse-light.png, browse-dark.png).

Two rules fail here.

First, LOOK_AND_FEEL's data-surface state 4 is "one red data line naming what failed and the retry", and Voice copy bar 3 is "Every error names what failed, then what to do" — "a fetch failed" names no read. Browse makes four reads (the events window, the listings view, field_provenance, sources), each reported separately on purpose, and the operator cannot tell from this line which one refused, or whether the database was unreachable at all rather than a query being wrong.

Second, the Feel's error principle is "the app shows what the database said ... A failed call surfaces the function's own refusal ... Errors are never swallowed and never replaced with a generic message." The client's own account IS more than what ships. Probed directly against the same sentinel URL, supabase-js returns an error object with message = "TypeError: fetch failed" and details = "TypeError: fetch failed / Caused by: Error: bad port / Error: bad port / at makeNetworkError ...", with empty hint and code. The cause lives in the details field; src/lib/db/result.ts's errorMessage reads only the message field, so the one field carrying what actually went wrong is discarded before it reaches a screen. What ships is the generic wrapper the principle names. (The cause string on staging will differ from this sentinel's "bad port"; the shape — wrapper in message, cause in details — does not.)

Provenance checked: result.ts is TASK-0002/TASK-0026 and browse/page.tsx is TASK-0015, both ticket-bearing, so this is a violation rather than a human-lane divergence. Note the not-provisioned path is NOT at fault — a table-absent code still renders the gray card naming the table, per bar 4; this is the transport-error arm only.

## Acceptance criteria
1. When a read fails, the rendered line names the read that failed — which object was being read — as well as the failure, so the four legs of Browse are distinguishable on screen.
2. The database client's own account of the cause reaches the screen: when the client returns a transport wrapper in its message field with the real cause in its details field, the cause is what the operator sees, verbatim and in mono, not the wrapper alone.
3. Nothing is invented: no generic replacement string, no apology, no "Something went wrong". The retry sentence stays in the app's voice beside it.
4. The classification is unchanged — an absent table or column still renders NotProvisioned in gray naming the object (bar 4), and only genuine failures render red (the Look: "Red means broken, never unavailable").
5. tests/offline/db covers the transport-error arm with a client error whose message is a bare wrapper and whose details carries the cause, asserting the cause survives into the DbResult; tests/offline/browse asserts the rendered error names its read.
Human-check: on /browse against an unreachable database, the red line tells an operator which read refused and why — enough to know whether to look at the network or the query — not merely that "a fetch failed". (human-checkable)

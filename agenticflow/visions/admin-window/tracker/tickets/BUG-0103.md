# The operator's own typed value steers the refusal's app-voice half, so the fix sentence can contradict what happened

## Description
Measured live 2026-09-09 on a production build of the landed tree (run/admin-window 70b37c9), 127.0.0.1:8846 against staging ubfjjqlvnpnoborczbdb, bundled Chromium, 1440x900, both themes, walk_sandbox row 00000000-0000-4000-8000-000000000001, reset-sandbox before AND after.

A coercion refusal QUOTES the operator's typed value back into its own text, and refusalFix (src/components/edit-refusal.ts:156-191) matches its arms against the WHOLE refusal string — earlier arms first (NOT_PROVISIONED :161, then 23502 :165, then 22P02 :171). So a value that happens to contain an earlier arm's prose selects that arm. The mono half stays truthful throughout; the app's voice does not.

REPRO (exact, from the cell, no module stubbing):
1. node tests/walk/reset-sandbox.mts, open /records/walk_sandbox/00000000-0000-4000-8000-000000000001
2. Click the 'tally' cell (integer NOT NULL), select-all, type: is not present in this database  — press Enter.
   Expected (criterion 2 of BUG-0098, 'one place decides it' from the refusal's own words): the coercion arm, since the database refused a TYPE — a sentence about the form tally stores.
   Found: mono half 'invalid input syntax for type integer: "is not present in this database" (22P02)' (Geist Mono 11px, rgb(193,0,7) light / rgb(255,100,103) dark) beside the app-voice half 'This edit needs a database object that has not arrived yet - nothing you retype will land until it does.' (Geist 12px). The app tells the operator that NO retype will land, when a correct retype lands immediately — the one sentence in the app's own voice is false and tells them to stop.
3. Same cell, type: violates not-null constraint — press Enter.
   Expected: the coercion arm.
   Found: mono 'invalid input syntax for type integer: "violates not-null constraint" (22P02)' + app-voice 'This column cannot be cleared - type a value into it.' — nothing was cleared; the operator typed a value.
   ('does not match' and '(23502)' steer it the same way — see the pin.)

Identical in light and dark; geometry unaffected (alert 320px wide at y271, inside the fields container y143-363).

Why it is P3 and not higher: today the only foreign text a refusal can carry is text the operator typed themselves at that same cell one second earlier, so the operator is unlikely to be misled by their own string. It stops being contrived the day a refusal quotes a value the operator did not type at that cell — a gate/registry refusal echoing a rejected value (FEAT-0011), or a settlement refusal quoting a payload field.

PINNED RED: tests/offline/ui/editable-cell.test.ts, 'PROBE: picks the arm from the database's words, not from what the operator typed' — currently it.fails(strict) so the suite stays green; the fix REMOVES .fails and the test must pass as a normal it(). It asserts relationally, never against copy: two refusals of the same class differing only in the quoted value must derive the same fix.

## Acceptance criteria
1. The arm is chosen from what the DATABASE said, not from the value quoted inside it: for a refusal of the shape 'invalid input syntax for type <t>: "<value>" (22P02)', the derived sentence is the same whatever <value> contains — including 'violates not-null constraint', 'is not present in this database', 'does not match' and '(23502)'.
2. Every arm BUG-0098 shipped still fires on the refusals it was built for: the real 23502 (label cleared), the real 22P02 (tally 'seven'), 22007 (observed_on 'nope'), the KS003 registry shape, the not-provisioned sentence, and the general fallback. No arm is lost to the narrowing.
3. tests/offline/ui/editable-cell.test.ts's PROBE test passes as a plain it() with .fails removed, and the rest of that file's refusal block is unchanged and green.
4. The mono half stays byte-identical to the database's message, both halves stay inside one role='alert', and the box's geometry is untouched.

# The data_conflict item's three verdict actions, one typed decision each

## Description
**SPEC F10 / spec §7, the `data_conflict` decision item.** Its close slot offers exactly three controls and no others:

1. **Choose a claimed value** — ONE control per evidence card, so the operator picks the observation they believe. Produces `action: "choose_claimed_value"` with `value.observation_id` set to that card's observation and `value.value` null.
2. **Supply a different value** — the operator's own value, admin tier. Produces `action: "supply_value"` with `value.value` set and `value.observation_id` null. The input is the shared edit cell's behaviour, not a second widget spelling.
3. **Keep current & settle** — the disagreement is fine as it stands; canonical holds and the rejections still land. Produces `action: "keep_current"` with `value` null.

Each control's submission is **exactly one** POST to the settle route and therefore **exactly one** call to `settle_review_item`. There is no client-side multi-step settlement and no second write path.

**The evidence cards already exist** (`src/components/review/evidence-cells.tsx`, `evidence/evidence-pair.tsx` — the app's signature block). This ticket adds a control to each card; it does not restyle the card, re-read the evidence, or change how a value is rendered (§11: machine identifiers render verbatim in mono; a uuid is resolved to a name or a link — LESSONS 5).

**Fixtures, not staging**: no `data_conflict` item exists on staging, so this is graded offline against `tests/fixtures/rows.ts`'s conflict fixture. "Built, not walkable on this data" is the honest grade, exactly as M1 graded the same gap. A criterion demanding a live conflict row is mis-authored.

**The absence is the normal case and is graded FIRST.** `verdicts` and `settle_review_item` do not exist on staging and will not until Ben installs the handoffs — that is the database `main` deploys against for the whole of M2. Build and grade the not-provisioned path before the happy path, and never offer a control that would call a missing function.

**No Admin-side workaround for the absent function may be written** — spec §10's one forbidden move: no queued write, no pending-overrides table, no retry buffer, no flag-guarded direct write.

## Acceptance criteria
1. With `verdicts` present (stub) and a `data_conflict` fixture: the close slot contains exactly one "choose this value" control per evidence card, exactly one "supply a different value" control and exactly one "keep current & settle" control — and no other control.
2. Each control's submission produces EXACTLY ONE call to `settleReviewItem`, asserted per control against the recording stub, carrying one typed decision whose `action`, `review_item_id`, `actor`, `note` and `value` are exactly as specified above; `decisionRefusals` returns `[]` for each of the three payloads.
3. "Choose a claimed value" carries the observation id of the card it sits on — asserted with a two-card fixture, so a control wired to the wrong card fails.
4. With `verdicts` absent: none of the three controls renders, the slot shows the not-provisioned card, and the evidence cards render exactly as M1 shipped them.
5. The empty and null cases render honestly (LESSONS 1): an evidence card whose value is null shows the dash with no qualifier, and an item with zero evidence rows renders its labelled empty state rather than a bare slot.
6. `npm run lint`, `tsc --noEmit`, the targeted offline file and the review-item live suite are green.

# /claims window line: 'narrow with the filters above to reach the rest' — no narrowing the page offers reaches past row 50

## Description
Found on the scoped re-look of `/claims` after BUG-0138 landed (designer, 2026-09-10; production build, own instance on 8783 against staging; evidence `agenticflow/tracker/evidence/M2/designer/claims-window-line-reach-the-rest.png`).

Every filled window on `/claims` ends with the same clause (`src/components/ui/window-line.tsx:496-508`, the `matched` arm, whose only caller is `/claims`):

    877 claims in all; the 50 longest-waiting are below —
    narrow with the filters above to reach the rest.

**Measured: no combination of the filters above reaches the rest.** The list is now a hard `limit 50` database window, so narrowing only reveals a row past the 50th if it takes the count below 50 — and every state reachable from the two rendered chip rows is far above it:

| what I clicked | held | rows shown |
| --- | --- | --- |
| nothing | 877 | 50 |
| `bucket: awaiting_row` | 769 | 50 |
| `bucket: awaiting_link` | 108 | 50 |
| `bucket: awaiting_row` + `source_id: ticketmaster` | 769 | 50 |
| `bucket: awaiting_link` + `source_id: ticketmaster` | 108 | 50 |

Two of the three sources hold zero claims, so the only source chip that changes anything is `ticketmaster`, which holds all 877. Maximal on-screen narrowing leaves 108 — still 58 claims the operator is told they can reach and cannot. There is no paging (deliberately deferred to the next milestone, BUG-0138 Description).

The clause is not new, but it became false with this change: before BUG-0138 the list carried the whole matching population up to `ROW_CAP`, so narrowing genuinely did surface more rows. A2 also removed the domain chip row — the one remaining facet with more than one live value.

Violates the Voice register ("the pipeline's engineer reading you its own logbook — plain, specific, no reassurance"): the sentence reassures rather than reports, and copy bar 3's rule that the app names a fix that works. LOOK_AND_FEEL bar 13 asks the line to state the read and its cap honestly; the count and the cap are right, the remedy is invented. It also lands on precisely the gap Ben named on his own walk — "not being able to load all claims if I want to is a huge oversight" — with the page telling him he can.

Provenance checked: `src/components/ui/window-line.tsx` carries ticket-bearing commits only (c84e7a7 BUG-0155, 831454b BUG-0123, 95f79fe BUG-0118, 741a293 BUG-0109). Not a human-lane divergence.

## Acceptance criteria
1. **The window line does not promise a remedy the screen cannot perform.** The clause "narrow with the filters above to reach the rest" is gone from `src/components/ui/window-line.tsx`; a truncated window states the count, the cap and what is not shown, and stops there — or, if it names an action, that action demonstrably reveals rows past the cap in the state it is rendered in.

2. **Both arms are fixed, not just one.** The unnarrowed arm ("877 claims in all; …") and the narrowed arm ("769 claims match these filters; …") both end honestly. The counts, the cap, the `population(...)` phrasing and the `besides(...)` scope subtraction are unchanged — only the remedy clause moves.

3. **The `matched` arm's other clauses stay byte-identical**: the lede (`SORT_STATEMENT`), "A window of at most 50 rows, not the whole view", and the did-not-fill arm (BUG-0109) are untouched, and `data-window-held` / `-limit` / `-truncated` do not move.

4. No other window arm regresses — `/cycles`, `/browse`, `/queues` and both gauges render exactly as today (`matched` has one caller, `src/app/claims/page.tsx:833`).

**Human-check (human-checkable):** open `/claims`, follow whatever the window line tells you to do, and either see a claim that was not in the first 50 or find that the line never promised you would.

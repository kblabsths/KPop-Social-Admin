# Paging /claims repeated a claim id at offset 50 on Ben's instance — a shipped surface can duplicate and silently omit rows

## Description
Ben walked /claims paging on his own instance (port 8771) on 2026-09-11 and pressed "Show the next 50 claims". The press errored once, then worked, and to him the 50 visible claims looked REPLACED in place rather than extended. The dispatcher filed his instance's dev log verbatim (inbox note 2026-09-11-ben-paging-rulings.md, section 4):

    GET /claims 200 in 3.0s
    GET /api/admin/claims/rows?offset=50 200 in 8.2s (next.js: 7.7s, application-code: 498ms)
    [browser] Encountered two children with the same key, `01a058f1-02c7-7e11-9191-adfa6207a0f0`. Keys should be unique so that components maintain their identity across updates. Non-unique keys may cause children to be duplicated and/or omitted

The 8.2 s is `next dev` compiling the route handler on demand (7.7 s of it the compiler) — a dev-instance artifact, NOT this bug and not to be "fixed" here.

The duplicate key IS the defect. The row key is `row.observationId` (src/components/claims/claim-list.tsx:199), so the page at offset 50 carried an observation_id the first 50 already held. React's own warning says the consequence is not cosmetic: children duplicated AND/OR OMITTED. A shipped operator surface that can repeat one claim and silently drop another breaks the thing the campaign rests on — that what is on screen is what the database says. M3 EC4 grades exactly this ("No id appears twice; no id is skipped") and PASSED, on one run against a production build, so the existing proof cannot see this.

ROOT CAUSE IS NOT KNOWN AND THIS TICKET ASSERTS NONE. The inbox note's hypothesis is a missing total order under the 817-row `observed_at` tie. Measured on run/admin-window before filing: THAT TIEBREAKER ALREADY EXISTS. src/lib/db/claims.ts:328-329 reads `.order("observed_at", { ascending: true, nullsFirst: false }).order("observation_id", { ascending: true })` before its `.range()`, and the docstring above it claims this is "the only reason paging this read cannot drop or repeat a claim between two requests". /browse carries the same shape (src/lib/db/browse.ts:133-135: sort field then `event_id`). So either that tiebreaker is not doing what the docstring says, or the mechanism is elsewhere. A fix that adds an order clause already in the file would close this ticket without fixing anything.

Suspects for the investigator — each cheap to rule in or out, none of them a conclusion:

1. `pending_claims` may not hold one row per observation_id (a fan-out in the view). Then a duplicate pair straddling the window boundary produces exactly this, the order is still not total, and the 877 head count over-counts. One live query settles it: row count vs distinct observation_id count.
2. The parked-bucket exclusion runs in JS AFTER the range (`selectClaims(drawn.data)`, src/lib/db/claims.ts:337-341), so the rows drawn can be fewer than the DB window the read consumed while the next bound is derived from the rows held. Drift there both repeats and skips, and can also read as early exhaustion.
3. The first screen's read and the route handler's read may not be over the same population or the same order (src/app/claims/page.tsx vs `filterFrom`/`tabFrom`/`listFilterOf` in src/app/api/admin/claims/rows/route.ts). Two narrowings that differ overlap by construction.
4. Ben's press errored first and then worked: one page may have been applied twice, or two requests for offset 50 raced. `beginLoading` no-ops while loading and the machine refuses an answer whose `offset !== state.held`, so this should be impossible — verify that it is, do not assume it.
5. PostgREST returning the tie in a different order per request despite the tiebreaker (e.g. the order not reaching the wire in the form the builder chain intends). Inspect the actual request query string, not the chain.

Whatever the mechanism, /browse shares the paging path and must be checked for the same class before this closes, even though 120 events is three pages.

Filed to the patch lane while M3 is in its endgame. It is a defect in shipped M3 behaviour: the M3 retro carries it, and the strength of EC4's proof is a retro item.

## Acceptance criteria
1. THE MECHANISM IS NAMED AND MEASURED BEFORE ANY FIX. The receipt states which suspect (or which other mechanism) actually produces a repeated id, with the measurement that proves it — a reproduction on staging data, not an argument. If the fix turns out to be an ordering change, the receipt says why the tiebreaker already at src/lib/db/claims.ts:328-329 did not hold, because "added a tiebreaker" alone is not evidence of anything.
2. Live, repeated, cross-run: tests/live/claims.live.test.ts walks the paged reads across the 817-row `observed_at` tie for at least three independent full walks of the first 200 rows, and asserts (a) zero duplicate observation_ids across the union of pages within a walk, (b) zero gaps — the union equals the same ids the unpaged ordered read returns for that range, and (c) the id at each position is identical across the three walks. A single-run distinct-count assertion does not satisfy this criterion.
3. `pending_claims` is asserted live to hold exactly one row per observation_id, or — if it does not — this ticket reports that fact in its receipt and the page's key and count story are corrected rather than papered over.
4. The mechanism found is pinned offline, in the suite that owns it (tests/offline/paging/machine.test.ts or the claims read's own offline test), on a fixture that fails before the fix and passes after. The test's name says what can no longer happen, in the operator's terms.
5. A full paged walk of /claims on a production build against staging produces zero browser-console errors or warnings — no duplicate-key warning on any press — recorded with the console capture in the receipt (LOOK_AND_FEEL bar 12 already requires the clean console; this is the evidence of it under paging).
6. The first server-rendered screen of /claims and /browse is unchanged: same window line, same figures, same row set on the same fixture (M3 EC4's first-screen invariant is not spent by this fix).
7. /browse is checked for the same class and the result is stated either way: either its paged reads carry the same proof as criterion 2 at its scale, or the receipt states the measurement showing the mechanism cannot reach it.

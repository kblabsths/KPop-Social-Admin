# A failed inline save shows the database's refusal and nothing else — no fix in the app's voice, unlike every read error

## Description
Measured on the M2 early walk, 2026-09-08, walk instance on 127.0.0.1:8771 against staging, bundled Chromium, 1440x900, `walk_sandbox` row `…0001` (`resetSandbox` before and after; the three rows read back to the fixture).

**Expected**, two lines of LOOK_AND_FEEL saying the same thing:
- Interaction principles, Error: "A failed call surfaces the function's own refusal in mono, **plus the fix in the app's voice**. Errors are never swallowed and never replaced with a generic message."
- Copy bar 3: "Every error names what failed, **then what to do**, with no apology."

The app already has that two-part form and uses it everywhere else. `src/components/ui/error-line.tsx` takes `failed` (the machine's words, `type-data` mono) AND `retry` ("What to do about it, in the app's voice", `type-body` sans), and its own docstring cites this rule. The same shape shows up on the robustness paths: `/queues/<unknown-uuid>` renders "No row with that id in review_items" **and** "Queues lists the items this database holds; check the id in the address bar"; `/records/walk_sandbox/not-a-uuid` renders the refusal **and** what a walk_sandbox id looks like.

**Found** — the one place the app writes rather than reads, the second half is missing. `EditStatus`'s `failed` arm (`src/components/EditableCell.tsx:332-338`) renders `{status.message}` alone, in `text-broken type-data`, and nothing else.

Two measurements, driven through the cell on the record page:

1. `tally` (integer column), typed `seven`, Enter. The whole of what the operator is told, red mono, 11px:
   `invalid input syntax for type integer: "seven" (22P02)`
   The field correctly reverts to `7`. Nothing on screen says tally holds a whole number.
2. `label` (a NOT NULL column), select-all + Delete, Enter. What the operator is told, in one 320px-wide box hanging over the row:
   `null value in column "label" of relation "walk_sandbox" violates not-null constraint Failing row contains (00000000-0000-4000-8000-000000000001, null, walk probe 0908, 7, f, 2026-01-15, 2026-09-09 05:10:25.030369+00). (23502)`
   Postgres's whole DETAIL line, every column value of the row included, and no sentence saying label cannot be emptied.

The success path is right and is not in question: `saving…` in secondary, then `saved` in healthy green (#016630) for ~1.5s, then gone — measured at 100/300/1000/1600/2200ms.

**Why it matters now.** This cell is the M2 override editor. When FEAT-0011 lands the override half, the gate's own refusals arrive in this box — `venues.country` must match `^[A-Z]{2}$` and `events.poster_url` must match `^https://` (registry patterns, `src/lib/edit/config.ts`), and this repo has no client-side validator by design, so a mistyped country will render as a bare regex refusal with no statement of what a country code looks like.

Not a duplicate: BUG-0086 (claimed) is the reflow of the cell's box; BUG-0095 (claimed) is an invisible-only value being stored as content. Neither names what a refusal says.

## Acceptance criteria
1. A refused write renders BOTH halves at the field: the database's own refusal verbatim in mono, and one sentence in the app's voice naming what to do — the same two-part anatomy `src/components/ui/error-line.tsx` already ships for reads (`failed` in `type-data`, the fix in `type-body`). No apology, nothing swallowed, nothing generic; the machine's words are never paraphrased away.
2. The app-voice half is derived, never hand-written per call site: one place decides it, so a refusal the walk never saw still carries a fix. Whatever it cannot recognise falls back to a general sentence rather than to nothing.
3. Asserted in the offline render suite on at least three refusals, each with its own fix sentence: a type coercion (22P02 on `tally`), a not-null clear (23502 on `label`), and a gate/registry pattern refusal of the shape FEAT-0011 will produce.
4. The field still reverts to its stored value on refusal, the failure still carries `role="alert"`, and the success path is untouched: `saving…` in secondary, `saved` in healthy for ~1.5s.
5. Red is the failure line only — the reverted value stays primary ink (LOOK_AND_FEEL: "Red means broken, never unavailable").
6. Human-check: paste a letter into `tally` on `/records/walk_sandbox/00000000-0000-4000-8000-000000000001` and press Enter — the operator is told both what the database refused and what to type instead. (human-checkable)
7. `npm run lint` and `tsc --noEmit` clean; the targeted offline files and the record page's live suite green.

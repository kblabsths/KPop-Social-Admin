# A settled review item's detail carries its own verdict inline

## Description
**SPEC F13, second half.** The investigation path ends where the decision was made: a **settled** item's detail renders its own verdict inline, rather than sending the operator to a different tab to find out what they themselves decided.

**What it renders**, in the close slot's place: the action verbatim in mono, the actor, the note (the dash with no qualifier when there is none), when it was decided, and a link to the observation it wrote (the dash when the verdict carried no value). An **unsettled** item's detail renders no verdict block at all — an empty verdict block on an open item is the "renders X but not the absence of X" defect LESSONS 1 is about.

**The read** joins `verdicts` by `review_item_id` and belongs beside the other verdict reads in `src/lib/db/verdict.ts` (one module owns this object; four pages hand-copying a helper is common violation 9). It is a by-id read, not a list read.

**Absence, in the two ways it arrives:**
1. `verdicts` absent (staging today) — the detail renders the same `not_provisioned` card the close slot already renders, naming `verdicts`, and the rest of the page is exactly what M1 shipped. Nothing throws.
2. `verdicts` present but carrying no row for a settled item — an honest gap in the data, not an absence of the table: the block says the item is settled and no verdict row was found, and does NOT render a blank slot or claim the table is missing. These two are different states and the test asserts both.

**Landing order**: this ticket and the close slot both write `src/app/queues/[reviewItemId]/page.tsx`, so it is chained behind them (ARCHITECTURE §13.9 — consolidation-shaped work is chained at its destination, because worktrees isolate builds and not landings).

## Acceptance criteria
1. A settled item's detail renders its verdict inline — action verbatim in mono, actor, note or the unqualified dash, the time, and a link to the observation or the unqualified dash — in the close slot's place.
2. An unsettled item's detail renders no verdict block at all, and the close slot behaves exactly as its own ticket shipped it.
3. With `verdicts` absent: the detail renders the `not_provisioned` card naming `verdicts`, the page answers 200, nothing throws, and the rest of the page renders as M1 shipped it.
4. With `verdicts` present but no row for a settled item: the block says so in its own words and is distinguishable in the markup from the not-provisioned state — both states asserted in the same test file.
5. The read lives in `src/lib/db/verdict.ts` and is a by-id read; no page issues its own query and no helper is hand-copied into the page.
6. The review-item live suite names the state kind before comparing anything and passes against staging, where the one real item is open and `verdicts` is absent.
7. `npm run lint`, `tsc --noEmit`, the targeted offline files and the review-item live suite are green.

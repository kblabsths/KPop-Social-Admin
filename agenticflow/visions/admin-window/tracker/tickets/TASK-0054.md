# The override write path: events and venues edit only as recorded admin-tier observations

## Description
**SPEC F11, the core.** `events` and `venues` become editable — and ONLY as recorded overrides the pipeline can see and protect.

**This ticket lives in the post-strike world** (Ben's ruling, 2026-09-08; DECISIONS 2026-09-08; ARCHITECTURE §9's two-regime bullet and §13.8). VISION's "groups/idols edit directly within it" is struck, `pre_cutover` no longer exists as a regime or as an identifier, and there are exactly TWO regimes: `resolver_owned` (`events`, `venues` — override through the gate) and `sandbox` (`walk_sandbox` alone — a staging-only fixture table in nobody's domain, which is why the strike does not reach its direct PATCH). **`groups` and `idols` are not in the map at all** (TASK-0040): `editConfigFor` returns null for them, their record URLs are routed 404s, and a PATCH is refused `unknown_table`. **The removal itself is the strategist's ticket, routed from the strike, and it lands before this one** — if `EDIT_CONFIG` still carries a `pre_cutover` entry when this ticket is claimed, say so and wait rather than doing the removal here.

**Never re-implement the struck path.** A ticket that re-adds a catalog table to the map under the `sandbox` regime, gives a `resolver_owned` table a direct write, or routes a catalog write around `settle_review_item` is wrong on its face. The pin that catches it, on two fixtures: **the only table whose write path is `direct` is `walk_sandbox`**.

**The regime decides the write path; configuration never does.** Adding a table to the map does not choose how it writes. `writePathFor(regime): WritePath` lands with TASK-0040 and is TOTAL — `resolver_owned` -> `"override"`, `sandbox` -> `"direct"`; a table Admin may not write is not in the map, so there is no "no path" arm to fall into. This ticket has `decideEdit` carry the path on its allowed decision, and the route branches on the PATH — never on the table name and never on a config key.

**What an override does** (spec §7/§8; ARCHITECTURE §9.2): one call to `settleReviewItem` with `action: "override"`, a **null `review_item_id`**, and the admin-tier observation's `value`. The function writes the observation through the gate, applies it through `apply_resolution` with the `admin_locked` fact key, and inserts the `verdicts` row. **Admin performs none of those steps itself** — there is no second write, no `field_provenance` insert, no `admin_locked` update from here.

**The map's `editable` entries for `events` and `venues` are Ben's answer** (TASK-0044, blocked). Until it lands, both keep an empty `editable`, and everything in this ticket except the two entries is still built and graded: the path derivation, the route branch, the refusals, the absent-function rendering. When the answer arrives, the entries are one edit in one file.

**Every refusal stays server-side** — hiding a widget is not a refusal (acceptance test 7). A forged PATCH naming a column absent from the map answers 403 naming the field, for `events` and `venues` exactly as it already does for the read-only tables. A forged PATCH naming a MAPPED `events` column while the function is absent is refused with the reason named — never a direct write, never a silent success.

**Per-field provenance at the field** already ships for a resolver-owned record (`lib/records/provenance.ts`, `components/records/record-fields.tsx`: "ticketmaster, applied 3d ago" / "admin-set Jun 12"). This ticket does not rebuild it; it asserts that an `admin_locked` decision row renders as "admin-set" with its date, and that the sandbox record's regime note stays honest (a value written there goes to a staging fixture, not "to the catalog"). Ben's 2026-09-02 provenance sentence for a pre-cutover table has no table left to render on — it goes with the map entries, and no copy of it is kept "just in case".

**Releasing an `admin_locked` fact is itself a verdict action on that fact**, not a direct write, and it is not built here.

**The absence is the normal case and is graded FIRST.** `verdicts` and `settle_review_item` do not exist on staging and will not until Ben installs the handoffs. Absent them, `events` and `venues` render READ-ONLY with the reason named — which is exactly what M1 already ships, so the surface degrades to M1 rather than to a broken control. **No Admin-side workaround** for the absent function may be written (spec §10's one forbidden move).

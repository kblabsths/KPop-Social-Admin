# The override write path: events and venues edit only as recorded admin-tier observations

## Description
**SPEC F11, the core.** `events` and `venues` become editable — and ONLY as recorded overrides the pipeline can see and protect.

**This ticket lives in the post-strike world** (Ben's ruling, 2026-09-08; DECISIONS 2026-09-08; ARCHITECTURE §9's three-regime bullet and §13.8). VISION's "groups/idols edit directly within it" is struck, `pre_cutover` no longer exists as a regime or as an identifier, and the regimes are `resolver_owned` (override through the gate), `read_only` (`groups`, `idols` — no write path at all) and `sandbox` (`walk_sandbox` alone — a staging-only fixture table in nobody's domain, which is why the strike does not reach its direct PATCH). **The removal itself is the strategist's ticket, routed from the strike, and it lands before this one** — if `EDIT_CONFIG` still carries a `pre_cutover` entry when this ticket is claimed, say so and wait rather than doing the removal here.

**Never re-implement the struck path.** A ticket that gives a `read_only` table an `editable` column, adds a fourth `Regime` with a direct catalog write, or routes a catalog write around `settle_review_item` is wrong on its face.

**The regime decides the write path; configuration never does.** Adding a table to the map does not choose how it writes. Author `writePathFor(regime): WritePath | null` in `src/lib/edit/config.ts` — `resolver_owned` -> `"override"`, `sandbox` -> `"direct"`, `read_only` -> `null` — and have `decideEdit` carry the path on its allowed decision. The route branches on the PATH, never on the table name and never on a config key. That is what makes re-implementing a direct catalog write require a new `Regime` member and a new arm of this function: a diff Ben reads.

**What an override does** (spec §7/§8; ARCHITECTURE §9.2): one call to `settleReviewItem` with `action: "override"`, a **null `review_item_id`**, and the admin-tier observation's `value`. The function writes the observation through the gate, applies it through `apply_resolution` with the `admin_locked` fact key, and inserts the `verdicts` row. **Admin performs none of those steps itself** — there is no second write, no `field_provenance` insert, no `admin_locked` update from here.

**The map's `editable` entries for `events` and `venues` are Ben's answer** (TASK-0044, blocked). Until it lands, both keep an empty `editable`, and everything in this ticket except the two entries is still built and graded: the path derivation, the route branch, the refusals, the absent-function rendering. When the answer arrives, the entries are one edit in one file.

**Every refusal stays server-side** — hiding a widget is not a refusal (acceptance test 7). A forged PATCH naming a column absent from the map answers 403 naming the field, for `events` and `venues` exactly as it already does for the read-only tables. A forged PATCH naming a MAPPED `events` column while the function is absent is refused with the reason named — never a direct write, never a silent success.

**Per-field provenance at the field** already ships for a resolver-owned record (`lib/records/provenance.ts`, `components/records/record-fields.tsx`: "ticketmaster, applied 3d ago" / "admin-set Jun 12"). This ticket does not rebuild it; it asserts that an `admin_locked` decision row renders as "admin-set" with its date, and that a `read_only` record keeps the sentence Ben ruled on 2026-09-02 — **the copy is his and does not change** even though the regime identifier behind it did.

**Releasing an `admin_locked` fact is itself a verdict action on that fact**, not a direct write, and it is not built here.

**The absence is the normal case and is graded FIRST.** `verdicts` and `settle_review_item` do not exist on staging and will not until Ben installs the handoffs. Absent them, `events` and `venues` render READ-ONLY with the reason named — which is exactly what M1 already ships, so the surface degrades to M1 rather than to a broken control. **No Admin-side workaround** for the absent function may be written (spec §10's one forbidden move).

## Acceptance criteria
1. `writePathFor` exists and is total over `Regime`: `resolver_owned` -> "override", `sandbox` -> "direct", `read_only` -> null; a structural test asserts the route selects its branch from that function alone, on two fixtures (one override-regime table, one sandbox), and that no configuration key can move a table between paths.
2. With `settle_review_item` ABSENT: an `events` record and a `venues` record render read-only with the reason named; zero inputs, selects, textareas or forms on either page; a forged PATCH naming a mapped `events` column is refused server-side with the reason, and the row is unchanged when re-read.
3. With the function present (recording stub): editing a mapped `events` or `venues` column produces EXACTLY ONE call to `settleReviewItem`, carrying `action: "override"`, a null `review_item_id`, the admin-tier value, and nothing else.
4. No `.update(`, `.insert(`, `.upsert(` or `.delete(` anywhere in `src/` targets `events` or `venues` on any path — proved by the structural guard in `tests/offline/edit/config.test.ts` on two fixtures (a probe that adds one must redden it; the shipped tree must not).
5. A column absent from the map on `events` or `venues` is refused server-side with 403 naming the field; a `read_only` table's every column is refused with its own reason; both are asserted at the route, not at the widget.
6. Provenance: an `admin_locked` decision row renders "admin-set" with its date at the field on a resolver-owned record; a source-won field renders the source and the age; a field with no decision renders the dash with no qualifier; a `read_only` record renders the sentence Ben ruled on 2026-09-02, unchanged, byte for byte.
7. `EDIT_CONFIG` carries no `pre_cutover` entry and no `Regime` member beyond the three; `groups` and `idols` have an empty `editable`; no id, key or timestamp is editable on any table.
8. `npm run lint`, `tsc --noEmit`, the targeted offline files, the record page's live suite and the http edit suite are green; M1's forged-request refusals still answer exactly the statuses the M1 verdict recorded.

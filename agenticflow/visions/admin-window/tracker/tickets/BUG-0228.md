# A host answering 200 with a JSON ARRAY that is not this table's rows still crashes four surfaces with a 500

## Description
EXPECTED (admin-window/BUG-0224's bar, carried unchanged through BUG-0227): "Whatever a host answers ... the operator reads the app's refusal naming pending_claims (or review_items, or sources)." Positively, and this is the property that ends the class rather than one more shape of it: NO body a host can put on the wire may make a surface throw — every route ANSWERS (200, no error shell), with the app's refusal naming the object it read, or with the rows if rows arrived.

FOUND on the landed BUG-0227 tree (run/admin-window @ 2102d150), measured 2026-09-15 by QA over real HTTP against a production build (own 'next start', port 8801/8802, SUPABASE_URL pointed at a loopback stub):

    MODE alien  (200, body [{"message":"no upstream"}])
      /        -> 500 errorShell=true
      /claims  -> 500 errorShell=true
      /browse  -> 500 errorShell=true
      /cycles  -> 500 errorShell=true
      /queues  -> 200 (states=empty,error)
      /sources -> 200 (states=empty,error)

Same five-hundreds with [[{"claim_id":"c1"}]], ["a","b"], [{}] and [{"foo":1}]; with [null,null] ALL SIX routes 500. Server log: 'TypeError: Cannot read properties of undefined (reading \'trim\')', '... (reading \'length\')', and for the null elements '... of null (reading \'started_at\')' / '(reading \'bucket\')' / '(reading \'queue\')' / '(reading \'observation_id\')' / '(reading \'event_id\')'. The same server answers 200 with a refusal in BUG-0227's 'foreign' mode and 200 with the empty card in 'empty' mode, so this is the payload shape and nothing else.

MECHANISM: BUG-0227 widened the row-set question to isRowSet = Array.isArray (src/lib/db/result.ts:1044). An array of things that are not rows PASSES that guard, so readRows/readComplete return {kind:'ok', data} typed Row[], and the first column the render reads throws on an element that has no such property. Measured with the real client (@supabase/supabase-js 2.x) against the same loopback host: error=null, data=array(1) [{"message":"no upstream"}], count=null — nothing in the answer says it is not a row set.

NOT A REGRESSION and NOT A RETYPE OF BUG-0227: that ticket's bar was 'did an ARRAY arrive', and on every non-array shape I could reach (string body, number, JSON object, object beside a Content-Range, null body) the landed fix refuses correctly on all six routes. This is the next shape in the same trigger family (a host that is not this database answering for it: a wrong SUPABASE_URL, a proxy/gateway in front of the service).

TWO CANDIDATE ANSWERS, and the builder should not enumerate payload shapes a third time (LESSONS 13 — this derivation has already cost BUG-0210, BUG-0224, BUG-0227):
  (a) the read seam asks a stronger question — every element is a non-null, non-array object, and/or each db module's read validates the columns its own callers read (it knows them: the reads name explicit column lists, e.g. PENDING_CLAIM_COLUMNS); or
  (b) a surface simply cannot 500 — the route owns an error boundary so a render throw becomes the same refusal card, whatever caused it.
(a) alone does NOT close the class: [{}] and [{"foo":1}] are arrays of plain objects and still crash. If the builder judges the answer is (b) or a design change, BOUNCE TO THE ARCHITECT rather than shipping a third predicate.

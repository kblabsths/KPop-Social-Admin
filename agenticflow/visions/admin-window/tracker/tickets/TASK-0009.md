# Dashboard — the breakfast view

## Description
Module: `src/app/page.tsx` + `src/lib/db/dashboard.ts`. Authority: spec section 4 (Dashboard) and section 1; section 6 (the kind is derived in code); `contracts/resolver.md` section 6 (`resolution_runs` columns) and section 11 (`review_items`); SPEC F3; M1 EC3, EC4; acceptance tests 2 and 9; LOOK_AND_FEEL 'Key screens — Dashboard' and quality bar 1.

Renders, above the fold at 1440x900 with no scrolling:

1. **The attention summary, decision and signal counts kept separate** — two counts side by side, each with open count, **max severity** and **oldest age**. The kind comes from `lib/review/shapes.ts` (TASK-0006); no column carries it. Severity is the registry's `low` / `high` verbatim — no score, no rank, no formula.
2. **Last night's cycles and runs** — recent `resolution_runs` and the adapter framework's `runs`, with `error_summary` surfaced verbatim as error lines. A cycle still running (`ended_at` null) and a `skipped` cycle each read as such.
3. **Everything links**: each attention count opens `/queues` filtered to that kind; each cycle or run line opens `/cycles`; an error line reaches the row that produced it. The Dashboard is the entry to the investigation path and never a dead end.

For the adapter `runs` half, show only what the Dashboard needs — source, when, outcome, error line. Which columns the **Cycles & runs page** shows for adapter runs is a separate blocked question (TASK-0015); do not answer it here.

No parked-section surface is rendered: no recommendations, no incidents, no agent runs, no operator, no free-form ticket box.

Every page ticket in this milestone carries the same standing rules (ARCHITECTURE sections 4, 5, 7):
- The page function is the **only** async component on the route; every child is a pure synchronous component taking plain props. That is what lets the tests render `await Page(props)` with `react-dom/server`.
- Read only through `src/lib/db/**`; never build a Supabase client in a page; never spell a table name outside `src/lib/db/tables.ts`.
- Render all four states from the `ui` primitives: loading, empty, **not provisioned** (naming the missing table, gray, never a zero), error (the database's own message). A missing backing table must not throw and must not take the rest of the app down.
- Use tokens and primitives, never raw hex, arbitrary type sizes or ad-hoc radii.
- **State lives in the URL**: every filter, sort and tab is a `searchParams` value and survives the back button.
- Voice: buttons are a verb plus their object; ages are relative with the absolute in the title attribute; scheduled times are absolute UTC with the zone stated once in the column header; machine identifiers render verbatim in mono; empty and not-provisioned states name what the surface holds and what fills it.
- **Nothing settles anything in M1.** No verdict action, no settle control, no fixed/won't-fix, no scaffolding toward them.

## Acceptance criteria
[tests 2, 9; EC3, EC4] Decision and signal counts render as two separate figures, each with open count, max severity and oldest age, and each links to `/queues` filtered to that kind. Recent cycles and runs render newest first with `error_summary` inline. Offline tests render the page function against stub clients and assert: the populated case, the empty case, and the not-provisioned case (200-equivalent markup naming the missing table, nothing thrown). A live-marked parity test asserts every rendered dashboard number against a count the test issues itself. No severity formula, score or computed rank exists. No parked-section surface renders. (human-checkable) The whole view answers 'did anything happen last night, what needs me' without scrolling at 1440x900, at the close-review screenshots.

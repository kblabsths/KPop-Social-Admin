# /sources' two scan-window lines name the narrowing their read carried

## Description
**Modules:** `src/components/sources/trends.tsx` (the two scan window lines), `src/app/sources/page.tsx` (which resolves the narrowing and hands it down), `src/lib/sources/routes.ts` (where `/sources`' unchipped facet table lands), and their offline + live suites.

**The defect (SPEC F15, M3 EC8).** `/sources`' two scan-window lines — `measured="Claims observed"` and `measured="Claims adjudicated"` in `src/components/sources/trends.tsx` — name NO narrowing, while the read beneath them carries one. `/sources` and `/sources?<facet>=<value>` therefore render byte-identical window lines over two different reads. This is precisely the defect BUG-0163 fixed on `/claims` one page over.

**`/claims` is the model, and it is COPIED BY IMPORT** (LESSONS 5; the whole reason TASK-0072 lands first): the phrase shape, the composition and the subtraction all live in `src/lib/url/narrowing.ts` and `src/components/ui/window-line.tsx` after that ticket. What this ticket writes is `/sources`' own facet table — which facets of this URL narrow which read, in this surface's own words — and the wiring that hands the resulting `scope` to the two lines. **A hand-written narrowing sentence in `trends.tsx` fails this ticket even if it renders the right words.**

**The rule the lines must obey** (ARCHITECTURE §4.3): a window line states the read that HAPPENED. So the scope is unconditional on what came back — a narrowed scan that returned nothing still names its narrowing — and it names the narrowing the READ carried, never the parameters the URL happened to spell. A facet this page DROPPED (`lib/url/dropped-params.ts`) narrows nothing and appears in no scope; a facet the read applied appears in both lines that carried it, and in neither line that did not.

**Both halves of the two-fact rule stay where they are:** this ticket changes what the LINE says (the read's scope), not which empty card the surface draws (DEBT-0008 owns that, and `data-empty` on this page is not this ticket's business).

**The other half of the same read — bounds — landed in TASK-0070.** If a figure on this page still disagrees with the line above it after both, that is a new finding: file it, do not patch it here.

**Live (M3 EC8):** `tests/live/sources.live.test.ts` grades a narrowed URL and an unnarrowed one, decides the state kind from `data-state` before comparing anything, addresses its surface by `data-surface`, and asserts the two window lines are NOT byte-identical between the two URLs when the facet narrows the read.

## Acceptance criteria
Both /sources scan-window lines name the narrowing their read carried, asserted on rendered HTML for an unnarrowed URL and for a narrowed one, and /sources versus /sources?<facet>=<value> do not render byte-identical window lines when the facet narrows the read — while a facet the page dropped changes neither line. A narrowed scan that returned no rows still names its narrowing (the line follows the read, not the rows). The sentence is imported, not retyped: src/components/sources/trends.tsx declares no narrowing phrase of its own and grep shows unchippedPhrase and narrowedTo declared once each in src, both outside this page's files; /sources' facet table is the only new declaration and it lives in src/lib/sources/routes.ts. Which empty card the surface draws is unchanged, no figure moves, no surface or control is added, the sidebar still holds exactly six links, and /sources' live parity suite is green with a narrowed and an unnarrowed URL graded by state kind first.

# ASK BEN: which Supabase env names does the APP read at runtime, and what do the campaign's live tests read?

## Description
**Contract silence.** ARCHITECTURE marker `OPEN-ENV`. Two rules the campaign must obey at once appear to point at different names:

- `contracts/admin-build.md` ground rule: *'Live work targets the staging project through `STAGING_SUPABASE_*` names ... an unset name is a refusal, never a fallback.'*
- `contracts/admin-build.md` ground rule: *'The deployed Railway service is never repointed by this campaign, and every push to `main` must leave the app deployable against whatever project the service targets.'*

The deployed service reads `SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY` (`src/lib/supabase.ts`, today). If the app's own code starts reading `STAGING_*`, the deploy breaks; if the live tests read `SUPABASE_*`, 'staging only' stops being structural.

Four things to settle, one answer:

1. **Which names does the app read at runtime?** (Recommend: `SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY`, unchanged — the service is never repointed.)
2. **How do the live tests point the app at staging?** (Recommend: `tests/live/setup.ts` is the one file that reads `STAGING_SUPABASE_URL` / `STAGING_SUPABASE_SERVICE_ROLE_KEY`, refuses when either is unset, and sets the process env for the live run only. Product code never mentions a `STAGING_` name. This keeps 'no fallback' true: the app has no knowledge of staging, and the tests have no fallback to the app's names.)
3. **Do the live tests get anything beyond URL + service key?** Acceptance test 2 says 'direct SQL on staging', but PostgREST cannot run SQL and the `supabase` CLI is an undeclared service the remote gate refuses. (Recommend: no database connection string. 'Parity' becomes: the page renders through `lib/db`, and the test issues its own independent PostgREST count — two paths to one number. If you want literal SQL, say so and name the connection-string variable; it would be a new secret name and a new dependency.)
4. **`agenticflow/docs/SERVICES.md` declares no service.** The remote gate refuses an undeclared service's CLI, and the live-test guard is designed to refuse a staging host that is not the one declared there. (Recommend: add a `## supabase` section naming the staging project as the target agents may touch. Names only — no key, ever.)

Also, for the record: **`.env` today carries `SUPABASE_URL` and `SUPABASE_ANON_KEY` and no service-role key**, so a local dev run or a walk cannot read anything through the service-role client. Whether that gets a local service-role key is part of this answer. No value of any of these names appears in this ticket, and none may appear in any transcript, commit or note.

**Blocks nothing structural**: TASK-0002 builds `client.ts` reading the app's existing names and TASK-0003 builds the live guard, both written so that this answer changes those two files and nothing else. What it does block is any live-marked test actually running.

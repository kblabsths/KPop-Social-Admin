# The write-path guard bans the admin_locked column NAME, so the provenance display spec §8 requires cannot be built

## Description
Raised by QA on TASK-0011 ("guard OVER-REACH, for the architect, not this ticket") and ruled a defect by the architect, 2026-09-02. QA was right not to narrow it themselves — loosening a catalog-ownership guard is not QA's call — and the builder was right not to weaken it.

## The defect

`tests/offline/edit/config.test.ts:358`, inside `it("builds no write path to a resolver-owned table or a link table")`:

```ts
expect(filesWhereCodeMatches(/settle_review_item|admin_locked|apply_resolution/)).toEqual([]);
```

`settle_review_item` and `apply_resolution` are **actions** — a name that appears in `src/` at all is a call, and banning the name is exactly right. `admin_locked` is a **column** of `field_provenance`. Reading it is not a write path, and spec §8 asks for precisely that read: admin stickiness visible in the provenance display ("admin-set Jun 12"). The guard as written bans the read as well as the write, so it forbids the app from showing a fact the design requires it to show — and it does so under a test title that claims to be about writes.

This is ARCHITECTURE Common-violation class 4 again — an absence pin keyed on a WORD rather than on the write it forbids — this time reaching past prose all the way into correct product code that nobody has been able to write yet.

## The narrowed guard (the exact predicate)

Three assertions replace the one, each pinning what the rule actually means. `filesWhereCodeMatches` and `codeLines` already exist in the file; nothing new is imported.

```ts
// The two ACTIONS stay banned by name: their name in src/ can only be a call.
expect(filesWhereCodeMatches(/settle_review_item|apply_resolution/)).toEqual([]);

// `admin_locked` is a COLUMN of field_provenance. READING it is the provenance
// display (spec §8: admin stickiness is visible at the fact). What may not
// exist is a path that WRITES it. Two pins, neither of which touches a read:

// 1. It is in no `editable` list, so the one write path cannot carry it.
for (const [table, config] of Object.entries(EDIT_CONFIG)) {
  expect(config.editable, table).not.toContain("admin_locked");
}

// 2. No code line anywhere under src/ names the column and a write verb.
expect(
  filesWhereCodeMatches(/admin_locked/).filter((file) =>
    codeLines(file).some(
      (line) => /admin_locked/.test(line) && /\.(update|upsert|insert)\(/.test(line),
    ),
  ),
).toEqual([]);
```

Assertion 1 is the strong one, and it is a **value** assertion rather than a text scan: the whole write path is `updateRecordField` consulting `EDIT_CONFIG` (`tests/offline/edit/config.test.ts`, "writes the database from exactly one module" — `.update(` appears only in `src/lib/db/records.ts`), so a column absent from every `editable` list cannot be written through it. Assertion 2 catches the only other shape — a hand-built payload naming the column beside a write verb — without saying anything about a read.

Keep the test title honest: this case is about a write path, and after the change it only asserts write paths.

## Why the cost is not acceptable as-is

The alternative ruling — leave the guard broad and let the provenance display do without `admin_locked` — costs a spec §8 requirement to protect a rule that is already enforced twice over (one writer module, one allowlist). It also sets the precedent that a guard may ban a column name, which is how this class keeps recurring: the app's vocabulary is the contract's vocabulary, and a ban keyed on a word forces correct code to be renamed or not written.

## Blast radius

Test-only. No product code changes in this ticket; `admin_locked` is not read anywhere in `src/` today, and the read that will use it belongs to the record-page display work (admin-window/TASK-0029), which is why this lands first.

## Acceptance criteria
1. tests/offline/edit/config.test.ts bans settle_review_item and apply_resolution by name, and bans admin_locked only as a WRITE: absent from every editable list in EDIT_CONFIG (a value assertion over the imported map), and absent from any src/ code line that also carries .update( / .upsert( / .insert(. 2. A READ of admin_locked anywhere under src/ passes the guard — verified by watching the narrowed guard stay green with a throwaway read line added and removed (report the observation; do not land the line). 3. The two neighbouring pins are untouched and still green: '.update( only in src/lib/db/records.ts' and 'no insert/upsert/rpc anywhere'. 4. No product code changes in this ticket.

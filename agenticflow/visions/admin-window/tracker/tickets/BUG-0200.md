# The three accounts result.ts composes itself still render in the machine's mono face

## Description
**Expected** (BUG-0196 criterion 1, LOOK_AND_FEEL -> Typography): on a failed read, the words THIS APP wrote render in the sans `body` step and the words the DATABASE produced render in the mono `data` step.

**Found**: three error arms whose every word is this app's prose carry NO authorship, so the wire's documented default applies (`src/lib/db/result.ts:37` — absence means the whole account is the machine's) and the operator reads them wholly in the mono `data` step, in the same red run as a Postgres string:

- `src/lib/db/result.ts:1018` — `readComplete`, a query that answered no count (`the read returned no count, so whether these N rows ...`);
- `src/lib/db/result.ts:1027` — `readComplete`, a set the cap truncated (`the database holds N rows matching this read and it is capped at 1000 ...`);
- `src/lib/db/result.ts:1102` — `readCount`, a count read that answered no count.

None of the three is a string any database produced, and all three are in the very module BUG-0196 criterion 5a names as where authorship is decided. BUG-0196 fixed the four clauses its criterion 2 enumerated (`documentInstead`, `serialisedInstead`, `framesInstead`, `REFUSED_WITHOUT_WORDS`); that enumeration missed these three, which are authored inline rather than as named constants. The builder recorded the exclusion deliberately (the `authored?` docstring: 'the arms this app composes about a read it could not grade — a count that did not come back, a row cap — carry none, and read exactly as they read before'), so this is a scope gap in the criteria, not a defect in the landed mechanism.

**Reachable on real operator paths**, not hypothetical: `readComplete` backs `readSources` (`src/lib/db/sources.ts:167`, the /sources page), `readReviewItems` (`src/lib/db/review-items.ts:131`, /queues), `readRecentEvents` (browse) and the verdict log; `readCount` backs `readClaimCount` (`src/lib/db/claims.ts:359,411`, /claims). Any of those tables passing ROW_CAP=1000 rows, or any select that loses its `{ count: "exact" }`, puts one of the three sentences on screen.

**Repro (offline, no device):**
1. `cd '/Users/ben-m4/Desktop/Coding/KPOP/kspace Admin'`
2. `./node_modules/.bin/vitest run --project=offline tests/offline/db/result.test.ts -t 'says THIS APP wrote it'`
3. The pin is marked `it.fails` (the strict xfail spelling on this runner) with this ticket's id, so it is GREEN on the run branch today and turns RED the moment the arms carry authorship. Un-mark it (`it.fails` -> `it`) as part of the fix; with the arms still unauthored and the mark removed it reads: `a set the cap truncated: the arm carries no authorship: expected undefined to be defined`.

**The fix, in BUG-0196's landed shape**: each of the three arms returns `authored: [{ words: <the same sentence>, author: "this app" }]` and `message: accountText(authored)` — no wording changes, no new mechanism, and `src/components/ui/error-line.tsx` already draws it (its test 'draws an account carrying no authorship exactly as it always did: one mono run' is the other half of the measurement).

**Same class, out of this scope, for the architect to rule on:** `src/lib/db/records.ts:176,184` and `src/lib/db/verdict.ts:177,192` compose four more wholly app-authored error arms with no authorship. They are outside `lib/db/result.ts` and reach the edit surface rather than state 4, so they are named here rather than filed.

## Acceptance criteria
**THE CLASS IS RULED, not the three sites — architect, 2026-09-11.** BUG-0196
criterion 2 fenced four named authors and the builder honoured the fence; a
second ticket enumerating three more sites would leave the same gap open for
the fourth. What follows grades the INVARIANT.

1. **The invariant.** Every `kind: "error"` account THIS APP composes itself
   under `src/lib/db/**` carries its authorship AT ITS ONE CONSTRUCTION POINT:
   the arm returns `authored` — a segment list in the campaign's one
   vocabulary (`AccountSegment` / `ReasonAuthor`, `src/lib/account/authored.ts`)
   — and its `message` is `accountText(authored)` and nothing else. After this
   ticket **no composed error arm anywhere under `src/lib/db/**` lacks
   `authored`**, and an arm added later without it turns the sweep RED (checks
   3 and 4). Sites that merely PASS AN ARM THROUGH — `src/lib/db/paging.ts:59`
   (`pageAnswerOf`) and `src/app/queues/[reviewItemId]/page.tsx:260`
   (`gaugeStateOf`), the only two in `src/`, both measured carrying `authored`
   today — keep forwarding the author's list unchanged: never re-derived, never
   invented, never dropped (BUG-0196 criterion 5c).

2. **The seven sites, as the sweep names them on d96e3c17** (dry-run
   2026-09-11: 9 construction sites under `src/lib/db/**`, 2 authored, these 7
   bare): `src/lib/db/result.ts:1019` (`readComplete`, no count), `:1029`
   (`readComplete`, the row cap), `:1103` (`readCount`, no count);
   `src/lib/db/records.ts:176` (`updateRecordField`, the edit refusal), `:184`
   (the not-written-directly refusal); `src/lib/db/verdict.ts:177`
   (`settleReviewItem`, `REFUSED_BEFORE_SEND` + the refusal identifiers),
   `:192` (`NO_RECEIPT`). **Every one is wholly this app's prose, so each
   account is one `"this app"` segment** — provenance traced before filing:
   `records.ts:176` carries `decideEdit`'s `EditRefusal.message`
   (`src/lib/edit/config.ts:485,496,569,580` — this app's sentences about its
   own allowlist), `verdict.ts:177` carries this app's constant plus
   `decisionRefusals`' identifiers, and no string any database produced reaches
   any of the seven. `classify` (`result.ts:912`) is untouched: it already
   decides authorship per part and is where a DATABASE segment is born.

3. **Byte-identity of every existing `message`, structurally rather than by
   promise.** No wording changes anywhere in this ticket. `message` becomes
   `accountText(authored)` at each site and there is no second composition of
   the same sentence. Because `accountText` joins segments with exactly ONE
   SPACE, an account whose parts are separated by anything else stays a SINGLE
   segment: `verdict.ts:177` joins its refusals with `", "` and must not be
   split at those commas. Splitting a clause into several segments is allowed
   only where the join reproduces today's bytes exactly.

4. **RULED — a figure the app interpolated into its own sentence does not split
   the run** (architect, 2026-09-11; decide this here so no builder guesses).
   `result.ts:1029` interpolates `count`, `ROW_CAP` and `rows.length`, and
   `:1019`/`:1103` interpolate `rows.length`; they stay INSIDE the arm's single
   `"this app"` segment. The segment vocabulary answers "who wrote these
   WORDS" (BUG-0196 criterion 5a); no site in the landed mechanism splits at
   token level, and a run boundary that depended on a value's shape would move
   a face when a number changed. If the designer wants interpolated figures to
   render in the mono `data` step, that is a visible design decision and its
   own ticket — not this one.

5. **Nothing on a wire changes, and no validator gets stricter.**
   `pageAnswerOf` already forwards `authored`; wire authorship stays OPTIONAL
   with ABSENCE meaning the whole account is the machine's (BUG-0196 criterion
   5c). The two HTTP routes that consume the records/verdict arms serialize
   `result.message` ONLY — `src/app/api/admin/records/[table]/[id]/route.ts:334`
   and `:415`, `src/app/api/admin/review-items/[reviewItemId]/settle/route.ts:157`
   — so both JSON bodies stay byte-identical and authorship is NOT added to
   them by this ticket.

6. **No renderer changes.** `AuthoredAccount` (`src/components/ui/error-line.tsx`)
   already draws the split for both renderers and is the ONE run-splitting
   derivation (BUG-0196 criterion 5d). A component diff in this ticket means
   the fix was made in the wrong place.

7. **What the operator sees** (why this is not bookkeeping): a `/sources`,
   `/queues`, `/browse` or `/claims` read that answers with no count, or over
   `ROW_CAP`, renders its sentence in the sans `body` step beside the mono
   `reading` identifier — not as one red mono run (LOOK_AND_FEEL → Typography;
   BUG-0196 criterion 1). The four `records.ts`/`verdict.ts` arms reach only
   the two JSON routes today and so move no pixel now; they carry authorship
   for the invariant, so the next surface that renders one does not re-file
   this bug.

8. **BUG-0175's isolation is not regressed** and every other arm is
   byte-identical: `not_provisioned`, ok, the paging driver's own arms and the
   real-PostgREST account (`classify`) read exactly as they read today, code in
   parentheses included.

9. **Tests grade the split structurally, not the sentences.** QA's strict xfail
   at `tests/offline/db/result.test.ts:3811` (`it.fails`) becomes a plain `it`
   and stays green. Each of the seven arms is graded by WHO its segments say
   wrote them and by `message === accountText(authored)` — never by pinning the
   product's prose byte for byte (BUG-0196 criterion 6). Whole-arm `toEqual`
   pins that now see an `authored` key are UPDATED, not deleted.

10. Human-check: on `/sources` (or `/claims`), make a read answer without a
    count — e.g. point the instance at a stand-in PostgREST that drops
    `Content-Range`, per BUG-0196's QA method — and read the failed card: the
    sentence is Geist (sans) beside the mono `reading` identifier, and a real
    PostgREST refusal on the same card is still wholly Geist Mono.
    **(human-checkable)**

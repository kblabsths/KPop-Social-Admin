# Claims: BUG-0041's 50-row window leaves the page's live parity oracle red — it still asserts every claim of the view is rendered

## Description
Landed on run/admin-window as e5cf327 (BUG-0041, commit 9012ef5). The PAGE is correct — I measured it in a browser on my own instance (:8783, staging, 1440x900): scrollHeight 2,806px, 50 rows, gauge h2 at y=2,213, bucket counts 108+769=877 = the window line's stated held. What is broken is the LIVE parity oracle that certifies the page against staging.

Expected: 'npm run test:live' is green on the run branch, and 'tests/live/claims.live.test.ts' certifies what /claims renders against a count the test issues itself (acceptance test 2/3, ARCHITECTURE.md section 10).

Found: 'tests/live/claims.live.test.ts:200-210' — the case 'lists every claim the view holds — a complete read, nothing dropped' — asserts 'expect(rendered).toHaveLength(whole)' where 'whole' is this test's own exact count over pending_claims (877 on staging) and 'rendered' is the ids the list drew. The list is now bounded to CLAIM_WINDOW=50, so the assertion is false BY DESIGN and the file is red:

  npx vitest run --project=live tests/live/claims.live.test.ts
  x lists every claim the view holds — a complete read, nothing dropped 4034ms
    -> AssertionError: expected [ ...(50) ] to have a length of 877 but got 50
    at tests/live/claims.live.test.ts:209:22
  Test Files 1 failed (1); Tests 1 failed | 5 passed (6)

Measured 2026-09-03 against staging on the landed tree. The other three live suites that read the same objects are green on the same tree (sources 6/6, runs 7/7, dashboard 7/7), so this is this diff's, not staging's.

Two things are wrong here, and a fix must answer both:
 1. The run branch ships a red live suite. BUG-0056 bounced BUG-0040 for exactly this on /cycles the same day.
 2. Deleting or relaxing the assertion would leave /claims with NO live check on its list contents at all. The property that replaced completeness is checkable and stronger: the drawn ids must be exactly the first CLAIM_WINDOW of the view's oldest-first order (independently queried by the test, not by lib/db), the count of drawn rows must equal min(CLAIM_WINDOW, whole), and the window line's data-window-held must equal the test's own 'whole' — which is what makes 'the read is still complete, only the drawing is bounded' a verified claim rather than a comment. The standing-tab case at :213 has the same latent shape (it compares a full id set) and only passes today because staging holds 0 standing claims; it will go red the day that bucket exceeds 50.

Note also 'tests/live/claims.live.test.ts:76-79' addresses surfaces positionally (section:nth-of-type(1)/(2)) — unchanged by this diff (the window line was added INSIDE the existing list section), but the same hazard BUG-0056 hit.

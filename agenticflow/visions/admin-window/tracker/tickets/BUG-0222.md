# A paged press draws a row the screen above it already holds: the same claim twice, and React's duplicate key

## Description
SPLIT FROM BUG-0221 by the architect's ruling of 2026-09-12 (that ticket's History carries it in full). BUG-0221 found two defects at one seam and the contract answers them differently: the SKIP is held for Ben's paging-shape decision (ARCHITECTURE §4.3 kind 3 already declines the snapshot promise, and its honest fix changes what the bound IS — the same layer Ben is deciding). THIS ticket is the other half, and it is buildable today under the contract exactly as it stands.

THE DEFECT. The wire bound is a POSITION (?offset=<rows held>, src/lib/paging/machine.ts:386 pageUrl; src/app/api/admin/claims/rows/route.ts:136 re-reads at that offset). A row INSERTED ahead of the bound between the screen read and the press moves every later row down one, so the page at offset N begins with a row the client already holds — and the surface concatenates it, drawing one claim twice. React's duplicate-key error is the operator-visible symptom in Ben's dev log (BUG-0221 repro B, measured 2026-09-11 on a dev instance: 100 rows drawn, 99 distinct, 01a058f1-02c7-7e11-9191-adfa6207a0f0 twice). In production the resolver and the scraper both write pending_claims while an operator reads it, so the trigger is ordinary traffic, not a dev-server artifact.

WHY THIS HALF NEEDS NO RULING. §4.3 kind 3's 'A concatenation is still not a total' permits the population to move under a bounded read; it does not permit one drawn list to hold one id twice. That is not a snapshot promise, it is the list disagreeing with its own count — and BUG-0216's own property ('what these surfaces draw is one contiguous run of the order their last read held') is the bar. The fix lives entirely in the CLIENT DRIVER: it does not change what the bound is, so it survives whichever paging shape Ben picks.

INTERFACE CONTRACT — what the machine must do (this is the design; a builder implements it, it is not re-decided in the lane):
1. THE STATE HOLDS THE IDS IT HAS DRAWN and appends only rows whose id it does not already hold. The drop happens on the APPEND, never on the wire.
2. THE WIRE BOUND STAYS THE OFFSET and advances by the number of rows THE ROUTE RETURNED — never by the number appended. If it advanced by the appended count, the next press would re-ask positions already answered and the overlap would repeat forever. So the wire bound and the drawn row count become TWO facts: each is stated by whoever owns it and neither is inferred from the other's size (§4.3 kind 3, rule 4 — the rule promoted from BUG-0174/BUG-0183, which is exactly this shape).
3. EXHAUSTION IS STILL THE ROUTE'S (exhausted === rows.length < size, §4.3 kind 3 'Full-or-exhausted, on BOTH sides of the wire'). A page deduped to zero appended rows is NOT exhaustion, and the control stays.
4. THE OVERLAP IS STATED, ONCE, IN CLIENT-LAND. The operator learns the list moved under them; a silent dedupe would hide the one fact that matters. It renders only after a press, so the first server screen stays byte-identical (M3 EC4) and NO data-window-* attribute is added (§4.3 kind 3, rule 3 of the window-line amendment). The WORDS are the designer's — grade the fact and the hook, never the prose (the Voice bars grade wording at the walk).
5. /browse carries the property through the same driver and the same primitive.

NOT IN THIS TICKET, and the ticket may not claim it: the SKIP (BUG-0221, blocked on Ben). Deduping does not fix a skipped row, and no sentence this ticket adds may imply the drawn run is contiguous or complete.

## Acceptance criteria
1. NO ID IS DRAWN TWICE on either paged surface, whatever the route answers. Driven offline through the machine on a fixture where a row is inserted ahead of the bound between the screen read and the press: every id in the drawn run is distinct, and the run's length equals its distinct count. The failing fixture and the passing one are both shipped (LESSONS 8): an overlapping page AND an ordinary page that must append every row it carried.

2. PROGRESS IS PRESERVED. The wire bound advances by the ROUTE's row count, so the press after an overlapping page asks the next unanswered positions and a walk still reaches exhaustion. Proved offline on a walk to the end of a population that moves once mid-walk — the walk terminates, appends no duplicate, and ends in the exhausted state.

3. THE OVERLAP IS STATED, NOT SWALLOWED. When a press returns rows the state already holds, the surface says so once, in client-land, through the paging area's own copy home (src/components/ui/paging.tsx), carrying a machine-readable hook an offline test asserts. No sentence added by this ticket claims the drawn run is complete or contiguous; no new data-window-* attribute is introduced; the words are the designer's to grade at the walk.

4. THE FIRST SERVER-RENDERED SCREEN IS UNCHANGED: same window line, same figures, same row set on the same fixtures (M3 EC4). The hook of criterion 3 is absent from the first render.

5. EXHAUSTION, REFUSAL AND NOTES BEHAVE AS THEY DO TODAY: a page deduped to zero appended rows is not exhaustion and keeps the control; a refused page still appends nothing, leaves the bound unmoved and retains the control; per-leg notes still merge as §4.3 kind 3 requires.

6. THE SKIP IS UNTOUCHED AND UNCLAIMED. tests/offline/paging/machine.test.ts keeps BUG-0221's it.fails pin exactly as QA wrote it — this ticket neither removes the marker nor makes the pin XPASS, and if the marker's case flips, that is a finding to report, not a criterion met.

7. The live walks stay green: tests/live/claims.live.test.ts and tests/live/browse.live.test.ts (the live population is frozen during a walk, so they grade the path this ticket must not change).

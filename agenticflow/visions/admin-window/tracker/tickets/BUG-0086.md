# Edit cell: opening one cell reflows the record table, so the next single click on another editable value is swallowed and the operator must click twice

## Description
Measured by QA on the TASK-0053 attack (2026-09-08), production build of
run/admin-window @ 98c69c0 on 127.0.0.1:8794, bundled Chromium, staging
`walk_sandbox`. NOT a TASK-0053 regression — the diff that landed there
(a text-decoration on the resting button, a ref on the field) cannot move a
box. It is a pre-existing defect of the shared edit cell that TASK-0053's
affordances make reachable and worth fixing: the underline now tells a
mouse-first operator which values they may click, and the second one they
click does nothing.

**Expected** — LOOK_AND_FEEL "Inputs and inline edit": "click a value, it
becomes an input". A click on an editable value opens that value, whether or
not another cell happens to be open. Correcting several fields of one record
is the edit surface's whole job (FEAT-0011).

**Found** — from an open cell, ONE click on another editable value does not
open it. The click focuses the target button and is then swallowed, because
the record table reflows out from under the pointer between mousedown and
mouseup.

Exact numbers, `/records/walk_sandbox/00000000-0000-4000-8000-000000000001`,
viewport 1400x950, light theme:

- at rest, the `note` resting button occupies x=459 y=238, 193x20;
- with `label` open it is at x=358 y=264 — the whole Value column moves
  **101px left and 26px down**, because the open field is full-width and the
  hint line ("Enter or leaving the field saves...") is added to the flow;
- a single human-timed click (mousedown, 120ms, mouseup) at the note button's
  then-current centre (455, 274) leaves `document.activeElement` =
  `BUTTON/note of walk_sandbox` — mousedown hit it — and
  `document.querySelectorAll('input,textarea')` EMPTY: nothing opened. The
  blur committed `label`, React swapped the input back for the button, the
  table snapped back, and by mouseup the pointer was over a different row:
  `document.elementFromPoint(455, 274)` is now `TD "7"` (the `tally` row);
- a SECOND click at the same coordinate opens nothing either and drops
  `activeElement` to `BODY` — that point is dead space once the table has
  snapped back;
- control, same click with nothing open: `note` opens, `activeElement` =
  `INPUT/note of walk_sandbox`. So the swallow is caused by the open cell,
  not by the click.

Reproduced identically with a 0ms click and with the `tally` cell as the
target (focus moved to `BUTTON/tally of walk_sandbox`, nothing opened).

**Risk this carries, stated as a risk and not as a measurement**: the mouseup
landed one row away, on a `<td>`, not on a button. A layout where it lands on
another editable value's BUTTON would open the WRONG field — and TASK-0053
now opens a field with its value selected, so the next keystroke replaces
that wrong field's value. That is the harm FEAT-0011's second affordance
exists to prevent ("a stranger wrote a wrong value into the shared catalog").

**Mechanism**, read off the source and consistent with the measurement:
`EditableCell`'s `onBlur` calls `commit()`, which calls `setEditing(false)`.
React flushes that discrete-event update synchronously, so the edit-mode
subtree — a field that claims the cell's full width plus the
`aria-describedby` hint span — is replaced by the intrinsic-width resting
button before the mouseup is dispatched. The cell's edit-mode and resting
renderings simply do not occupy the same box.

**On pinning it with a test.** This campaign's tiers structurally cannot see
it: `tests/offline` is environment node with `renderToStaticMarkup` and no
jsdom, and there is no browser tier (STACK.md §4 — "no jsdom, no Testing
Library, no Playwright dependency in this campaign"). It is the same class of
browser fact as BUG-0069's focus and TASK-0053's selection, and the house
answer to both is on record: extract the decision as a pure exported unit,
pin the unit offline, and measure the rendered fact in the walk
(`focusVerdict`, `selectOnOpen`). QA wrote no red test for this one and says
so rather than shipping a green one that pins nothing; the fix carries its
own pin plus a walk measurement of the box.

## Acceptance criteria
1. From a cell that is open, ONE click on another editable value on the same
   record opens that value: measured in a walk on a production build against
   staging `walk_sandbox`, `document.querySelectorAll('input,textarea')`
   carries the clicked field's `aria-label` after a single human-timed click,
   and the previously open cell has committed or reverted as it did before.
2. Opening a cell does not move the other cells: the resting bounding box of
   every other editable value on the record is unchanged (0px in x and y)
   while one cell is open, measured in the same walk in both themes.
3. Whatever decides it is a pure exported unit pinned in
   `tests/offline/ui/editable-cell.test.ts`, red against the current code —
   the `focusVerdict` / `selectOnOpen` precedent — rather than a class
   literal asserted out of the markup.
4. TASK-0053's two affordances are unchanged: the resting hairline underline
   still renders on editable values and none on read-only ones, and a cell
   still opens with its whole value selected (input and textarea alike).
5. `npm run lint`, `tsc --noEmit`, the targeted offline file and the record
   page's live suite are green.

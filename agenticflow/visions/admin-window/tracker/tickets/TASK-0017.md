# The edit config map and the one PATCH route that obeys it

## Description
Module: `src/lib/edit/config.ts` (**the one hand-written config**), `src/app/api/admin/records/[table]/[id]/route.ts` (the one write path) and `src/lib/db/records.ts` (the read + the direct update). Authority: spec section 8 and section 3; acceptance doc ground rule 'One hand-written config drives the edit surface: the {table -> editable columns} map. Write path and widget derive'; `AGENTS.md` data-ownership rule (BINDING); SPEC F8; M1 EC10; acceptance test 7 (pre-cutover half).

Interface contract:

```ts
// src/lib/edit/config.ts
export type Regime = "pre_cutover" | "resolver_owned";
export interface TableEditConfig {
  readonly table: string;                // the canonical table
  readonly pk: string;                   // groups.id, idols.id, events.event_id, venues.venue_id
  readonly regime: Regime;               // decides the WRITE PATH; never configured per column
  readonly editable: readonly string[];  // user-facing scalars only
}
export const EDIT_CONFIG: Readonly<Record<string, TableEditConfig>>;
```

- **`groups` and `idols` are `pre_cutover`**: they edit **directly**, within their allowlist — legal and unprovenanced, as the ownership rules allow. Seed `editable` from the columns the retired routes allowed (they are the vetted set): groups — `name, korean_name, short_name, company, status, type, member_count, debut_date, image_url, bio`; idols — `stage_name, real_name, korean_name, position, nationality, gender, bio, birth_date, image_url, status, height_cm, weight_kg, blood_type, mbti, agency, birth_place`. Primary key is `id` for both.
- **`events` and `venues` are `resolver_owned`** and appear in the map with an **empty** `editable` list in M1. **No write path to them exists** — no PATCH branch, no helper, no scaffold, no commented-out future code. Their override path is M2's, through `settle_review_item`.
- **User-facing fields only: never ids, keys or timestamps.** Never widen a list to a link or a non-scalar — performers and venues are `event_performers` / `venues` rows, not fields of `events`.
- **The route reads the same `EDIT_CONFIG`.** A column absent from the map is refused **server-side**, with the row unchanged and a refusal naming the field — hiding the widget is not the refusal (acceptance test 7). A table absent from the map is refused. A `resolver_owned` table is refused. There is no second allowlist anywhere in the repo.
- The route sits behind `requireAdmin()` like every route before it, and it neither inserts nor deletes a row. `scraped_events` and any `*_legacy` table are never written. No DDL, no migration, no SQL-executing route.

Out of scope: the record page and its widgets (TASK-0018); any observation, any `admin_locked` stamp, any `verdicts` row, any entity picker — all M2.

## Acceptance criteria
[test 7 pre-cutover half; EC10] Offline tests prove the config map is the single source: a column in `editable` is accepted; a column absent from it is refused with the row unchanged; a table absent from the map is refused; a `resolver_owned` table is refused; an id, key or timestamp column is refused even when spelled correctly. An http test proves the refusal is **server-side** by sending a forged PATCH naming an unmapped column directly to the route and asserting a non-2xx response and an unchanged row. The route requires an admin session. No insert or delete of a catalog row exists in the repo, nothing writes `scraped_events`, and no write path to `events`, `venues` or `event_performers` exists.

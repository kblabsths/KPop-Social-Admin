# A failed read's account renders the app's own sentences in the mono face reserved for the machine's words

## Description
**Where the rule is.** `agenticflow/docs/vision/LOOK_AND_FEEL.md` → The Look → Typography:
*"**Mono carries every value the database produced** — counts, ids, timestamps,
values, source names, buckets, tiers, error strings. Sans carries every word the
app wrote — labels, headings, buttons, prose. That split *is* the typographic
idea: the operator can always see which words are the machine's."* This campaign
has already fixed this rule once, at P2, in this exact family: BUG-0175 moved
the paging refusal's app-authored reason out of the mono run.

**What I measured**, 1440x900, light, production build of f9165d18 on the walk
instance, `/claims`, the paging route answered with each arm's real shape:

| the answer's `message` | what renders, and in what face |
| --- | --- |
| `a 4524-character markup document arrived here instead of the database's own words` | `pending_claims — a 4524-character markup document arrived here instead of the database's own words` — **Geist Mono 11px**, `rgb(193,0,7)`, one span |
| `the read was refused with no words to explain it` | `pending_claims — the read was refused with no words to explain it` — **Geist Mono 11px**, one span |
| `TypeError: fetch failed Caused by: … (3 runtime stack frames dropped)` | the whole run, frames clause included — **Geist Mono 11px**, one span |

Every one of those sentences was written by THIS APP, in
`src/lib/db/result.ts`: `documentInstead` (:389), `serialisedInstead` (:410),
`framesInstead` (:427) and `REFUSED_WITHOUT_WORDS` (:575). None of them is a
string any database produced. They reach the operator in the face the palette
and the type scale reserve for the machine, inside the same red mono run as a
real Postgres string, and nothing on screen distinguishes them from one.

**The document clause is the sharpest case: its own content says "these are not
the database's words", and it says it in the database's face.**

**Two renderers carry it, not one.** The account is one string by the §4.1
contract, and both places that render a failed read spell it as a single mono
span:

- `src/components/ui/error-line.tsx:46` — `<span className="type-data">{named ? \`${reading} ${EM_DASH} ${failed}\` : failed}</span>`, which is data-surface state 4 on **every** page;
- `src/components/ui/paging.tsx:713` — the paging refusal's `machineWrote` arm, which takes the same account off the wire.

So this is not a paging defect; paging is where M3 made it easy to see. The
same three clauses render in mono in `/cycles`' error column path, the Dashboard's
error lines, and every `/claims`, `/queues`, `/sources` and `/browse` card whose
read refuses.

**Reachable, not hypothetical.** ARCHITECTURE.md's dated 2026-09-11 entry
records QA measuring *"a 4,530-character Cloudflare document rendered into three
`/claims` error cards"* on this stack, and `result.ts`'s own docstring records a
4,524-character document arriving through `code` on a production build. The
clause exists because that shape arrives; the face it arrives in is what this
ticket is about.

**Not a prescription, but the shape of the problem, so the scope is right:** the
account crosses `lib/db → view` as ONE string, so no renderer can tell the app's
clauses from the database's. Whatever separates them has to be decided where the
clauses are authored, not guessed at by a regex in the view — a view-side
"does this sentence look like ours" test is the fourth question `result.ts`
already refuses to ask (LESSONS 4, ARCHITECTURE §7 common violations row 15).

## Acceptance criteria
1. On a failed read, the words THIS APP wrote render in the sans `body` step and
   the words the DATABASE produced render in the mono `data` step, in the same
   line, on both renderers — `src/components/ui/error-line.tsx` (state 4, every
   page) and the paging refusal's machine arm
   (`src/components/ui/paging.tsx`). The object being read stays a machine
   identifier in mono in every arm, and the retry stays in sans, as they are today.
2. The four clauses that move are exactly the four `src/lib/db/result.ts`
   authors: `documentInstead` (:389), `serialisedInstead` (:410),
   `framesInstead` (:427) and `REFUSED_WITHOUT_WORDS` (:575). Their WORDING is
   not changed by this ticket — only which face carries them.
3. A database message that answers none of the account's three questions still
   crosses byte-identical and still renders wholly in mono: a real PostgREST
   refusal reads exactly as it reads today, code in parentheses included.
4. Where the app's clause and the database's words appear in ONE account (a part
   that kept its cause sentence and dropped frames), both faces appear in that
   one line, each over its own run. No account is dropped, truncated or
   reordered to make this easier.
5. The decision about who authored a part is made where the part is authored
   (`src/lib/db/result.ts`), never by inspecting the rendered string in a
   component. No renderer matches a sentence against a list of the app's own
   phrases.
6. `tests/offline/db/result.test.ts` and `tests/offline/ui/primitives.test.ts`
   assert the split structurally — which run each part lands in — and not by
   pinning the product's sentences byte for byte.
7. Human-check: on `/claims`, force the paging route to answer
   `{"kind":"error","reading":"pending_claims","message":"a 4524-character markup
   document arrived here instead of the database's own words"}` and press the
   control; the sentence reads in Geist (sans) beside the mono
   `pending_claims`, and a forced real Postgres message still reads wholly in
   Geist Mono. **(human-checkable)**

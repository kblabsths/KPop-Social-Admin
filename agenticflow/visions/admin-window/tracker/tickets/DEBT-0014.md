# selectClaims is exported twice with unrelated shapes — the claims vocabulary's own narrowedTo, left untracked by two lanes

## Description
Expected (ARCHITECTURE §11, 'contract vocabulary is the app's vocabulary, in code as in copy'; DEBT-0010 criterion 1, 'no identifier is exported twice from src/ with two different meanings'): a grep for a vocabulary word returns one declaration.

Found: two exported `selectClaims`, with unrelated signatures and no relationship a reader can see —

- `src/lib/db/claims.ts:261` — `(readonly ClaimRow[], filter: ClaimsFilter = {}) => ClaimRow[]`. Its own doc calls it 'the app's ONE claim predicate, so "the rendered counts equal the view's counts, per bucket and per source filter" is a property of one function'. Honours `filter.bucket`. Imported by `src/app/claims/page.tsx:35` and called at lines 316, 592, 618.
- `src/lib/gauges/pending-claims.ts:215` — `(input: PendingClaimsRows) => PendingClaimRow[]`. Takes the whole bundled read rather than rows plus a filter, reads the filter off `input.filter`, and has no bucket arm at all. Imported by `src/lib/gauges/standing-disagreements.ts:20` and called at 86.

Repro (run from the repo root, on run/admin-window at 9702ff8):

    grep -rn 'export function selectClaims' src

Observed: two hits, `src/lib/db/claims.ts` and `src/lib/gauges/pending-claims.ts`. Expected: one.

This is verbatim DEBT-0010's hazard, one domain over. Two adjacent modules of the SAME domain export one word; nothing catches an import from the wrong one except the type checker, and only because the shapes happen to differ — the sentence the architect wrote about `narrowedTo` reads unchanged here. The underlying bucket rule does NOT diverge (both reach `lib/db/claims.ts`' vocabulary: the gauge calls the exported `isRenderableBucket`, the db one compares against `UNRENDERABLE_BUCKET`), so nothing renders wrong today — this is the same naming debt, not a behaviour bug.

Two lanes have now walked past it: DEBT-0008's QA recorded it as a residual with no ticket ('selectClaims is exported twice with unrelated meanings (lib/db/claims.ts:261, lib/gauges/pending-claims.ts:215) - DEBT-0010's class'), and DEBT-0010 did not carry it — it is in neither that ticket's description nor its touch_scope, and criterion 1's operative constraint names the two `narrowedTo` functions.

Suggested shape (the builder's call, as in DEBT-0010): the db one keeps the bare word, because it is the one every claims surface calls and its doc already claims the name; the gauge's is the gauge's own selection over a bundled read and can say so. Do NOT merge them — they take different row types and different inputs, and the gauge's caller has no `ClaimsFilter` to hand.

When it lands, add the name to the OWNER map in `tests/offline/url/narrowing.test.ts`, which already grades declarations AND aliases for exactly this rule; that is the pin, and it costs one line.

P3: no user-visible path. It is a readability and wrong-import hazard, filed so the next ticket on a claims-counting surface reads one vocabulary.

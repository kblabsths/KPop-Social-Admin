# The registry reader takes a narrower declaration grammar than the sibling's own parser, so a typing pass next door reddens npm test and a single-quoted claim passes

## Description
QA attack on admin-window/BUG-0213, 2026-09-11, run/admin-window at 3920c720 (landed).

BUG-0213's fix answers attribution from a declaration on each side, per the architect's ruling — correct, and its own repro is dead (measured below). But the sibling's registry is the SIBLING's file, and what counts as a declaration in it is defined next door as code: `_declared_by` / `code_declarations` in `kspace Scraper/tests/live_safety/test_codes_named_once.py:72-105` parse the file with `ast` after blanking comments, and accept an `Assign` OR an `AnnAssign` whose single target is a Name and whose value is a string constant. Quote style never reaches the tree, and the docstring says it outright: "a declaration parked inside a comment is invisible, one WEARING a comment is not".

Expected: the guard reads a registry entry in every form the sibling's own parser reads as a declaration — those three forms declare the same meaning, so our four stay green, and a stranger's claim stays red whichever of them it is written in.
Found: `CODE_DECLARATION` (tests/offline/handoff/settle-review-item.test.ts:325) is `/^[ \t]*([A-Z][A-Z0-9_]*)[ \t]*=[ \t]*"(KS\d{3})"[ \t]*$/gm` — one line, bare `=`, double quotes, nothing after the closing quote. Three forms the neighbour calls declarations are invisible to it, and the gap runs in BOTH directions.

MEASURED, on a scratch replica of the sibling built from read-only copies (never a write next door; replica since deleted), running the file's own live check `-t 'allocates no code the sibling'`:
 - faithful replica -> exit 0 (baseline)
 - registry entry re-typed the way `kspace Scraper/tests/helpers/` types its other constants (`SYNTHETIC_NAME_PREFIX: Final[str] = "ENTITY_LINK_TEST_"`, catalog_rows.py:58) — `UNREADABLE_VERDICT: Final[str] = "KS029"` -> exit 1:
     KS029: raised next door in supabase/migrations/20260908000002_the_verdict_settles_the_item.sql, and tests/helpers/ks_codes.py declares no meaning for it (we declare UNREADABLE_VERDICT)
   The registry DOES name it; the sibling's own parser reads that line as `UNREADABLE_VERDICT` (checked with its `_declared_by` logic on the same text: sees ['UNREADABLE_VERDICT'], our regex sees []). npm test red for every builder in this repo over a next-door typing pass that changes no meaning — BUG-0213's failure mode with a new trigger.
 - the same entry wearing a trailing comment (`UNREADABLE_VERDICT = "KS029"  # raised by the admin handoff`) -> exit 1, same finding.
 - a stranger claiming one of our four in the other quote (`LEASE_NOT_RENEWED = 'KS029'` appended beside ours) -> exit 0. A real collision, declared in a form the neighbour calls a declaration, passes SILENTLY — BUG-0212's direction.
 - control: stranger claiming it in double quotes -> exit 1, "KS029: we declare UNREADABLE_VERDICT, tests/helpers/ks_codes.py declares UNREADABLE_VERDICT, LEASE_NOT_RENEWED" (the fix works where its grammar matches).

Why it is reachable and not theoretical: `Final[str]`-annotated string constants are the prevailing style in the very directory the registry lives in (`tests/helpers/ambient.py`, `canonical_snapshot.py`, `catalog_rows.py`), and the sibling is mid-campaign next door.

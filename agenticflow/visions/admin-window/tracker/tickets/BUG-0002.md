# http suite certifies whatever holds port 8772, not the app it started

## Description
Expected (TASK-0001 item 7 + the interface contract "http tests ... port 8772"): tests/http/auth.http.test.ts starts the built app on 8772 and asserts against THAT server.
Found: startServer() reports ready as soon as anything answers 200 on GET /api/health at 127.0.0.1:8772. It never checks that the process it spawned owns the port, so a foreign listener silently answers every assertion and the suite goes green without next start ever binding.

Repro (measured 2026-09-02 on run/admin-window @ 1c46dfa, after npm ci):
1. Start a foreign listener on 127.0.0.1:8772 that answers GET /api/health with 200 and GET / with 307 Location: /login (logging each request).
2. ./node_modules/.bin/vitest run --project=http
3. Observed: "Test Files 1 passed (1) / Tests 1 passed (1)" in 30ms, exit 0. The foreign listener log shows it served all three requests the suite made (GET /api/health twice, GET / once). tests/http/auth.http.test.ts:41-49 (waitForReady polls the port, not the child) and :52-62 (startServer never confirms the child bound).

Why it matters here: package.json test:http is the self-contained check every later ticket is told to run (TASK-0005 extends this file to every route). Two lanes running npm run test:http concurrently, or one orphaned next start from a crashed run, makes lane B certify lane As build - a green nobody earned, and undetectable from the output.

Pin (already committed, currently RED): tests/http/auth.http.test.ts > "refuses to certify a server it did not start when the port is already held" fails with "startServer() reported ready while a foreign listener held port 8772". It passes if startServer() rejects instead. Fix in tests/ only - e.g. pre-flight bind check, or have waitForReady confirm the spawned child is the listener - do not change src/.

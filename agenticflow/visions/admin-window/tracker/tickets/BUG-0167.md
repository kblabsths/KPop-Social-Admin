# the gauge's two legs truncate on different orders, so at the row cap a tie on the boundary instant drops claims the id list kept

## Description
**Expected** (TASK-0074 acceptance criterion 2): "The claim set is UNCHANGED" — the windowed claims leg selects the same claims the id-list join did.
**Found**: at the row cap the two sets differ. The windowed shape returned 2 claims where the id-list join returned 3.

**Why.** The two legs of `fetchPendingClaims` (src/lib/gauges/pending-claims.ts:224) carry the SAME cap (`PENDING_CLAIMS_DEFAULTS.limit` = `GAUGE_ROW_CAP` = `ROW_CAP` = 1000, src/lib/db/result.ts:55) but NOT the same order:

- claims leg — `readPendingClaimsInWindow` (src/lib/db/claims.ts:181) orders `observed_at asc, observation_id asc`. A TOTAL order, and its own test asserts that is the point: 'so which claims are inside a truncated window is decided by the database and not by a tie'.
- observations scan — `readPendingObservations` (src/lib/db/gauges.ts:355) orders `observed_at` ALONE. No tiebreak, so `limit` over rows tied on the boundary instant returns an ARBITRARY subset.

`fetchPendingClaims` then intersects the claims with the scan's ids (pending-claims.ts:236). When the two legs cut the tie differently the intersection is smaller than either leg, and smaller than what `.in(<the scan's ids>)` returned before this ticket. The old shape could not diverge: it asked for exactly the ids the scan returned.

**Reachability is near, not theoretical.** TASK-0074's own census: staging holds 877 live pending claims in the 90-day window and 877 pending observations — 88% of the 1000 cap, 123 rows of headroom. The live check that proves the two shapes agree (tests/live/claims.live.test.ts, 'the windowed claims read and the id-list join select the same claims') asserts BOTH legs came back under their cap and says so in its own message: 'a truncated read would make this a question about where two windows were cut'. So the regime this ticket is about is the one that live proof deliberately excludes, and it is the regime the view enters at 1000 rows.

**Repro (exact), pinned in the suite.** tests/offline/gauges/pending-claims.test.ts, test 'PIN admin-window/BUG-0167: at the cap, a tie on the boundary instant costs claims the id list kept' — currently `it.fails`, i.e. it is RED against the landed code and `it.fails` is what keeps the suite green. Four claims share one instant (2026-08-01T00:00:00Z), ids …c01–c04, cap 3:
- the scan came back with {c02, c03, c04} — a legal answer for `order by observed_at limit 3` over four tied rows;
- the claims leg, ordered totally, took {c01, c02, c03};
- `fetchPendingClaims` returns {c02, c03}; `readPendingClaimRows(idsOf(scan))` returns {c02, c03, c04}.
Watched red before the pin was applied: `AssertionError: expected [ …(2) ] to deeply equal [ …(3) ]`, the missing id being …c04.

**User-visible effect** once the view crosses 1000 rows in the window: /claims' and /sources' pending-claims figures lose an arbitrary handful of claims that the scan itself saw, and the number moves between renders because the tie subset the database picks is arbitrary per query. The window is flagged `truncated` in that state and the page calls its figures a floor, which is why this is P2 and not P1 — but it is a lower floor than the read actually had in hand, and a nondeterministic one.

**The remedy that makes the identity unconditional** (proposed, not prescribed): give the scan the same total order the claims leg has — `.order("observation_id", { ascending: true })` after its `observed_at` order in `readPendingObservations`. With one total order and one cap over a population the claims are a SUBSET of, the claims below the scan's cutoff are exactly the claims leg's first N, so the intersection is the id-list join's set in every state, ties included. Whatever shape is chosen, flip the pin from `it.fails` to `it` — a strict pin, so it reddens the day the divergence returns.

**Not in scope**: CHUNK_FANOUT, the per-bucket counts and seeks, paging, and anything rendered.

## Acceptance criteria
The pin `PIN admin-window/BUG-0167: at the cap, a tie on the boundary instant costs claims the id list kept` in tests/offline/gauges/pending-claims.test.ts is flipped from `it.fails` to a plain `it` and passes, with its BUG id spelled in the test name — the windowed claims leg and the id-list join select the same claims when both legs truncate at the same cap and the boundary instant is tied. The identity holds for at least one more shape than the tie: add a cap fixture where the boundary instant is NOT tied and the populations differ (a pending observation the view holds no claim for, so the claims leg reaches further in time than the scan) and assert the two shapes still agree. Nothing about the ticket's own guarantees moves: the two legs are still issued together (the in-flight-order test stays green and still fails against the sequential shape), the observations refusal still wins when both legs refuse, no refusal becomes a half-filled gauge or a zero, and nothing rendered changes on /claims, /sources, /queues or the review item — their offline page suites and tests/live/claims.live.test.ts are green unchanged. The live set-equality check keeps its own cap guard: it must still refuse to compare when either leg came back at 1000, since a green there would then be about the cap and not about the shapes. /claims warm server time over HTTP against a production build does not regress past 1.4 s (QA measured 1.134 s median, 7 warm samples, on the tree this bug was found on); state the median you measured in the closing History entry.

# The edit surface's override half: events and venues write only as recorded overrides

## Description
**SPEC F11.** `events` and `venues` become editable — but ONLY as recorded overrides the pipeline can see and protect. This is the half of the edit surface M1 deliberately shipped read-only.

**The regime decides the write path; configuration never does.** The one hand-written `{table -> editable columns}` map gains `events` and `venues` entries, but adding a table to the map does not choose how it writes: `EDIT_CONFIG`'s `Regime` does. A resolver-owned table's edit lands as an **admin-tier observation through the gate**, applied synchronously through `apply_resolution`, provenance stamped **`admin_locked`**, and logged in `verdicts` as `action = 'override'` with a **null `review_item_id`** — spec §7's "an override is the same row without the item". `groups`/`idols` keep the pre-cutover direct write untouched; `walk_sandbox` keeps its `pre_cutover` entry (DECISIONS 2026-09-03).

**No direct write path to `events` or `venues` may exist.** The entry point is `settle_review_item`, item-less. M1 proved the negative for these two tables by measurement (the only mutating call in `src` was one `.update()` reachable only through `decideEdit`, and `events.title` / `venues.name` PATCHes answered 403); M2 must keep the negative true while making the tables editable. That is the whole difficulty of this ticket.

**Absence degrades to M1, not to a broken control.** With `settle_review_item` absent — staging today, and `main`'s deploy target until Ben installs FEAT-0009 — `events` and `venues` render READ-ONLY with the reason named. No control appears that would call a missing function. This is graded before the happy path.

**Per-field provenance shows at the field** for a resolver-owned record, read from `field_provenance`: "ticketmaster, applied 3d ago" / "admin-set Jun 12", so admin stickiness is visible. A pre-cutover record keeps the rendering Ben confirmed on 2026-09-02 ("no provenance recorded (pre-cutover table)") — do not change it. Releasing an `admin_locked` fact is itself a verdict action on that fact, never a direct write.

**Two affordances the M1 user-sim walks earned, on the shared edit cell (both regimes):**
1. An editable value is **distinguishable from a read-only one before it is touched** — a 1px hairline underline on the value, not colour and not weight. A stranger found the edit affordance by tabbing, not by looking, and said a mouse-first colleague would read the page as read-only.
2. A click-to-edit cell **opens with its existing value selected**, so a straight retype replaces and an arrow key still appends. A stranger wrote a wrong value into the shared catalog because the caret sat at the end and nothing was selected.

**Contract gap, blocked not guessed (SPEC named gap 7):** WHICH columns of `events` and `venues` are editable at all is not enumerated anywhere. Spec §8 says the map is hand-written and says nothing more; AGENTS.md narrows it ("performers and venues are LINKS — `event_performers` / `venues` — not fields of `events`") without fixing it. The first `events`/`venues` map entry is an ASK BEN, not a builder's pick. Widening the allowlist to a non-scalar is forbidden by AGENTS.md outright.

vision_trace: "The edit surface driven by one hand-written map of what is editable: groups/idols edit directly within it; events/venues edit only as recorded overrides that the pipeline can see and protect; a reference field links rows, never text; provenance is visible at the field."

## Acceptance criteria
1. With `settle_review_item` ABSENT: an `events` record and a `venues` record render read-only with the reason named; zero inputs, selects, textareas or forms on either page; a forged PATCH naming a mapped `events` column is refused server-side with the reason, and the row is unchanged when re-read. `groups`/`idols` editing is unaffected and still works.
2. With the function present (recording stub): editing a mapped `events` or `venues` column produces EXACTLY ONE call to `settle_review_item` carrying `action = 'override'`, a null `review_item_id`, the admin-tier observation, and nothing else. No `.update()`, `.insert()`, `.upsert()` or `.delete()` in `src` targets `events` or `venues` on any path.
3. A column ABSENT from the map on `events` or `venues` refuses a forged request server-side with 403 naming the field — the same refusal `groups`/`idols` already give, not a hidden widget.
4. The write path is chosen by `Regime` and by nothing else: a structural test asserts the pre-cutover branch and the override branch are selected by the regime enum, on two fixtures (one of each), and that no configuration key can move a table between them.
5. Per-field provenance renders at the field on an `events`/`venues` record from `field_provenance`; a pre-cutover record still renders the sentence Ben confirmed 2026-09-02, unchanged.
6. On the shared edit cell, both regimes: an editable value carries a resting affordance distinguishing it from a read-only value without hover, focus or click; opening a cell selects its existing value so a straight retype replaces it. Asserted in the offline render suite.
7. The `events`/`venues` allowlist was answered by Ben on a blocked ticket, not chosen by a builder; every column in it is a vetted scalar of that table, and no link column (`venue_id`, performers) appears in it.
8. `npm run lint`, `tsc --noEmit` and `npm test` green; the record page's live suite green; M1's forged-request refusals still 403/404/405 exactly as the M1 verdict recorded them.

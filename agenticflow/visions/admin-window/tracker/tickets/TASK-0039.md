# Dashboard: one line saying when the resolver last actually applied something

## Description
**One line on a card that already exists.** The Dashboard's job, in VISION's own words, is "did anything happen last night". A user-sim watched the resolver apply nothing for eleven hours while the Dashboard read calm, and named his condition for coming back: "a line on the dashboard telling me when the resolver last actually wrote something." Source: `agenticflow/tracker/evidence/user-sim-m1/DESIGNER-JUDGEMENT.md` §5.

**What to add:** on the existing cycles/runs card of the Dashboard, one line stating when the resolver last APPLIED something — the most recent `resolution_runs` row with a non-zero `applied`, rendered as its age the way every other age on that page is rendered. Not the last cycle that RAN (the page already shows that, and the distinction is the whole point: 69 cycles ran and none of them wrote).

**What must NOT happen — read this before writing a line of it:**
- **No dial. No threshold. No colour that means "too long".** This is a timestamp, not a gauge. A builder who adds "amber after N hours" has built the exact thing Ben said he will build himself after this campaign closes. Ben's standing principle also applies: a dial-able value must not live in a file — and there is no row to read one from.
- **No new card, no new gauge, no seventh page.** It is a line on a card that exists.
- **A zero is a real figure, and an unmeasurable one is a refusal, not a zero** (LESSONS class 2, DECISIONS 2026-09-02). If no `resolution_runs` row in the window has a non-zero `applied`, the line says so honestly and names the window it looked in — it does not print "0" and it does not print a dash with no reason.
- **The window line follows the read, not the rows** (DECISIONS 2026-09-04).

**Parity:** the Dashboard's live oracle gains this figure, asserted against direct SQL on staging — and it names the page's state kind before it compares anything (DECISIONS 2026-09-02). A ticket that touches this page carries `tests/live/dashboard.live.test.ts` in its checks; that rule is already in the stored checks below.

vision_trace: "Ben, the ecosystem's operator, at breakfast: did anything happen last night, what needs me, who keeps being wrong."

## Acceptance criteria
1. The Dashboard's existing cycles/runs card carries one line naming when the resolver last applied something, derived from the most recent `resolution_runs` row with a non-zero `applied`, rendered as an age in the page's existing age format.
2. The line is distinct from "the last cycle that ran": with cycles present but none carrying a non-zero `applied`, the page shows the recent cycles AND says plainly that nothing has been applied in the window it read, naming that window.
3. No threshold, no dial, no state colour keyed to elapsed time: the line renders in the page's ordinary ink in every case, and `grep` finds no comparison of this age against a constant.
4. No new card, no new gauge, no new page, no new nav link — the sidebar still holds exactly six links and the Dashboard's card count is unchanged.
5. When the read is refused or the table is absent, the line drops whole (it does not render a dash, a zero, or a stale value) and the page's not-provisioned behaviour is unchanged.
6. `tests/live/dashboard.live.test.ts` asserts the rendered figure against direct SQL on staging, and names the page's state kind before comparing.
7. `npm run lint`, `tsc --noEmit`, `npm test` and the Dashboard live suite all green.

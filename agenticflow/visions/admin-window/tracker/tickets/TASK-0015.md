# Browse — the recent-events curated view and its column selector

## Description
Module: `src/app/browse/page.tsx` + `src/lib/browse/views.ts` (the view definitions) + `src/lib/db/browse.ts`. Authority: spec section 4 (Browse — 'each view is defined in code — the query, the columns it may show, the default sort — with a runtime column selector over the configured set'); `contracts/data-model.md` (per-field provenance); SPEC F7; M1 EC9; acceptance tests 10, 2, 9.

- **Exactly one curated view ships: recent events.** Everything that came through the pipeline, **newest first** — that is arrival order, `events.created_at desc`, not the calendar; `starts_at` is a column the view shows, never its sort (ARCHITECTURE section 11).
- The spot-verification columns: **title, description, poster image, date, venue** — and **the source(s) behind the row, read from the `field_provenance` join** (`entity_type = 'events'`, `entity_id = event_id`), resolved to source names through `field_provenance.source_id`. Read events through `event_listings` where the venue name is wanted; the keys are `event_id` (AGENTS.md).
- **The view is defined in code**: a single exported definition carrying its query, the columns it *may* show, and its default sort. The **runtime column selector shows and hides exactly the configured set** — every configured column offered, nothing outside it — and its state lives in `searchParams`.
- An event row links to `/records/events/<event_id>` — which is read-only for events in M1.
- **No whole-table browsing, no free-SQL runner, no second curated view** (spec section 1 and section 4 rationale). Adding a second view is a later decision, not a builder's.

Standing rules for every page ticket (ARCHITECTURE sections 4, 5, 7): the page function is the only async component on the route and every child is a pure sync component; read only through `src/lib/db/**`; table names live only in `tables.ts`; render all four states from the `ui` primitives (a missing table never throws and never renders as 0); tokens and primitives, never raw values; every filter, sort and tab is a `searchParams` value; ages relative with the absolute in the title attribute, scheduled times absolute UTC with the zone in the column header, machine identifiers verbatim in mono; **nothing settles anything in M1**.

## Acceptance criteria
[tests 10, 2, 9; EC9] Offline tests assert: rows render newest-first by `created_at`; every spot-verification column renders, including the source names from the provenance join; the column selector's option set **equals** the view definition's configured column set — every configured column offered and nothing outside it — and toggling a column changes exactly that column; the selector state round-trips through the URL. A live-marked test asserts the rendered order and the first page of rows against a query the test issues itself. Exactly one view definition exists. No table browser, no SQL-executing route and no second view exists in the repo. With `field_provenance` absent the page renders its not-provisioned state and the event rows still render or the page says which table is missing — either way nothing throws.

# A narrowing clause names what a facet DID, not that it is set — /claims' chip clause

## Description
**Modules:** `src/lib/url/narrowing.ts` (the leaf that gains the rule), `src/lib/claims/filters.ts` (the claims adapter and its facet sets), `src/app/claims/page.tsx` (the three sentences and the one new read leg), `src/lib/db/claims.ts` (read-only here — `readClaimCount` / `readClaimCountIn` already exist and are what the new leg calls).

**The defect, measured by QA on staging 2026-09-11 (residual of admin-window/BUG-0191):** one chip, two opposite verdicts.

- `/claims?source_id=<ticketmaster>` — a source the whole view carries — removes zero rows. `bucketsNarrowed` is false (two facts: rendered === population), the caption takes its unnarrowed arm and says "nothing above narrows these counts" with that chip standing active.
- `/claims?source_id=<ticketmaster>&domain=events` draws exactly the counts `?domain=events` draws alone — the domain did all of it — and the caption says "under the filters above".

Each sentence is true of its own reading: the first of EFFECT, the second of PRESENCE. The page renders `narrowed && chipped`, where `narrowed` is `claimsNarrowed` (two facts, `isSurfaceNarrowed`) and `chipped` is `hasChipNarrowing` (a `!== undefined` over `CHIP_FACETS`) — two different questions about two different subjects, ANDed as if they were one.

**The ruling this carries (architect 2026-09-11, ARCHITECTURE §4.3, DECISIONS of the same day, Common violations row 24): a clause that ATTRIBUTES a narrowing — to a control ("under the filters above", "matching these filters") or to a named facet — is a claim about rows THIS read lost, and may render only where that subject's own effect is established. Presence is never evidence of effect.** A clause that merely states what the read CARRIED (the control-less phrases of BUG-0160, "in the events domain") is not an attribution and keeps its presence gate.

**Three corollaries make this nearly read-free, and they are the design:**

1. The unnarrowed arm needs nothing new. `rendered === population` proves no facet in force removed anything, so "nothing above narrows these counts" is TRUE at `?source_id=<a source the view carries>` — that half of QA's finding is the CORRECT sentence and does not move. `BUCKET_CAPTION.everyBucket` (TASK-0071) stays exactly as it is.
2. Where the only facets in force are chips, the surface's own two-fact answer already IS the chip family's effect — free.
3. The single ambiguous state is BOTH families in force. There, and only there, the fact is bought with one bounded `head: true` count of the same read with the URL's chip facets dropped. On today's `/claims` that state is `?source_id=…&domain=…` and nothing else.

**Interface contract — the rule goes in the leaf, beside `isSurfaceNarrowed`, and is not a claims-shaped thing:**

```ts
// src/lib/url/narrowing.ts
/** Did THIS FAMILY of facets remove rows from this surface? The attribution
 *  question, one level below `isSurfaceNarrowed`'s "is this surface narrowed". */
export function isFamilyNarrowing(args: {
  /** A facet of the family the clause names is set on this read. */
  inForce: boolean;
  /** A facet OUTSIDE that family is set on this read. */
  othersInForce: boolean;
  /** This surface's own two facts. */
  surface: SurfacePopulation;
  /** Rows the same read draws with the family's facets dropped — supplied only
   *  where both families are in force, which is the only state that needs it. */
  withoutFamily?: number;
}): boolean;
```

`!inForce` → false. `inForce && !othersInForce` → `isSurfaceNarrowed(true, surface)`. Both in force → `withoutFamily !== undefined && surface.rendered !== withoutFamily` — an unsupplied count means the page says NOTHING about that control rather than guessing, because silence is always true and an attribution is not. It stays a pure leaf: booleans and numbers, no filter type, no import (§4 rule 7).

**The page side.** `chipped` / `chippedWithoutBucket` stop gating the three attribution clauses directly; each becomes this question asked of the surface that says it — the list's window line (`listScope`, `NARROWED_BY_FILTERS`), the bucket caption (`BUCKET_CAPTION.underTheFilters`), the empty card (`narrowedEmpty`'s `NOTHING_MATCHED.filters`), and the gauge's line (page.tsx:1300), which BUG-0191 already bound to the caption's answer and must stay bound to it. The presence predicate itself survives — renamed `hasChipFacet` by TASK-0072 — because corollaries 1 and 2 still ask "is a chip set at all".

**The new read leg, and why it is one and not three.** On the buckets tab `listFilter` minus the URL's chip facets and `tableFilter` minus them are the SAME filter (they differ only by the bucket facet, which is a chip), so ONE `readClaimCount` serves the list line, the caption and the empty card — the one-binding shape BUG-0191 established for `chippedWithoutBucket`. The gauge's set is a WINDOW, so where its own clause needs the fact it takes `readClaimCountIn(gaugeBounds, …)`, the way `gaugePopulation` already does. Both join the existing `Promise.all` as conditional legs (`needed ? read(…) : null`, exactly as `structural ? readClaimCount(populationFilter) : null` does today): no sequential round trip is added, and nothing is issued in a state where it cannot change a word (the issue-gating of DEBT-0012). Read DEPTH stays one.

**Two hazards, measured, so they are not discovered at the receipt:**

- **The tab's bucket is not a control above.** `listFilterOf` merges the standing tab's own `bucket` into the list's filter. The family subtraction drops the chip facets **the URL carried** (from `asked`), never the tab's own bucket — dropping that would compare this tab's rows against the other tab's population.
- **The existing pin at `tests/offline/claims/page.test.ts` derives the chip clause by `differingClause` between `{domain: NARROWING}` and `{source_id: SOURCE.first, domain: NARROWING}`, and asserts it is non-empty.** Measured in `tests/offline/claims/population.ts` on this tree: `domain: "venues"` (which is what `NARROWING` is in that block) is served by `SOURCE.first` ALONE — 2 claims — so under this fix that render loses the chip clause and the derivation goes vacuous and reds. Use a pair where the source really removes rows: `domain: "events"` is served by `SOURCE.first` and `SOURCE.second` (5 claims), so `{domain:"events"}` vs `{source_id: SOURCE.second, domain:"events"}` keeps the clause non-vacuous, and `{source_id: SOURCE.first, domain:"venues"}` is the state under test. Do not add fixture rows to fix this: `population.ts` is read by every claims suite and a new row moves figures three files over.

**Copy is not this ticket's to change.** Every clause keeps its words; what changes is which of them render in one state. If a state ends up with no honest clause available, the sentence says less — it does not gain new wording. Any rewording is the designer's walk, not a criterion here.

## Acceptance criteria
isFamilyNarrowing is declared exactly once in src, in src/lib/url/narrowing.ts, is a pure leaf (no imports beyond the file's own types) and answers the three states of its contract: not in force is false; in force with no other family is the surface's own two-fact answer; both families in force is decided by the count with the family dropped, and an absent count answers false. tests/offline/url/narrowing.test.ts pins all three and names the owner. On /claims, no clause that points at a control renders where that control's family removed no row from the surface saying it: at the offline state where the source facet is set beside a domain facet that did all the narrowing (source_id SOURCE.first with domain venues, measured: identical figures to domain venues alone), the bucket caption, the list's window line and the empty card carry no chip clause, and at the state where the source really removes rows (source_id SOURCE.second with domain events) all three still carry it — non-vacuous in both directions, with the clause read off the app by differingClause or by the app's own exported NARROWED_BY_FILTERS, never typed into a test. The caption and the gauge still give ONE answer about a chip narrowing in both directions (BUG-0191's pin still passes, unedited in substance). The unnarrowed arm is untouched: with a chip set whose family removed nothing and no other facet in force, the page renders exactly the bytes it renders today, everyBucket clause included. The new fact costs no round trip of DEPTH: the count joins the existing Promise.all as a conditional leg, is a head:true count, and is issued only where both families are in force and the surface is narrowed - proved by the stub client's recorded calls at the four states (bare, chip only, unchipped only, both). Nothing else on the page moves: no copy is rewritten, no figure changes, no data hook is added or removed, and the live claims parity suite is green.

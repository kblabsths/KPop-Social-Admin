# F14 — paging past the window, on Claims and on Browse

## Description
Ben, 2026-09-10: "not being able to load all claims if I want to is a huge oversight." He named the mechanism too: on-demand CLIENT-SIDE fetching against a route handler — not a server round trip per page, not an unbounded read. Claims and Browse ONLY.

Behavior: SPEC F14. Read it before decomposing; it is the contract, this description is the why.

THE CONTRACT AMENDMENT COMES FIRST. ARCHITECTURE §4.3 says today: "Paging is not the answer to a cap and none is built: nothing in the spec asks for it, and complete-or-refuse means there is never a partial page to continue." §4 rule 1 forbids a component fetching; §5 makes the page function the only async component on a route. This feature is the first thing in the campaign to cross all three. **The ARCHITECT amends those contracts at the start of M3, before any page diff lands** — a builder that finds a contract in its way files a blocked question and never interprets one. M3.md EC3 grades that ordering.

Shape that must not drift:
- The FIRST screen does not change. Same server-rendered window, same window line, same figures, same row set. Paging is what the operator can do AFTER that screen exists.
- Each 'more' is ONE client request against a route handler, carrying an explicit bound. One press, one request; no press, no request.
- The affordance is drawn only when there IS more, and never claims a total the read did not establish. Exhausted means the surface says so.
- Absent the tables, the not-provisioned state renders and NO affordance is drawn — a control that cannot be honoured is never offered (F10's rule).
- A refused page never half-fills the list. Complete-or-refuse still holds inside a page.
- The route handler is gated exactly as the pages are, and no service-role material crosses to the client.
- Paging is NOT whole-table browsing and does not reopen it: Browse keeps its one curated view; a second view, a table picker, a SQL runner and a search box all remain out (M2 out-of-scope, still standing).

vision_trace: VISION, 'What success looks like' — "Six pages ... each showing real staging rows whose numbers match what the database says ... An investigation never leaves the app." A surface that caps at 1,000 rows with no way past it sends the operator to a SQL client, which is exactly the failure two user-sim walks recorded.

## Acceptance criteria
Against staging (877 claims), a paged walk of /claims from the first screen reaches a claim beyond the first window's last row, and the count of distinct claim ids reachable by paging equals the exact count the page's own head figure states — no id twice, none skipped. The same walk on /browse reaches an event beyond the first window's last row. Each 'more' is exactly one route-handler request carrying an explicit bound, asserted in the offline suite against a recording stub; presses and requests are equal in number and zero presses issue zero requests. The first server-rendered screen of /claims and /browse is byte-identical in window line, figures and row set to today's, on the same fixture. On an exhausted fixture the affordance is absent and the surface says the set is complete; on a fixture with more rows it is present. Against PGRST205 both pages render data-state=not_provisioned with zero occurrences of the affordance in rendered HTML. A refused page leaves the rendered row count unchanged and names the object, proved on one fixture that must refuse and one that must not. An unauthenticated request to the route handler is refused before the handler body runs, on every method it accepts; a forged out-of-range bound is refused with the reason named, never clamped in silence. The sidebar still holds exactly six links and src/app gains no page route.

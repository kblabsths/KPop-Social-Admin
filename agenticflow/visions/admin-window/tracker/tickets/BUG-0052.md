# Record page: the unknown-id empty state sends the operator to Browse, which does not list groups or idols

## Description
Found by the document-blind user-sim walk (Priya, 2026-09-03), `agenticflow/tracker/evidence/user-sim-m1/priya.md` Leg 2; confirmed live on :8771 and at source 2026-09-03.

**Voice copy bar 4:** "Every empty and not-provisioned state names what the surface holds and **what fills it**."

`/records/groups/<unknown-id>` and `/records/idols/<unknown-id>` render:

    No groups record with that id
    Browse lists the records that exist; check the id in the address bar.

**Browse does not list groups or idols.** It is the recent-events view and nothing else (SPEC F7: one curated view ships). So the empty state names a filler that cannot fill it — it points the operator at a page that structurally cannot help, in the one moment they most need help.

The sentence is a static literal, applied to every table the map carries, at `src/app/records/[table]/[id]/page.tsx:164`:

    filledBy="Browse lists the records that exist; check the id in the address bar."

For `events` it is true (Browse links to `/records/events/<id>`). For `groups` and `idols` it is false. One string, two regimes.

Priya's own words: "Browse does not list groups. The tool sent me to a page that cannot help me, in the one moment I most needed help. **This is where I would have closed the tab.**" She then left the app for a SQL client to obtain a group id.

Confirmed live 2026-09-03 on the walk instance:
`GET /records/groups/00000000-0000-0000-0000-000000000000` -> 200, body contains "No groups record with that id | Browse lists the records that exist; check the id in the address bar."

Evidence: `agenticflow/tracker/evidence/user-sim-m1/07-group-nonexistent-id.png`.

**Not a scope request.** That groups/idols have no listing or search is deliberately outside M1 (SPEC F7, and see `DESIGNER-JUDGEMENT.md`). This ticket is only that the copy must stop claiming a route the app does not have. What replaces it says what is true for a pre-cutover table — that these records are reached by id, and where an id comes from — without pointing at Browse.

## Acceptance criteria
The empty state on `/records/groups/<unknown-id>` and `/records/idols/<unknown-id>` no longer tells the operator that Browse lists the records that exist. What it says instead is true of a pre-cutover table: it names how such a record is reached (by id) and does not name a surface that cannot list it.

The `events` (and `venues`) empty state may keep naming Browse, because Browse does list events — the fix is regime- or table-aware copy, not a blanket deletion.

The delivered HTML of `/records/groups/<unknown-id>` contains no sentence claiming any in-app surface lists groups.

`tests/offline/records/page.test.ts` asserts the rendered empty-state copy for `groups` and for `events` separately, and asserts the groups copy does not contain "Browse".

Human-check: open `/records/groups/00000000-0000-0000-0000-000000000000` and follow the sentence's advice — it must lead somewhere that exists. (human-checkable)

# Edit cell: an edit that ends drops keyboard focus to <body> and never gets it back, so the operator's next Tab restarts at the top of the document

## Description
Measured by QA on the BUG-0060 pass (2026-09-03, production build against
staging, bundled Chromium), left unfiled and ruled a defect by the architect
2026-09-04.

**Expected** — LOOK_AND_FEEL quality bar 9: "Keyboard reaches everything. Every
action on every page is reachable by Tab with a visible focus ring." Reachable
means reachable in sequence: an operator editing the third field of a record
tabs to the fourth. This component's own docstring makes the same promise
("the display is a real button, so editing is reachable by Tab and never only on
hover").

**Found**: committing with Enter leaves `document.activeElement` as `<body>`.
The next Tab therefore starts at the top of the document — the whole nav and
every field above, before the operator is back where they were.

**Mechanism, read off the source and consistent with the measurement**
(`src/components/EditableCell.tsx`): `commit()` calls `setEditing(false)`, so
React unmounts the input the operator was focused in. What replaces it is the
resting `<button>`, and while `status.kind === "saving"` that button is
`disabled` (line 217) — nothing on the page can hold focus, so it falls to
`<body>`, and when the button re-enables after the response nothing puts focus
back. `autoFocus` covers the way IN (entering edit mode) and nothing covers the
way out.

**Escape is the same seam and QA did not measure it**: it also calls
`setEditing(false)`, the input unmounts, and the resting button — enabled this
time, since no write started — is not focused either. A fix that returns focus
only on the commit path leaves half the defect standing. Both ways out are this
ticket's.

**Clicking away is NOT this defect.** Blur commits, and an operator who clicked
a link or another cell went somewhere on purpose; stealing focus back from where
they clicked would be a worse bug than the one being fixed. The fix returns
focus to the cell only when the edit ended without the operator moving focus
themselves.

**How it is proved, and how it is not.** Focus is a browser fact and the offline
tier cannot see it: `tests/offline` runs environment `node` with
`renderToStaticMarkup` only (STACK §4 — no jsdom, no Testing Library). So the
offline suite pins what it can (the resting control is present, focusable, and
its markup is unchanged — `tests/offline/records/page.test.ts`'s
"markup-identical to the primitive" assertion must still hold), and the focus
return itself is measured in a browser walk exactly as its absence was: enter
edit mode from the keyboard, press Enter, read `document.activeElement`, press
Tab, see where it lands.

**Depends on BUG-0066** and lands after it. Both tickets change the in-flight
state of the same component in the same file, and BUG-0066's own fix restructures
what renders while `status.kind === "saving"` — the exact window in which focus
is lost here. Two builders folding into that state in parallel collide at the
merge, and the second one's diff is worthless.

## Acceptance criteria
When an edit ends WITHOUT the operator moving focus themselves — committed with Enter, or cancelled with Escape — keyboard focus lands on that cell's own resting control rather than on <body>, and it lands there once the control can hold it (after the write settles, not while it is disabled); the operator's next Tab therefore continues from that field and not from the top of the document. An edit ended by the operator clicking or tabbing somewhere else does NOT pull focus back — focus stays where they put it, and the value still saves. No new commit path, no second save, and no change to what any key does: Enter still commits (single-line), Escape still reverts without writing, leaving the field still commits. The resting markup is otherwise byte-identical, so tests/offline/records/page.test.ts's markup-identical assertion and the ui suite's Look pins stay green as they are. Offline the suite pins what a static render can see (the resting control is present and focusable in every status, and the saved/failed lines still render as they do today); the focus behaviour itself is measured in a browser walk — enter edit mode from the keyboard, press Enter, read document.activeElement, press Tab — the same way QA measured its absence. (human-checkable: the focus position and the Tab landing are browser facts no node-environment test in this repo can assert.)

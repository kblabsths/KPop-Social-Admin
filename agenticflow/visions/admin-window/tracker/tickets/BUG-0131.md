# A queue block still blames a facet in another name that removed none of its rows

## Description
Found attacking BUG-0129 (QA, 2026-09-09), on the surface that fix owns. BUG-0129 is correctly fixed for the `kind` facet; this is the same rule, on the two other facet VALUES that select exactly one block’s own set. Pre-existing, not caused by BUG-0129 — but BUG-0129 is what established the rule and the mechanism (`isNarrowed(filter, within)`), so it belongs on that seam.

**Expected** — LOOK_AND_FEEL, the four states ("a table with no rows and a filter that matched nothing are different states and never share a rendering") and its scoped-zero rule, as BUG-0129 restated it: a block whose rendered set is identical with and without a URL facet may not tell the reader that facet is why it is empty, nor scope its open figure by it.

**Found** — `src/app/queues/page.tsx:288-298`. `ownNarrowing` is `{ kind }` and `isNarrowed` excludes a URL facet only when `filter[facet] === within[facet]` (`src/lib/review/queue-filters.ts:196-203`), i.e. only ever a `kind` facet. But the SIGNAL block’s own set is also selected exactly by two other facet values, structurally and not by fixture accident:
- `shape=entity_link_source_pattern` — `shapesOfKind("signal")` is that one shape and no other (`src/lib/review/shapes.ts:136`), and `kindOf` maps it to `signal`;
- `queue=entity_link` — every row of that shape has `queue: "entity_link"` by `shapeOf` (`src/lib/review/shapes.ts:121-128`), and no other queue can produce a signal row.

Both are rendered chips on this very page: `/queues?shape=entity_link_source_pattern` and `/queues?queue=entity_link` are hrefs in the FilterBar (measured — `[data-facet="shape"] a` and `[data-facet="queue"] a`), so each is one click from `/queues`.

Same two URLs on an EMPTY `review_items` table, signal block rows region:
- `/queues` and `/queues?kind=signal`: `No signals / The resolver files one when a source crosses its stuck-record threshold.`
- `/queues?shape=entity_link_source_pattern` and `/queues?queue=entity_link`: `No items matching these filters / Widen a filter above; the "all" chip on any row shows everything again.` — Expected: the unfiltered card, since neither facet removed a row.

- `/queues`: `nothing open`
- either URL above: `nothing open in this filtered view`

So the reader is told to "widen a filter" on a queue already showing everything it has, and a whole-queue zero is dressed as a scoped one — the exact two states LOOK_AND_FEEL forbids sharing a rendering.

NOT A REGRESSION of BUG-0129: `/queues?kind=decision|signal`, `?kind=decision&status=settled`, `?kind=decision&kind=signal`, `?kind=bogus|Decision|""` were all re-driven and are correct; the block’s whole markup is byte-identical to unfiltered under its own kind facet, populated and empty (three new passing tests beside the pin).

NOTE FOR THE FIX (not a prescription): `within = { kind }` cannot express this — the narrowing a block applies to itself is a SET, and `shape`/`queue` values entail it rather than equal it. `shapesOfKind(kind)` already exists and is the app’s own statement of the shape half. Whatever shape the fix takes, it must not turn a block’s narrowing off wholesale: `?shape=data_conflict_fact`, `?shape=entity_link_fact` and `?queue=data_conflict` DO remove rows from the decision block (measured 5/7, 2/7, 5/7) and must keep naming their scope.

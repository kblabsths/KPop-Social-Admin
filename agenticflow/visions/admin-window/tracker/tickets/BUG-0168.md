# A short non-exhausted page ends paging silently: held leaves the bound grid and PageMore draws 'no further rows'

## Description
Found attacking TASK-0064 (landed b292796), offline, no route needed.

**Repro** (`tests/offline/ui/paging.test.ts`, describe "a page that arrives short of the window", first case — currently pinned `it.fails`, campaign admin-window/BUG-NNNN; flip it to `it` to see it red):

1. A surface with window `size = 50` whose first screen held 50 rows: `{rows: [], held: 50, status: "idle", refusal: null}`.
2. One press. The answer is a legal `PageAnswer`: `{kind: "ok", rows: <30 rows>, offset: 50, exhausted: false}` — i.e. the server says it served a short page AND that the set continues.
3. `requestPage` (src/lib/paging/machine.ts, the `ok` arm) returns `{held: 80, status: "idle", rows: 30}` — it ends in `exhausted` only when `answer.exhausted` is true OR `answer.rows.length === 0`.
4. Render `PageMore` with that state, `size = 50`.

**Expected:** the operator can still reach the rest of the set, or is told the set is complete. Either ending is honest, and the pinning assertion accepts both (control drawn, or `data-paging="exhausted"`).

**Found:** `pageBound("80", 50)` refuses (80 is not a multiple of the window), so `drawsControl` is false in src/components/ui/paging.tsx and the markup is exactly:
`<div class="flex flex-col gap-2"><p data-paging="limit" ...>This view shows no further rows.</p></div>`
— zero controls, and a sentence that contradicts the answer the operator just received. `held` is off the grid `pageBound` enforces and nothing ever puts it back, so paging is dead for the life of the view; the rest of the set needs a reload. That is the exact complaint FEAT-0015 exists to answer ("not being able to load all claims if I want to is a huge oversight").

**Also:** machine.ts already claims the fixed behaviour in prose. The `ok` arm comment reads "A short or empty page is the end of the set, whichever of the two said so first" while the condition tests only `rows.length === 0`. Code and comment disagree; one of them is the bug.

**Two honest fixes, architect to rule — the pin accepts either:**
(a) the driver treats a short page as the end of the set (what its own comment already says), or
(b) the route contract is full-or-exhausted and the driver refuses a short non-exhausted page OUT LOUD (a refusal, `held` unmoved, the control retained) rather than silently dropping the affordance.
What must not stand is the third outcome now shipping: the affordance disappears and the surface says nothing is wrong.

**Not a bounce of TASK-0064.** Its criteria specify the `limit` arm exactly as built, and the widget implements them; the defect is the driver letting `held` leave the grid the bound guard requires. Filed before TASK-0066 lands the route on purpose: the route either has to guarantee full pages or this has to be fixed, and the route is being written now.

**Non-vacuity:** the second case in the same describe is the must-NOT-flag fixture — the identical path with a FULL window (50 rows, `exhausted: false`) leaves `held = 100`, draws the control, and is green today.

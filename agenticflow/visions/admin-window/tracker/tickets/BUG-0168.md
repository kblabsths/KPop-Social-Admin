# A short non-exhausted page ends paging silently: held leaves the bound grid and PageMore draws 'no further rows'

## Description
Found attacking TASK-0064 (landed b292796), offline, no route needed.

**Repro** (`tests/offline/ui/paging.test.ts`, describe "a page that arrives short of the window", first case — currently pinned `it.fails`, campaign admin-window/BUG-NNNN; flip it to `it` to see it red):

1. A surface with window `size = 50` whose first screen held 50 rows: `{rows: [], held: 50, status: "idle", refusal: null}`.
2. One press. The answer is a legal `PageAnswer`: `{kind: "ok", rows: <30 rows>, offset: 50, exhausted: false}` — i.e. the server says it served a short page AND that the set continues.
3. `requestPage` (src/lib/paging/machine.ts, the `ok` arm) returns `{held: 80, status: "idle", rows: 30}` — it ends in `exhausted` only when `answer.exhausted` is true OR `answer.rows.length === 0`.
4. Render `PageMore` with that state, `size = 50`.

**Expected:** the operator can still reach the rest of the set, or is told the set is complete. Either ending is honest, and the pinning assertion accepts both (control drawn, or `data-paging="exhausted"`).

**Found:** `pageBound("80", 50)` refuses (80 is not a multiple of the window), so `drawsControl` is false in src/components/ui/paging.tsx and the markup is exactly:
`<div class="flex flex-col gap-2"><p data-paging="limit" ...>This view shows no further rows.</p></div>`
— zero controls, and a sentence that contradicts the answer the operator just received. `held` is off the grid `pageBound` enforces and nothing ever puts it back, so paging is dead for the life of the view; the rest of the set needs a reload. That is the exact complaint FEAT-0015 exists to answer ("not being able to load all claims if I want to is a huge oversight").

**Also:** machine.ts already claims the fixed behaviour in prose. The `ok` arm comment reads "A short or empty page is the end of the set, whichever of the two said so first" while the condition tests only `rows.length === 0`. Code and comment disagree; one of them is the bug.

**Two honest fixes, architect to rule — the pin accepts either:**
(a) the driver treats a short page as the end of the set (what its own comment already says), or
(b) the route contract is full-or-exhausted and the driver refuses a short non-exhausted page OUT LOUD (a refusal, `held` unmoved, the control retained) rather than silently dropping the affordance.
What must not stand is the third outcome now shipping: the affordance disappears and the surface says nothing is wrong.

**Not a bounce of TASK-0064.** Its criteria specify the `limit` arm exactly as built, and the widget implements them; the defect is the driver letting `held` leave the grid the bound guard requires. Filed before TASK-0066 lands the route on purpose: the route either has to guarantee full pages or this has to be fixed, and the route is being written now.

**Non-vacuity:** the second case in the same describe is the must-NOT-flag fixture — the identical path with a FULL window (50 rows, `exhausted: false`) leaves `held = 100`, draws the control, and is green today.

## Acceptance criteria
RULED (b), the route contract: a paged answer is full-or-exhausted and the driver refuses anything else out loud — see the ruling comment on this ticket and DECISIONS.md 2026-09-10. requestPage reads deps.size (it never did) and grades the ok arm against it on four shapes, each driven offline against a recording stub: rows.length === size with exhausted false appends in the order received, grows held by size, clears the refusal and stays idle; rows.length <= size with exhausted true appends its rows and ends exhausted, the zero-row case behaving exactly as it does today; rows.length < size with exhausted false is REFUSED — the row list comes back identical in length, members and order, held is unchanged so the next press asks for the same bound, status returns to idle, the refusal names the route, and fetchJson was called exactly once; a page LONGER than the window is refused the same way, on any value of exhausted (QA drove 60 rows for a 50 window and it left held at 110). The invariant that kills the class is asserted as a property over that whole matrix and named as such in the test: after any requestPage, either pageBound(String(state.held), deps.size).kind === "ok" or state.status === "exhausted" — held leaves the bound grid only on the final page. PageMore's five arms are unchanged with one case added: an exhausted state whose held is NOT on the grid (the legitimate final short page, e.g. held 80 with size 50) draws the exhausted sentence and data-paging="exhausted", never the limit arm — the limit arm keeps its own case (held = MAX_PAGE_OFFSET + size) and still never says the set is complete. The pin in tests/offline/ui/paging.test.ts, describe 'a page that arrives short of the window', is a plain it() that passes and no it.fails marker remains in that file; because the ruled ending appends nothing, its two non-vacuity assertions are re-expressed against the ANSWER the stub served (30 rows, exhausted false) rather than against the resulting state, and the test says in one line why — an assertion rewritten silently is how a pin stops proving what it was filed for. Its must-NOT-flag sibling (the same path at a full window) stays a plain it and stays green. The window stops being supplied twice with nothing reconciling the copies (QA residual 4): usePageRows returns the size it was handed alongside state and press, so a surface spells the number once and the widget's size prop is fed from the hook rather than retyped, and one offline case drives a consumer-shaped probe proving the value the driver checked against and the value PageMore rendered are the same one. Nothing else moves: the double-press proof, pressing()'s identity arms, fetchJson's Error contract and the four other PageMore arms are green unchanged; machine.ts is still a pure leaf importing only ./bounds and tests/offline/db/layering.test.ts is green over it; the token and primitives guards are green; exactly one fetch( stands under src/components; no route handler, page or component outside src/components/ui/paging.tsx is touched; and the six live parity suites for the two surfaces that will consume this are unchanged.

- 2026-09-11T00:18:46Z [architect] RULING (architect, 2026-09-10): **(b) — the route contract is full-or-exhausted, and the driver refuses a short continuing page OUT LOUD.** Recorded in DECISIONS.md (2026-09-10, 'a paged answer is full-or-exhausted') and in ARCHITECTURE §4.3 kind 3, which gains the bullet 'Full-or-exhausted, on BOTH sides of the wire'.

**Why not (a), which the driver's own comment already claims.** (a) is cheaper and it is what the code was trying to say — but it makes the CLIENT infer the end of a set from a row count. A page that arrives short for any reason other than the set ending (a truncating proxy, a stale deploy, a route mid-rewrite, a mangled body) then renders as 'the set is complete', which is a false totality claim on the one surface that exists because Ben said 'not being able to load all claims if I want to is a huge oversight'. §4.3 exists to make exactly that impossible: an answer is complete or it is refused, never silently partial. The refusal arm costs the operator one retry; the inference arm costs them rows they will never know were missing. And (b) is not a new rule — §4.3 already said 'Complete-or-refuse holds INSIDE a page … never a half-filled ok'; what was missing was its client half.

**What (b) buys beyond this bug.** `held` grows by exactly one window on every continuing page, so `pageBound(String(held), size)` is ok BY CONSTRUCTION until the last page — the invariant in criterion 3. That closes the class, not the instance: residual 5 (usePageRows has no bound guard of its own, so a second consumer can press past the ceiling) and any future surface wiring the widget slightly differently can no longer re-open it, because the driver itself refuses to leave the grid.

**The contract TASK-0066 owes, and why it is chained behind this** (its criteria are amended the same day): the route derives `exhausted === rows.length < CLAIM_WINDOW` from the read it just made, and NEVER emits a short-and-continuing or over-long page. Both sides then hold the same rule and the refusal arm is unreachable in normal operation — which is the point: it exists for foreign data on a wire, like `isPageAnswer`'s arm, not for our own route's ordinary answers.

**Two traps, both of which will otherwise cost a bounce:**
1. **The pin's own non-vacuity assertions contradict this ending.** `tests/offline/ui/paging.test.ts:612-624` asserts `expect(next.rows).toHaveLength(30)` before it checks the markup — true under (a), FALSE under (b), where the refused page appends nothing. The pin is fix-agnostic in its markup assertion and not in its setup. Re-express the two setup assertions against the ANSWER the stub served (30 rows, `exhausted: false`) and say in one line why they moved; do not weaken the markup assertion, and do not touch the must-NOT-flag sibling below it.
2. **Order the arms so `exhausted` wins over `limit`.** A legitimate FINAL page is short: `held` 80 with `size` 50, `status: "exhausted"` — off the grid, and honestly so. `PageMore` must read that as the exhausted sentence, never as the limit arm, or this ticket ships the same wrong sentence it was filed to remove. The limit arm's own case (`held = MAX_PAGE_OFFSET + size`, an IDLE state) is unchanged.

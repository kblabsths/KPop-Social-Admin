# The reference field edits as an entity picker whose choice carries its confirmed match

## Description
**SPEC F12, the edit half.** A field whose kind is `reference` edits through an **entity picker**, never a free-text cell — the type of the thing being edited decides the widget (spec §8: "the widget follows the field's kind").

**What the choice carries, and why it is not a `venue_id`** (ARCHITECTURE §9.2, read from the installed registry 2026-09-08). Events v3 declares `venue` as `{"ref": "<the source's own id for the venue>"}`, and the link stage resolves `(source, 'venues', external_ref)` through `confirmed_matches` into `venue_id` — `venue_id` is produced, never observed. So the picker's choice lands as **the admin-tier observation PLUS its confirmed match**: the decision carries `value.field = "venue"` and `value.ref = <the chosen venue's id, used as the admin source's own external_ref>`, and `settle_review_item` writes the `confirmed_matches` row with `matched_by = 'verdict'` (a value that CHECK already admits) before applying. The apply therefore produces a `venue_id` row link and never a string. **No code path submits a reference field's value as text.**

**The picker's manners:**
- It searches within the referenced entity's own table, through a new read in `src/lib/db/records.ts` (the only layer that may spell a table name is `lib/db/tables.ts` — §4 rule 4). The read is a **named window** (§4.3: `readRows` with an explicit order and limit) and the surface says which window it is showing; it is not a complete-read claim about the whole table.
- It offers **only rows that exist**, and it **never creates an entity** — entity creation is the resolver's, not Admin's. Zero controls in the picker create, insert, or accept an unmatched value.
- **It is not a door** (SPEC F12's second hard limit): it is reachable only from a reference field on a record page already open. It is not a nav item, not a Browse view, not a global search box. ROADMAP question 1 is Ben's alone.
- Empty and null render honestly (LESSONS 1): no matches renders a labelled empty state saying what would fill it, and a row whose display name is null renders the dash with no qualifier rather than a blank line.

**The absence is the normal case and is graded FIRST.** `verdicts` and `settle_review_item` do not exist on staging and will not until Ben installs the handoffs — that is what `main` deploys against. The surface renders its not-provisioned state naming the missing object, offers no control it cannot perform, and nothing throws. **No Admin-side workaround** for the absent schema may be written (spec §10's one forbidden move).

With the function absent the picker **does not render at all**: the reference field is read-only with the reason named — the same degradation every override-regime field takes.

## Acceptance criteria
1. A `kind: reference` field renders a picker and never a text input; a structural test asserts no code path submits a reference field's value as a string (one probe it must flag, one shipped path it must not).
2. The picker's submission payload carries the chosen entity's id as `value.ref` and identifies the field as the registry's `venue`, asserted against the recording stub; the payload contains no free text for that field and no `value.value`.
3. The picker offers only rows the search read returned; it has zero create/insert affordances and refuses an unmatched typed value rather than submitting it.
4. The search read is a named window with an explicit order and limit, and the surface states the window it is showing; it makes no exactness or total claim (§4.3).
5. Zero matches renders a labelled empty state; a null display name renders the dash with no qualifier.
6. With `settle_review_item` absent: no picker control renders, the field is read-only with the reason named, the page answers 200 and nothing throws.
7. No listing page, no global search input, and no second Browse view is added: the sidebar still holds exactly six links and Browse still renders exactly one curated view.
8. `npm run lint`, `tsc --noEmit`, the targeted offline files and the record page's live suite are green.

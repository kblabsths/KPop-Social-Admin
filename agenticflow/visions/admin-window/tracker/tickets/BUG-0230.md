# A host total of "-0" is published as the figure "-0" — a count of no rows wearing a minus sign

## Description
EXPECTED (the bar, positively, as BUG-0229 states it for the derivation and this states for the rendering): a figure this app publishes over a count reads as the number of ROWS it is — a non-negative integer with no sign on it — whatever the host wrote after the slash in Content-Range.

FOUND on the landed BUG-0229 tree (run/admin-window @ acba80cd), measured 2026-09-15 by QA over real HTTP against a production build (npm run test:http harness, app started by tests/http/server-harness.ts, SUPABASE_URL pointed at the loopback PostgREST stub in 'miscounted' mode):

  host answers 200, body [], header 'content-range: */-0'
    /claims -> 200, the Total counts table publishes '-0' in EVERY bucket row
               ('standing_disagreement -0', 'awaiting_link -0', 'awaiting_row -0',
               'escalated -0', 'agreeing -0'), and there is NO refusal anywhere on
               the page (0 elements with data-state=error).
  Controls measured on the same run, all correct: '*/-5', '*/*' and
  '*/9007199254740992' each refuse naming pending_claims with a digit-free total
  region; '*/0' still draws the real zeros with no refusal.

MECHANISM (two halves, either one closes it):
  1. src/lib/db/result.ts:1172 isCount asks 'typeof number && Number.isSafeInteger(count) && count >= 0'. All three are TRUE of IEEE negative zero: Number.isSafeInteger(-0) is true and -0 >= 0 is true. supabase-js reaches the count with parseInt over the text after the slash, and parseInt returns -0 for '-0' and for ANY negative fraction ('-0.5', '-0.9'). So readCount returns {kind:'ok', data:-0}.
  2. src/lib/format.ts:155 count() then renders it with n.toLocaleString('en-US'), and ECMA-402 formats negative zero as the string '-0' (String(-0) would have been '0'; Intl is where the sign survives). The bucket table publishes that string.

Offline repro (no server, no database):
  expect(count(-0)).toBe('0')   // src/lib/format.ts
  Actual: AssertionError: expected '-0' to be '0'.

NOT A REOPEN OF BUG-0229: its derivation is right — -0 IS numerically zero rows, so the guard is not wrong to admit it — and every one of its criteria is green on this tree (QA re-ran all five stored checks). This is the RENDERING half of the same class, in a different module, and the one-line fix belongs wherever the repo prefers to normalise the sign of zero (format.count returning '0' for Object.is(n,-0), or the count seam handing on 'count + 0'). One derivation either way, no enumeration of header spellings.

PINS, both watched RED on this tree 2026-09-15 before they were marked, then flipped to the campaign's it.fails marker so the run branch stays green:
  tests/offline/format.test.ts  'renders a zero as a zero, whatever sign the number carries'
    (RED: AssertionError: expected '-0' to be '0')
  tests/http/absence.http.test.ts  'publishes no minus-signed figure for a host total of "-0"'
    (RED: /claims published a minus-signed figure on a total of "-0": expected 'Total countsbucketclaimsoldeststandin…' not to match /-\s*\d/)

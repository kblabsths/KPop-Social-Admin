# Cycles table: raw snake_case headers mixed with prose, and a cycle's id headed RUN_ID against the glossary

## Description
Found on the M1 endgame designer walk (2026-09-03), walk instance :8771 against staging, 1440x900.

`/cycles`, the CYCLES table, renders this header row verbatim:

    RUN_ID | STARTED | OUTCOME | DURATION | FACTS_EXAMINED | APPLIED | HELD | ESCALATED | ENTITIES_CREATED | CLAIMS_LINKED | CLAIMS_REREJECTED | ERRORS | ERROR_SUMMARY

Two rules break here.

**1. The glossary.** LOOK_AND_FEEL.md pins `cycle` (resolver) and `run` (adapter) as separate nouns — "two different producers, two different tables ... synonyms erase it". The first column of the CYCLES table, sitting on a page whose other section is headed ADAPTER RUNS, is headed **RUN_ID**. The one place the operator most needs the two nouns kept apart is the page that shows both, and there the cycle's identifier is called a run.

**2. One header row, two naming systems.** Seven headers are the app's own words (STARTED, OUTCOME, DURATION, APPLIED, HELD, ESCALATED, ERRORS); six are raw database column names (RUN_ID, FACTS_EXAMINED, ENTITIES_CREATED, CLAIMS_LINKED, CLAIMS_REREJECTED, ERROR_SUMMARY). LOOK_AND_FEEL's `micro` step is a SANS label ("the eyebrow label above a value"), and Voice bar 5 keeps machine identifiers verbatim in MONO — a snake_case name uppercased into a sans micro label is neither.

The app already contradicts itself about this: the Dashboard renders the same cycle data under STARTED / OUTCOME / APPLIED / ESCALATED / ERRORS / ERROR, and `/cycles`' own cycle-health gauge renders the label **FACTS EXAMINED** (no underscore) a few thousand pixels below the table that says FACTS_EXAMINED. Two builders who never met produced two vocabularies for one column — exactly what the Look exists to prevent.

Evidence: `agenticflow/tracker/evidence/designer-walk-m1/cycles-light.png` (the header row), `dashboard-light.png` (the same columns, named in prose), `cycles-dark.png`.

Not prescribing which vocabulary wins — but the cycle's identifier is a cycle's, and one table should not speak both.

**What this adds that BUG-0040 does not.** BUG-0040 is about WHERE the two sections sit on `/cycles` (the adapter runs are 4,419px below the fold); this one is about what the cycles table's columns are CALLED. Same file, disjoint changes — 0040 moves markup, 0044 rewrites thirteen strings. If 0040 lands first, every word named here is still wrong.

## Acceptance criteria
The CYCLES table's identifier column is not called a run. (Glossary: `cycle` (resolver) / `run` (adapter) are two nouns; a cycle's id is a cycle's id.)

Every header in that one table comes from the same naming system: either all the app's own words, matching what the Dashboard already calls these columns, or all verbatim database names rendered as the Look renders machine identifiers. No row mixes the two.

`FACTS EXAMINED` on the cycle-health gauge and the corresponding table header read the same way as each other.

`tests/offline/cycles/page.test.ts` asserts the rendered header set, so a later column addition cannot reintroduce a raw name silently.

Human-check: read the CYCLES header row aloud — it sounds like one person wrote it, and nothing on the page calls a cycle a run. (human-checkable)

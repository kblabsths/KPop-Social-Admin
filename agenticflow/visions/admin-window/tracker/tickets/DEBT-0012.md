# readPopulation issues all three shape counts on every narrowed /queues URL, including the two the URL's own kind cannot render

## Description
M2 structure walk finding (architect, 2026-09-09), measured on run/admin-window.

`readPopulation` (`src/lib/db/review-items.ts:203-231`) maps over `SHAPES` — all three of them — and issues one `readCount` per shape, unconditionally:

    const answered = await Promise.all(
      SHAPES.map((shape) => readCount(T.reviewItems, (client) => countQuery(client, shape), db)),
    );

It is called from `readReviewQueues` (:291) whenever `narrows(filter)`. On `/queues?kind=signal` only `entity_link_source_pattern` can render a row, and on `?kind=decision` only the other two — so one or two of the three counts are read, folded into a `population` entry, and thrown away by a page that renders no block of that kind.

They are `head: true` counts issued in parallel, so the cost is bounded: two extra round trips on a `?kind=`-narrowed URL, none on the others. No number on screen is wrong — this is waste, not a defect, which is why it is P3 debt and not a bug.

It is filed because it is the same shape as the two costs M2 did measure and did file: BUG-0138 (`/claims` reading the whole population every request, ~14 sequential round trips, 2.9-3.8s warm) and BUG-0139 (`/sources` reading runs once per registered source, ~9 round trips, 2.0-2.3s warm). A read that answers questions the URL did not ask is the class those two belong to, and this is the third instance.

## Acceptance criteria
**Amended 2026-09-09 (architect) — criteria 1 and 5 only.** Criterion 1's
original direction ("a count per shape OF THAT KIND, and no others") was
BACKWARDS, and the builder measured it before implementing it. Criteria 2, 3, 4
and 6 are unchanged.

1. **`readPopulation` issues a count only for the kinds whose population the
   page's rendering actually CONSULTS — the kinds the URL NARROWS, which is the
   opposite of the kind it NAMES.** `isSurfaceNarrowed`
   (`src/lib/url/narrowing.ts`) ANDs fact 1 (structural: can any facet of this
   URL remove a row of this kind at all) with fact 2 (this kind's whole-table
   population), so for a kind whose fact 1 is false no count could change a
   word its block renders — that is the read this ticket is about. Both blocks
   ALWAYS render (`src/app/queues/page.tsx` maps `KINDS`), and the kind a URL
   EXCLUDES is exactly the one whose zero has to be explained: its rows are all
   gone from the filtered read, which is precisely the count BUG-0133 made
   load-bearing. So `/queues?kind=signal` skips the SIGNAL count and issues the
   DECISION ones. The set is one call of the same predicate the page asks per
   block — `isNarrowedBeyond(filter, narrowingOfKind(kind))` per kind — declared
   once beside that predicate in `src/lib/review/queue-filters.ts` and imported
   by `src/lib/db/review-items.ts` rather than retyped, so the set the read
   ISSUES counts for and the set the page CONSULTS cannot come apart.
   A kind that was not counted answers a declared THIRD state, distinct from a
   refusal (nothing failed, nothing to report) and from a counted zero (a zero
   is a claim about the table, and this state makes none); its block falls back
   to fact 1 alone, which is `false` by construction for exactly those kinds.

2. The bare `/queues` still costs exactly ONE query — an unnarrowed read IS the
   whole table, so its own rows are the population (the property the function's
   own docstring states today).

3. Every population figure and every empty-state arm on `/queues` is identical
   to today's for every facet combination the existing suites cover, including
   the four states BUG-0129/0131/0133 settled and the per-kind refusal reporting
   BUG-0135 landed. A kind whose counts were not read renders exactly what it
   renders now, because the page never showed them.

4. A refusal of one shape's count still says nothing about the others, and is
   still carried per kind as its own `DbResult` reported beside the rows —
   BUG-0135's ruling, unchanged. The third state is NOT a refusal and reports
   nothing.

5. **The saving is graded, not asserted, and the numbers are measured rather
   than authored.** A test counts the reads issued against the stub client for a
   bare `/queues`, a `?kind=`-narrowed URL and a non-kind-narrowed URL, and
   names WHICH count legs make up each number — not merely how many, because the
   stub answers per-shape counts BY POSITION and a URL that skips a shape would
   otherwise let a count answer the wrong leg. `review_items` reads = 1 row leg
   + one count leg per shape of a narrowed kind (decision has two shapes, signal
   one). Measured on run/admin-window, 2026-09-10:
   - bare `/queues` — **1** (no count issued at all; criterion 2)
   - `?kind=decision` — **2** (was 4): the signal kind's single shape
   - `?kind=signal`, `?queue=entity_link`, `?shape=entity_link_source_pattern` —
     **3** (was 4): the decision kind's two shapes. The last two IMPLY the
     signal kind, so they narrow it no further than it narrows itself.
   - `?status=open`, `?source_id=<a carried source>`, `?queue=data_conflict`,
     `?shape=data_conflict_fact` — **4**, unchanged: no kind's own narrowing
     implies a status or a source, and the decision kind spans both queues and
     both fact shapes, so BOTH blocks have a zero to explain and all three
     counts are load-bearing.

6. `npm run lint` and `tsc --noEmit` clean.

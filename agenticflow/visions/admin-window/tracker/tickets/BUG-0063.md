# Claims: the window line renders a count it never took — data-window-held="0" on a failed read

## Description
Found while re-checking admin-window/BUG-0041 (whose diff introduced the line) on run/admin-window at 02a2aed. Not a defect of BUG-0041's criteria — the window bound, the stated cap, the bucket-count parity and the geometry all hold; this is the error path the criteria never drive.

REPRO (offline, deterministic, no database):
  npx vitest run --project=offline tests/offline/claims/page.test.ts -t "claims no count it never took"
The test renders /claims with the pending-claims read refused (permission denied) and again with a transport failure, both via the stub client, and reads the window line's hooks.

Expected: on a read that returned nothing, the page publishes no count for that read. That is this page's own rule and the app's: the bucket table drops `data-bucket-claims` entirely on the same failed read ("Never a zero standing in for a table nobody could read", tests/offline/claims/page.test.ts:722), ARCHITECTURE.md:338 promotes it — "a null count is a refusal, never a zero" (LESSONS class 2, BUG-0007) — and LOOK_AND_FEEL.md bar 4 / states 3-4 forbid a failed or absent read rendering as a zero. The sibling surface pins the stronger form: src/app/cycles/page.tsx:970 renders the runs window line only when the read is ok, and tests/offline/runs/page.test.ts:471 grades it ("claims no window it never read": absent on refused/absent, present on an EMPTY window, which is still a window the page looked in).

Found: src/app/claims/page.tsx:513-520 renders the paragraph on the error branch too, with `held` computed from `shown`, which the same function sets to `[]` when the read is not ok (src/app/claims/page.tsx:487-497). Observed markup, refused read:
  <p data-window="claims" data-window-limit="50" data-window-held="0" data-window-truncated="false" ...>Oldest first — ... A window of at most 50 rows, not the whole view.</p>
So "0 claims held" is emitted for a read that counted nothing, and 0 is a value this hook can produce in NO other state: a genuinely empty matching set renders the Empty card with no window line at all (src/app/claims/page.tsx:507-511). Every reader of that attribute seeing 0 is looking at a failed read being told it is an empty one.

Why it is worth fixing rather than tolerating: `data-window-held` is the hook the live parity oracle grades this page by (tests/live/claims.live.test.ts:272) — a count hook that answers confidently on a failed read is how a false green is manufactured, which this campaign has already paid for twice (BUG-0056, BUG-0057). The visible prose has the milder version of the same fault: it states "A window of at most 50 rows, not the whole view" above a table that could not be read, i.e. it describes a window the page never looked in.

FIX IS OPEN, one clause either way — drop the attribute on a non-ok read, or drop the whole line the way /runs does. The pinned test grades only the count, so either satisfies it. Note for the architect: /cycles renders ITS list window line in every state too (src/app/cycles/page.tsx:1219-1232), so choosing the /runs form here makes three surfaces two-to-one; that cross-surface consistency call is yours, not the pin's.

PIN: tests/offline/claims/page.test.ts, describe "absence and failure", test "claims no count it never took when the list's read fails" — landed as a strict `it.fails` xfail (this repo's idiom, cf. tests/offline/edit/route.test.ts:221), so it is green while the divergence lives and reddens the day it is fixed. The builder flips it back to a plain `it(...)` with the fix, in the same commit.

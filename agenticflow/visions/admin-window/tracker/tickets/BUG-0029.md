# The offline suite is flaky in a fresh worktree: its slowest test sits 6% under vitest's 5s default, so receipts go red at random

## Description
Found while computing the evidence receipt for BUG-0024. The SAME TREE produced a RED receipt and then a GREEN one, minutes apart, with no code change between them — receipt.py runs `npm test` in a fresh private worktree, and the offline suite is not fast enough there to fit its own default timeout.

## Repro (two runs, same tree hash 853df590..., git head 00a53c8)

1. `python3 agenticflow/scripts/receipt.py BUG-0024` -> `receipt RED`. `npm test` exit 1, two failures, NEITHER related to the ticket:
   - `tests/offline/claims/page.test.ts > QA: the whole tab x bucket x source x domain cross-product > renders exactly the claims and counts the view holds, on the buckets tab` -> `Error: Test timed out in 5000ms.` (page.test.ts:943)
   - `tests/offline/toolchain.test.ts > type-check program` -> `Error: Command failed: .../tsc --noEmit --listFilesOnly --tsBuildInfoFile ...` (toolchain.test.ts:113)
2. `python3 agenticflow/scripts/receipt.py BUG-0024` again, nothing changed -> `receipt GREEN`, both commands exit 0.

## Expected vs Found

Expected: `npm test` is deterministic — a green suite is green in the primary tree and in a receipt worktree alike, because a receipt is the factory's proof that a check passed on the code that shipped.
Found: it is timing-dependent, and the margin is measured, not guessed.

- vitest.config.mts:22-28 — the `offline` project declares NO `testTimeout`, so every offline test runs on vitest's 5000ms default. The `live` project sets 60_000 and `http` 180_000; only offline was left on the default.
- In the WARM primary tree that same cross-product test measures **4712ms** of a 5000ms budget — a **6% margin** (full run: 49 files, 1436 tests, exit 0; the file totals 7033ms across 59 tests). A receipt worktree is always colder — no vite transform cache — so the margin is routinely negative there. That is the whole defect: a test written to run 4.7s under a 5s cap is a coin flip, not a test.
- `tests/offline/toolchain.test.ts > type-check program` spawns a real `tsc` child process (toolchain.test.ts:113) and fails under load; BUG-0024's builder independently measured it failing 2 of ~12 full runs and passing 10 straight afterwards.

## Why it matters (the cost is already paid once)

A ticket cannot close without a green receipt, so a suite that reddens at random blocks arbitrary closes on the run branch and burns a lane cycle each time — exactly the deadlock pattern the campaign already hit once. It also poisons the signal: a genuinely broken fix and a coin flip look identical in a RED receipt.

## The bar (not the implementation — the fix is the builder's call)

No offline test may sit within 2x of its timeout budget. Either raise the offline project's `testTimeout` to a value the slowest test cannot approach, or split the cross-product loop at page.test.ts:942-945 into per-tab/per-bucket cases so no single `it()` carries 59 renders — and make `toolchain.test.ts`'s tsc probe robust to a loaded machine (it shells out to a real compiler; a 5s default is not a budget for that). Re-measure and state the new slowest offline test and its margin in the handoff.

Do NOT fix this by deleting or skipping either test: both assert real behaviour (the claims cross-product is the page's whole filter matrix; the toolchain probe is what makes the offline/live glob separation structural).

# A column-absent envelope with no message string has its column mined out of the app's own JSON rendering of the error record — classify names a column nothing ever mentioned

## Description
**Module:** `src/lib/db/result.ts` — `messageOf` (lines 160-173) feeding `columnFromMessage` at `classify`'s COLUMN-ABSENT arm (line 715).

**Expected** (`messageOf`'s own docstring, src/lib/db/result.ts:151-157): "The `message` field alone, verbatim — what CLASSIFICATION reads. Kept separate from the full account below on purpose: the column-absent arm mines this string for the column the database named, so it must see exactly what the database put in `message`. A `details` payload quoting some other identifier would otherwise be read as the missing column." And `classify`'s header as admin-window/BUG-0181 left it: "A message naming no column ... falls back to the object the query asked for rather than putting a stranger's text where an object name belongs."

**Found:** when `message` is NOT a string, `messageOf` falls through to `JSON.stringify(error)` (line 167) and returns the WHOLE error record serialized. `columnFromMessage` then takes the first quoted run of that JSON — which is a **field NAME** of the envelope, not anything the database said about a column — and since a JSON key is identifier-shaped it passes `COLUMN_NAME` and is admitted into `missing`. The envelope's author chooses the key and its order, so the author chooses the column half of `missing`; with no author at all, the app still fabricates `review_items.code` out of its own serialization.

MEASURED (qa, 2026-09-11, run/admin-window at 24eb1b5, the landed BUG-0181; probe `agenticflow/tracker/evidence/BUG-0181/attack.ts`, driven with `./node_modules/.bin/vite-node`), `classify(error, "review_items")`:

| error | `missing` returned |
| --- | --- |
| `{code:"42703"}` (no message field) | `review_items.code` |
| `{code:"42703", message:null}` | `review_items.code` |
| `{code:"42703", message:12}` | `review_items.code` |
| `{code:"42703", message:{text:'column "severity" does not exist'}}` | `review_items.code` (the real column in the nested object is NOT what is read) |
| `{contact_support_at_evil_example:1, code:"42703"}` | `review_items.contact_support_at_evil_example` |
| `{code:"42703", details:'column "otherthing" does not exist'}` | `review_items.code` |

**Reachability is BUG-0181's own path, one field NOT SET.** Driven end to end through the real `@supabase/supabase-js` client with a stubbed transport (a 400 whose JSON body is the envelope) into `readRows("review_items", ...)` — postgrest-js hands the parsed body back AS the error object, so no `message` key is required of it:
- body `{"code":"42703"}` -> `{kind:"not_provisioned", missing:"review_items.code"}`
- body `{"contact_support_at_evil_example":1,"code":"42703"}` -> `{kind:"not_provisioned", missing:"review_items.contact_support_at_evil_example"}`

That value is then inlined into app-authored prose with no box around it: `src/app/api/admin/records/[table]/[id]/route.ts:325` and `:408` and `src/app/api/admin/review-items/[reviewItemId]/settle/route.ts:149` all build `` `${result.missing} is not present in this database` `` into a 503 JSON body — so the operator is told a column named `code` (or a stranger's chosen word) is not present in a database that has no such column and was never asked about one.

**Not culpable to admin-window/BUG-0181**, which implemented its six criteria faithfully (all verified green by QA on the landed tree, including the architect's four measured envelopes and the four honest spellings). Its grammar gate is on the mined column; this is about the string that is mined IN THE FIRST PLACE not being the database's message at all. The class pre-dates the fix (`messageOf`'s JSON fallback is unchanged by it) and the fix could not have seen it: every criterion-named envelope carries a string `message`.

**Not admin-window/BUG-0182** (the account's per-line counting of one document) and **not admin-window/DEBT-0020** (the transport account's twice-stated cause): both are about the `error` arm's prose. This is the `not_provisioned` arm's `missing`, and neither ticket's fix touches `messageOf`'s non-string fallback.

**Repro (exact), offline:**
1. `./node_modules/.bin/vitest run --project=offline tests/offline/db/result.test.ts -t "mines a column only out of what the database put in message"`
2. Watched RED on 24eb1b5 before this ticket was filed: `AssertionError: no message field at all: expected { kind: 'not_provisioned', missing: 'review_items' } ... Received missing: "review_items.code"` (tests/offline/db/result.test.ts:328).
3. The test is PINNED on the run branch as `it.fails(...)` naming this ticket, so the suite is green while it is open; lifting the pin is part of the fix (check 2 greps for the unpinned spelling).

**For the architect, not decided here:** the honest fix may be as small as "no string `message` means no column" (return the queried object), or may extend to what the `error` arm should say for a record with no message — which is `errorMessage`'s question, not this one. The twin this fix must keep (LESSONS 8) is in the pinned test already: an envelope whose `message` really is `column "severity" does not exist` still qualifies to `review_items.severity`.

## Acceptance criteria
1. PROVENANCE DECIDES WHAT MAY BE MINED, and it is asked in the shape admin-window/BUG-0179 already established for the account (`AccountPart = {raw, serialised}`: the one fact no amount of reading the text could recover is WHO WROTE IT). src/lib/db/result.ts gains ONE accessor — `databaseMessage(error): string | null` — returning the words the DATABASE authored (`typeof error === "string"`, or `typeof record.message === "string"`) verbatim, and `null` when it authored none, which is exactly the state `messageOf` answers by rendering the whole value through `JSON.stringify`. `classify`'s column-absent arm mines `databaseMessage(error)`, never `messageOf(error)`: `null` means no column was named, so the verdict is the arm that already exists, `{kind:"not_provisioned", missing}` naming the object the query asked for. On QA's six measured envelopes, `classify(error, "review_items")` returns `review_items` for all five message-less shapes — `{code:"42703"}`, `{code:"42703", message:null}`, `{code:"PGRST204", message:12}`, `{code:"42703", message:{text:'column "severity" does not exist'}}` (the nested object names a REAL column and is still not mined: the app rendered it, the database did not say it), `{contact_support_at_evil_example:1, code:"42703"}` — and `review_items.severity` for the honest one. No JSON key, and no field name an envelope's author chose or ordered, can ever be the column half of `missing` again.

2. THE HONEST PATH IS BYTE-IDENTICAL AND BUG-0181's GRAMMAR TABLE IS UNTOUCHED. `COLUMN_NAME_GRAMMAR`, `COLUMN_NAME`, `UNQUOTED_COLUMN_REFERENCE`, `lastSegment` and the body of `columnFromMessage` are unchanged byte for byte — this ticket changes WHICH STRING is handed to that gate, never the gate. All four spellings a real Postgres/PostgREST column-absent message uses still qualify, qualifier dropped: `Could not find the 'severity' column of 'review_items' in the schema cache`, `column "severity" does not exist`, `column "severity" of relation "review_items" does not exist`, `column events.badcol does not exist`. The `column === missing` and `missing.endsWith(".<column>")` de-duplications are unchanged. The rule is about the TYPE of `message`, never its length: `{code:"42703", message:""}` is a message the database authored that names no column, and still falls back to the table by the path it already takes. The four FOREIGN_COLUMN_ABSENT_ENVELOPES still return `{not_provisioned, review_items}`, and every pre-existing verdict in tests/offline/db/result.test.ts is green with none rewritten.

3. THE OTHER CLASSIFICATION READ MOVES WITH IT — one question, asked one way. `MISSING_OPERATOR.test(messageOf(error))` at `classify`'s function arm is the only other place the CLASSIFICATION reads a message, and it reads it for the same reason: what the database said about what is missing. It is asked of `databaseMessage(error)` too (a `null` message tests nothing and makes no operator claim), so a `42883` envelope carrying no string `message` stays the absent function the caller asked for — the file's own standing rule, "a 42883 that says nothing at all is still an absent function to a caller that asked for one". Its MUST-NOT-FLAG twin (LESSONS 8) is unmoved: an honest `{code:"42883", message:"operator does not exist: timestamp with time zone ~~* unknown"}` on a function read still refuses the absence and stays `kind:"error"`, and every 42883 case already in the suite (the TABLE-read arm, the asked-object rule, admin-window/BUG-0058 and BUG-0080) is green with none rewritten.

4. THE `error` ARM DOES NOT MOVE — QA's second question is ALREADY ANSWERED by admin-window/BUG-0179's serialised flag, and the answer here is no-motion, not a new rule. The same non-string-`message` record is decided for the account in two places that both stay exactly as they are: `accountParts` returns one part `{raw: messageOf(error), serialised: serialisedWhole(error)}`, which `partOfAccount` replaces with `serialisedInstead(raw)` — counted, never quoted — and `codeOfAccount` returns `null` in that state so the whole document does not trail the clause that counted it. So `messageOf` KEEPS its signature and its return value for every input, `JSON.stringify` fallback included (a builder who makes it return `null` or `""` for a non-string message blanks the account and re-opens admin-window/BUG-0173 and BUG-0016); `serialisedWhole` keeps its exact meaning — a RECORD with no string `message` — so a thrown number or a thrown string does not newly become "serialised"; `serialisedInstead`, `documentInstead`, `framesInstead`, `REFUSED_WITHOUT_WORDS`, `withoutSecrets` and `errorMessage`'s assembly are byte-untouched. Pinned by the suite: the 114-character envelope is still counted and still quotes none of its keys or values, and ACCOUNT_FIXTURES still grades ten fixtures, five reduced and five untouched, with none rewritten.

5. ONE PREDICATE, IN ONE HOME, AND NO FOURTH QUESTION. "Did the database author this string?" is spelled ONCE in src/lib/db/result.ts and both readers go through it: `messageOf` is expressed through `databaseMessage` (its `JSON.stringify` path is what `databaseMessage` returning `null` MEANS), so the account's provenance and the classification's provenance cannot drift apart — one question answered two ways is the class this file keeps catching (admin-window/BUG-0179's own per-granularity note, ARCHITECTURE.md Common violations rows 15 and 20). It is not re-asked by any consumer, not copied into src/lib/paging/**, src/components/** or the API routes, and no call site is asked to isolate a value that is already an object name. Nothing is added to `partOfAccount`'s three questions. Nothing on this path scans for `<`, `!DOCTYPE`, `html`, a codepoint class, a runtime vocabulary or a length cap — provenance is asked of the VALUE's shape, never of its text.

6. THE DOCSTRINGS DESCRIBE THE LANDED CODE. `messageOf`'s doc no longer claims it is "what CLASSIFICATION reads" — it is what the ACCOUNT reads, and it says which accessor classification reads instead and why (the contradiction this ticket was filed on). `classify`'s header, which BUG-0181 left saying that a message naming no column falls back to the object the query asked for, says the same of a value that carries no message at all. `columnFromMessage`'s doc says the string it receives is the database's own, so its "first quoted run anywhere" is bounded by provenance as well as by the grammar.

7. THE PIN FLIPS, ON THE STRICT SPELLING QA WROTE. `it.fails("mines a column only out of what the database put in message", …)` in tests/offline/db/result.test.ts becomes `it(…)` and is green with its five message-less shapes and its twin (a real `column "severity" does not exist` still qualifying to `review_items.severity`) UNCHANGED — the test is QA's, not the builder's to re-scope; its docstring stops saying PINNED and states the landed derivation. One case is added beside it for criterion 3's pair: a function read of `{code:"42883"}` with no string message is `{not_provisioned, <fn>}`, and the honest operator message on the same read is still `kind:"error"`.

8. The diff is the two files of the touch scope and nothing else (a builder is concurrently in src/components/**/window-line.tsx on admin-window/BUG-0183 — no overlap); `npm run lint` and `npm run typecheck` are clean and the targeted suites are green. Targeted rather than the full suite for BUG-0181's measured reason: this changes one verdict's STRING for message-less input only, the KIND never moves, and tests/offline/absence/pages.test.ts is the consumer sweep that would see a changed not-provisioned surface (409 tests, 8.5s measured on this tree today).

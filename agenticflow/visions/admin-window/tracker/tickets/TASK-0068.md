# Browse: the events window takes an offset, and its paging route handler answers one page

## Description
**Modules:** `src/lib/db/browse.ts` (the events window gains an offset; the three join legs follow it) and a NEW route handler `src/app/api/admin/browse/rows/route.ts`. `PAGE_ROUTES.browse` is its ONE spelling.

Browse's shaping is already shared — `joinBrowseRows` in `src/lib/browse/rows.ts` — so this ticket has no extraction to do. It is TASK-0065 and TASK-0066 in one, because the read change is small and the handler is the same shape as the claims one; read that handler before writing this one and follow it exactly (LESSONS 5: the second copy is what drifts — where the two handlers share a step, the shared step is `src/lib/paging/**` or `src/lib/db/paging.ts`, not a paste).

**Interface contract:**

```ts
// src/lib/db/browse.ts
export async function readRecentEvents(
  view: BrowseView,
  db?: SupabaseClient,
  offset?: number,           // default 0 — every existing caller unchanged
): Promise<RecentEventsListing>;
```

The events window keeps its total order — `view.sort.field` then `event_id`, same direction — and ends in `.range(offset, offset + view.window - 1)` in place of `.limit(view.window)`. **The three legs are per PAGE, not per table:** venues, provenance and sources run over the ids of THIS page's window exactly as they run over the first window's today, they stay COMPLETE reads (§4.3 kind 1: "the latest decision" is only knowable over the complete log), and a leg that refuses is still reported on its own — a leg that renders no row of its own may not decide the surface's state (common violations row 14).

```ts
// GET /api/admin/browse/rows?<the view's own params>&offset=<n>
// -> 200 PageAnswer<BrowseRow>  |  400 PageAnswer refused  |  the gate's redirect
export async function GET(request: Request): Promise<Response>;
```

Same five steps, same order, as the claims handler: `requireAdmin()` first; the view and its columns resolved by `src/lib/browse/views.ts` — the ONE definition layer, so a request cannot name a view or a column the config does not carry; `pageBound(raw, view.window)`; `readRecentEvents(view, undefined, offset)`; `pageAnswerOf(listing.events, offset, view.window)`.

**The two legs that fill columns travel with the answer or not at all.** A page whose provenance leg refused must not silently render events with an empty Sources column: carry the two `DbUnavailable | null` notes in the answer's `ok` arm (extend the answer for this surface with a `notes` field on the `ok` arm ONLY, declared in `src/lib/paging/bounds.ts` beside `PageAnswer` so both sides know it) and render them the way the first screen renders them today. If that turns out to cost more than it buys, file the question blocked — do not silently drop the notes.

**GET only. No service-role material crosses to the client.** Extend `tests/http/paging.http.test.ts` (TASK-0066's file) with this route rather than starting a second one.

**Browse does not gain width here** (SPEC F14, ARCHITECTURE §4.3 kind 3): one curated view, the same column selector, no second view, no table picker, no SQL runner, no search box. Paging lets the operator walk further down the view that exists.

## Acceptance criteria
readRecentEvents accepts an optional offset defaulting to 0 and issues its events window as order(view.sort.field), order(event_id), range(offset, offset + view.window - 1) — asserted against the offline stub at offset 0 and at one window in, including that the three legs run over exactly that page's ids and that each still reports its own refusal separately. GET /api/admin/browse/rows answers a PageAnswer<BrowseRow> as JSON: ok with that page's rows and exhausted as the biconditional the driver enforces — exhausted === rows.length < view.window — so the handler answers either a full page that continues or a page of at most view.window rows that says the set is exhausted, and NEVER a short page with exhausted false or a page longer than the window (admin-window/BUG-0168's ruling, ARCHITECTURE §4.3 'full-or-exhausted, on BOTH sides of the wire': requestPage refuses any other combination out loud, so a route that emits one turns every press on /browse into a refusal). Both edges are driven offline: a read returning view.window rows answers exhausted false, a read returning fewer — including zero — answers exhausted true. not_provisioned naming events against a PGRST205 stub; error carrying the database's own message.

THE URL's OFFSET REACHES NOTHING BUT pageBound, AND A REFUSED BOUND REACHES NO READ. The handler imports pageBound and OFFSET_PARAM from src/lib/paging/bounds.ts and does its own arithmetic on the raw parameter nowhere: the route file contains no Number(, no parseInt and no parseFloat, and the only value that reaches readRecentEvents' offset is the number pageBound returned on its ok arm. Driven offline against a stub that RECORDS every read it is asked for, the whole refusal table answers HTTP 400 with kind "refused" naming the reason and the bound AS SENT and leaves the recorder empty — no offset param at all, "", "abc", " 50", "+50", "050", "50.0", "1e2", "-50", "49", "51", "100050" — while the one canonical bound in the same table ("50", one view.window) is served and DOES record exactly one read, so the table cannot pass by refusing everything. This is the measured failure it exists to stop (QA, TASK-0065 close): Number("abc") is NaN, .range(NaN, NaN) is answered by staging with an ok page of zero rows, and a zero-row ok page is exhaustion — a malformed URL would render to the operator as a set that has ended rather than as a refusal.

THE ROUTE OWNS THE SHAPE OF WHAT IT SERVES. isPageAnswer is a cheap gate on the CLIENT — it checks the discriminant and each arm's own fields and cannot see inside a row — so the row type is established here: the handler's declared return is its own PageAnswer<BrowseRow> (rows: BrowseRow[], offset: number, exhausted: boolean) written on the answer rather than inferred, and its offset ECHOES the bound the request carried, asserted on every ok fixture to equal the offset the request sent and the offset the read was given, never a number recomputed from rows.length. Every body the handler emits on all four arms is fed back through isPageAnswer in the offline suite and accepted.

A venue or provenance leg that refused is carried in the ok answer and rendered as the first screen renders it, never dropped. requireAdmin() is the first statement of the handler body, an unauthenticated GET never reaches it (asserted over HTTP against the built app), the route accepts GET only, and the client-bundle scan finds no SERVICE_ROLE, no service_role, no STAGING_SUPABASE and no staging URL. Browse gains no view, no column and no control: BROWSE_VIEWS still holds exactly one entry and /browse's live parity suite is green.


THE SEARCH-PARAM ADAPTER IS ONE LEAF, AND ITS RECORD HAS NO PROTOTYPE. The `URLSearchParams` -> Next-shaped-`searchParams` adapter TASK-0066 left inside the claims route (`searchParamsOf`) is LIFTED, not copied: `src/lib/url/search-params.ts` declares it exactly once — a pure domain leaf beside the other URL rules (ARCHITECTURE §4 rule 7; it imports nothing, reaches no database and no `process.env`), typed with the `UrlParams` that `lib/url` already owns — and BOTH paging routes import it from there. The claims route keeps no copy and declares no adapter of its own, so exactly one file under `src/` declares `function searchParamsOf` and it is that leaf. Its record is built with `Object.create(null)`, so a key the URL carries is always an OWN property and can never reach an object's prototype: given `?__proto__=a&__proto__=b` the adapter answers a record whose `__proto__` entry is the own array `["a","b"]` (`Object.getOwnPropertyNames(params)` includes `__proto__`, `Object.getPrototypeOf(params)` is `null`) and no object's prototype is changed — measured today as a live hazard, not a hypothetical: on a plain `{}` that same URL assigns an ARRAY through the `__proto__` setter and re-parents the params object (QA walked `?__proto__=x&offset=50` on TASK-0066's close; it answered 200 because every facet happens to be an own property). Pinned in a new `tests/offline/url/search-params.test.ts`: the `__proto__` case above, repeats becoming an array in the order sent (`?bucket=a&bucket=b` -> `["a","b"]`, and the reading leaf then takes the first), a single key, an empty value (`?bucket=`), and the empty query. Behaviour for every non-`__proto__` key is byte-for-byte what the claims route answered before the lift, and no consumer reads the record through `params.hasOwnProperty` (a null-prototype record has none — `Object.hasOwn` or `in` instead): `tests/offline/paging/claims-route.test.ts` is green UNCHANGED, its facet pass-through and its standing-tab seam cases included.

A GATED ANSWER IS NEVER STORABLE — THE ROUTE SAYS SO ITSELF. Every dynamically rendered page in this app already answers `Cache-Control: private, no-cache, no-store, max-age=0, must-revalidate` because Next sets it (`node_modules/next/dist/server/base-server.js`), while a Route Handler answers with NO `Cache-Control` at all unless it writes one — so the rows BEHIND the gate are the only admin answers a browser store, a corporate proxy or anything later placed in front of Railway may keep, and the first screen and its continuation would be one surface under two cache policies. The value is declared ONCE — `PAGE_ANSWER_CACHE_CONTROL` in `src/lib/paging/bounds.ts`, beside `PAGE_ROUTES` and `OFFSET_PARAM`, the vocabulary both routes already share — spelled exactly as Next spells it, never a second string typed into a route. The browse route sets it on EVERY answer it emits: the `ok` page, `not_provisioned`, `error` and the 400 refusal alike, asserted offline on all four arms via `response.headers.get("cache-control")` and over HTTP against the built app in `tests/http/paging.http.test.ts` on a signed-in GET and on a refused bound. (The claims route inherits the same constant under admin-window/BUG-0171, which is chained behind this ticket because this ticket is what declares it.)

THE PAGE'S ROW COUNT IS THE WINDOW READ'S OWN COUNT — NOTHING DROPS A ROW AFTER `.range()`. `readRecentEvents` filters, dedupes or otherwise removes no event row between the window read and the answer: `joinBrowseRows` maps one row per event in arrival order and the three legs FILL columns, so the count `pageAnswerOf` grades full-or-exhausted against is exactly the count `.range(offset, offset + view.window - 1)` returned. This is the claims shape's one latent trap, named by QA on the TASK-0066 close and RULED here rather than copied: `readClaimWindow` applies `selectClaims` AFTER `.range()`, so a full window that lost a row in code would answer `exhausted: true` and end the operator's paging early with rows still behind it — unreachable today only because the query carries the same `neq`. Browse must not acquire that shape: any narrowing browse ever needs is applied IN the query, before the range, never to the rows it returned. Driven offline: a stub returning exactly `view.window` event rows whose three legs return NOTHING at all — no listing row, no provenance row, no source row — still answers `view.window` rows with `exhausted: false` (and carries the legs' notes), so a leg that contributes no row of its own cannot shorten the page or end the set (common violations row 14); and a stub returning `view.window` rows of which several share a venue or name no source at all answers `view.window` rows too.

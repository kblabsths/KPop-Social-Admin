# Browse: the events window takes an offset, and its paging route handler answers one page

## Description
**Modules:** `src/lib/db/browse.ts` (the events window gains an offset; the three join legs follow it) and a NEW route handler `src/app/api/admin/browse/rows/route.ts`. `PAGE_ROUTES.browse` is its ONE spelling.

Browse's shaping is already shared — `joinBrowseRows` in `src/lib/browse/rows.ts` — so this ticket has no extraction to do. It is TASK-0065 and TASK-0066 in one, because the read change is small and the handler is the same shape as the claims one; read that handler before writing this one and follow it exactly (LESSONS 5: the second copy is what drifts — where the two handlers share a step, the shared step is `src/lib/paging/**` or `src/lib/db/paging.ts`, not a paste).

**Interface contract:**

```ts
// src/lib/db/browse.ts
export async function readRecentEvents(
  view: BrowseView,
  db?: SupabaseClient,
  offset?: number,           // default 0 — every existing caller unchanged
): Promise<RecentEventsListing>;
```

The events window keeps its total order — `view.sort.field` then `event_id`, same direction — and ends in `.range(offset, offset + view.window - 1)` in place of `.limit(view.window)`. **The three legs are per PAGE, not per table:** venues, provenance and sources run over the ids of THIS page's window exactly as they run over the first window's today, they stay COMPLETE reads (§4.3 kind 1: "the latest decision" is only knowable over the complete log), and a leg that refuses is still reported on its own — a leg that renders no row of its own may not decide the surface's state (common violations row 14).

```ts
// GET /api/admin/browse/rows?<the view's own params>&offset=<n>
// -> 200 PageAnswer<BrowseRow>  |  400 PageAnswer refused  |  the gate's redirect
export async function GET(request: Request): Promise<Response>;
```

Same five steps, same order, as the claims handler: `requireAdmin()` first; the view and its columns resolved by `src/lib/browse/views.ts` — the ONE definition layer, so a request cannot name a view or a column the config does not carry; `pageBound(raw, view.window)`; `readRecentEvents(view, undefined, offset)`; `pageAnswerOf(listing.events, offset, view.window)`.

**The two legs that fill columns travel with the answer or not at all.** A page whose provenance leg refused must not silently render events with an empty Sources column: carry the two `DbUnavailable | null` notes in the answer's `ok` arm (extend the answer for this surface with a `notes` field on the `ok` arm ONLY, declared in `src/lib/paging/bounds.ts` beside `PageAnswer` so both sides know it) and render them the way the first screen renders them today. If that turns out to cost more than it buys, file the question blocked — do not silently drop the notes.

**GET only. No service-role material crosses to the client.** Extend `tests/http/paging.http.test.ts` (TASK-0066's file) with this route rather than starting a second one.

**Browse does not gain width here** (SPEC F14, ARCHITECTURE §4.3 kind 3): one curated view, the same column selector, no second view, no table picker, no SQL runner, no search box. Paging lets the operator walk further down the view that exists.

## Acceptance criteria
readRecentEvents accepts an optional offset defaulting to 0 and issues its events window as order(view.sort.field), order(event_id), range(offset, offset + view.window - 1) — asserted against the offline stub at offset 0 and at one window in, including that the three legs run over exactly that page's ids and that each still reports its own refusal separately. GET /api/admin/browse/rows answers a PageAnswer<BrowseRow> as JSON: ok with that page's rows and exhausted only when the page came back short; not_provisioned naming events against a PGRST205 stub; error carrying the database's own message; 400 kind "refused" naming the reason and the bound for a bound that is absent, non-canonical, not a multiple of view.window, below view.window or above MAX_PAGE_OFFSET, with no read issued — two fixtures, one that must refuse and one that must not. A venue or provenance leg that refused is carried in the ok answer and rendered as the first screen renders it, never dropped. requireAdmin() is the first statement of the handler body, an unauthenticated GET never reaches it (asserted over HTTP against the built app), the route accepts GET only, and the client-bundle scan finds no SERVICE_ROLE, no service_role, no STAGING_SUPABASE and no staging URL. Browse gains no view, no column and no control: BROWSE_VIEWS still holds exactly one entry and /browse's live parity suite is green.

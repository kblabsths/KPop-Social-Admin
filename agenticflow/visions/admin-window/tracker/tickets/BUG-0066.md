# Edit cell: while the write is in flight the cell shows the new value and states no work, so 'being written' and 'written' differ only by 50% opacity

## Description
Expected: LOOK_AND_FEEL.md 'Interaction principles → Latency' (line 258): "every action acknowledges within 100ms — the control disables and states its work ('settling…')". The same doc's button rule (line 151) says a disabled control's own label must NOT change, so the statement of work belongs beside the field — the slot where the green 'saved' word already appears for 1.5s after the write.

Found: from the moment an edit is committed until the PATCH answers, the cell renders ONLY the new value in the resting button, disabled and at 50% opacity, with no statement of work anywhere. Measured twice on the production build of the landed tree (next build && next start --port 8794, staging data, minted cookie, bundled Chromium), 2026-09-03, groups 15ff6af9-178a-4f44-ae11-8bdc0c11b296, field short_name:

  AT +400ms of a 2.087s write (CDP latency emulation, the length a cold route or a remote database really takes):
    cell html    : <button type="button" aria-label="short_name of groups" disabled="" class="type-data cursor-text rounded-control px-1 py-0.5 text-left text-ink transition-colors hover:bg-chrome cursor-not-allowed opacity-50">Tuzi INFLIGHT</button>
    [role=status]: 0
    work stated? : False   (no /settl|saving|writing|…/ anywhere in the page body)
  The same state with NO throttling at all, on a cold dev server whose PATCH route still had to compile (2.266s response): at +250ms the cell was byte-for-byte the same disabled button carrying 'Tuzi QA-BLUR'.

So a committed-but-unwritten edit and a written one are distinguished only by opacity, and the confirmation the design specifies ('saved', green, 1.5s) arrives only after the response. src/components/EditableCell.tsx:159 sets status 'saving' and :158 sets the new value optimistically, but nothing renders for status.kind === 'saving' — the two status branches at :231 and :236 cover 'saved' and 'failed' only.

REPRO (self-contained, restores the row in a finally):
  1. Launch a walk instance per STACK.md §5 and mint a cookie.
  2. ( set -a && source .env && set +a && agenticflow/.venv-tools/bin/python agenticflow/tracker/evidence/BUG-0060/repro-inflight.py http://localhost:<port> )
  Its output is the block above.

WHY IT MATTERS, measured rather than argued: this state is what produced BUG-0060's false fourth observation. The verifier saw a disabled cell holding the typed value, reloaded 1.5s later while the write was still in flight, read the pre-write value, and filed 'blur silently discards what was typed' — costing a full builder session to disprove. An operator has the same eyes. On Railway (remote Supabase) the window is longer than the 0.26s a warm local server takes.

NOT a data-loss bug and priority reflects that: I could not lose a value under any timing I could reach. Blur, Enter and Tab each PATCH 200 and land in the database on a cold dev server, a warm dev server and a production build; a reload at +200ms of a 1.5s-latency write still lands; clicking a nav link mid-write on a 3s-latency link still lands; Escape never writes.

PINNING, honestly: this is not pinnable in the offline suite as the component stands. tests/offline runs environment 'node' with renderToStaticMarkup only (STACK §4: no jsdom, no Testing Library), and the 'saving' state is internal React state a static render cannot reach — the same wall BUG-0060 hit, which it solved by extracting the pure exported EditField. The fix should extract the status rendering the same way (e.g. a pure component or function over Status) and pin in tests/offline/ui/editable-cell.test.ts that the in-flight status renders a live region stating the work, and that the resting and saved states still render what they render today. Assert the BEHAVIOUR — that work is stated and announced — never the sentence.

## Acceptance criteria
While an edit's write is in flight, the cell states that work beside the field (announced to assistive technology, as the 'saved' confirmation already is), so an operator can tell a save that is underway from one that has landed; the disabled control's own label still does not change, the green 'saved' confirmation still follows the response, and the failure line still names the refusal and reverts the field. THE IN-FLIGHT STATE IS RENDERED THROUGH A PURE SEAM, as BUG-0060's EditField was, and for the same reason: tests/offline runs environment node with renderToStaticMarkup only (STACK 4 — no jsdom, no Testing Library), so a state reachable only from React's internal state is a state no offline test can render. The status rendering therefore becomes a pure exported unit over Status (a component or a function — the shape is the builder's), and tests/offline/ui/editable-cell.test.ts renders it directly to pin that the saving status states work in a live region, and that the idle, saved and failed statuses still render exactly what they render today. A fix that leaves the in-flight rendering unreachable from a static render has no bar and does not close this ticket. Assert the BEHAVIOUR — that work is stated and announced — never the sentence. src/components/EditableCell.tsx is also BUG-0069's file and the same in-flight window is its subject: land this one first, it depends on nothing, and BUG-0069 is chained behind it.

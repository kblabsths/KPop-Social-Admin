# The paging control stays drawn and enabled after a page answers not_provisioned — the one arm whose text offers no press

## Description
M3 endgame verification, 2026-09-11, HEAD bed26500, production build on port 8775 against staging, Chromium 1440x900, walk cookie.

STEPS: load /claims (50 rows, control reads 'Show the next 50 claims'); intercept the next request to /api/admin/claims/rows and fulfil it 200 with the handler's own shape {"kind":"not_provisioned","missing":"pending_claims"}; press the control once.

OBSERVED: rows 50 -> 50 (correct), window line byte-unchanged (correct), and the refusal renders exactly the gray clause it should: 'pending_claims isn't in this database yet — it arrives with the scraper repo's migrations.' — with no 'Press it again', correctly, because Refusal's not-provisioned arm deliberately offers 'no fix the operator cannot take' (src/components/ui/paging.tsx, the comment above that arm). BUT the control itself is still there, directly beneath that sentence, enabled: [data-paging="more"] present, disabled=false, label unchanged. Screenshot at agenticflow/tracker/evidence/M3/verifier/claims-arm-not_provisioned.png (gitignored; the measurement above is the durable record).

The other two arms keep the control on purpose and say so ('Press it again to ask for the same rows.') — that is right for a refused bound and for a read error. This arm is the one where the app has just learned the table is not there, and M3 EC5's own heading is 'a paging affordance is never drawn where it cannot be honoured'; F14 says 'a control that cannot be honoured is never drawn (F10's rule, applied here)'.

NOT A FAILURE OF EC5's GRADED CLAUSES, and I say so plainly: all three pass. On the server-rendered PGRST205 surface the affordance is genuinely absent (zero 'data-paging' occurrences, zero 'Show the next' on /claims and /browse, measured on an instance pointed at a PGRST205 stub); on an exhausted set it is absent; a refusal extends no list. This is the mid-session arm only — the table went away between the server's screen and the press — and it is filed low for that reason.

WHY FILE IT AT ALL: it is the one arm where the sentence and the widget disagree about whether there is anything left to ask for.

## Acceptance criteria
After a page answers not_provisioned, the surface offers no press: [data-paging="more"] is absent from the rendered markup (not merely disabled), the not-provisioned clause still names its table exactly once, the rows already on screen are untouched, and the window line is byte-identical to before the press. The refused-bound and error arms are unchanged — they keep their control and their 'Press it again' sentence, pinned so this fix cannot spread to them.

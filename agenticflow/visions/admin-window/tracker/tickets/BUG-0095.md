# An invisible-only cell value is stored as content while every surface draws it as an absence

## Description
**Expected** (the app's one definition of blank, admin-window/BUG-0089): a string with nothing VISIBLE in it is an absence — `isAbsent` (`src/lib/format.ts:250`) asks `visibleContent` and every surface draws such a value as the em dash. A value the app renders as "no value" is therefore not stored as content; and clearing a `not null` column is refused BY THE DATABASE, which the surface must show (STACK.md §5: "clearing one of those three is refused by the database (Postgres 23502) and the surface must show that refusal without claiming the save landed").

**Found:** the record edit path never asks that question, so the surface and the store disagree. `EditableCell.commit` decides blank with `draft.trim()` — `src/components/EditableCell.tsx:578`, `const trimmed = draft.trim(); const next = trimmed === "" ? null : trimmed;` — and the PATCH route clears on `null` and `""` alone (`readEdit`, `src/app/api/admin/records/[table]/[id]/route.ts:164`). Neither strips the Cf characters a paste out of a web page or a PDF carries, so an invisible-only value (U+200B, U+2060, U+00AD, U+FEFF, U+3164) is written to the column as content while the record page draws it as an absence — and on a `not null` column it fakes the clear the database exists to refuse.

**Measured on staging** (`walk_sandbox` row `…0001`, `resetSandbox` before and after, run from a detached `_receipt-` worktree at 638dc8e, 2026-09-09; the rows read back byte-identical to `tests/walk/sandbox-fixture.ts` afterwards):

    PATCH /api/admin/records/walk_sandbox/00000000-0000-4000-8000-000000000001
      {"field":"note","value":"​"}   -> 200
      read back with an independent client: note is NOT null, one code point, 200b
      isAbsent(stored note) = true; the rendered record page contains no U+200B
      and 8 em dashes — the surface says "no value", the database says "one character"
      {"field":"label","value":"​"}  -> 200   (label is NOT NULL)
      {"field":"label","value":null}      -> 500, Postgres 23502 not-null violation

    So the clear the database refuses is one an operator gets anyway by pasting an
    invisible character, after which the cell shows the dash for a column that is
    not null.

**Repro (exact):**
1. Open `http://localhost:8771/records/walk_sandbox/00000000-0000-4000-8000-000000000001` (STACK.md §5 launch line; reset the sandbox first).
2. Click the `note` value, select all, paste a single U+200B ZERO WIDTH SPACE — nothing appears in the field.
3. Press Enter. The cell confirms the save and settles to the em dash.
4. Expected: the column is cleared to null, or the save is refused naming why. Actual: the column holds U+200B and the page renders it as an absence. Repeat on `label` (not null): the same paste answers 200 where an ordinary clear answers 23502.

**Pinned RED before filing**, on the landed tree: `tests/offline/edit/route.test.ts` — "does not store as content a value every surface draws as an absence"; observed `AssertionError: "​": status 200, wrote "​": expected { '"​"': false } to deeply equal { '"​"': true }`. Its must-NOT-flag companion ("still stores a value that has anything visible in it, however it is padded") passes: `​BLACKPINK​`, U+2800 and `0` are stored byte-identical, so the pin is not vacuous (LESSONS 3). The assertion is deliberately either/or — refuse the write, or clear the column — because which of the two the app should do is the fix's choice, not the test's.

**Scope note for whoever takes it.** admin-window/BUG-0089's own thesis applies: the route is the contract (a forged body reaches it without ever meeting the cell), the cell is the courtesy. Both read the one definition (`hasVisibleContent` / `visibleContent`, `src/lib/verdict/decision.ts`) or the two disagree again. A whitespace-only value ("   ") is the same hole through a forged body — the cell's `trim()` keeps it off the UI path, and the same one-definition fix closes it.

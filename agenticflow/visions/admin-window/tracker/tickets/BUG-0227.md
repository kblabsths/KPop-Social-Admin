# A host answering 200 with a body that is not a row set crashes every surface with a 500 instead of refusing

## Description
EXPECTED (admin-window/BUG-0224's own bar, stated in its description and unchanged by its fix): "Whatever a host answers — a bodyless 404, a 204, an HTML error page from a proxy, A 200 WITH A BODY THAT IS NOT A POSTGREST ANSWER — the operator reads the app's refusal naming pending_claims (or review_items, or sources)."

FOUND on the landed BUG-0224 tree (run/admin-window @ 5961235c), measured 2026-09-15 over real HTTP against a production build: a host answering 200 with a JSON OBJECT crashes every graded surface. Not a refusal, not an empty card — Next's error shell and HTTP 500:

    MODE foreign /        -> 500 errorShell=true   TypeError: d.map is not a function
    MODE foreign /claims  -> 500 errorShell=true   TypeError: k.data.map is not a function
    MODE foreign /queues  -> 500 errorShell=true   TypeError: a is not iterable
    MODE foreign /sources -> 500 errorShell=true   TypeError: k.data.map is not a function
    MODE foreign /browse  -> 500 errorShell=true   TypeError: a.map is not a function

(the same five routes answer 200 in the `blank` and `empty` modes on the same server, so this is NOT admin-window/BUG-0226 — that one needs a database serving ROWS, and its error reads "Functions cannot be passed directly to Client Components".)

MECHANISM, measured with the real client (@supabase/supabase-js 2.x) against a loopback host answering `200 {"message":"no upstream"}`:

    rowset   .select("*").limit(5)                  error=null data=object {"message":"no upstream"} count=null
    count    .select("*",{count:"exact"}).limit(0)  error=null data=object                            count=null
    complete .select("*",{count:"exact"}).limit(5)  error=null data=object                            count=null

The count legs refuse correctly through BUG-0224's one rule, because the COUNT is missing. The row-set leg does not: src/lib/db/result.ts:1061 asks only `if (result.data === null)`, and a foreign object is not null, so `readRows` returns `{kind:"ok", data:{message:"no upstream"}}` — a non-array typed as `Row[]` — and the first `.map` in the render throws. ARCHITECTURE.md 4.1's "no read throws" holds literally (the read layer returns), but the PAGE throws on what it returned.

This is not a regression from BUG-0224: pre-fix `readRows` did `result.data ?? []`, which passes a non-null object through just the same. It is the third of the four host answers BUG-0224's bar names, still open — the rule asks whether the payload is MISSING, not whether it is the SHAPE the read asked for.

THE BAR, positively (LESSONS 13): a row-set read that did not come back with an ARRAY did not come back with a row set, and refuses through the one rule (`unreadableAnswer`) naming its object — whatever non-array thing arrived. Same question for `readComplete`'s row leg, which has the identical test on `data` and is reachable the day a host sends both an object and a Content-Range. No second derivation: the existing rule's predicate widens, it is not retyped (BUG-0224 criterion 4 still holds after the fix).

REPRO (exact, no database needed):
1. `tests/http/postgrest-stub.ts` carries the mode this was measured in: `foreign` — status 200, body `{"message":"no upstream"}` (committed by QA with this ticket).
2. `tests/http/absence.http.test.ts` carries the pin, currently marked an EXPECTED FAILURE: "refuses every panel against a host answering 200 with something that is not a row set". Flip the marker to a plain `it` and run `npm run test:http`: it is RED at `/?probe=foreign status: expected 500 to be 200`, watched 2026-09-15 (two tests red, 32 passing).
3. The client-level measurement above is reproducible with any loopback server answering `200 {"message":"..."}` and a `createClient(url, key).from("pending_claims").select("*")`.

THE FIX FLIPS THAT MARKER back to `it` (check 2 refuses the close while it stands) and adds `"foreign"` to `EVERY_MODE` in that file, so the call-site-prose sweep covers this mode like every other.

# Settlement readiness asks about the TABLE only, so a half-installed world offers an override whose save 503s

## Description
QA residual 3 on BUG-0215, ruled into a ticket by the architect 2026-09-12.

MEASURED BY QA, not argued: readSettlementReadiness (src/lib/db/verdict.ts:253) reads the verdicts TABLE and nothing else, while the save it authorises calls the settle_review_item FUNCTION. The §9 handoff is two artifacts installed by two statements, and staging was observed in BOTH mixed worlds during the install on 2026-09-11 (BUG-0215: at 23:22Z the table answered 200 while the function was still absent; by 23:26Z both were there). In the table-present/function-absent world the record page computes overrideClosed = false, renders the override regime with its editable widgets, and the operator's save reaches an absent function: a 503. Nothing grades that state — no offline case, no live case.

WHY IT IS P3 AND NOT HIGHER, stated so nobody re-prices it: the window is an install window, both ends of it are honest (the widget appears; the save refuses in the app's own words naming the object it called), and the person in that window is Ben. It is filed because a control that cannot be honoured is drawn at all — SPEC F10's rule, which this campaign has enforced everywhere else — and because 'no case grades that state' is the part that will still be true at the next install.

THE POSITIVE BAR, which is what the fix must install (LESSONS 13): READINESS IS THE CONJUNCTION OF EVERY OBJECT THE SAVE CALLS, and the refusal names the one that is missing. Not 'the table is there', not a list of symptoms — one derivation, one owner, asked once per render.

A NON-WRITING PROBE FOR THE FUNCTION EXISTS AND IS ALREADY WRITTEN HERE: PostgREST's schema description (GET /rest/v1/) lists exposed RPCs; tests/live/parity.ts's functionsOnStaging() reads exactly that, exported by BUG-0215's builder, and harness.live logs 'settle_review_item is INSTALLED (of 56 function(s) exposed)'. Never call the function to test for it. If the probe's cost on a record-page render is the problem, cache it for the process and say so in the note — do not substitute a guess, and do not make the page slower than the fact is worth.

## Acceptance criteria
1. READINESS IS A CONJUNCTION. src/lib/db/verdict.ts derives settlement readiness from every object the override save calls — today the verdicts table AND the settle_review_item function — in ONE derivation with one owner. A world where either is absent is NOT ready.

2. THE MISSING OBJECT IS NAMED. When readiness fails, the record page renders the same honest absence it renders today and the reason names WHICH object is missing, in the app's own voice, through the existing absence rendering (no new sentence invented; if one seems needed, that is a designer question, filed).

3. ALL FOUR WORLDS ARE GRADED OFFLINE, on fixtures: neither installed, table only, function only, both. The first three draw no override widget and name the missing object; the fourth behaves exactly as the page behaves today. A world asserted only by its absence of widgets also asserts the reason it gives (LESSONS 8: one fixture that must flag and one that must not).

4. NOTHING PROBES BY CALLING. No code path added by this ticket calls settle_review_item, apply_resolution or any other mutating RPC to discover whether it exists; the probe is a READ of PostgREST's schema description. A test asserts that no .rpc() call is made on the readiness path.

5. The live edit suite stays green and keeps reading which world staging is in rather than assuming one (BUG-0215's property): tests/live/edit.live.test.ts passes against staging as installed today, and no live case writes an override.

# The entity picker's saved confirmation never retires — the 1.5s clock lives in EditableCell alone, and the picker renders the same status without one

## Description
**Expected** — LOOK_AND_FEEL, Inputs and inline edit: "Confirmation is a green `data` word beside the field **for 1.5s**"; and Motion: "120ms color transitions on hover and active state, **and the 1.5s save confirmation**. That is the entire motion budget."

**Found** — the reference picker built by TASK-0055 renders the shared `EditStatus` (`src/components/records/entity-picker.tsx:359`) from its own `reducePick` state, and nothing in that module ever retires a confirmation. Measured structurally, 2026-09-09:

- `src/components/EditableCell.tsx:917-921` is the **only** place the clock is armed: `const delay = confirmationDelayMs(cell.status); … setTimeout(() => dispatch({ kind: "elapsed", edit }), delay)`.
- `src/components/records/entity-picker.tsx` contains **zero** occurrences of `elapsed`, zero `useEffect`, zero `setTimeout`, and zero references to `confirmationDelayMs` or `CONFIRMATION_MS` (grepped; `CONFIRMATION_MS` is defined at `EditableCell.tsx:58` and referenced only there).
- `reducePick` handles exactly three events — `choosing`, `settled`, `cleared` — and the only one that returns a state with an idle status is `cleared`, dispatched from the picker's reopen handler (`entity-picker.tsx:514`).

So after a successful override through the picker, the green `saved` word stands beside the field **indefinitely** — until the operator reopens that same picker. The click-to-edit cell three rows above it, which shares the `EditStatus` component and the `Status` type, retires its own after ~1.5s (measured on the walk: `saving…` at t=0.01s, `saved` at t=0.20s, gone at t=1.72s). One control's confirmation is transient, the other's is permanent, from the same status renderer.

**Honest grade: built, not walkable on this data.** The picker only renders when `settle_review_item` may be called, and it is absent on staging for the whole of M2 — `events` and `venues` render read-only with the reason named (F11, and the surface does exactly that today). So this is measured from source and from the rule, not from a rendered screen, and it will first *appear* on the morning after Ben installs the two handoff migrations, on the app's only catalog write path. That is why it is worth a P3 now rather than a surprise then.

Provenance checked before filing: `git log src/components/records/entity-picker.tsx` returns ticket-bearing commits only (3cfeae3/7ce9f91 BUG-0099, 0023a40 BUG-0097, aebcfcd TASK-0055). No human-lane divergence; violation, not reconciliation.

## Acceptance criteria
1. A successful choice through the entity picker shows `saved` in healthy green and it retires on its own after the same `CONFIRMATION_MS` the click-to-edit cell uses — one constant, one clock, not a second copy in the picker.
2. The clock is armed by the state, not by a call site: the picker arms it wherever `confirmationDelayMs` returns a delay, the way `EditableCell` does, so a path that reaches a confirmation without going through the click handler still retires it.
3. A refusal is **not** put on a clock: a failed choice's red line stands until the operator acts on it, and BUG-0107's rule for when that is (Escape, blur, opening another control) applies to the picker too if it lands first.
4. The clock belongs to the choice that armed it: a superseded write's timer never retires a newer statement, which is the rule `reduceEdit`'s `elapsed` arm already enforces and `reducePick` must not weaken (BUG-0075, BUG-0097).
5. A write still in flight keeps `saving…` on screen and is not retired by any clock.
6. Asserted in the offline suite against `tests/offline/records/entity-picker.test.ts` with a fake timer: `saved` present at t=0, absent after the delay; a refusal still present after twice the delay.
7. `npm run lint` and `tsc --noEmit` clean; the targeted offline files green.

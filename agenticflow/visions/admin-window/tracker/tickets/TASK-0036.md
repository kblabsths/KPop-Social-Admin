# Reset the walk sandbox between walks: the seed fixture, the reset tool, and the walk recipe

## Description
Ben's inbox note, 2026-09-03: "a table that always exists which walkers can
interact with. **After a walk it should be reset for the next walk.**" This
ticket is the reset, the fixture it resets to, and the two paragraphs in
STACK.md that make a walker able to use both without reading this ticket.

**Blocked on TASK-0034**, which rules the mechanism (whether the tool creates
the table or only reseeds a table Ben created by hand), where the tool lives,
and the cadence. The scope on this ticket is a candidate, not a ruling — expect
it to be amended when TASK-0034 lands.

## What the tool does

Truncate the sandbox table and reseed it from a checked-in fixture, so two
runs in a row leave byte-identical rows and a walk that edited every editable
column leaves no trace of having happened. Nothing more: it is not a migration
runner and it is not a general staging fixture tool.

Four properties it must have, all of them borrowed rather than invented:

1. **It refuses against anything that is not the declared staging target.**
   `tests/live/staging-target.ts` already encodes that decision and
   `SERVICES.md` already declares the project — reuse them; do not write a
   second host check with its own idea of what staging is.
2. **It prints no value.** Host and declared target are identifiers and may
   appear in a refusal (that is the live setup's own rule); keys and DSNs
   never appear anywhere, in success or failure.
3. **The seed values carry no `admin-window` marker.** The moment TASK-0035
   lands, `tests/live/residue.live.test.ts` sweeps this table for that string
   and a fixture containing it reads as campaign residue on every run.
4. **It is not reachable from the app.** Nothing under `src/` imports it, and
   nothing it does goes through `src/lib/db/**`.

## The recipe

STACK.md §5 already tells a walker how to launch the instance and mint a
cookie (`tests/walk/session-cookie.mts`). This adds the third step beside
them, in the same voice: the one command that resets the sandbox, when to run
it (TASK-0034's cadence), the deep link a walk opens
(`/records/<table>/<key>`), and — plainly, because a walker will otherwise
file it as a bug — that a save 403s for the walker identity until Ben answers
the `admin_allowed_emails` question, so a read-and-render walk is what this
buys until then.

## What this replaces

Until this chain lands, walkers use the groups/idols exception: one field on
one existing row, the original value noted, restored before the walk ends,
residue sweep after. When the sandbox exists, STACK.md should say plainly that
the sandbox is the walk surface and the exception is retired — otherwise both
practices live on and the next walker picks the wrong one.

**Sibling to TASK-0034** (same inbox note, and both touch STACK.md). TASK-0034
decides *what may exist and by what mechanism* and writes that ruling into
ARCHITECTURE/DECISIONS; this ticket builds the tool and the fixture and writes
the walker-facing recipe into STACK.md §5. If they merge, the merged ticket
still owes both artifacts — a ruling nobody can run, and a tool nobody was
told about, each fail on their own.

## Acceptance criteria
tests/walk/reset-sandbox.mts exists, is run by node exactly as tests/walk/session-cookie.mts is, imports nothing from src/, and resets public.walk_sandbox to the checked-in fixture in tests/walk/sandbox-fixture.ts by deleting every row and re-inserting it through PostgREST with @supabase/supabase-js (no pg driver, no DDL, no TRUNCATE): run twice in a row it leaves identical rows, and run after a walk that edited every editable column it restores the fixture exactly. It takes SUPABASE_URL and SUPABASE_SERVICE_ROLE_KEY from its OWN process environment (mapped from the staging names on the command line, the STACK 5 launch idiom), loads no .env, and mentions no STAGING_ name anywhere — tests/live/setup.ts stays the one reader of those. It refuses non-zero having written nothing, through resolveStagingTarget from tests/live/staging-target.ts and SERVICES.md, against an unset name, an unparseable URL, no declaration, or any host that is not the declared staging target; no second host check is written. It prints no key and no DSN on either stream. Against a staging project where the table has not been pasted yet it exits non-zero naming walk_sandbox and saying it is created by hand (for-human/TASK-0034.md), never attempting DDL. tsconfig.json gains allowImportingTsExtensions: true so the .mts may import ../live/staging-target.ts by its real extension; ./node_modules/.bin/tsc --noEmit, npm run lint and npm run build all stay green. tests/offline/walk/sandbox-fixture.test.ts pins the fixture offline: it contains no "admin-window" substring, every fixture key is a mapped column of the EDIT_CONFIG walk_sandbox entry, the keys are the three ruled uuids 00000000-0000-4000-8000-000000000001, ...0002 and ...0003 (ARCHITECTURE 9.1 item 9 — the record page's id gate refuses a non-uuid segment before any read, so text keys made both of the sandbox's states unreachable), and at least one row has a null note and one a null observed_on. STACK.md section 5 carries the reset step beside the session-cookie step: the exact command, the cadence (immediately BEFORE every walk, mandatory — TASK-0034 item 4 — and again after a walk that wrote, when convenient), the deep link /records/walk_sandbox/00000000-0000-4000-8000-000000000001, that clearing label, tally or is_flagged is refused by the database on purpose and is not a bug, and that the sandbox is now the walk-write surface and RETIRES the one-field-on-groups/idols exception the same section currently prescribes. Finally, resolveStagingTarget takes the CALLER'S NAME and every LiveGuardError it raises begins with it, so this tool's refusals say the reset tool refuses rather than the live suite refuses; the missing-name refusal no longer asserts that the caller does not read SUPABASE_URL / SUPABASE_SERVICE_ROLE_KEY (false for this tool, which reads exactly those two from its own environment) — that clause moves to the live setup's own call site, or is worded to fit both callers. tests/live/setup.ts passes 'the live suite'; the whole live suite and tests/offline/live-guard.test.ts stay green, with the offline guard's refusal assertions updated to the parameterised text and one of them proving the tool's caller name appears.

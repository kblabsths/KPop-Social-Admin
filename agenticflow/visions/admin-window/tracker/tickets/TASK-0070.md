# A scan and the count printed beside it read the same window: ReadBounds carries both edges, and all five scans apply them

## Description
**Modules:** `src/lib/db/gauges.ts` (the `ReadBounds` contract and every scan under it), `src/lib/db/claims.ts` (the count printed beside one of them), `src/lib/gauges/**` (the callers that resolve the bounds), and the offline + live tests of both.

**The defect, as SPEC F15 names it:** `readClaimCountSince` has no upper bound while the scan it is printed beside is `[since, until]` and capped at 1,000. A count over a different interval than the rows beside it is a false relationship (LESSONS 2), whichever way it is resolved.

**Measured on this tree before authoring, and this is why the ticket is the CLASS and not the one figure:** `ReadBounds` in `src/lib/db/gauges.ts` carries only `{ since, limit }`, while `resolveBounds` in `src/lib/gauges/gauge.ts` returns `{ since, until, limit }` and hands `until` to the window line, which PRINTS it ("read to <until>"). **All five scans state an upper edge they do not apply** — `started_at`, `applied_at`, `observed_at`, `opened_at`, `rejected_at`. Fixing the claims pair alone and leaving four is how a class survives five tickets (LESSONS 2, and the whole of the M2 root-cause pass).

**The ruling — bound both edges at the READ, do not weaken the sentence:**

```ts
// src/lib/db/gauges.ts
export interface ReadBounds {
  /** Inclusive lower bound on the table's own time column, as an ISO instant. */
  since: string;
  /** EXCLUSIVE upper bound on the same column — the instant the read was resolved. */
  until: string;          // now REQUIRED: a scan cannot be written without stating its edge
  limit: number;
}
```

Every scan in `lib/db/gauges.ts` gains `.lt(<its own time column>, bounds.until)` beside its existing `.gte(<same column>, bounds.since)`. Nothing else about any of them changes. And the count that is printed beside the claims scan takes both edges from the same object:

```ts
// src/lib/db/claims.ts   — readClaimCountSince is REPLACED, not widened
/**
 * How many claims of this narrowing were observed in [since, until) — the same
 * window the scan beside it read. Two questions still get two functions
 * (readClaimCount is the whole narrowing's total); this one is the WINDOW's.
 */
export function readClaimCountIn(
  bounds: { since: string; until: string },
  filter?: ClaimsFilter,
  db?: SupabaseClient,
): Promise<DbResult<number>>;
```

The pair is handed ONE bounds object at the call site in `src/app/claims/page.tsx` — the `gaugeBounds` it already resolves — so the two reads cannot be given different edges by construction. Do not add an optional `until` and default it: an optional edge is the same defect one release later (LESSONS 4 — a predicate answering two questions gets widened by whichever one broke last).

**A row dated in the future is the fixture that proves it** (LESSONS 8, two fixtures): a claim observed after `until` — clock skew at a source, a source dating ahead — is counted today and is outside the window the line states. One fixture where the unbounded upper edge changes the number and one where it does not.

**The live oracles take the same two edges** (§10, common violations row 7): an independently written count that applies only `.gte` grades a different set than the surface renders, so every live assertion over a gauge window applies both edges and says in its message which window it compared.

**No rendered sentence changes in this ticket.** The window lines already state `[since, until]`; this makes the reads under them true.

## Acceptance criteria
ReadBounds.until is required and every scan in src/lib/db/gauges.ts applies both edges on its own time column — .gte(since) and .lt(until) — asserted against the offline stub for all five scans, each on a fixture holding a row dated after until (the figure changes) and one holding none (it does not). readClaimCountSince no longer exists in src: readClaimCountIn takes a single bounds object carrying both edges, and src/app/claims/page.tsx hands the same gaugeBounds object to the scan and to the count. On a fixture where an unbounded upper edge would change the number, the count rendered beside the scan equals the scan's own population, asserted on the rendered page and again at the read. Every live oracle that counts a gauge window applies the same two edges and names in its assertion message which window it compared. No rendered sentence changes: the window lines state what they stated before, and the offline page suites for /claims, /sources, /cycles and /queues are green with their existing copy assertions untouched.

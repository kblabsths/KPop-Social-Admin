# The evidence pair writes its own em dash for an unreadable tier, so the table's labelled absence and the pair's bare character say the same thing two ways

## Description
Found attacking BUG-0132's landed fix (QA, 2026-09-09, run/admin-window @ 697c5c5), offline, `renderToStaticMarkup` of the review-item page. BUG-0132 taught the four evidence CELLS to draw the app's dash. The block one paragraph above them still writes its own.

**Expected** — the app has ONE absence rendering and it is an element, not a character:
- `nullDash()`, src/lib/format.ts:216-222 — `<span class="text-ink-disabled" aria-label="no value">—</span>`. The `aria-label` is the whole point of it being an element: it is the only way the absence reaches a reader who cannot see the ink.
- `Column.cell`, src/components/ui/data-table.tsx:47-52 — "the cell never decides that itself".
- ARCHITECTURE.md §6 trap 5 — "A tier this app could not read is **the app's own dash**".
- The pair already obeys this for a VALUE: `CardValue`, src/components/evidence/evidence-pair.tsx:39-43, is `orDash(value)`.

**Found** — `contenders()`, src/components/review/shape-views.tsx:262, is `tier: row.tier ?? EM_DASH`, and `EvidenceClaim.tier` (src/components/evidence/evidence-pair.tsx:26) is `string`, not `string | null`. The null is therefore consumed by the caller and the pair receives a bare character it renders as ordinary text in the `source · tier · age` line. Inside ONE card the two absences are now rendered by two different mechanisms.

Both spellings, transcribed from a single render (`entity_link` fact item `01920000-0000-7000-8000-000000000201`, `sources` registry unreadable — `stuckScript({ [T.sources]: { error: tableNotInSchemaCache(T.sources) } })`, the same state BUG-0132 lists first among its three):

- pair, contender card:
  `<span class="type-data text-ink-secondary">01920000-0000-7000-8000-000000000102 · — · <span title="2026-08-31 23:30 UTC">8d ago</span></span>`
- table, the SAME claim's tier cell:
  `<td class="type-data px-2 py-1.5 text-ink"><span data-tier-now=""><span class="text-ink-disabled" aria-label="no value">—</span></span></td>`

Measured on that render: `[data-surface="evidence"] [aria-label="no value"]` = 2 — the table cell and the canonical card's absent value. The contender card's tier is not one of them. So a screen reader announces the table row's absent tier as "no value" and reads the pair's as nothing at all, and the two dashes are drawn in different ink on one screen.

This is pre-existing rather than a regression — BUG-0132's own Found section quotes the pair's `—` as the reference the table had to catch up to — which is why it is filed here and not as a bounce of that ticket.

Not reachable on staging's current data: staging's one review item is a source-pattern shape, which renders no pair at all (QA production-build walk, port 8791, 91 rows, 667 cells, 0 dashes, both themes). The path is reached by a `data_conflict` or `entity_link` fact item whose `sources` read refuses — a state src/app/queues/[reviewItemId]/page.tsx and BUG-0021 both handle deliberately.

It is graded on the ACCESSIBLE NAME, never on ink, and it carries the second fixture (LESSONS 3): the healthy registry leg asserts the card holds the source's tier verbatim and NO absence element, so a fix that labelled every tier reddens. Fix it and the pin turns red with "Expect test to fail" — drop `.fails` and keep the test.

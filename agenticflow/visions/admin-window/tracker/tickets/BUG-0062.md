# Queues: the queue-health live oracle reads one honest sub-empty card as the whole surface's state, so it is red on the run branch and the gauge's figures are never graded

## Description
Red on run/admin-window today (reproduced at d848b61/d8a796d, in isolation, 2026-09-03). THE PAGE IS CORRECT — this is a defect in the ORACLE, and a builder must not 'fix' src/app/queues/page.tsx or src/lib/gauges/queue-health.ts.

Repro (repo root, staging names in .env):
  npx vitest run --project=live tests/live/queues.live.test.ts -t "renders each queue's open count over its own window"
  -> Tests 1 failed | 6 skipped (7), 402ms
  -> StateMismatchError: 'section:not([data-queue] section)' rendered its EMPTY state, but this test counted 1 row(s) of 'review_items', which is OK.
     at tests/live/parity.ts:776, thrown from tests/live/queues.live.test.ts:328

Expected (ARCHITECTURE.md section 10 rule 1, and tests/live/parity.ts:700-705's own contract for 'excluding'): the surface's state kind is read from the state cards that surface answers for, and sub-surfaces carrying their own state are named in 'excluding'.

Found: tests/live/queues.live.test.ts:325-333 calls gradeSurface({markup, within: HEALTH, object: T.reviewItems, counted: open}) with NO 'excluding'. stateOf (tests/live/parity.ts) then collects EVERY descendant [data-state] card in the Queue health section. Measured on live markup 2026-09-03, that section holds exactly one such card:
  STATE_CARDS = [{state: 'empty', text: 'data_conflict open ageNo open items in this window...'}]
— the data_conflict queue's open-age panel, which is HONESTLY empty because data_conflict holds 0 open items. One sub-panel's empty is therefore returned as the whole gauge's state, and the case throws before reaching its assertions at :344-346. Consequence: the queue-health gauge has NO live certification at all today — the figures the case exists to grade are never compared.

The page's own figures, read off the same live markup, are all correct:
  readNumber(markup, 'entity_link open')  = 1   ('1 high, 0 low', 'oldest 1d ago', week 2026-08-31 opened 1)
  readNumber(markup, 'data_conflict open') = 0  ('nothing open in this window')
and staging holds exactly one review_items row: queue entity_link, status open, opened_at 2026-09-02T14:30:33Z — inside the gauge's window (QUEUE_HEALTH_DEFAULTS days: 180, 'Items opened since 2026-03-07 23:11 UTC'). So no surface says empty while a row exists: the four-state contract is not violated by the product. The window-vs-total hypothesis is NOT what fires today — today the whole-table open count (1) and the in-window count (1) are equal.

Second, independent leg, latent and not yet firing: 'counted: open' at :327 is exactUnt over the WHOLE table (status=open), while the health gauge's set is 'items opened in the window' (src/lib/db/gauges.ts:376, .gte('opened_at', bounds.since)). The test's own comment at :336-340 says those two can never be equal by definition. The day an open item ages past 180 days — or carries opened_at NULL, which .gte silently drops — this case goes red again for a second, different wrong reason. Same class as BUG-0037 (one count cannot grade two different sets). A fix that only adds 'excluding' leaves this one live.

Fix direction is the builder's call, but both legs must be answered: the surface's state must be read without the per-queue sub-panels' cards, and its expected kind must come from a count of the set the GAUGE reads (opened_at within the window), not the whole table. Do not weaken the case to 'render something' — the <= assertions at :344-346 are the point of it and must actually be reached.

## Acceptance criteria

The queue-health surface's state kind is read without counting the per-queue sub-panels' own state cards: a queue that is honestly empty inside a gauge that holds rows must not make the whole gauge read EMPTY. Proven by watching the case redden against a page whose gauge really is empty, and pass against today's (1 open entity_link item, 0 data_conflict).

The expected state kind comes from a count of the set the gauge actually reads — review_items with opened_at inside the gauge's window — not from the whole table's open count, so an open item older than the window (or with a NULL opened_at) does not redden it.

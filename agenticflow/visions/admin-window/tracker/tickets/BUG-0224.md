# A host that 404s with zero bytes makes /claims say 'No claims waiting' over a read that failed, beside a sentence about this app's own call site

## Description
BUG-0210's named residual, filed by the architect 2026-09-12 now that its trigger is stated and reachable. QA measured it on the landed tree and left it unfiled for lack of a criterion driving it; the trigger QA named — 'a deploy pointed at a host that 404s with zero bytes' — is a wrong SUPABASE_URL or a proxy/gateway in front of Railway, which is a deploy-time accident, not a database state.

MEASURED (QA, 2026-09-11, on BUG-0210's landed fix): against a host answering 404 with an EMPTY body, supabase-js rewrites the answer to 204 / error:null / count:null, so classify() sees neither rows nor an error code. /claims then renders BOTH halves of the wrong answer at once: the developer sentence 'the query returned no count, so the number of rows is unknown; a count read requires { count: "exact" }' (src/lib/db/result.ts:1185-1186) AND an empty card, 'No claims waiting', over a read that FAILED. /queues and /sources render readComplete's untouched twin, 'a complete read requires ...'.

BUG-0210 fixed the PostgREST-shaped absence (the count leg is a GET now, so PGRST205 arrives). It did not fix the class: a read whose answer the app cannot classify still lands on an arm that says something FALSE and something INTERNAL. The false half is the worse one — an empty card is a positive claim about the population ('there is nothing here'), made on the strength of a read that never happened. VISION's 'absence is honest' is exactly this.

THE POSITIVE BAR (LESSONS 13 — state the property, not the instance): A READ THE APP CANNOT CLASSIFY IS A REFUSAL NAMING THE OBJECT IT ASKED ABOUT. Never a zero, never an empty card, and never a sentence about this app's own call arguments. Whatever a host answers — a bodyless 404, a 204, an HTML error page from a proxy, a 200 with a body that is not a PostgREST answer — the operator reads the app's refusal naming pending_claims (or review_items, or sources), and the diagnostic about our own call, if it survives at all, lives where a developer reads it and not in the markup.

Both arms carry the defect and both are in scope: readCount's no-count arm and readComplete's twin.

Proof tier: tests/http — the offline stub client returns structured results and has never been able to see this (LESSONS 10). tests/http/postgrest-stub.ts already models a PGRST205 host and already withholds a HEAD's body as the real server does; this ticket adds the zero-byte-404 mode beside it. Do not add a fifth stub: extend the one that exists.

## Acceptance criteria
1. AGAINST A HOST THAT 404s WITH ZERO BYTES, every panel on /claims, /queues and /sources renders the app's refusal naming its object, and NO panel renders an empty/zero state. Driven over real HTTP against the extended stub, asserted on the markup.

2. NOT ONE of the app's own call-site strings reaches the markup in any mode of that stub: 'count read requires', 'complete read requires', 'count: "exact"'. Asserted as an absence over the rendered HTML, with the same assertion passing in the PGRST205 mode it already passes in.

3. THE EXISTING CLASSIFICATION IS NOT WIDENED INTO A SWALLOW. A real error still renders the database's own words (the 403/42501 and 500/57014 cases QA drove on BUG-0210 keep behaving exactly as they do today), a real PGRST205 still renders not_provisioned, and a genuine empty table still renders its empty card. One fixture per arm, and the empty-table arm is the one that proves the fix did not turn 'no rows' into 'refused'.

4. ONE DERIVATION. The rule is stated once in src/lib/db/result.ts and both readCount and readComplete consume it; neither spells its own version of 'unclassifiable' (LESSONS 11).

5. The offline result suite stays green with no assertion deleted or loosened, and npm run test:http is green including the new mode.

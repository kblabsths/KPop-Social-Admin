# not_provisioned learns the absent FUNCTION: PGRST202 and 42883 join the classifier

## Description
**Module**: `src/lib/db/result.ts` — the ONE helper that decides `not_provisioned` from an error code (ARCHITECTURE §4.1). Today it knows four codes, all of them about a table, a view or a column: `PGRST205`, `PGRST204`, `42P01`, `42703`.

**What changes.** M2 reads and calls an object of a fifth kind — a FUNCTION — and the absence of a function has its own codes: PostgREST answers a call to a function that is not in its schema cache with **`PGRST202`**, and Postgres raises **`42883` undefined_function**. Both join the same one helper, and `missing` carries the function's name exactly as `lib/db/tables.ts` would spell it, so the rendered card says which object is absent and nothing throws.

**Why it is its own ticket, first**: it is a shared surface every M2 write path depends on (ARCHITECTURE §13.2's stated exception), and three tickets would otherwise each add a code to the same file. One owner (§10, "one owner per structural guard").

**Scope discipline.** This ticket adds two codes and their tests. It does NOT add the call seam, a page, or a control — those are the next tickets. It does not widen `kind: "error"`'s meaning: every code that is not one of the six is still an error carrying the database's own words, and a null count is still a refusal (§4.3).

**The absence is the normal case and is graded FIRST.** `verdicts` and `settle_review_item` do not exist on staging and will not until Ben installs the handoffs — that is the database `main` deploys against for the whole of M2. Build and grade the not-provisioned path before the happy path.

**No Admin-side workaround for the absent function may be written** — spec §10's one forbidden move, this campaign's brightest line: no queued write, no "pending overrides" table, no retry buffer, no flag-guarded direct write, no second path "until Ben installs it". The surface degrades to what M1 already ships.

**The live probe is free and permanent**: `settle_review_item` genuinely does not exist on staging, so `tests/live/harness.live.test.ts` can assert the classification against a real absent function without inventing one — the same trick §4.1 already records for the absent `verdicts` table.

## Acceptance criteria
1. The classifier in `src/lib/db/result.ts` returns `kind: "not_provisioned"` for `PGRST202` and for `42883`, alongside the four codes it already knows, and `missing` carries the object name the caller passed.
2. Offline: one fixture per code — six not-provisioned codes each classify as not-provisioned, and at least two neighbouring codes it must NOT flag (e.g. `57014` statement timeout, `23502` not-null violation) still classify as `error` carrying the database's own message. The guard proves itself on both kinds of input (LESSONS 3).
3. A null count is still a refusal and not a zero; nothing in this change makes an absent object render a confident number (§4.3, common violation 2).
4. `tests/live/harness.live.test.ts` asserts the classification of a real absent function on staging by calling `settle_review_item` — a call that writes nothing because the function does not exist — and asserts the result is `not_provisioned` naming it, never `error`.
5. `tests/offline/absence/pages.test.ts` still grades every existing surface exactly as it did; no page's behaviour changes in this ticket.
6. `npm run lint`, `tsc --noEmit`, the full offline suite (shared-surface exception, ARCHITECTURE §13.2) and the harness live suite are green.

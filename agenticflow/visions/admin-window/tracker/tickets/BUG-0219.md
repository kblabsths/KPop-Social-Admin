## Description

EXPECTED: `npm run test:live -- tests/live/edit.live.test.ts` exits 0 (BUG-0215's own stored check; the whole tier exiting 0 is M3's exit guard, M3.md:98-100).
FOUND, run started 2026-09-11T23:55:29Z: EXIT=1, `Tests 2 failed | 23 passed (25)`.

  - tests/live/edit.live.test.ts:854 "a resolver-owned record page > shows the venue source on EVERY event the log holds a venue decision for, and moves no scalar's line" -> AssertionError: 6527b112-3de7-459f-b081-17aee6d7a002.event_id: expected null not to be null
Two re-runs were green: targeted (`-t "venue"`) 2 passed at 00:00Z, whole file 25/25 EXIT 0 at 00:03Z. Neither failing line is in anything BUG-0215 changed (that commit's last hunk in this file ends near line 532).

MECHANISM — read-only probes on the declared staging target (project ref ubfjjqlvnpnoborczbdb; no credential printed), taken ~10 minutes after the red run:
  - GET /rest/v1/events?event_id=eq.6527b112-3de7-459f-b081-17aee6d7a002 -> [] (0 rows)
  - GET /rest/v1/field_provenance?entity_id=eq.6527b112-3de7-459f-b081-17aee6d7a002 -> [] (0 rows)
  - the graded population (entity_type=events, field=venue) is 108 rows / 108 distinct ids, every one 01a0-prefixed (uuidv7). `6527b112-…` is v4-shaped and matches no catalog generator.
So the id the case graded came OUT of field_provenance during the run and was gone from both tables minutes later: a concurrent writer on the Supabase project three repos share (the scraper repo carries `delete_acceptance_rows(p_external_ref_prefix)` for exactly that create-then-delete shape). A record page for an entity with no row renders the honest "no such record", so `provenanceOf()` answers null for EVERY mapped column — which is why the failure names the PK column (`event_id`) first, not `venue_id`.

THE PREMISE, which is the defect: both cases assume an `entity_id` read from `field_provenance` still has an `events` row by the time its page renders. :854 renders up to 108 pages over ~27 s; :718 renders one. The product is right in both worlds — the case is what cannot tell "this page drew no provenance line" from "this entity no longer exists".

WHY IT MATTERS: `npm run test:live` exiting 0 is M3's exit guard, and this case is already the tier's flake hotspot — BUG-0208 (P1, fixed) was this same case timing out under parallelism. A red that is a stranger's row costs a full diagnosis cycle every time it fires; it cost this QA lane one.

NOT REPRODUCIBLE ON DEMAND — it needs a concurrent writer, so do not spend a session chasing a repro. What is fixable without one is the premise: make the case say WHICH fact it found instead of asserting against an id it read minutes earlier — e.g. treat a page that reports no such record as a vanished entity (named in the message and excluded from the coverage claim) rather than as a missing provenance line, and keep the "every decided event was graded" claim honest by stating the exclusion. A guard needs both fixtures (LESSONS 8): an id whose row is there (graded) and an id whose row is not (named, not asserted against).

Expected/Found anchor: Expected a provenance line for every mapped column of every decided event (tests/live/edit.live.test.ts:854); Found null for `6527b112-….event_id`, an entity that exists in neither `events` nor `field_provenance` on the same database minutes later.

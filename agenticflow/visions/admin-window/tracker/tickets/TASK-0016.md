# Cycles & runs — the adapter framework's runs half

## Description
Module: `src/lib/db/runs.ts` (new) and the adapter-runs section of
`src/app/cycles/page.tsx` (the seam TASK-0014 left named and empty). Authority:
spec §4 ('`resolution_runs` and the adapter framework's `runs`, newest first,
with the counts as columns and `error_summary` inline'), SPEC F5, acceptance
tests 2 and 9, and **Ben's ruling of 2026-09-02** — recorded as a dated
paragraph in `agenticflow/docs/DECISIONS.md` and in ARCHITECTURE.md §12's
settled paragraph. **The question that held this ticket is answered; it is
startable.**

### The column set — exactly nine, no more, no fewer

`source`, `started_at`, `ended_at` (a row with none is still running and reads
as such), `outcome`, `error_summary` (inline, verbatim, mono), `records_parsed`,
`claims_emitted`, `records_unlinked`, `failure_class`
(`transient | structural | config`).

Migration `20260829000001` gives the table 22 columns. The other thirteen —
`checkpoint_before/after`, `payloads_fetched`, `payloads_archived`,
`records_rejected`, `claims_dropped_empty`, `claims_collapsed`, `claims_ai`,
`records_linked`, `records_escalated`, `batches_written`,
`observations_returned` — are out of M1 scope; adding one re-opens a settled
decision rather than extending a table.

### Reuse the Dashboard's read shape

`/` already reads and renders the first five of these: `DashboardRunRow` /
`readRecentRuns` in `src/lib/db/dashboard.ts` select `run_id, source,
started_at, ended_at, outcome, error_summary`, ordered `started_at desc` then
`run_id desc`, through `readRows` with a clamped limit. `src/lib/db/runs.ts`
takes that same shape and adds the four counts plus `failure_class`. Keep
`run_id` as the row key and the order tiebreak — it is the primary key, not a
tenth displayed column. Do not re-derive anything the Dashboard already owns,
and do not widen `dashboard.ts` (it is another ticket's landed surface and is
deliberately narrower).

**The read stays a WINDOW read** (ARCHITECTURE §4.3). Every number this section
renders is a column of the row it sits in, never a count over the set, so a
bounded newest-first window is honest — and no figure on this page may be
computed from `rows.length`. Do not use `readComplete` here. No `?? 0` on any
read path: a null the database gave is not a zero.

### `?source=<name>` — the Sources page's seam

`/sources` links `/cycles?source=<name>`; today the Cycles page ignores it
silently (QA residual, relayed on this ticket 2026-09-02). `resolution_runs`
carries no source column at all, so the facet narrows **this half only** and the
page says so when it is applied. Match by NAME — `runs.source` is text with no
foreign key, deliberately (§6 trap 6) — never by key, and a source name with no
matching `sources` row is still a run that renders. A facet that matches nothing
yields the section's `empty` state with a 0, never the error state.

### Settled already, do not re-decide

Newest first by `started_at` with a total order; `error_summary` inline and
verbatim; an in-flight run and a `skipped` run each legible as such; the
data-table rule and the four states — with `runs` absent the section renders its
not-provisioned state naming `runs` and the cycles half of the page still works;
an empty result renders `empty` with a real 0 (DECISIONS 2026-09-02, "a counted
zero is a real figure").

### Brief, from the Common-violations ledger

Design tokens only, never raw values. A live test reads the state kind from
`data-state` before it compares a number: `error` is always a FAIL, `empty` is a
pass with a 0 (ledger row 6). Assert behaviour, never rendered wording. Imports
stay inside `src/` (§1.2 as narrowed). This ticket owns
`src/lib/db/runs.ts` and the adapter-runs section of `src/app/cycles/page.tsx`
exclusively — correct the stale "open question" comments in those two files; the
same comments in `src/app/page.tsx`, `src/lib/db/dashboard.ts`,
`src/lib/db/sources.ts` and the Dashboard offline tests are outside this scope
and stay.

Do not read `adapters.md` from a sibling repo path — it is not in this repo's
`contracts/`, and the ruling above is the whole contract for these columns.

You are one of eight builders about to write a `lib/db` module without seeing each other's code; the bound is decided once, in TASK-0026 (now a dependency), not eight times.

Two read kinds. Pick deliberately; do not blur them.

1. **Complete read — `readComplete(missing, run, db?)`, new in `src/lib/db/result.ts`.** Use it whenever the surface presents the result as the whole set: a list the page shows in full, a count, an oldest age, an "exactly the matching items" claim. The `run` callback passes `{ count: "exact" }`, a total `.order()` ending in the primary key, and `.range(0, cap - 1)` with the cap handed in. If the exact count exceeds the rows returned, it returns `kind: "error"` naming the object, the count and the cap. **An `ok` array from a complete read is the whole matching set** — that property is what every figure in this app rests on, and it is why no caller needs a "was this all of it?" flag.
2. **Window read — `readRows`, unchanged.** The caller's own `.order()` + `.limit()` define a named window, and the surface says which window it is showing. This is section 8's gauge contract and TASK-0007's landed gauges use it correctly. A window read's rows must never become a figure presented as a total.

Also: no read helper may substitute a number the database did not give. `readCount` returned `count ?? 0` — BUG-0007's user-visible twin — and TASK-0026 makes it refuse a null count instead. Do not reintroduce a `?? 0` on any read path.

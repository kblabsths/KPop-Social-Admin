# The account's one derivation, applied evenly: the code arm, a body with no words, and a document one line down

## Description
**Module:** `src/lib/db/result.ts` — `errorMessage`'s CODE arm (the `(${code})` tail), the one field of the client's account that is never asked admin-window/BUG-0173's three questions.

**Expected** (admin-window/BUG-0173 acceptance criterion 2, "COUNTED, NEVER QUOTED"): "for a serialised envelope of N characters the account contains N and contains neither the envelope's keys nor its values — including when the envelope nests a document".

**Found:** the account contains N AND the envelope's `code` value, whole. Measured three ways on run/admin-window at 86177e5:

1. Through the real `@supabase/supabase-js` client with a stubbed transport (403 + JSON body `{"success":false,"ray":"8f3c1attack","code":"<!DOCTYPE html>\\n<html>…4482 chars…</html>"}`), `readRows("pending_claims", …)` returned a **4,587-character** message:
   `a 4524-character body carrying no sentence of its own arrived here instead of the database's own words (<!DOCTYPE html>\\n<html><head><title>Attention Required! | Cloudflare</title></head><body>xxx…</body></html>)`
   — it matches both `/<!DOCTYPE/i` and `/<\\/?html[\\s>]/`, the two regexes admin-window/BUG-0170's rule exists to defeat.
2. At the real surface. Production build of this tree served on port 8783 with `SUPABASE_URL=http://127.0.0.1:8785` (a local stub answering every request 403 + that envelope), `/claims` fetched with a minted walk cookie, answered 200. **Three** `data-state="error"` cards (`pending_claims`, `sources`, `observations`) each rendered **4,530 characters** of the Cloudflare document into `ErrorLine`'s `failed` span — 4,842-4,849 characters of markup per card. The same value also reaches the PATCH route's JSON body (`Response.json({error: result.message})`, `src/app/api/admin/records/[table]/[id]/route.ts:334`).
3. A shorter, blander shape does it too: `{"blocked":true,"code":"R".repeat(300)}` → a 404-character account, 300 of them the intermediary's.

**Reachability is the ticket's own path, one field over.** postgrest-js hands the parsed body back AS the error object for ANY non-2xx response — `error = JSON.parse(body)`, `node_modules/@supabase/postgrest-js/dist/index.mjs:143` — so an intermediary refusing with a JSON envelope authors every field of it, `code` included. That is exactly how admin-window/BUG-0173's own fixture (3), `{"success":false,"errors":[…],"ray":"…"}`, arrives; `code` is simply the field the loop never sees, because `errorCode` reads it off the record directly and `errorMessage` appends it after every question has been asked.

**Not culpable to admin-window/BUG-0173**, which ruled its scope as "errorMessage's part assembly and nothing else" and left the code arm explicitly untouched. This is the next member of the class that ticket named — `an account carries the parts the DATABASE authored` — and the ruling on HOW to answer it belongs to the architect, not to a builder widening scope. Two shapes worth deciding between: routing the code through `partOfAccount` like any other part (it is already a part in everything but name), or leaving it a machine identifier and bounding it as one. **What it must not become is a fourth text question** (LESSONS 4, ARCHITECTURE §7 row 15) — no `<`-scan of the code, no length-cap on prose.

**Repro (offline, exact):**
```
./node_modules/.bin/vitest run --project=offline tests/offline/db/result.test.ts -t "never trails a foreign code"
```
The pin is `it.fails("never trails a foreign code verbatim after the clause that counted its body (admin-window/BUG-0176)")` in `tests/offline/db/result.test.ts`, watched RED as a plain `it` on 86177e5 (`AssertionError: expected 'a 4490-character body carrying no sen…' not to contain '<!DOCTYPE'`) before it was flipped. **Flip it back to a plain `it` when this is fixed** — strict, so it reddens the day the divergence disappears.

**Does not regress anything admin-window/BUG-0173 shipped:** its ten-fixture table, both new named cases and all 114 other cases of `tests/offline/db/result.test.ts` are green on the same tree, and `withoutSecrets` still runs last, so a credential in `code` is still redacted (`redacts a JWT arriving in the code` passes).

## Acceptance criteria
ONE DERIVATION, NO FOURTH QUESTION. Every string that reaches a kind:"error" result's `message` passes through `partOfAccount`'s three questions in src/lib/db/result.ts — the `code` included, which is the one field that has never been asked them. The questions stay three, in their order and in their text: no `<`-scan written for the code, no length cap on prose, no codepoint filter, no runtime vocabulary, no second detector for a shape nobody measured (LESSONS 4, ARCHITECTURE §7 row 15 — this ticket is that row's class arriving one field over, not a licence to widen it). `classify`'s CLASSIFICATION is untouched: `errorCode` still decides the absence arms, the column-absent arm still mines `messageOf` alone, and every not_provisioned verdict in the suite is unchanged.

A CODE THE APP ITSELF SERIALISED IS ALREADY COUNTED, AND IS NOT APPENDED AGAIN. Where the value carried no string `message`, `messageOf` rendered the WHOLE object — `code` and all — so the account is that one counted clause and the code arm adds nothing to it, for the same reason `details` and `hint` are not appended in that state. On QA's measured envelope {"success":false,"ray":"8f3c1attack","code":"<!DOCTYPE html>…"} the account contains the serialised length (4524 on the pin's literal), matches neither /<!DOCTYPE/i nor /<\/?html[\s>]/, is under 400 characters, and holds no key and no value of the envelope — "success", "ray", "8f3c1attack" and the document's own text all absent. The blander shape does the same: {"blocked":true,"code":"R".repeat(300)} yields the counted clause and no run of the intermediary's characters. The strict pin flips to a plain `it` under its exact existing name — it("never trails a foreign code verbatim after the clause that counted its body (admin-window/BUG-0179)") — and stays strict, so it reddens the day the divergence returns.

A CODE BESIDE A REAL MESSAGE IS ASKED THE SAME QUESTIONS AND OTHERWISE RENDERS EXACTLY AS TODAY. With a string `message` present the code is asked questions 2 and 3 and still renders LAST, in parentheses, so the four-field PostgREST refusal still ends "(42501)" byte-for-byte and the field order (message, details, hint, code) is unchanged. A code that ANSWERS a question is replaced by the same app-authored, counted, never-quoted clause any other part gets. A code that answers none crosses VERBATIM however long it is — the bar is the same derivation, not a shorter one, and a cap on the code would be the fourth question this ticket exists to refuse. An empty or blank code is still not printed (no "()"), the account still never ends in whitespace, the code is still dropped when the account already spells it, and `withoutSecrets` still runs LAST over the whole account, so it("redacts a JWT arriving in the code") passes unchanged.

THE ACCOUNT SAYS SO WHEN THE CLIENT SAID NOTHING (QA residual (a) of BUG-0173's close, folded here by the architect 2026-09-11: same function, same derivation, same file, and a ticket of its own would collide at this destination). A non-2xx with an EMPTY body reaches us as {message: ""} — postgrest-js's JSON.parse(body) throws and the catch builds `error = { message: body }` (node_modules/@supabase/postgrest-js/dist/index.mjs:152-155) — which is the path every bodiless 502/503/429 takes and the path all six HEAD count reads on /claims take. Today every part is blank, no code survives, `errorMessage` returns "" and ErrorLine renders "pending_claims — " naming no failure at all. Where NO part and NO code survives, the account is ONE app-authored clause saying the read was refused with no words: at least four words, not one of this app's generic sentences ("something went wrong", "sorry"), attributing no words to the database, and inventing no number. It renders in that state ONLY — {code:"42883", message:""} still renders "(42883)" and nothing else, and it("invents nothing when the client said nothing at all") and it("does not read an EMPTY code as a code, or print one") stay green. The HTTP status is deliberately NOT named and not reached for: `DbResponse` carries `data` and `error` alone, the error object carries no status, and threading one would mean widening the data-layer contract and every reader in lib/db/** — out of scope here.

THE DOCUMENT QUESTION IS ASKED OF EVERY MULTI-LINE PART, FRAMED OR NOT (QA residual (b), folded for the same reason). `withoutRuntimeFrames` returns a frameless part untouched today, so details = "reference 8f3c1\n<!DOCTYPE html>…" crosses WHOLE while the identical document one line above a stack frame is counted — the same question, asked at two granularities. Question 2 is asked line by line of every part, whatever else the part holds, and a line that answers it is counted rather than quoted exactly as it is inside a framed part. The untouched guarantee stands where nothing answers: a multi-line part in which no line is a document and no line is a frame is returned exactly as the pre-ticket tree returns it — same newlines, same indentation, same words, and no count of frames nobody dropped — so fixture (9), the indented "at the end of the statement" prose, still crosses with its newline and its four leading spaces. This adds no question and no line-level deduplication: the transport account's twice-stated cause sentence is DEBT-0020 and is not touched here.

THREE NEW NAMED CASES, EACH WITH ITS MUST-NOT-TOUCH TWIN (LESSONS 8), in tests/offline/db/result.test.ts and each a local literal: it("asks the code the same questions as every other part") — the document-carrying code beside a real message, counted; the 300-character code beside a real message, crossing verbatim; and "(42501)" unmoved. it("says the read was refused when the client said nothing at all") — {message: ""} through `classify`, and its twin {code:"42883", message:""} which says "(42883)" and no clause. it("counts a document on any line of a part, framed or not") — the frameless two-line part whose second line is a document, counted, with the prose line kept; and its twin, the indented non-frame prose of fixture (9), returned byte-identical. All three are plain `it`, never `it.fails`.

THE TEN-FIXTURE TABLE KEEPS ITS SHAPE AND EVERY ASSERTION: five reduced, five crossing whole, each row's carries/never lists unchanged, and no row rewritten to make room for the above. Every other case of tests/offline/db/result.test.ts is green with none rewritten — the cause, wrapper, order, cycle, redaction and classification cases named in BUG-0173's criteria included, and BUG-0170's pin keeping its name. BUG-0173's refusals still hold structurally: "DOCTYPE", "SyntaxError", "not valid JSON" and "ENOTFOUND" appear on no CODE line of src/lib/db/result.ts, and `canSpellUrlValue` is neither called nor named there. The diff is the two files of the touch scope and nothing else; npm test and npm run lint are green on the landed tree. The full suite is a check here rather than a targeted run because this module is the shared data-layer contract every page's error arm inherits with no line of its own.

# The paging driver carries a page's leg notes to the state, and the one fetch refuses in the app's own words

## Description
**Modules:** `src/lib/paging/bounds.ts`, `src/lib/paging/machine.ts` (both pure leaves — ARCHITECTURE.md §4 rule 7), `src/components/ui/paging.tsx` (the one framed network exception), and their three offline suites. Two seams in the paging plumbing, one session, no surface changes: `/claims` and `/browse` render byte-identically through this ticket.

## A. The legs a page brought must reach the state

**Measured (QA on admin-window/TASK-0068, landed tree).** `GET /api/admin/browse/rows` answers a `NotedPageAnswer<BrowseRow, BrowseLegNotes>`: its `ok` arm carries `notes: { venues, provenance }`, the two legs that FILL columns over the events window, each `null` when that leg answered (`src/lib/paging/bounds.ts`, `src/app/api/admin/browse/rows/route.ts`). `requestPage` returns a `PageState<Row>` with four fields and none of them is `notes` (`src/lib/paging/machine.ts`), and `isPageAnswer` accepts the answer unchanged because an extra field is not a missing one. So the legs are **dropped at the driver**: a page whose provenance leg refused reaches the operator as events with a silently empty Sources column — the exact outcome TASK-0068's contract says must not happen ("the legs travel with the answer or not at all"). Nothing renders them because nothing can: no surface can read what the state does not carry.

**Interface contract** (ruled here so TASK-0069 consumes a landed one rather than inventing it):

```ts
// src/lib/paging/bounds.ts — the shape, beside the answer it rides on
/**
 * ONE leg's own report: the two rowless arms, spelled exactly as
 * `PageWithoutRows` spells them. Structurally a `DbUnavailable` and a
 * `StateOf`-renderable `UnavailableRead`, which is what lets a surface render
 * a paged note through the same primitive the first screen uses — and this
 * leaf still names no `DbResult`, not even as a type (§4 rule 7).
 */
export type PageNote =
  | { kind: "not_provisioned"; missing: string }
  | { kind: "error"; reading: string; message: string };

/** A surface's legs, by the SURFACE's own key. `null` = that leg answered. */
export type PageNotes = Readonly<Record<string, PageNote | null>>;

/**
 * Is this parsed value a notes record at all? The same question
 * `isPageAnswer` asks of the body, asked of the field: foreign data is a
 * refusal, never something a surface renders.
 */
export function isPageNotes(value: unknown): value is PageNotes;
```

```ts
// src/lib/paging/machine.ts — one field added, nothing else moved
export interface PageState<Row> {
  readonly rows: readonly Row[];
  readonly held: number;
  readonly status: "idle" | "loading" | "exhausted";
  readonly refusal: PageRefusal | null;
  /**
   * The legs that reported on the pages THIS STATE has taken in — never the
   * first screen's, which are the page's own to render, exactly as `rows`
   * holds no first-screen row.
   */
  readonly notes: PageNotes | null;
}
```

The rules, each one decided here:

- **`initialPage(held, more)` keeps its signature** and starts `notes: null`. A surface's first screen renders its own legs server-side; this state holds what PRESSES brought.
- **`pressing` carries `notes` through untouched**, and still hands back the SAME object from `loading` and `exhausted` — the identity guard the double-press proof rests on is unchanged.
- **On the `ok` arm, after the full-or-exhausted rules and before the append:** if the answer has an own `notes` property, it satisfies `isPageNotes` or the press is **REFUSED naming the route** — zero rows appended, `held` unmoved, `status` back to `idle`, the refusal reason app-authored (a new sentence beside `SHORT_PAGE` and `OVERLONG_PAGE`, carrying no figure and no foreign text). Appending the rows and dropping the notes is the defect this ticket exists to close; rendering a note this app cannot read is the one thing worse than dropping it.
- **A readable record MERGES, per key**: a key already carrying a note KEEPS the one it has; a key that is absent or `null` takes a non-null note from the new page. **Why merge and not replace**: the rows a refused leg left unfilled are still on screen after the next press, so a note that vanished when a later page's legs answered would be the silently-empty-column defect one press later.
- **An `ok` answer with NO `notes` property changes nothing** — the standing notes stand. `/claims`' route carries none and `/claims` is byte-identical through this ticket.
- **A refusal press leaves the notes it held**, exactly as it leaves `rows` and `held`.
- The leaf **never reads, trims, reworders or renders a note**: `isPageNotes` answers yes or no, and the note objects reach the state byte-identical to what the answer carried. The object an operator reads is the database's own `missing` / `reading` and message (§4.1, common violations row 15).

## B. `fetchJson` refuses in the app's own words, not the JSON parser's

**Measured (QA, this pass).** `fetchJson` (`src/components/ui/paging.tsx`) calls `response.json()` without ever asking whether this app's own route answered at all. A session that expires mid-walk is answered with the login redirect **followed to an HTML page at status 200**; `response.json()` rejects with the parser's own `SyntaxError`, `asError` passes its words through, and `requestPage`'s `reasonOf` puts them in the refusal slot — so the operator reads the JSON parser's vocabulary as this app's account of why the press added no rows. Same class as admin-window/BUG-0170 (text the app did not author inside a sentence it wrote), and **not** covered by it: BUG-0170's one derivation is inside `errorMessage` in `src/lib/db/result.ts`, which this path never touches — nothing here comes from `lib/db`.

What is added, and only this:

- Read `response.headers.get("content-type")`. Unless it **declares JSON** — a case-insensitive `application/json`, with parameters such as `; charset=utf-8` allowed — the request rejects with `new Error(ANSWERED_BY_SOMETHING_ELSE)`: one app-authored sentence that quotes nothing. Not the content type, not the status, not a byte of the body.
- A body that DOES declare JSON and does not parse rejects with `new Error(UNREADABLE_ANSWER)`, on the same terms.
- Both constants are exported from `src/components/ui/paging.tsx` (the offline tier reads them) and **neither reaches the `src/components/ui` barrel** — only `PageMore`, a component, crosses that boundary (admin-window/BUG-0094, pinned by this file's own barrel test).
- The object the operator sees is already right and is not touched: `requestPage` names `deps.route` on this arm, which is this app's own relative path.

**`response.ok` is deliberately NOT the discriminator** — the status is not the question. The route answers a refused page as a `PageAnswer` with a 400 to match, and that body is the operator's refusal; throwing it away for its status would replace the server's reason with one this app made up (the existing pin: "does NOT reject on a non-ok status"). And the measured defect arrives at **status 200**, which a status check misses entirely. The declared type is what separates "this app's route answered" from "something else did".

Unchanged: `credentials: "same-origin"`, the non-2xx JSON path, `asError`'s passthrough of a platform rejection's own words (the `Failed to fetch` pin), and every decision in `lib/paging/**` about what an answer does to the row list.

**Do not widen this ticket.** No surface file, no route handler, no `lib/db/**`, no new state arm, no change to `isPageAnswer`, `pageBound`, `pageUrl` or the full-or-exhausted rules.

## Acceptance criteria
THE LEGS TRAVEL TO THE STATE, OR THE PRESS IS REFUSED — NEVER DROPPED. `PageState` carries `notes` and `requestPage` fills it, driven directly against the recording stub on this fixture table: (1) an `ok` page whose `notes` name a not-provisioned `field_provenance` and a null venues leg appends its rows AND leaves the provenance note on the next state, byte-identical to what the answer carried — same `kind`, same `missing`, same message, no rewording; (2) both legs null appends rows and holds a record with two nulls; (3) an answer with NO `notes` property at all — the claims route's — appends rows and leaves the standing notes exactly as they were; (4) an unreadable `notes` field REFUSES naming the route, on five shapes: a string, an array, a note whose `kind` is a word this app does not know, a note whose `missing` is a number, and a note that is itself a nested record — each with zero rows appended, `held` unmoved, `status` back to `idle` and a refusal reason this app authored; (5) the MERGE: a page reporting a refused provenance leg followed by a page whose legs answered leaves that note standing, with both pages' rows in the list in the order they arrived; (6) a refused press — a short continuing page, a rejected request, a body that never parsed — leaves the notes the state held. `initialPage` still takes `(held, more)` and starts `notes: null`; `pressing` carries notes through and still hands back the SAME object from `loading` and `exhausted`.

NOTHING ELSE IN THE LEAF MOVES. `isPageAnswer` is unchanged and still accepts a noted answer (an extra field is not a missing one); `pageBound`, `pageUrl`, `MAX_PAGE_OFFSET`, `PAGE_ROUTES`, `PAGE_ANSWER_CACHE_CONTROL` and every full-or-exhausted rule are unchanged, with no assertion in the offline paging suite weakened or removed. `lib/paging/**` still imports nothing but itself: `tests/offline/db/layering.test.ts` and the leaf-closure guard in `tests/offline/claims/read.test.ts` are green, and `isPageNotes` names no `DbResult` type.

THE CLAIMS SURFACE IS BYTE-IDENTICAL THROUGH THIS TICKET. `/claims` renders the same markup on the same fixtures — `tests/offline/claims/page.test.ts` green with no expectation edited — because its answers carry no notes and every default added here is the state it already had.

THE REFUSAL IS THE APP'S OWN WORDS, NAMING THIS APP'S OWN ROUTE. On a response whose content-type does not declare JSON, `fetchJson` rejects with `ANSWERED_BY_SOMETHING_ELSE` and `requestPage`'s refusal reason is EXACTLY that sentence with the route as its object — proved on four fixtures: the measured one, an HTML login page at status 200 with `content-type: text/html`; a `text/plain` proxy page; a body with no content-type header at all; and an empty body. The reason quotes nothing this app did not author: for the login-page fixture the rendered refusal contains no fragment of the body, no content type, no status code, and none of the parser's vocabulary — it matches neither /JSON/i nor /token/ nor /</ nor /SyntaxError/. A body that DECLARES JSON and does not parse (a truncated document sent as `application/json`) rejects with `UNREADABLE_ANSWER` on the same terms. Both sentences are the app's voice, name what arrived rather than how it failed, and are not one of this app's generic apologies.

WHAT `fetchJson` ALREADY DOES RIGHT IS PINNED UNCHANGED. A 400 carrying a `refused` page answer still reaches the driver with the SERVER's reason and the row list untouched — that existing case stands verbatim, and a JSON body on any other non-2xx status reaches it the same way, because the status is not the discriminator. `response.ok` is not consulted (the measured defect arrives at 200). The existing hostile-body table still yields an `Error` with words for every entry, and a platform rejection's own words still pass through (`Failed to fetch`). `credentials: "same-origin"` and the single call per press are unchanged.

THE CLIENT BOUNDARY HOLDS. `ANSWERED_BY_SOMETHING_ELSE` and `UNREADABLE_ANSWER` are exported from `src/components/ui/paging.tsx` and neither is re-exported through the `src/components/ui` barrel — the barrel test's rule is unchanged and now covers them: only `PageMore` crosses, because a server module importing a VALUE out of this file builds green and answers 500 in production (admin-window/BUG-0094). `npm run build` is green.

# Five of six gauges ask for more rows than PostgREST will return, so a truncated read reports window.truncated false and its counts read as totals

## Description
Expected (ARCHITECTURE.md 4.3: 'PostgREST caps a response at its db-max-rows (Supabase's default is 1000) and says nothing about it ... a count built on it is wrong rather than refused - the one failure mode this data layer exists to make impossible', and ROW_CAP is set to 1000 'so the app never silently fights the platform cap'; src/lib/gauges/gauge.ts:62-68 WindowInfo.truncated: 'The scanning query came back with exactly limit rows, so the window may hold more than was read. Every count in the aggregate is then a FLOOR, not a total - the card must say so'): when the server truncates a gauge's scan, window.truncated is true and the card presents its counts as a floor.

Found: five of the six gauges declare a default limit ABOVE the platform cap, so the server truncates first and the gauge's own truncation test - windowOf() at src/lib/gauges/gauge.ts:117-124, 'truncated: rowCount >= bounds.limit' - can never fire. The server hands back 1000 rows, bounds.limit is 2000 or 5000, 1000 >= 5000 is false, and the aggregate reports window.truncated FALSE with counts that are floors.

The declared defaults (measured 2026-09-02 on run/admin-window 4de5cd6):
  src/lib/gauges/cycle-health.ts:34         limit 800    <= 1000   OK
  src/lib/gauges/resolution-latency.ts:43   limit 2000   > 1000    DEFECT
  src/lib/gauges/pending-claims.ts:104      limit 5000   > 1000    DEFECT (also standing-disagreements.ts, which reuses fetchPendingClaims)
  src/lib/gauges/queue-health.ts:46         limit 5000   > 1000    DEFECT
  src/lib/gauges/settled-values.ts:57       limit 5000   > 1000    DEFECT

Repro (offline, no database, fabricated rows only), from the repo root - this is what a capped PostgREST hands back:
1. const stub = stubClient({ review_items: { data: <1000 reviewItemDataConflict rows> } });
2. const r = await fetchQueueHealth({ now: '2026-09-01T12:00:00.000Z' }, stub.asSupabaseClient());
3. r.data.window  ->  { since:'2026-03-05T12:00:00.000Z', until:'2026-09-01T12:00:00.000Z', limit:5000, truncated:FALSE }
   expected truncated:true - the server gave everything it will give and more rows may exist unseen.
4. aggregateQueueHealth(r.data).items -> 1000, presented as the window's item count with truncated:false.
Same result measured for resolution latency (asked 2000, given 1000, truncated false, applies:1000), pending claims, standing disagreements and settled values (rerejected:1000, truncated:false). Cycle health at its own 800 correctly reports truncated:true, which is the proof the mechanism works and only the five defaults defeat it.

Why it matters: every count, every percentile and every weekly series in these five gauges is a floor at operational scale, and truncated:false tells TASK-0008's cards to render them as complete. The knobs the gauges exist to tune - escalation cutoffs from queue depth, source health from re-reject counts - are then judged from silently short data. review_items over a 180-day window and observations over a 90-day window are exactly the row sets that pass 1000 in normal operation. Note this is invisible to the landed suite because tests/fixtures/stub-client.ts returns whatever the script says, never modelling the server's cap.

Pinned: tests/offline/gauges/bounded.test.ts, describe 'a gauge read the server truncated at its own cap' - six it.fails() cases marked 'PIN admin-window/BUG-XXXX'. Written first as plain it() and watched RED: 'Tests 5 failed | 23 passed', one failure per defective gauge, cycle health the only pass.

Fix direction (builder): the limit a gauge asks for must never exceed the rows the platform will return - either cap every default at the platform row cap, or have the window read learn the cap and compute truncated against min(limit, cap). Do not raise db-max-rows; ARCHITECTURE 4.3 fixes the app's ROW_CAP at the platform default deliberately. Then flip the six it.fails() cases back to plain it() and delete the PIN comments, so the check below genuinely verifies the fix.

Out of scope: readCount's count ?? 0 (no gauge uses it - a structural test asserts that); the unfilled stuck_pattern threshold seam (TASK-0024); the settle/verdict naming question in QA's handoff.

# data_conflict on a reference field offers a free-text supply_value, so a venue NAME settles a venue_id fact

## Description
**Expected** (spec §7 "supply a different value (**the override form, §8**)"; spec §8 "the widget follows the registry's field settings: a scalar column edits as a cell, a \`kind: reference\` field as an entity picker" and "a reference field's override carries the chosen entity … so the apply links rows (\`venue_id\`, \`event_performers\`) **instead of writing text**"; \`src/lib/verdict/decision.ts\` \`PAYLOAD_SLOTS\`, which gives \`supply_value\` the \`value\` slot ALONE and states "a reference chosen by an operator arrives as an \`override\` from that same record surface, **never as a \`supply_value\`** — widening this to a ref-carrying \`supply_value\` would be a decision for the architect"): a \`data_conflict\` item whose field is a REFERENCE field must not be offered a scalar, free-text "supply a different value" control.

**Found**: `conflictActions` offers the scalar supply control for every whole fact triple, whatever kind the field is — `src/components/review/close/conflict-actions.tsx:110-120` (the `if (fact !== null)` arm pushes `supply_value` with `supplies: \`${fact.domain}.${fact.field}\`` and no consultation of the field's kind), rendered by `SuppliedControl` as a free-text `EditableCell` (`src/components/review/close/form.tsx:213-233`).

**Repro (offline, no database needed)** — from the repo root:

    ./node_modules/.bin/vitest run --project=offline tests/offline/review-item/conflict-actions.test.ts

The two pins under `describe("the kind of fact the item is about — QA attack")` are landed as `it.fails(…)` (strict xfail: they go RED the day the defect is fixed, which is the signal to flip them back to `it`). Observed red as plain `it` on 5e99b3a before pinning:

    × offers no scalar supply control for a reference field
      → expected [ { action: "supply_value", supplies: "events.venue", … } ] to deeply equal []
    × builds no text-carrying decision for a reference fact
      → expected [] to not deeply equal []

Measured directly on the landed tree (worktree at 5e99b3a), item `reviewItemDataConflict({ field: "venue" })`:

- offered actions: `supply_value` with `supplies: "events.venue"`, plus `keep_current`;
- the body that control posts: `{"action":"supply_value","note":null,"value":{"domain":"events","entity_id":"…0201","field":"venue","observation_id":null,"value":"The Forum, Inglewood","ref":null}}`;
- `decisionRefusals(...)` on that decision: `[]` — nothing between the operator's keystrokes and `settle_review_item`. The `ref` slot, which is how §8 says a reference override travels, is null.

**Reachability** — this is a real pipeline path, not a test-only construction. `contracts/resolver.md` §6 escalates a reference fact to `data_conflict` exactly as it escalates a scalar one (steps 1–2); step 3's `awaiting_link` hold applies only while the reference is UNRESOLVED, so two sources that each resolved to a different venue contest and escalate. `events.venue` is the app's one known reference field: `src/lib/edit/config.ts:193` `reference: { field: "venue_id", domain: "venues" }`.

**The arbitration this needs (the reason it is filed at the FEAT, not bounced to the builder).** TASK-0050 built `SuppliedControl` as a second spelling of the override input, and TASK-0054 (FEAT-0011, in flight) builds the record surface's item-less `override` through `src/components/records/field-editor.tsx` with `venue_id` in `display` and NOT in `editable` — i.e. the record surface deliberately refuses to edit the reference field at all today, while the close slot offers it as free text. Spec §7 says these are ONE thing ("the override form, §8"). They are currently two, and only one of them has the registry's field-kind knowledge. The architect's call:

1. `conflictActions` consults the field's kind and omits the supply control for a reference field until F12's picker exists (smallest fix; matches the module's own stated doctrine that "an action offered with a payload the function would refuse is worse than an action not offered", and matches what the record surface already does); or
2. the supply control and the record surface's override editor become one widget that takes its rendering from the registry/edit map — spec §8's own sentence — with the reference arm arriving with F12's picker.

Either way the shipped behaviour must stop building a text-carrying decision for a reference fact.

**Out of scope, noted for the same reader**: the close slot also offers the scalar supply control for `events` fields the edit map deliberately excludes (`status`, `event_type`, `time_precision`, `ends_at`, `ticket_url` — CHECK-constrained or unruled per TASK-0054 criterion 8). Unlike the reference case that may well be correct — the close slot writes through the registry, not through the edit map's allowlist — but if the architect rules the two surfaces share a widget, it is the same question.

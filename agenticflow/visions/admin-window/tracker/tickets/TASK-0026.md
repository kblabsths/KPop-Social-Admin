# Complete reads: an ok row set is the whole matching set, or the read refuses

## Description
Module: `src/lib/db/result.ts` (the shared helper) and `src/lib/db/review-items.ts` (its first caller). Authority: ARCHITECTURE.md section 4.3 (added 2026-09-02 by this ruling), section 8; acceptance test 2 ("two paths to one number") and test 4 ("a filter returns exactly the matching items"); BUG-0007's finding, generalised.

**Why this ticket exists.** QA found on TASK-0006 that `listReviewItems` builds its query with no `.range()`, no `.limit()` and no `.order()`. Against PostgREST's `db-max-rows` (Supabase default 1000) that row set truncates **silently, in unspecified order** — so `readReviewAttention`'s open count and oldest age would be WRONG rather than refused, and "the filter returns exactly the matching items" would be false with nothing to show for it. Eight more `lib/db` modules are about to be written by eight builders who cannot see each other's code. The bound belongs in one helper, decided here, not eight times.

**The two read kinds (ARCHITECTURE section 4.3). Do not blur them.**

1. **Complete read** — the caller names an exact set and the surface presents it as complete (a queue list, a count, an oldest age, "exactly the matching items"). This ticket adds it.
2. **Window read** — `readRows`, unchanged: the caller's own `.order()` + `.limit()` define a named window and the surface says so. That is section 8's gauge contract and TASK-0007's landed gauges use it correctly. **Do not change `readRows`' semantics** — six gauge modules call it and are out of scope.

**Interface contract** (later tickets code against this without reading it):

```ts
// src/lib/db/result.ts

/** The most rows one complete read may return. 1000 matches PostgREST's own
 *  default db-max-rows, so the app never silently fights the platform cap. */
export const ROW_CAP = 1000;

/** The PostgREST response shape a complete read needs: rows AND the exact count. */
export type DbCountedResponse<T> = { data: T | null; error: unknown; count: number | null };

/**
 * A complete row-set read. The `run` callback MUST pass `{ count: "exact" }`,
 * a total `.order()` ending in the primary key, and `.range(0, cap - 1)`.
 * `cap` is handed in so the caller never spells the number itself.
 */
export async function readComplete<Row>(
  missing: string,
  run: (db: SupabaseClient, cap: number) => PromiseLike<DbCountedResponse<Row[]>>,
  db?: SupabaseClient,
): Promise<DbResult<Row[]>>;
```

`readComplete` behaviour, in order:

- a database error -> `classify(error, missing)`, exactly as `readRows` does. Absence still reads as `not_provisioned`.
- `count === null` with no error -> `kind: \"error\"`, naming the object and that a complete read requires `{ count: \"exact\" }`. **Never fabricate a number the database did not give** — this is BUG-0007's rule, moved to the user-visible path.
- `count > rows.length` -> the read was truncated by SOMETHING (our cap, or the server's `db-max-rows`, which our cap alone cannot detect). Return `kind: \"error\"` naming the object, the exact count, the cap and the rows returned, e.g. `review_items: the database holds 1732 rows matching this read and it is capped at 1000 (1000 returned); narrow the filter or raise ROW_CAP.` **Refused, never a partial array.**
- otherwise `{ kind: \"ok\", data: rows ?? [] }`.

**The property this buys, and the only reason it is worth a ticket: an `ok` array from `readComplete` is the WHOLE matching set.** Every figure, count, oldest-age and exactness claim in the app rests on it, and no caller needs a \"is this all of it?\" flag, because a partial answer never becomes an `ok`.

**Then fix `readCount` in the same file.** It returns `count ?? 0` (line ~201): a PostgREST answer with `error: null` and `count: null` — exactly what a select written WITHOUT `{ head: true, count: \"exact\" }` returns — becomes a rendered `0` for a table holding 47 rows. That is BUG-0007's user-visible twin (BUG-0007 fixed only the test-side `countRows`, and its closing note relays this one). `readCount` must return `kind: \"error\"` naming that the query returned no count and that `{ head: true, count: \"exact\" }` is required. It must NOT throw — section 4.1 stands.

**Then migrate `src/lib/db/review-items.ts`** to `readComplete`:

- `{ count: \"exact\" }` on the select, `.range(0, cap - 1)`, and a **total** server-side order: `.order(\"status\").order(\"severity\").order(\"opened_at\").order(\"review_item_id\")`, all ascending.
- Measured, and the reason ascending is right on all four: `open` < `settled` and `high` < `low` lexicographically, so ascending text order already puts open before settled and high before low — the server order agrees with `queueOrder`. **That agreement is a convenience, not the contract:** the server order exists to make the row set deterministic (and therefore the refusal reproducible); `queueOrder` in `src/lib/review/shapes.ts` remains the only authority on display order and stays applied after the read. If a third severity or status value ever lands, the server order is merely arbitrary-but-stable and `queueOrder` is still right.
- `readReviewAttention` keeps its current shape (`listReviewItems({status:\"open\"})` -> `summarizeByKind`). It becomes correct-by-construction: its input is complete or the read refused.
- The exported signatures do not change: `listReviewItems` still returns `Promise<DbResult<ReviewItemRow[]>>`. TASK-0009/0010/0011 code against TASK-0006's contract unchanged.

Out of scope: `src/lib/gauges/**` (window reads, correct as landed); any page or component; paging/infinite scroll UI (nothing in the spec asks for it, and with a complete-or-refuse read nothing needs it at this scale); a new `DbResult` variant (the union is a landed decision — truncation is an `error`, and LOOK_AND_FEEL sanctions it: "a failed call surfaces the function's own refusal in mono, plus the fix in the app's voice").

## Acceptance criteria
Offline tests over stub clients prove all four of readComplete's branches: a database error classifies as before (not_provisioned for an absent table); a response with error null and count null returns kind error naming that a complete read requires count exact, and NEVER an array; a response whose exact count exceeds the rows returned returns kind error naming the object, the count and the cap, and NEVER a partial array; a response whose count equals the rows returned returns kind ok carrying every row. readCount refuses a null count the same way instead of returning 0, and still returns 0 when the database actually counted 0. listReviewItems reads through readComplete with count exact, an explicit range bounded by ROW_CAP, and a total server-side order ending in review_item_id; its exported signature is unchanged and every landed TASK-0006 test still passes. queueOrder remains the only display-order authority and is still applied after the read. readRows keeps its current signature and semantics (the six gauge modules that call it are untouched).

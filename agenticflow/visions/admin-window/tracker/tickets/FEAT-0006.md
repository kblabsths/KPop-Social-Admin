# The six threshold gauges

## Description
VISION: "with the six threshold gauges each answering its knob question". SPEC F6. Contracts read 2026-09-01: admin-observability.md §5 (the table of six gauges — the "one glance shows" column and the knob each judges); resolver.md §12 (the thresholds). Six views render from staging rows: cycle health (recent resolution_runs — duration vs cadence, facts examined vs writes, outcome counts, errors), resolution latency (observed_at to outcome latency percentiles, per domain), pending claims (the classification buckets with counts and age percentiles, filterable by source and domain, plus the per-source awaiting_row trend against its pattern threshold), queue health (per queue: open count, age distribution, opens vs settles per week, fold rates), standing disagreements (live contradictions with age and per-source split), settled values (per-source re-reject counts over time). Each gauge sits on the page whose data it judges — the per-source trends on Sources. Every gauge is a server-side read-only query in this app: this build adds queries and charts, never tables and never database views. Where a gauge needs a value that lives only in scraper registry YAML (the per-source resolver.stuck_pattern dial), that is a flagged gap and a blocked ticket per §10 — never a hand-copied value.

## Acceptance criteria
M1 EC8. Acceptance test 11: the six gauges render from staging rows, each answering its knob question per §5 (human-checkable on the close-review screenshots). No table and no database view is added — `bash -c "test $(ls supabase/migrations | wc -l) -eq 2"` passes and every gauge query is read-only. Acceptance test 2: the counts a gauge shares with its page satisfy that page parity check.

# A paged press asks for a POSITION, so a claim settled ahead of the bound between the screen and the press is silently skipped

## Description
Found while attacking BUG-0216 (whose own fix is sound and closed): BUG-0216 removed the case where the FIRST SCREEN is re-rendered under kept client state. The case where the POPULATION moves under an unchanged first screen is still open, and it produces the same two symptoms Ben's report named.

Expected (the ticket BUG-0216 was filed for, and the property that surface rests on): what /claims and /browse draw is one contiguous run of the order their last read held — no id twice, no id skipped.
Found: the press puts only a POSITION on the wire. src/lib/paging/machine.ts:386 pageUrl() appends ?offset=<rows held>, and src/app/api/admin/claims/rows/route.ts:136 re-reads pending_claims at that offset when the press arrives — seconds or minutes after the screen above it was read. Nothing ties the second read to the first: PageState.after, the bound BUG-0216 added, is never sent. So a claim settled AHEAD of the bound between the two reads moves every later claim up one, and the claim that stood at the bound is never drawn — no duplicate, no refusal, nothing in the console; the operator's list just steps over it. A row INSERTED ahead of the bound draws the bound's own row twice instead (React's duplicate-key error — the exact line in Ben's log).

Repro A (offline, exact, in the suite now): tests/offline/paging/machine.test.ts, describe 'a claim is never skipped when another settles between the screen and the press'. It is marked it.fails(...) so the branch stays green; DELETE the .fails marker to see it red. Screen read at T0 = a,b (bound b) of order a,b,c,d,e; 'a' settles; the press asks offset=2 and the route answers the CURRENT order's positions 2..3 = d,e. Drawn = a,b,d,e. Measured: expected ['b','c','d','e'], found ['b','d','e'] — claim c is on no screen.
Repro B (real browser, measured 2026-09-11 at f0ee24a8 + BUG-0213, dev instance on my own port 8783 against staging): with the page's read and the route's read over populations one row apart, /claims drew 100 rows / 99 distinct, 01a058f1-02c7-7e11-9191-adfa6207a0f0 twice, React's duplicate-key error verbatim. (In that run the skew came from the dev server's route-module cache rather than from a write — no agent may write pending_claims — but the arithmetic at the seam is the population's, not the compiler's: offset N over a view that moved is off by the number of rows that moved.)

Why it is not reachable on staging and no existing proof sees it: nothing writes pending_claims during a walk, so BUG-0216 criterion 2's three live walks and the M3 EC4 walk are over a frozen population by construction. In production the resolver and the scraper both move this view while an operator reads it.

NOT A ONE-LINE FIX — it wants an architect's ruling before a builder starts. The honest fix is keyset paging: put the bound on the wire (?after=<last row id>) and have the read continue from it (.gt('observation_id', …) inside the observed_at tie, or a composite bound) instead of .range(offset, …). PageState.after, which BUG-0216 added, is already exactly that datum; the reads at src/lib/db/claims.ts:328-341 and src/lib/db/browse.ts:133-135 already order totally, which is what keyset paging needs. The alternatives (accept the skip and say so on the surface; re-read the whole held window on each press) are cheaper and worse. Priority P2 rather than P1 only because the window is narrow — impact, when it lands, is BUG-0216's own: a claim the operator never sees.

## Acceptance criteria
1. A press continues from the BOUND the screen it continues ends at, not from a position: a claim settled or inserted ahead of that bound between the screen read and the press changes nothing about which claims the operator ends up seeing, and none is drawn twice.
2. The pin in tests/offline/paging/machine.test.ts ('a claim is never skipped when another settles between the screen and the press') passes with its it.fails marker REMOVED — an XPASS under the marker is a red suite and is the signal, not a pass.
3. /browse carries the same property, proved the same way (it shares the driver and the route shape).
4. The live three-walk proofs of BUG-0216 (tests/live/claims.live.test.ts, tests/live/browse.live.test.ts) still pass, and one of them additionally walks a bound that no longer exists in the order — the answer must be a well-formed page or a refusal the surface states, never a silent restart.
5. First screens unchanged: same window line, same figures, same row set on the same fixtures.

# The state classifier grades a surface green while it carries an ERROR card the classifier did not account for

## Description
Module: tests/live/parity.ts (stateOf / pageStates), the shared oracle seam every live test grades through. Authority: ARCHITECTURE §10 rule 6 (an error is a FAIL) and TASK-0032's own title — 'an ERROR page may not pass'.

Two lines in stateOf/pageStates let a card the classifier does not account for be absorbed into a NON-error verdict. Neither is reachable from a page the app renders TODAY (the two declared wrappers, [data-queue] in src/components/queues/queue-list.tsx:168 and [data-surface=runs] in src/app/cycles/page.tsx:931, each render exactly one card per state, and the four ui primitives emit only the four known values) — this is a defect in the SEAM, and the seam's docstrings promise the opposite of what it does. It reaches a user the same way BUG-0016 and the four vacuous /claims passes did: the live suite is this campaign's only staging-facing check, and a classifier that can answer 'ok' about markup carrying an ErrorLine is the exact false green TASK-0032 exists to remove. The next surface that grows a second read — a StatCard whose sub-line makes its own read, a gauge inside a queue block — makes it live, silently.

REPRO 1 (the headline) — tests/live/parity.ts:208-211. The wrapper's declared data-state is cross-checked against the card inside it ONLY when there is exactly one distinct card kind (`if (distinct.length === 1 && distinct[0] !== kind)`). With two, the declaration wins unchecked:

    const markup = '<div data-surface="q" data-state="ok">' + <Empty/> + <ErrorLine/> + '</div>';
    assertState(markup, '[data-surface]', 'ok');   // returns; nothing thrown

Expected: a refusal — the surface carries data-state="error" markup, and rule 6 makes that a FAIL naming the read. Found: assertState returns normally and the live case goes green on a page in its error state. Watched red as PROBE B in tests/offline/live-guard.test.ts.

REPRO 2 (the same contract, the other line) — tests/live/parity.ts:149 and :201. Both card scans filter on `CARD_STATES.has(...)`, so a data-state value outside the four is dropped before asKind ever sees it. pageStates' own docstring says the opposite in as many words: 'Throws rather than skipping on a value it does not know: an unknown data-state means the markup grew a fifth state nobody taught this oracle about, and silently ignoring it is how a broken page goes green.'

    pageStates('<p data-state="degraded">…</p>')                       // [] — no throw
    stateOf('<div data-surface="q"><div data-state="not-provisioned">review_items</div></div>', '[data-surface]')   // 'ok'

Expected: MarkupReadError naming the unknown value. Found: the card is invisible and the surface reads 'ok'. The hyphenated misspelling is the live form of this: this codebase's attribute idiom is hyphenated everywhere (data-bucket-claims, data-window-limit, data-empty), so 'not-provisioned' is the typo a future primitive is most likely to carry — and it grades an unprovisioned surface as OK. Watched red as PROBES C and D.

Pinned: three strict expected-fail pins in tests/offline/live-guard.test.ts, describe 'QA: the classifier, attacked' (PROBE B, C, D), each written as `it.fails(...)` naming this ticket, plus one green test that pins the guarantee that DOES hold today (a mixed surface never grades as a non-error kind — it refuses). THE FIX MUST CONVERT THE THREE it.fails PINS TO PLAIN it AND LEAVE THEM PASSING; while the defect stands they are green as expected failures, and the day the classifier is fixed they turn red (XPASS) and send the reader here.

Not to be fixed by widening what counts as a card: an unknown data-state must REFUSE, not be renamed. Suggested shape (architect's call): cross-check the declaration against every distinct card kind rather than only a lone one, let 'error' outrank a declaration outright, and drop the CARD_STATES pre-filter so asKind refuses what it does not know.

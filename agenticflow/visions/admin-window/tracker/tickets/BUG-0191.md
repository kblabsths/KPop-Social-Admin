# /claims?bucket=X&domain=Y: the bucket caption blames "the filters above" and denies the only filter above, in one sentence

## Description
MEASURED IN A REAL BROWSER on a production build against staging (own port 8785, my PID, killed; reads only), 1440x900, and reproduced offline on the page's own fixture.

REPRO (exact): sign in, open `/claims?bucket=awaiting_row&domain=events`. Read the paragraph under the Buckets table, and read the chip rows above it.

Expected (admin-window/BUG-0160's rule, pinned in tests/offline/claims/page.test.ts, describe "a narrowing with no chip row": «"these filters" and "the filters above" appear only where a CHIP facet is set, and where both kinds are set the sentence is true of both»; LESSONS 2): the bucket table's counts under that URL were narrowed by `?domain=` alone — a facet this page draws NO chip for — so the caption names the domain and claims no filter above, exactly as it does at `/claims?domain=events`.

Found (staging, 2026-09-11): the caption reads

  "Every bucket the classification view can hold, with the claims in the events domain in it UNDER THE FILTERS ABOVE — these counts answer for every bucket; THE BUCKET FILTER ABOVE DOES NOT NARROW THEM. A bucket with no claims is a real zero."

while the two chip rows above it read `awaiting_row` and `all`. The only chip filter set is the bucket one, and the same sentence's next clause says that filter does not narrow these counts. So the clause blames a control set that contains exactly one member, which the sentence itself denies. The counts prove it: bare `/claims` 0/108/769/0/0, `?domain=events` 0/108/741/0/0, and `?bucket=awaiting_row&domain=events` 0/108/741/0/0 — identical to the domain-only read, i.e. the bucket facet removed not one row and the domain did all the narrowing.

MECHANISM (named as evidence, not as a prescription) — src/app/claims/page.tsx:
- line 1060: `const chipped = hasChipNarrowing(filter)` — true when ANY of CHIP_FACETS (`bucket`, `source_id`) is set (src/lib/claims/filters.ts:162, :71).
- line 1531: that page-wide `chipped` is handed to `<BucketCaption>`, whose line 469 renders `narrowed && chipped ? BUCKET_CAPTION.underTheFilters : ""`.
- but this table's read DROPS the bucket facet on purpose (`bucketStats`, page.tsx:1223 and the comment at :1217-1221: "the bucket facet removes not one row from this table and cannot be what narrowed it"), and `bucketsNarrowed` (:1226) is computed against that bucket-dropped total. The gauge section one screen down already derives its own answer the right way — `gaugeChipped = hasChipNarrowing(gaugeFilter(filter))` at :1073, over a filter with the bucket facet dropped. The bucket caption is the one sentence on the page still asking the UNDROPPED filter whether a chip narrowed it.

NOT INTRODUCED BY admin-window/TASK-0071, AMPLIFIED BY IT: line 469's gate is byte-unchanged by that ticket's diff, so `/claims?bucket=X&domain=Y` rendered the false "under the filters above" before it too. What TASK-0071 added is the true clause that now stands beside it and contradicts it in the same sentence, which is how this was found. `?bucket=X&source_id=Z` is NOT affected — there the source chip really narrows and the arm is true of it (TASK-0071's own judgement call, graded correct).

Only the bucket CAPTION is wrong. The list's window line under the same URL is correct: the bucket facet really does narrow the LIST, so "matching these filters" is true there. Any fix must not move it.

THE PIN: tests/offline/claims/page.test.ts, describe "a narrowing with no chip row", `it.fails("claims no filter above when the only chip set narrows this table by nothing")` — watched RED as a plain `it` on ebe30005 before filing ("expected '…' not to contain ' under the filters above'"). It types neither phrase: the chip clause is read off the app as the only thing the `?source_id=&domain=` caption says that the `?domain=` caption does not, so a rewording moves the test with it. Flip it to a plain `it(...)` when it passes.

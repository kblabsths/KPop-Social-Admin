# The credential-layering guard misses bracket-form env reads, so the one-reader criterion is unproven

## Description
Expected (TASK-0002 acceptance criterion): 'src/lib/db/client.ts is the only file under src/ reading SUPABASE_SERVICE_ROLE_KEY', proved by tests/offline/db/layering.test.ts.

Found: the guard matches DOT access only. tests/offline/db/layering.test.ts:130 scans with /process\.env\.SUPABASE_SERVICE_ROLE_KEY/ (and :136 with /process\.env\.SUPABASE_[A-Z0-9_]+/). A second file under src/ that reads the key with BRACKET access is invisible to all 7 assertions. That form is not exotic: src/lib/db/client.ts:37-38 documents it by name ('Direct member access, not process.env[name]'), so it is the known alternative spelling, and src/lib/db/client.ts:21 already exports DB_KEY_ENV_NAME, making process.env[DB_KEY_ENV_NAME] the natural way a later page writes it.

Exact repro (run from the repo root, on run/admin-window at 0f49b28):
  1. printf 'export const key = process.env["SUPABASE_SERVICE_ROLE_KEY"];\n' > src/__probe.ts
  2. ./node_modules/.bin/vitest run tests/offline/db/layering.test.ts
  3. Observed: 'Tests 8 passed (8)' — the new credential reader is not reported.
  4. rm src/__probe.ts
Control: the same probe written with dot access reddens 4 assertions ('expected [ ... ] to deeply equal [ src/lib/db/client.ts ]'), so the guard works for that form alone.

Impact: STACK.md's trust boundary is public-surface and names 'service-role material leaking into a client bundle' as in scope. Every remaining M1 ticket adds files under src/; one of them reading the service-role key in bracket form ships with the layering suite green, and the criterion's structural proof is what was supposed to prevent exactly that.

The divergence is pinned at tests/offline/db/layering.test.ts, describe 'the credential guard itself', as it.fails (strict xfail, watched red as a plain assertion: 'expected [ src/lib/db/client.ts ] to include src/__credential_guard_probe__.ts').

Fix: widen the credential patterns to catch bracket access (both the string-literal and the named-constant form), keep the dot form, then DROP the '.fails' from that test so it asserts normally. Do not weaken the exemption list — it is correct and each of its 4 entries genuinely violates a rule today.

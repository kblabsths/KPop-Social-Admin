# the /cycles gauges render Empty at a counted zero while the live oracle grades them emptyAtZero:false, so cycles.live is red on the run branch

## Description
**Expected** (`tests/live/cycles.live.test.ts:282` `emptyAtZero: false` with `figure: "Cycles in this window"`, and LESSONS 7 — "An empty set still renders its labelled figure as a real 0", admin-window/BUG-0027): with zero rows in the gauge's window, `[data-surface="cycle_health"]` renders its OK state and the labelled figure reads 0.
**Found**: it renders its EMPTY card, and the live oracle throws. Same at `[data-surface="resolution_latency"]` (`tests/live/cycles.live.test.ts:313`).

**Repro (exact), from the repo root on run/admin-window @ 554dd78:**

```
npm run test:live -- tests/live/cycles.live.test.ts
```

exits 1 — `Tests 2 failed | 5 passed (7)` — run twice back to back (failing cases 241ms/232ms then 221ms/190ms), identical both times, so this is deterministic and NOT a staging race:

```
StateMismatchError: '[data-surface="cycle_health"]' rendered its EMPTY state, but this test counted 0 row(s) of 'resolution_runs', which is OK.
StateMismatchError: '[data-surface="resolution_latency"]' rendered its EMPTY state, but this test counted 0 row(s) of 'field_provenance', which is OK.
```

**Both sides are deliberate and both are anchored — they contradict each other:**

- `src/components/cycles/cycle-health.tsx:105` — `const empty: EmptyWords | undefined = health.cycles === 0 ? { holds: "cycles in this window", filledBy: "The resolver wakes on its cron and files a row, and the window fills." } : undefined;`, introduced with the comment at :102 — "A window with no cycles at all is the state a reviewer sees first against a database whose resolver has not run. It is an emptiness with a reason, so it is said in the page's own words rather than left to a table of zeros." `src/components/cycles/latency.tsx:31` is the same shape over `latency.applies === 0 && latency.verdictUnsets === 0`.
- `tests/live/cycles.live.test.ts:282` and `:313` — `emptyAtZero: false`, i.e. this surface may NEVER render Empty: a counted zero must still be the OK state carrying a real 0.

**Neither side is new, and the red is not TASK-0075's.** `emptyAtZero: false` arrived with admin-window/TASK-0032 (76c2963); the component's empty branch with admin-window/DEBT-0004 (0543d42). The contradiction was latent while staging's resolver window held rows and became visible once it emptied — staging now counts 0 `resolution_runs` since the gauge's `since` and 0 `field_provenance` applies, which is what the oracle's own message reports. TASK-0075's diff (e21e990) touches only `tests/live/claims.live.test.ts` and `tests/live/parity.ts`, and the parity.ts hunk is purely additive (one new export, `snapshotAsOf`); `gradeSurface` is byte-identical, so nothing in that diff reaches this file. Reproduced on the landed tree twice by QA.

**Cost while it stands:** `npm run test:live` is red on the run branch for every M3 lane and for the milestone's own full-suite pass, on a file no M3 ticket touches — the exact "distrust a red live suite" tax TASK-0075 was opened to remove, one file over.

**The direction is an architect ruling, not a builder's pick.** LESSONS 7 argues the COMPONENT moves (a counted zero is a pass with a number, never an absence); LESSONS 3 / ARCHITECTURE §4.3 and the component's own comment argue the ORACLE moves (an emptiness with a reason is a real state, explained from two facts). Whichever way it goes, the two must stop contradicting each other and the losing side's rule must stay pinned by a test that would catch its return.

**Already pinned:** the two failing cases above ARE the pin; watched red twice on the landed tree before filing. Do not add a third assertion of the same behaviour — extend these two.

## Acceptance criteria

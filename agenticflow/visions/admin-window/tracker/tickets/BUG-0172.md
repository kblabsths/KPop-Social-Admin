# A paged surface still says rows are withheld after the walk reached the end of the set — /browse and /claims

## Description
**Modules:** `src/components/ui/paging.tsx` (the client module that owns the press), `src/components/ui/window-line.tsx` (the SHARED primitive — §13.2's exception applies and the offline checks below are wide), `src/app/browse/page.tsx`, `src/app/claims/page.tsx`, both paged wrappers, and the offline suites of all of them.

## What QA measured (kept verbatim from the filing, it is the bar)

After the operator pages to the end of the set, `/browse` publishes two answers to one question: `[data-paging="exhausted"]` under the table ("All events in this view are shown", 120 rows drawn) and, above it, `[data-window="events"][data-window-truncated="true"]` still saying events that arrived before the ones below are not shown. The stale clause is visible before exhaustion too: with 100 rows drawn the line still says the screen holds at most 50 and `data-window-held` stays `"50"`. **Same class on `/claims`**: 616 rows on screen under "the 50 longest-waiting are below — the rest are not shown", `data-window-held="877"`.

Not the builders' error. TASK-0069 and TASK-0067 ordered the first server-rendered screen byte-identical (§5 as amended 2026-09-10) and the window line is the PAGE's, rendered above the client wrapper, so a press changes the rows underneath a sentence nothing can reach.

## The ruling (architect, 2026-09-11) — the line follows the READ, and paging is a read

§4.3's standing rule is that a window line states the read that HAPPENED. A press IS a read on these two surfaces, so the line that describes it cannot be a server-rendered constant. Two alternatives were considered and are rejected here so nobody re-opens them:

- **A second, client-rendered continuation line below the rows** — rejected: it leaves the false sentence on screen, and it is the one an operator reads before scrolling. It also gives the page two `[data-window]` elements, which `stateOf`'s one-element rule and `tests/offline/absence/pages.test.ts` both grade as a defect.
- **Rewording the truncated clause to "the first screen shows…" so it stays true** — rejected: the contradiction QA measured is published in the HOOKS (`data-window-truncated="true"` beside `data-paging="exhausted"`), which no rewording touches, and copy is not where a machine-readable verdict is fixed. LESSONS 11: one row, one verdict.

**So: on a paged surface the window line is ONE element, it is rendered inside client-land, and every fact in it is a fact of the read the operator now holds. The first server render stays byte-identical because a `"use client"` component is server-rendered on the first request with the very facts the page composes today.**

### The mechanism, ruled — do not fork it

`src/components/ui/paging.tsx` gains two exports beside `usePageRows`:

```tsx
// src/components/ui/paging.tsx  ("use client" — the module that already owns the press)

/**
 * The paging state ONE surface holds, published to every part of that surface
 * that states a fact about it: the rows, the control, and the window line.
 * It renders NO markup of its own (a context provider emits none), so the
 * page's DOM is byte-identical to today's on the first render.
 */
export function PagingProvider<Row>(props: {
  initial: PageState<Row>;
  deps: Omit<PageDeps, "fetchJson">;
  children: ReactNode;            // server-rendered children pass straight through
}): ReactNode;

/**
 * The window line of a surface that may CONTINUE its window. Same element,
 * same position, same primitive as the page renders unpaged; the facts it
 * hands `WindowLine` are the first screen's, updated by the press.
 */
export function PagedWindowLine(props: {
  gauge: string;
  window: DrawnWindow;            // the FIRST SCREEN's facts, composed by the page
  shows: DrawnSentence;
}): ReactNode;
```

- The provider calls `usePageRows` (so both offline suites' existing `usePageRows` spy keeps working unchanged) and publishes `{ state, press, size }` through context. `PagedBrowseTable` / `PagedClaimList` stop calling the hook and consume the context instead; nothing else about them changes.
- The page renders `<PagingProvider>` around the SAME children in the SAME order it renders them today — on `/browse` the line, the column selector, the two first-screen leg notes and the wrapper; on `/claims` the line and the wrapper. `ColumnSelector` and the leg notes stay SERVER components passed through as children (a server parent may hand server-rendered JSX to a client component); nothing about them moves into the client bundle.
- The page composes its first-screen `DrawnWindow` ONCE and hands the same object to `PagedWindowLine` (paged arm) or to `WindowLine` (every other arm). Two spellings of those facts is how the two come to disagree.
- Import `PagingProvider` / `PagedWindowLine` straight from `@/components/ui/paging`, the way the wrappers import `usePageRows`. The `src/components/ui` barrel is not widened (BUG-0094: a server module importing a VALUE out of a `"use client"` module builds green offline and answers 500 in production; `tests/offline/shell/client-boundary.test.ts` owns that rule).

### The one new fact on the shared primitive

```ts
// src/components/ui/window-line.tsx
export interface DrawnWindow extends WindowFacts {
  …
  /**
   * The rows the operator now holds from this window, on a surface that may
   * CONTINUE it — `null`/absent on one that cannot.
   *
   * absent/null                     → this surface has no paging: every arm
   *                                   renders exactly what it renders today.
   * === the first window's rows     → nothing appended yet: every arm renders
   *                                   exactly what it renders today, to the byte.
   * >  the first window's rows      → the window has been CONTINUED: the arm
   *                                   states what is on screen, and takes its
   *                                   held-back verdict from `truncated` alone.
   */
  drawn?: number | null;
}
```

**No new `data-window-*` attribute.** The first screen is byte-identical (SPEC F14, §5), and an added attribute is not. `drawn` changes the sentence and — on `/browse` only — the number `held` already publishes.

### What each fact means after a press

- **`truncated` is the paging state's own answer and nothing else**: `state.status !== "exhausted"`. It is derived in ONE place (the provider, or the line reading the provider) and never re-derived by counting rows beside it. On the first render it equals what each page computes today by construction — `/browse`'s `pageable` is `pageBound(String(held), window).kind === "ok"`, which on a window read of at most `window` rows is the same question as `held >= limit`; `/claims`' `pageable` requires the count-derived `truncated` — which is what keeps the first screen byte-identical.
- **`/browse`'s `held` is the rows the surface's reads came back with**, so it grows with `drawn` (QA's second finding: it was stuck at `"50"` under 100 rows).
- **`/claims`' `held` stays the matching COUNT its own count read established.** Paging reads no new claim into that count, the `matched` arm's clause is built on it, and `tests/live/claims.live.test.ts`'s paged-walk oracle grades the walk against exactly this hook (`data-window-held`). Changing it would silently move a live oracle's expectation.
- **`didNotFill` is unreachable when `drawn` is a number.** The wrapper is only drawn on a window that FILLED, so "The window did not fill — 50 of at most 50" must never appear; the not-truncated case of a continued window is the set being complete on screen, which is a different sentence.
- **A refusal settles nothing.** A refused press appends no rows and moves no bound, so the line is byte-identical to what it was before that press — and at the bound ceiling (`data-paging="limit"`) the line still says rows are not shown, because they are.

**Voice:** the words are the designer's jurisdiction. The two new sentences (a continued window that still holds rows back; a continued window that is complete) use the app's existing nouns, and the exhausted line must not parrot `PageMore`'s own "All N in this view are shown" — the walk grades the copy, the checks grade the hooks.

### Destination collisions (§13.9)

`src/components/ui/window-line.tsx` is also TASK-0072's destination and `src/app/claims/page.tsx` is also TASK-0070's and TASK-0071's. **This ticket lands FIRST**: TASK-0071 and TASK-0072 now depend on it (set 2026-09-11), because this is a truth defect on two live surfaces and both of those are contract work with a declared behaviour of zero. TASK-0072 converts `scope` to an array afterwards and inherits whatever arms exist then.

**No live file is touched** (`tests/live/**` stays out of scope): the first screen is unchanged, and `tests/live/claims.live.test.ts` has three lanes queued on it already. If a live oracle reddens on this, that is a finding to file, not a patch to make here.

## Acceptance criteria
1. On /claims and /browse, in EVERY state a press can end in - offered, loading, refused, refused-at-the-bound-ceiling and exhausted - the page publishes exactly ONE [data-window] element and its data-window-truncated agrees with the paging state below it: "true" only while rows this surface could show are not shown, "false" once the read has said the set is exhausted. Asserted on rendered markup through the real driver from the real deps the page handed it, on BOTH pages; no word of any sentence is pinned. 2. After a press appends rows, /browse's data-window-held is the number of event rows on screen, and /claims' data-window-held is still the matching count its own count read established (paging reads no claim into that count, and the live paged-walk oracle grades the walk against that hook). 3. Neither page renders the did-not-fill clause for a window that filled and was continued: on a paged surface the not-truncated case is the set being complete on screen, and the words 'did not fill' appear in no state a press can reach. 4. The first server render is byte-identical: with no press, both pages render the window line they render today - same element, same position (above the column selector and the leg notes on /browse, immediately above the list on /claims), same attributes, same words - and the existing first-screen window-line cases still stand and pass unmodified in both offline suites ('publishes the read's own facts, and says the window did not fill' and 'says the window filled its cap, and names no floor of its own' on /browse; 'states the cap and the number of claims it holds back' and 'does not claim to be truncated when every matching claim is drawn' on /claims). No data-window-* attribute is added. 5. One derivation, one verdict: the held-back verdict is the paging state's status and nothing else, derived in one place; neither page file nor either wrapper re-derives it by counting rows, and neither page file names a paging state type. The first-screen window facts are composed ONCE per page and handed to whichever component renders them. 6. A refused press settles nothing: the window line after a refusal is byte-identical to the line before it, and at the bound ceiling (data-paging="limit") it still says rows are not shown. 7. The nine unpaged window lines are untouched - /cycles x2, /queues, /sources x2, /review, the Dashboard's two panels and the entity picker render byte-identical lines on their existing fixtures, their suites pass unmodified, and WindowLine called without the new fact renders exactly what it renders today. 8. (human-checkable) The exhausted window line and the exhausted paging sentence read as one voice: they agree, and the line neither contradicts nor parrots 'All N in this view are shown'. The designer's walk grades the words. 9. QA's pin is green with its marker gone - tests/offline/browse/page.test.ts 'does not claim rows are withheld once the walk has reached the end of the set' passes with it.fails removed - and its sibling exists in tests/offline/claims/page.test.ts, pressing /claims to exhaustion through the same driver. 10. No surface, control or figure is added; the sidebar still holds exactly six links; lint is clean and a PRODUCTION build is green (a server module importing a value out of a "use client" module builds green offline and answers 500 in production).

# /browse still says rows are withheld after the operator has paged to the end of the set

## Description
Expected (SPEC F14 'Exhausted means the surface says so'; LESSONS 11 one row, one verdict; LESSONS 2 a sentence claims only the scope its read had): once the paged walk has reached the end of the set, nothing on /browse still tells the operator that rows are being held back.

Found: the window line is server-rendered ONCE, above the table, and a press changes the rows below it without changing it. After the walk reaches the end, the page publishes two contradictory answers to the same question:
  - [data-paging="exhausted"] under the table — every row of the view is on screen;
  - [data-window="events"][data-window-truncated="true"] above it — its clause names events that arrived before the ones below and says they are not shown.

MEASURED IN A BROWSER, production build of the landed tree (68cf523) on staging ubfjjqlvnpnoborczbdb, own port 8781, minted walk cookie (playwright, agenticflow/.venv-tools):
  1. GET /browse -> 200, 50 rows, one control.
  2. Press the control twice (bounds 50 then 100; one request each, zero on load).
  3. 120 rows on screen, [data-paging]=exhausted.
  Above them, verbatim from the DOM: 'The newest events by arrival, newest first - a window of at most 50, not the whole catalog. The window filled its cap, so events that arrived before the ones below are not shown.' Below them: 'All events in this view are shown.' All 120 events ARE shown; the first sentence is false, and it is the one an operator reads before scrolling.

The stale clause is visible before exhaustion too: with 100 rows drawn the same line still says the screen holds at most 50 and data-window-held stays '50'.

SAME CLASS ON /claims (measured on the same instance, not this ticket's surface, listed so the fix is scoped once): after 12 presses 616 rows were on screen under 'the 50 longest-waiting are below - the rest are not shown', data-window-held='877'.

NOT TASK-0069's builder's error: that ticket ordered the first screen byte-identical and the window line is the page's, above the wrapper. Whether the fix belongs to the browse page, to the client wrapper, or to the shared window line (and therefore to /claims at the same time) is an architect call - file a blocked question rather than widening the scope silently.

PIN: tests/offline/browse/page.test.ts, 'does not claim rows are withheld once the walk has reached the end of the set' - it.fails today (strict: it reddens the day the page stops contradicting itself, which is the signal to delete the marker). It presses ONE short page through the real driver from the real deps the page handed it, asserts the state really is exhausted and that all 90 rows are drawn, then asserts [data-window="events"] no longer publishes data-window-truncated="true". Both handles are the app's own hooks; no sentence is pinned.

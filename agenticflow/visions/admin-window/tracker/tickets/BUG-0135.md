# A population read no row depends on deletes the rows the URL's own complete read returned

## Description
Found attacking BUG-0133 (QA, 2026-09-09), on the code that fix landed. BUG-0133's rule is correct and must not be reverted; this is the cost its READ paid for it.

**Expected** — this app's own composed-read practice, stated on this very page (`src/app/queues/page.tsx:565-567`: "Reported separately: with the gauge's window unreadable the lists still render, and each surface names the read that refused") and shipped on `/claims` (`src/app/claims/page.tsx:723-728`: the source-registry leg refuses, every claim still renders, and the refusal is reported on its own naming its own object). A read that decides FOUR WORDS of a sub-line and which of two empty cards shows may not delete the rows a complete read already returned. ARCHITECTURE §4.3's refusal also names its own remedy — "narrow the filter or raise ROW_CAP" — so a narrowed URL must be able to act on it.

**Found** — `readReviewQueues` (`src/lib/db/review-items.ts:170-186`) returns the POPULATION leg's refusal as the whole read's refusal, and that leg is unconditionally `listReviewItems({})` — the whole table, which no URL facet narrows. So once `review_items` holds more than `ROW_CAP` (1000) rows, EVERY faceted `/queues` URL renders the error state and no rows, including the `?queue=` and `?status=` URLs whose own read is complete because PostgREST narrowed them by a real column, and which rendered before BUG-0133 (`git show 2686116 -- src/app/queues/page.tsx`: the page read `listReviewItems(filter)`). The error line the user then reads tells them to narrow the filter — the thing they just did, and the one thing that can no longer help on this surface.

MEASURED, offline, on run/admin-window @ bc9db28, stub-scripted so leg 1 (the URL's own read) is COMPLETE and leg 2 (the population) is truncated:

- read level: `readReviewQueues({queue:"data_conflict"})` with leg 1 `{data: 2 rows, count: 2}` and leg 2 `{data: 10 rows, count: 1500}` returns
  `{"kind":"error","reading":"review_items","message":"the database holds 1500 rows matching this read and it is capped at 1000 (10 returned); narrow the filter or raise ROW_CAP."}`
  — the two rows leg 1 held are gone.
- page level, same script, `/queues?queue=data_conflict`: BOTH blocks render `data-state="error"`; the decision block's text is `... review_items - the database holds 1500 rows matching this read and it is capped at 1000 (10 returned); narrow the filter or raise ROW_CAP. Reload to try the read again.` Zero rows on a page whose own read returned rows.
- the SAME script with no facet (`/queues`) refuses too, and always did: the pre-existing >ROW_CAP refusal is not this ticket. What is new is that narrowing no longer escapes it.

REPRO (offline, no database, from the repo root):
1. `./node_modules/.bin/vitest run --project=offline tests/offline/review/review-items.test.ts -t "POPULATION leg is truncated"`
2. It is landed as `it.fails` and therefore PASSES while the defect is live. Drop `.fails` to see it red — measured: `expected 'error' to be 'ok'` at `tests/offline/review/review-items.test.ts` in `readReviewQueues`.

The pin asserts only that the rows survive; it prescribes no shape. Two shapes satisfy it — carry the population as a per-kind `DbResult` so the block falls back to BUG-0131's structural rule (and says so) when it could not be counted, or report the population leg's refusal as its own sub-surface the way `/claims` reports the source registry. Which one is the architect's call; both keep BUG-0133's rule intact wherever the population IS readable.

NOT a reason to revert BUG-0133: the sibling test "refuses a truncated read rather than counting a population it did not see" (both legs truncated) must stay green — a partial FILTERED read still refuses, because those rows really are unknown.

# A population read no row depends on deletes the rows the URL's own complete read returned

## Description
Found attacking BUG-0133 (QA, 2026-09-09), on the code that fix landed. BUG-0133's rule is correct and must not be reverted; this is the cost its READ paid for it.

**Expected** — this app's own composed-read practice, stated on this very page (`src/app/queues/page.tsx:565-567`: "Reported separately: with the gauge's window unreadable the lists still render, and each surface names the read that refused") and shipped on `/claims` (`src/app/claims/page.tsx:723-728`: the source-registry leg refuses, every claim still renders, and the refusal is reported on its own naming its own object). A read that decides FOUR WORDS of a sub-line and which of two empty cards shows may not delete the rows a complete read already returned. ARCHITECTURE §4.3's refusal also names its own remedy — "narrow the filter or raise ROW_CAP" — so a narrowed URL must be able to act on it.

**Found** — `readReviewQueues` (`src/lib/db/review-items.ts:170-186`) returns the POPULATION leg's refusal as the whole read's refusal, and that leg is unconditionally `listReviewItems({})` — the whole table, which no URL facet narrows. So once `review_items` holds more than `ROW_CAP` (1000) rows, EVERY faceted `/queues` URL renders the error state and no rows, including the `?queue=` and `?status=` URLs whose own read is complete because PostgREST narrowed them by a real column, and which rendered before BUG-0133 (`git show 2686116 -- src/app/queues/page.tsx`: the page read `listReviewItems(filter)`). The error line the user then reads tells them to narrow the filter — the thing they just did, and the one thing that can no longer help on this surface.

MEASURED, offline, on run/admin-window @ bc9db28, stub-scripted so leg 1 (the URL's own read) is COMPLETE and leg 2 (the population) is truncated:

- read level: `readReviewQueues({queue:"data_conflict"})` with leg 1 `{data: 2 rows, count: 2}` and leg 2 `{data: 10 rows, count: 1500}` returns
  `{"kind":"error","reading":"review_items","message":"the database holds 1500 rows matching this read and it is capped at 1000 (10 returned); narrow the filter or raise ROW_CAP."}`
  — the two rows leg 1 held are gone.
- page level, same script, `/queues?queue=data_conflict`: BOTH blocks render `data-state="error"`; the decision block's text is `... review_items - the database holds 1500 rows matching this read and it is capped at 1000 (10 returned); narrow the filter or raise ROW_CAP. Reload to try the read again.` Zero rows on a page whose own read returned rows.
- the SAME script with no facet (`/queues`) refuses too, and always did: the pre-existing >ROW_CAP refusal is not this ticket. What is new is that narrowing no longer escapes it.

REPRO (offline, no database, from the repo root):
1. `./node_modules/.bin/vitest run --project=offline tests/offline/review/review-items.test.ts -t "POPULATION leg is truncated"`
2. It is landed as `it.fails` and therefore PASSES while the defect is live. Drop `.fails` to see it red — measured: `expected 'error' to be 'ok'` at `tests/offline/review/review-items.test.ts` in `readReviewQueues`.

The pin asserts only that the rows survive; it prescribes no shape. Two shapes satisfy it — carry the population as a per-kind `DbResult` so the block falls back to BUG-0131's structural rule (and says so) when it could not be counted, or report the population leg's refusal as its own sub-surface the way `/claims` reports the source registry. Which one is the architect's call; both keep BUG-0133's rule intact wherever the population IS readable.

NOT a reason to revert BUG-0133: the sibling test "refuses a truncated read rather than counting a population it did not see" (both legs truncated) must stay green — a partial FILTERED read still refuses, because those rows really are unknown.

## Acceptance criteria
**Ruled 2026-09-09 (architect): shape B for the SURFACE + shape A for the SCOPE
decision, and the population leg becomes a COUNT read so `ROW_CAP` cannot bite
it at all.** BUG-0133's rule is kept wherever the population IS readable and is
never reverted; what changes is that a leg which renders no row of its own may
no longer decide the surface's state.

1. **The URL's own read decides the whole read.** `readReviewQueues` returns
   non-`ok` only when `listReviewItems(filter)` — the leg the URL narrows — is
   non-`ok`. A population leg that refuses is never returned as the read's
   refusal and never removes a row the filtered leg returned. The pin
   `keeps the rows its own complete read returned when only the POPULATION leg
   is truncated (admin-window/BUG-0135)` drops its `.fails` and passes; its
   sibling `refuses a truncated read rather than counting a population it did
   not see` stays green — a truncated FILTERED leg still refuses whole, because
   those rows really are unknown.

2. **The population is a COUNT, never rows.** Each kind's whole-table
   population is read with `readCount` (`{ head: true, count: "exact" }`, no
   rows returned), one count per SHAPE, summed over `shapesOfKind`. `ROW_CAP`
   therefore cannot apply to it: a `review_items` table of any size answers a
   faceted `/queues` URL with its rows AND its populations. No subtraction
   between legs and no arithmetic across reads — a kind's figure is the sum of
   counts the database gave, or a refusal (a null count is a refusal, never a
   zero; ARCHITECTURE §4.3).

3. **The kind mapping keeps its one owner.** The column conditions each `Shape`
   is defined by — `queue`, and whether `source_id` is null, with
   `data_conflict_fact` constraining only `queue` (`shapeOf`'s own rule: a
   `data_conflict` row is a fact item whatever else it carries) — are declared
   as pure data in `src/lib/review/shapes.ts`, beside `shapeOf`, and
   `src/lib/db/review-items.ts` BUILDS its count queries from that declaration.
   `lib/db` spells no queue value and no null-check of its own: that would be a
   second definition of kindhood, which §6 ("the kind is derived in code — no
   column carries it") forbids and acceptance test 4 rests on. An offline test
   pins the two spellings together: over the edge population, the rows the
   declaration selects for a shape are exactly the rows `shapeOf` assigns to
   it, for all three shapes, `data_conflict` + non-null `source_id` included.

4. **The population is carried per kind, each leg answering for itself.**
   `ReviewQueues.population` becomes `Record<Kind, DbResult<number>>` — `ok`
   with the count, or the refusal of the leg that kind's shapes needed. Both
   kinds are always present, so an unreadable population is never a gap. On a
   URL with no facet the read still costs exactly ONE query and each kind's
   population is `ok` from the rendered rows (the pin `reads ONCE when the URL
   narrows nothing, and is its own population` stays green).

5. **A block's state, rows and figure come from its OWN read.** In `Queue`
   (`src/app/queues/page.tsx`) the `data-state` on the `[data-queue=…]`
   wrapper, the rows, the open figure and the `Empty` / `NotProvisioned` card
   are decided by the filtered read alone. A refused population never sets
   `error`, never empties the block, never suppresses the figure, and never
   replaces the `Empty` card — the four states keep their four renderings
   (LOOK_AND_FEEL, Emptiness).

6. **The refused population leg is reported as its OWN sub-surface, beside the
   rows.** When a block's own read produced rows or a counted zero and its
   population did not, the block renders the app's existing refusal state
   (`StateOf`, so the object `review_items` is named in its own spelling and
   the `data-read-failed` hook is carried) INSIDE its own wrapper, below the
   rows region, on its own `data-surface` — one per kind, so a live oracle can
   address it by name rather than by position (ARCHITECTURE §10) — under an
   eyebrow naming the fact that could not be read (the words are the
   designer's; no criterion here pins copy). This is exactly the `/claims`
   source-registry rendering (`src/app/claims/page.tsx` ~723-728) and this
   page's own stated practice (`src/app/queues/page.tsx` ~565-567). No line
   when the population is `ok`; no line in the block's `error` /
   `not_provisioned` arms, where the block's own state already names the same
   object.

7. **The scope decision falls back, and the fallback is never silent.** With
   the population `ok` the words are decided exactly as BUG-0133 landed them —
   `isBlockNarrowed(filter, ownNarrowing, { rendered, population })`, the
   comparison unchanged — so an empty queue is still never blamed on a facet
   and `?kind=`/`?shape=`/`?queue=` still read unfiltered on the block they
   imply (BUG-0129, BUG-0131). With the population refused the block falls back
   to the STRUCTURAL rule alone (`isNarrowed(filter, ownNarrowing)`), and
   criterion 6's sub-surface is what says so. `isBlockNarrowed` keeps its
   signature and its `number` population: no `null`/`undefined` sentinel is
   threaded through the pure module.

8. **Measured at the page, offline** (`tests/offline/queues/page.test.ts`):
   scripted so leg 1 is COMPLETE and the population legs refuse,
   `/queues?queue=data_conflict` renders its rows; no block carries
   `data-state="error"`; each block whose population refused carries its own
   `data-read-failed="review_items"` node inside its own `[data-queue=…]`
   wrapper and nowhere else. The pre-existing case is unchanged: a filtered leg
   that is itself truncated still renders the error state for the block.

`src/lib/db/review-items.ts`

    export interface ReviewQueues {
      /** The items matching the URL filter, in queue order — what the page renders. */
      items: ReviewItemRow[];
      /**
       * Per kind, the rows the TABLE holds with no URL facet at all — a count,
       * never rows. `ok` is the number the database gave; a non-`ok` arm is
       * THIS kind's population refusing, and it is the caller's to report, not
       * the read's to propagate.
       */
      population: Record<Kind, DbResult<number>>;
    }

    export async function readReviewQueues(
      filter?: ReviewItemFilter,
      db?: SupabaseClient,
    ): Promise<DbResult<ReviewQueues>>;   // non-`ok` ⟺ listReviewItems(filter) is non-`ok`

`src/lib/review/shapes.ts` (the pure module; the mapping's one owner) gains the
INVERSE of `shapeOf` as data plus a predicate over it — the name is the
builder's, the content is not:

    queue: ReviewQueue                    // always constrained
    sourceIdIsNull: boolean | null        // null = unconstrained, which is
                                          // exactly `data_conflict_fact`

    data_conflict_fact          -> { queue: "data_conflict", sourceIdIsNull: null }
    entity_link_fact            -> { queue: "entity_link",   sourceIdIsNull: true }
    entity_link_source_pattern  -> { queue: "entity_link",   sourceIdIsNull: false }

The three are disjoint and exhaustive over the table, which is why the counts
sum without arithmetic: `population[kind] = Σ count(shape) for shape in
shapesOfKind(kind)`, and a shape whose count refused makes that kind's
population that refusal. **No subtraction from a table total** — a figure is a
sum of counts the database gave or it is a refusal.

Query per shape, through `readCount` (`{ head: true, count: "exact" }`, no
rows, no `.range`, no `.order` — a head count needs none and `readComplete`'s
cap does not apply):

    .from(T.reviewItems).select("*", { head: true, count: "exact" })
      .eq("queue", …)                       // always
      .is("source_id", null)                // when sourceIdIsNull === true
      .not("source_id", "is", null)         // when sourceIdIsNull === false

`src/app/queues/page.tsx` — `Queue`:

    const pop = result.data.population[kind];
    const narrowed = pop.kind === "ok"
      ? isBlockNarrowed(filter, ownNarrowing, { rendered: items.length, population: pop.data })
      : isNarrowed(filter, ownNarrowing);          // BUG-0131's structural half

and, when `pop.kind !== "ok"`, the block renders — inside its own
`[data-queue]` wrapper, BELOW the rows region, never in place of them:

    <div data-surface={POPULATION_SURFACE[kind]}>
      <StateOf result={pop} eyebrow={…} />
    </div>

`POPULATION_SURFACE` is one name per kind, spelled once in the page module
beside `VERDICT_SURFACE` / `VERDICT_PROVENANCE_SURFACE`, so a live oracle
addresses it by `data-surface` and never by position (ARCHITECTURE §10). The
rendering slot is a new optional `note?: ReactNode` on `QueueList` — NOT the
existing `line`, which is the `DataTable` placeholder and suppresses the rows
(`src/components/queues/queue-list.tsx:170-186`). `line` keeps its one meaning.

Two things the builder will meet in the tests and should not fight:

- `stubClient` answers EVERY read of a table from one script entry unless the
  entry is a queue (`tests/fixtures/stub-client.ts:85-87`), so the existing
  `withRows(rows)` helper will hand the same `count` to all three shape legs.
  The population assertions in `tests/offline/review/review-items.test.ts`
  (`returns the filtered rows beside BOTH kinds' whole-table counts`, `counts a
  kind the filter emptied…`, `reports a real zero for a kind the TABLE holds
  none of`) must be re-scripted per leg. Rewriting them is in scope; weakening
  them is not — what they assert about BEHAVIOUR survives verbatim, only the
  scripting and the `DbResult` unwrapping change.
- Skew between the row read and the count reads can make `rendered >
  population` under a concurrent write. Leave it: the comparison stays
  `rendered !== population`, which reads as "filtered" — an over-claim on a URL
  that IS structurally narrowed, never a lie about a facet. Do not clamp, and
  do not infer a population from the rows.

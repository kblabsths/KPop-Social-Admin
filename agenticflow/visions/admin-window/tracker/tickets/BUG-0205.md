# The record page describes an edit it records, one paragraph before saying no field can be edited

## Description
Filed from the M3 user-sim walk of Tomas Berg (`agenticflow/tracker/for-human/M3-usersim-tomas.md`), 2026-09-11, the section "The record page argues with itself":

> "Every record page opens with two paragraphs in a row:
> > events is resolver-owned: its values change through the resolution pipeline, never by a direct edit. **An edit here is recorded as an admin override** — a claim at the admin tier, applied through the pipeline and logged — and the pipeline then leaves that field alone.
> > **No field here can be edited**: an edit is recorded through the resolution pipeline, and what records it is not present in this database. Every value below is read-only until it is.
>
> I read the first one, went looking for the edit control, found none, then read the second one and understood. Thirty seconds wasted on a page that describes a capability in the present tense immediately before saying it does not exist. The second paragraph is the true one and it is the one I needed first."

**Expected** — LOOK_AND_FEEL → The Voice → Register: *"it talks like the pipeline's engineer reading you its own logbook — plain, specific, no reassurance."* An engineer reading you their logbook does not describe a control you have, in the present tense, one line before saying you do not have it. This is the same jurisdiction and the same shape as BUG-0197 (two individually-true clauses that, read in order, argue with each other); wording is the designer's, and both sentences' facts are correct — what is wrong is that the closed path is stated second.

**Found** — two independent strings, rendered in this order by two different components:
- `regimeNote(config)` (`src/app/records/[table]/[id]/page.tsx:114-126`), rendered by `RecordFrame` at :403 as `<p data-note="regime">`. Its resolver-owned branch is unconditional and permanent: it describes what an override IS and asserts, in the present tense, that an edit HERE is recorded as one.
- `OVERRIDE_UNAVAILABLE` (:142-146), rendered by the page at :552 as `<p data-note="override-unavailable">`, only when `settlement` is not `ok` — i.e. only while `verdicts` is absent from this database.

So the page already knows the true state when it renders the second paragraph; the first is composed by a frame that has not been told. While the override path is closed (today, and until Ben installs the §9 migrations) the first paragraph's second sentence is a description of a capability the page does not offer.

**What this is not.** Not a truth defect — both paragraphs are true statements, one about the regime and one about this database. Not the not-provisioned card's problem: the card below `OVERRIDE_UNAVAILABLE` names its missing object correctly and Voice bar 4 is met. Not a licence to soften the regime note where the path IS open: when `verdicts` lands, the override sentence is exactly right and must come back verbatim.

**The cost, so the ticket is scoped honestly:** `RecordFrame` composes the note and the page owns the `settlement` state, so the fact has to reach the frame — one prop, one call site. A builder that instead moves `OVERRIDE_UNAVAILABLE` above the note is welcome to (criterion 1 is about what a reader meets, not about which paragraph moves), but it is the same prop either way.

Provenance checked before filing: `git log "src/app/records/[table]/[id]/page.tsx"` returns ticket-bearing commits only (BUG-0126, BUG-0120, BUG-0112, TASK-0054, TASK-0025). Not a human-lane divergence.

## Acceptance criteria
1. On a resolver-owned record whose override path is **closed** (`settlement` not `ok`), a reader meeting the page's paragraphs in order is never told that an edit here is recorded before being told that no field here can be edited. The true state of this database comes first, or the sentence that describes the control is not said at all while there is no control.
2. My preferred shape, which a builder may match or better without breaking bar 1: while the path is closed, the regime note stops after its ownership sentence — "`events` is resolver-owned: its values change through the resolution pipeline, never by a direct edit." — and `OVERRIDE_UNAVAILABLE` carries the rest, unchanged.
3. Where the override path is **open**, every string on the page is byte-identical to today, the override sentence included, in both regimes (`resolver_owned` and the sandbox's `direct` branch, which this ticket does not touch at all).
4. Nothing else moves: the identifier-in-prose spelling of the table name, the provenance legend, the six-column disclaimer, the field table, every state card and every `data-note` hook render as they do today.
5. The offline suite grades both arms: a test named `states the closed override path before it describes an edit` (that string, so the check below can find it) asserts the order/absence rule with the path closed, and asserts the open-path strings unchanged.
6. Human-check: at 1440x900, an `/records/events/<id>` page's opening paragraphs do not contradict each other, and a reader who stops after the first paragraph does not go looking for an edit control that is not there. **(human-checkable)**

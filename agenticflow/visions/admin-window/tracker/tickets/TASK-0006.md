# Review-item domain module: kind derived from shape, the ordering, the filters

## Description
Module: `src/lib/review/shapes.ts` (pure) plus `src/lib/db/review-items.ts` (the reads). Authority: spec section 6 (**'The kind belongs to the shape and is derived in code — no column carries it'**) and section 4 (Queues); `contracts/resolver.md` section 11 (`review_items` columns); SPEC F4; M1 EC6; acceptance test 4. Two later tickets (Queues, item detail) code against this without reading it — get the contract right first.

Interface contract:

```ts
export type Kind = "decision" | "signal";
export type Shape = "data_conflict_fact" | "entity_link_fact" | "entity_link_source_pattern";
export function shapeOf(item: ReviewItemRow): Shape;   // queue + whether source_id is set
export function kindOf(shape: Shape): Kind;            // the ONE place this mapping lives
export function queueOrder(items: ReviewItemRow[]): ReviewItemRow[]; // open first, severity then age
```

The three shapes today and their kinds (spec section 6):

- `queue = 'data_conflict'` with a fact subject (`domain`/`entity_id`/`field` set) -> `data_conflict_fact` -> **decision**
- `queue = 'entity_link'` with `source_id` null (a fact subject) -> `entity_link_fact` -> **decision**
- `queue = 'entity_link'` with `source_id` set (the per-source stuck-record pattern) -> `entity_link_source_pattern` -> **signal**

`source_id` set versus null is the discriminator the schema actually gives you: migration `20260901000002` says `source_id` is 'set on per-source items (the stuck-record pattern); null on per-fact ones'. Do not invent a column.

Ordering: **open items first, then severity, then age** — severity ranks by the registry's `low` / `high` **alone**; there is no formula, no score, no computed rank (spec parks the severity formula; VISION non-goal). Age is `opened_at`. Settled items remain browsable.

`src/lib/db/review-items.ts` exposes the list read (filterable by queue and by shape, returning `DbResult`) and the counts the Dashboard and the queue-health gauge need: per kind, open count, max severity, oldest age. **A filter must return exactly the matching items** — no extras, none missing (acceptance test 4), so filtering happens in one place, not per page.

Out of scope: any page or component; the item detail read (TASK-0011's); any settle/verdict control — the close is M2's and **nothing may be scaffolded toward it**.

## Acceptance criteria
[test 4; EC6] Offline tests over the fixture builders prove: each of the three shapes is classified `decision`/`decision`/`signal`; `queueOrder` puts open before settled, then `high` before `low`, then oldest `opened_at` first; every queue filter and every shape filter returns exactly the matching id set for a fixture population containing all three shapes in both statuses. The kind mapping exists in exactly one module. No severity score, rank or formula is computed anywhere. No settle or verdict function exists.

# Rule the walk sandbox: a staging-only table walkers may edit, created and reset by kit-side tooling

## Description
**The exception is granted; the mechanism is yours.** Ben, 2026-09-03, inbox
note (`2026-09-03-walker-sandbox-table.md`), verbatim:

> I don't think walkers should be editing staging tables. groups/idols is an
> exception but ideally we make a test table that walkers can interact with
> through the ui. [...] I would say that we should just create a table that
> always exists which walkers can interact with. After a walk it should be
> reset for the next walk.

And his ruling the same day, which fixes the shape and is not open for
re-litigation here:

- The table **must not exist in production**. It is a legitimate exception to
  the schema-ownership rule (AGENTS.md) *because* it is a test-case table
  reset after every walk — not a catalog fact, never canonical, never read by
  the mobile app.
- Therefore **not a scraper-repo migration**: a migration reaches every
  project `supabase db push` targets, which is exactly what must not happen.
- Instead: **staging-only, created and owned by kit-side walk tooling** under
  the existing live guard — never through Admin's own PostgREST client
  (`src/lib/db/**`), never from `src/`.
- Admin's whole side is one `EDIT_CONFIG` entry that renders the honest
  not-provisioned state wherever the table is absent — which is production,
  permanently, and is the same code path acceptance test 9 already pins.

What is **not** settled, and is what this ticket asks you to rule: the
mechanism, where the tooling lives, the name, the columns, the exposure, and
the reset cadence.

## The collision you have to rule on first

TASK-0021 is your own standing ruling, pinned by a stored check:
`STAGING_SUPABASE_DB_URL` "stays a name nothing under `src/` or `tests/`
reads", and no pg / postgres.js dependency exists in this repo. Creating a
table is DDL, and PostgREST cannot execute DDL. So there are three candidates
and only you can pick one:

**A — Ben creates it by hand, once**, in the staging SQL editor from a
paste-ready block. Tooling then only truncates and reseeds: pure DML, which an
independently constructed supabase-js client does fine (the
`tests/live/parity.ts` idiom). No DB URL read, no driver, no DEP, TASK-0021
untouched. Cost: a manual step, and a table silently absent if a new staging
project is ever stood up — the walk then reports not-provisioned, which is at
least honest.

**B — tooling does create-if-absent over `STAGING_SUPABASE_DB_URL`** with a
pg driver. Self-healing, but: a new DEP through the toolsmith's supply gate; a
second credential *shape* in this repo (a DSN with an embedded password — the
shape `src/lib/db/result.ts`'s redactor had to be taught to scrub); and either
the tooling lives outside `src/` and `tests/`, or TASK-0021's pin is amended
by you with a recorded ruling and a new stored check. Note that "kit-side" is
not automatically outside the pin: `tests/walk/session-cookie.mts` is under
`tests/`.

**C — B, but the tooling lives outside `src/` and `tests/` entirely** (a
`tools/walk/` or the kit's own scripts) so the pin holds literally. Cost: a
fourth place walk tooling lives, and lint/tsc/CI scope questions for that
directory.

## What the columns are for

Coercion, not modelling. The widget is one text cell for every type
(`src/components/records/values.ts`, `fields.ts`: `FieldWidget = "cell" |
"read_only"`), so all the type work happens in PostgREST on the way in. Ben
asked for one of each edit type; a candidate shape, yours to change:

```sql
create table if not exists public.walk_sandbox (
  sandbox_id  text primary key,   -- deterministic key: /records/walk_sandbox/walk-1
  label       text not null,      -- text
  note        text,               -- nullable text: the em-dash absence, then fill it
  tally       integer not null default 0,   -- integer coercion
  is_flagged  boolean not null default false, -- boolean coercion (groups/idols cover none)
  observed_on date,               -- date coercion, nullable
  updated_at  timestamptz not null default now()  -- not in the map, not editable
);
```

Deterministic keys (`walk-1`, `walk-2`, …) so a walk recipe deep-links without
a lookup first. Decide and record: RLS on with no policy (service role only)
versus left off, and whether the table is in the exposed schema at all.

**A third question the map itself raises:** `Regime` today is `pre_cutover` |
`resolver_owned`, and the sandbox is honestly neither. Rule whether it reuses
`pre_cutover` with a comment saying why, or earns a third regime — and say it
in words, because the next reader will ask.

## Two traps to rule on explicitly

1. **The residue sweep will cover it the moment it is in the map.**
   `tests/live/residue.live.test.ts` derives its search space from
   `EDIT_CONFIG`'s tables and fails on any value carrying the `admin-window`
   marker. That coverage is a gift — and it means the **seed values must not
   contain the string `admin-window`**, or the fixture reads as residue on
   every single run.
2. **A walker cannot save today, and this table does not change that.**
   STACK.md §5: the PATCH route calls `requireAdmin()`, staging's
   `admin_allowed_emails` does not hold `walker@admin-window.local`, so every
   save from `EditableCell` gets a 403 — and STACK says that row is **Ben's
   call and no agent adds it**. So "walkers can interact with it through the
   ui" needs a second thing from Ben, not just a table. It is asked in
   `agenticflow/tracker/for-human/TASK-0034.md`; do not decide it and do not
   add the row.

## Scope and blast radius

This ticket writes a ruling and no code: no table is created, no DDL is run,
no dependency is added. It also fixes the two dependent tickets' scopes —
TASK-0035 (the map entry) and TASK-0036 (the tooling and the recipe) are
scoped on candidate paths today and should be amended to whatever you rule.

**Not M1.** Nothing here gates the M1 endgame, which proceeds on the
groups/idols exception exactly as it stands: one field on one existing row,
the original noted, restored before the walk ends, residue sweep after. That
exception stays the rule until this whole chain lands.

vision_note: VISION's non-goal reads "No schema beyond the two handoff
pieces … no schema change from Admin code, no migration in this repo." Ben's
ruling keeps every word of that literally true — nothing enters `src/`,
nothing becomes a migration, nothing reaches production — while adding a
staging-only test fixture the non-goal never contemplated. It is his
exception to grant and he has granted it; record it as an exception rather
than pretending the non-goal always meant this.

## Acceptance criteria
A ruling recorded in ARCHITECTURE.md (with the dated paragraph in DECISIONS.md) that names, in words a builder can act on without asking again: (1) which of candidates A/B/C is taken and why, and if B or C, whether TASK-0021's stored pin is untouched or amended — an amended pin lands as an amended check on TASK-0021 in the same pass; (2) the table's name and its exact columns with types, covering text, integer, boolean, date and one nullable; (3) whether RLS is enabled and whether the table is exposed to PostgREST at all; (4) where the reset tooling lives, what resets it, and the cadence (before each walk, after, or both); (5) which Regime the EDIT_CONFIG entry carries and why, since the sandbox is neither pre_cutover nor resolver_owned as those are defined today; (6) an explicit sentence that the seed values carry no 'admin-window' marker, so residue.live.test.ts does not read the fixture as leftover.

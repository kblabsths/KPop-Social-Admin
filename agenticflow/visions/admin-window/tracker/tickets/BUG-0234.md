# A host answer is admitted leg by leg, so three legs still admit an answer that is not a PostgREST answer

## Description
The alien-host chain BUG-0224 -> BUG-0227 -> BUG-0228 -> BUG-0229 -> BUG-0230 fixed five true properties one at a time, each found by the next QA lane. This ticket is the class stated as ONE bar (LESSONS 13) and the three legs the bar still does not hold on. It changes no surface behaviour against a real PostgREST.

THE BAR (now ARCHITECTURE.md §4.1, "What a PostgREST ANSWER is", ruled 2026-09-15): a response is this app's answer only when EVERY leg the read named arrived in the shape PostgREST is specified to send it; anything else refuses as a WHOLE through the one rule (`unreadableAnswer`) naming the object, before any surface derives a row, a figure or an emptiness from it. Legs: error (`classify`), rows (`isRowSet`/`isRowOf` against this read's own `columns`), count (`isCount`), and — for a read that asks the host about ITSELF — the schema description document (`src/lib/db/schema.ts`).

Three legs measured open on this tree (QA on BUG-0223 and BUG-0229, 2026-09-14/15):

1. `readComplete` (src/lib/db/result.ts:1282+) admits `count < rows.length`. The truncation arm asks only `count > rows.length`, so a host publishing a total SMALLER than the rows it sent reaches a surface as an ok read whose head figure contradicts its own list. Both directions are one refusal: a total that is not a total OF THIS SET is not a total.

2. `readOne` (result.ts:1343+) treats `data === null` as "no row". supabase-js rewrites a bodyless 404 to `status 204, error: null, data: null` (PostgrestBuilder's `res.status === 404 && body === ''` arm — the same rewrite `countRead`'s docstring already records), so /queues/<uuid> against a blank-404 host says "No row with that id" over a read that never happened. An empty `.maybeSingle()` from PostgREST is a 200 carrying `null`; a 204 is not an answer. The response status is on the object supabase-js returns.

3. `functionsIn` (src/lib/db/schema.ts:88-95) admits any `typeof paths === "object"`, and a JSON ARRAY is one. A host whose OpenAPI body carries `paths: [...]` yields an empty function set, so `readFunctionInstalled` answers `not_provisioned` — a FALSE absence about the database, from a document this app could not read. `unreadableDescription` is the answer that shape already has.

OUT OF SCOPE, ruled here so nobody re-opens them one at a time:
- Per-column TYPES. The row leg asks which columns are PRESENT, never what they hold. A row carrying every declared column with wrong-typed values is admitted and a render that then throws is caught by the route error boundary (companion ticket), not by a fifth predicate in lib/db — `[{}]` defeats an element-type guard and the next shape defeats its successor.
- supabase-js `parseInt` leniency on `Content-Range` (`*/5-` -> 5, `*/0x10` -> 16, `*/1e20` -> 1). Indistinguishable from a real total at this layer; named as a limit in §4.1, re-opened only by a measured body, never by a vocabulary guess about the digits.
- `/records/<table>/<uuid>` drawing a page of dashes for a nonexistent row under ANY_COLUMNS: that is the record surface's contract as designed (a read with no declared columns has no column leg to ask). Leg 2 above is what makes the blank-host case refuse.

## Acceptance criteria
1. `readComplete` refuses when count and rows contradict each other in EITHER direction, through `unreadableAnswer` naming the object — the existing `count > rows.length` truncation message (which names ROW_CAP and tells the reader to narrow the filter) stays for the truncation direction only, because it is true only there.
2. `readOne` admits `data === null` as "no row" only from an answer that carried one: a response supabase-js rewrote to 204 is `unreadableAnswer`, not an absence and not a row. A real empty `.maybeSingle()` (200, `data: null`) is unchanged.
3. `functionsIn` treats an array `paths` — and any body whose `paths` is not a plain object — as a document it could not read (`unreadableDescription`), never as a database exposing no functions.
4. Offline cases, one per leg, named exactly (the checks grep these titles): "a total smaller than the rows it came with is not a total of this set" (tests/offline/db/result.test.ts), "a single-row read admits no row only from an answer that carried one" (tests/offline/db/result.test.ts), "a description whose paths is not an object is unreadable, not an absence" (tests/offline/db/schema.test.ts). Each states BOTH fixtures (LESSONS 8): the shape it MUST flag and the real PostgREST shape it must NOT.
5. No new predicate family: the three fixes are legs of the same admission rule and each refuses through `unreadableAnswer` / `unreadableDescription`. No length cap, no value inspection, no per-column typing.
6. The docstrings say the RULE, not the incident list: each names the leg and what PostgREST is specified to send, citing ARCHITECTURE.md §4.1. (human-checkable)

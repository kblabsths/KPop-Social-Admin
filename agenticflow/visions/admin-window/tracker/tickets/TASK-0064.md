# The paging affordance: one control, five states, one fetch — drawn only where it can be honoured

## Description
**Module:** `src/components/ui/paging.tsx` (a NEW `"use client"` module) exported through the `src/components/ui/index.ts` barrel. This is the affordance BOTH paged surfaces draw, seeded before either of them so it is not hand-copied twice (§13.7, common violation 9: `StateOf` stands byte-for-byte in four pages).

**Read first:** ARCHITECTURE §4 rule 1's amendment of 2026-09-10 (the one framed fetch exception) and §5's client-state amendment. This module is the ONLY component in the repo permitted to call `fetch`, it calls this app's own route handler and nothing else, and the decision of whether to call it at all is not written here — it is `requestPage` in `src/lib/paging/machine.ts` (TASK-0063).

**Interface contract:**

```tsx
"use client";
import { type PageDeps, type PageState, requestPage } from "@/lib/paging/machine";

/** Binds the pure driver to a press. The ONLY fetch in this repo's components. */
export function usePageRows<Row>(
  initial: PageState<Row>,
  deps: Omit<PageDeps, "fetchJson">,
): { state: PageState<Row>; press: () => void };

/** The affordance itself: the control, the refusal, the exhausted sentence. */
export function PageMore(props: {
  state: PageState<unknown>;
  /** What the surface holds, in the app's own noun: "claims", "events". */
  holds: string;
  /** The window's size — what one press asks for. */
  size: number;
  onPress: () => void;
}): ReactNode;
```

`usePageRows` is a two-line binding: it calls `requestPage(state, { ...deps, fetchJson })` and sets the returned state. `fetchJson` is `fetch(url, { credentials: "same-origin" })` → `res.json()`, and it never throws out of the hook — the driver turns a rejection into a refusal (TASK-0063 rule 5).

**What `PageMore` renders, by state — this is the LOCK, the LIFETIME and the CONTENT of a transient status, and LESSONS 1 is the reason all three are in one component instead of two pages:**

- `status: "idle"`, not exhausted → the control, built from the existing `Button` primitive, reading `Show the next <size> <holds>`, with `data-paging="more"`.
- `status: "loading"` → the same control, **inert** (`disabled`), `data-paging="loading"`. A second press while one is in flight cannot happen from the markup, and cannot happen from the driver either.
- `status: "exhausted"` → **no control at all**, and one sentence saying the set is complete, `data-paging="exhausted"`. A control that cannot be honoured is never drawn (SPEC F10's rule, applied by F14).
- `refusal !== null` → the refusal line beside the rows, naming the object in the app's voice with the database's own words where it has them (§4.1, LOOK_AND_FEEL "the app shows what the database said"), `data-paging-refusal` on it. The control stays unless the state is exhausted, because a refusal is retryable — and the row list is untouched.

**Look and feel (both halves, or the ticket is mis-built):** the control is the shared `Button`, the sentence uses the design tokens through the existing primitives, no raw colour or spacing values, and the copy is plain and quiet — it names what the operator gets, never "load more data". Inter-element spaces are written `{" "}` (the whole-tree rule in `tests/offline/ui/copy.test.ts`).

**The client boundary is a real trap here** (`tests/offline/shell/client-boundary.test.ts`, BUG-0094): a SERVER module importing a VALUE out of a `"use client"` module compiles, lints and renders green offline, then answers 500 in a production build. Nothing outside a client module may import a value from this file. Everything both sides need is already in `src/lib/paging/**`, which has no directive.

**No page is wired in this ticket.** The two paged surfaces land in TASK-0067 and TASK-0069; this ticket proves the affordance renders its four states from props, offline.

## Acceptance criteria
PageMore renders its states from props, asserted on rendered markup: idle draws the control with data-paging="more" and the next window's size in its words; loading draws the same control inert with data-paging="loading"; exhausted draws NO control (zero occurrences of the control in the markup) and one sentence saying the set is complete, with data-paging="exhausted"; a refusal draws the refusal line naming its object with data-paging-refusal while the row markup handed in is unchanged. A state whose NEXT bound cannot be honoured draws no control either: given held = MAX_PAGE_OFFSET + size (the bound pageBound refuses for being above the ceiling), the markup carries zero occurrences of the control and one sentence saying this view shows no further rows, marked data-paging="limit" and never data-paging="exhausted" — the set is not finished and the surface must not say it is (SPEC F10, QA residual 4 off TASK-0063). The control is the shared Button primitive and the module introduces no raw colour, spacing or type value — the token guard and the primitives guard are green. tests/offline/shell/client-boundary.test.ts is green with the new client module in the tree, and no server module imports a value from it. usePageRows calls requestPage and does not re-implement any of its rules: the only fetch in the module is inside fetchJson, and grep shows exactly one fetch( call in src/components. pressing() is exported from src/lib/paging/machine.ts and driven offline: pressing(idle) returns status "loading" with rows, held and refusal untouched, pressing(loading) and pressing(exhausted) return the SAME object by identity, and requestPage called with a pressing() state issues zero calls to fetchJson — the double-press proof, composed from pure pieces because the offline tier has no DOM. The hook publishes pressing(current) before it awaits and hands the pre-press state to requestPage; its press guard reads the current state through a ref and never fires a request from inside a setState updater (React 19 StrictMode invokes updaters twice — two requests from one press). fetchJson is exported and rejects only with an Error carrying words: driven against a stubbed global fetch it rejects with an Error for a non-JSON body and for an empty body, never with a bare string, null or undefined, and it does NOT reject on a non-ok status — a 400 carrying the refused PageAnswer parses and reaches the driver. machine.ts remains a pure leaf and tests/offline/db/layering.test.ts is green over it. The six live parity suites for the two pages that will consume it are unchanged and green.

**1. The transient status is the LEAF's decision, published before the await.** TASK-0063's builder trap 1: `requestPage` publishes NO interim state — it returns only the state a press ENDS in — so the `loading` arm that makes a double press safe exists only if this ticket writes it. It is a paging decision, so it lives where every other paging decision lives and where the offline tier (no DOM, `renderToStaticMarkup` only) can drive it:

```ts
// src/lib/paging/machine.ts — one new pure export, leaf rules unchanged
/**
 * The state a press publishes BEFORE its request resolves: `idle` becomes
 * `loading` with rows, held and refusal untouched; any other status comes
 * back as the SAME object, so a second press changes nothing.
 */
export function pressing<Row>(state: PageState<Row>): PageState<Row>;
```

`usePageRows` then: publish `pressing(current)`, and hand the PRE-press (`idle`) state to `requestPage`, whose answer replaces the state when it resolves. **The press guard reads the current state through a ref, never inside a `setState` updater** — React 19 StrictMode invokes updaters twice in development, and a `fetch` fired from inside one is two requests from one press, which is the exact defect this arm exists to prevent.

**2. `fetchJson` rejects with an `Error`, always.** `requestPage`'s `reasonOf` renders a non-Error rejection with `String(thrown)`, so a rejection carrying `undefined` becomes the word "undefined" in the operator's refusal line. Export it from this module so the offline tier can drive it against a stubbed global `fetch`:

```ts
export function fetchJson(url: string): Promise<unknown>;   // fetch(url, { credentials: "same-origin" }) -> res.json()
```

A body that is not JSON (an HTML error page, an empty body) already rejects with a `SyntaxError` — an Error with words; what must not happen is a rejection with a bare string, `null` or `undefined`. A 400 is NOT a rejection: the route answers the `refused` PageAnswer as JSON and the driver reads it (TASK-0066 §3), so `fetchJson` must not throw on a non-ok status — it parses the body.

**3. Residual 4, ruled IN scope, and it is this widget's rule (not TASK-0067's).** Past `MAX_PAGE_OFFSET` the state never reaches `exhausted` — a bound refusal returns to `idle` by design (TASK-0063 rule 4) — so today's spec would keep drawing a control every press is refused for, forever: precisely what SPEC F10 forbids and what this ticket's own title promises ("drawn only where it can be honoured"). The widget already holds both halves of the question (`state.held`, `size`), and `pageBound` is the one place that answers it, so: **`PageMore` draws no control when the bound the next press would carry cannot be honoured** — `pageBound(String(state.held), size).kind !== "ok"` — and instead draws one plain sentence saying this view shows no further rows, marked `data-paging="limit"`. Not `data-paging="exhausted"`: the set is not finished and the surface must not say it is. This is a props-driven markup assertion, so it costs one offline case (`held: MAX_PAGE_OFFSET + size`), no DOM and no fetch.

TASK-0067 needs nothing for this: the page builds its initial state from the first screen (`held` = one window), never past the ceiling, and its own drawing rule — a count established there is more — is unchanged.

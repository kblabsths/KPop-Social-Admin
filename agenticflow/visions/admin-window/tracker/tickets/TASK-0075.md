# claims.live stops racing the scraper: one snapshot instant for the identity proofs, whileStill for the page-vs-database ones

## Description
**Modules:** `tests/live/claims.live.test.ts` (every case in it that compares two reads) and `tests/live/parity.ts` (one new export). Test tier only — **no product code changes in this ticket**, and no other live file is touched.

**Why.** `npm run test:live -- tests/live/claims.live.test.ts` reddened **3 of 5 consecutive runs** for builder-250 on ccd48e1 (TASK-0064's lane, whose diff does not reach this file), a DIFFERENT case each time, and was 12/12 green twice for the QA lane an hour later. Every failure is two live reads of staging disagreeing with each other: run 3, 'the windowed claims read and the id-list join select the same claims' — 877 ids expected, 879 received, the two extra carrying a uuidv7 timestamp prefix (`01a08dbb`) hours newer than every other id in the set. The scraper inserted two pending claims between the suite's two reads. Run 5 failed on 'renders each bucket's count exactly as the view holds it', the same shape one layer up. This file is a stored check on TASK-0066, TASK-0067, TASK-0070 and BUG-0167, so the tax is every M3 lane, and the first thing it teaches a bounced builder is to distrust a red live suite.

**The ruling this implements** (architect, 2026-09-10, DECISIONS.md — read it, it is three rules and a closed door):

1. **Where the test writes every query** — an identity or set-equality proof between two shapes — capture ONE instant at the top and give every leg the same explicit UPPER edge. Deterministic, no retry, and it sharpens the proof: what is compared is the two shapes, not the two clocks.
2. **Where one leg is the app's own read** and cannot take an upper edge (a rendered page against a test query) — `whileStill`, already in `tests/live/parity.ts` and already the ruled device for this class since the 2026-09-02 `/cycles` 38-vs-39 finding. `cycles.live.test.ts` and `dashboard.live.test.ts` use it; this file is the holdout.
3. **Never a numeric tolerance.** "±2 claims" cannot tell an insert from a drop, and it is precisely the slack that would have hidden BUG-0167 (the two legs of one gauge diverging by a single claim out of 877). A live proof about the SHAPE of a read grades by identity or it proves nothing. No `--retry`, no `it.skip`, no widened comparison, no retry loop around an assertion.

**Interface contract — the shared instant gets ONE spelling** (LESSONS 5; two files would otherwise each invent a `Date.now()`):

```ts
// tests/live/parity.ts
/**
 * The instant every leg of one live identity proof reads UP TO — captured
 * once, handed to each leg, ending strictly before now so a row arriving
 * mid-test lands outside the window both legs asked for.
 */
export function snapshotAsOf(settleMs?: number): string;   // ISO 8601; default settle 5_000 ms
```

The settle margin is for insert latency and clock skew between this process and the database, not for jitter: state in the docstring which one it is, and keep it small.

**Where it goes in this file.** `describe("the two shapes of the pending-claims gauge against staging")` — SHAPE A (`.from(pendingClaims) … .gte("observed_at", since)`) and SHAPE B's scan (`.from(observations) … .gte("observed_at", since)`) each gain `.lt("observed_at", asOf)` with the SAME `asOf`, captured once before either is issued. B's id-chunk legs need no edge: they are bounded by the ids the scan returned. The bucket-count cases in `describe("the classification buckets against staging")` are the page-vs-database class and take `whileStill` instead — the page's own read carries no upper edge and this ticket does not give it one (that would be product code).

**Non-vacuity is not negotiable.** The window stays 90 days minus the settle margin, so `fromWindow.length > 0` still holds on staging (877 pending claims in the window as of TASK-0074's census) — say the number you measured. Both cap guards stay exactly as they are: a leg at 1000 still refuses to compare, because a green there would be about the cap and not about the shapes (and BUG-0167 is the open ticket about that regime).

**Out of scope, deliberately:** the other eleven live files (`browse.live` was 5/5 green through the same window); any change to what the pages read; `CHUNK_FANOUT`; BUG-0167's tie-break (it lands next, on top of this).

## Acceptance criteria
snapshotAsOf is exported from tests/live/parity.ts with a docstring saying what the settle margin is for, and it is the only spelling of the shared instant: grep shows no other Date.now() or new Date() composing a read bound inside tests/live/claims.live.test.ts. In the two-shapes describe, the windowed claims read and the observations scan carry the SAME asOf as an explicit upper edge on observed_at, captured once before either leg is issued and handed to both — not re-derived per leg — and the id-chunk legs are left bounded by the scan's ids as they are today. Both bucket-count parity cases ('renders each bucket's count exactly as the view holds it' and its per-source-filter sibling) compare the rendered page against the database through whileStill, the same way cycles.live.test.ts and dashboard.live.test.ts already do, so an insert between the render and the count is retried against the same comparison and a database that will not hold still throws rather than passing. Nothing is graded with slack: every comparison in the file is still exact equality, there is no toBeCloseTo, no retry option, no skipped case and no widened assertion anywhere under tests/live. Both cap guards in the identity proof survive verbatim (each leg still asserted below 1000 with its own message) and the proof is still non-vacuous on staging — fromWindow.length > 0, and the closing History entry states the claim count measured. The file is run FIVE times back to back on the landed tree and is green every time, with the five results and the elapsed times stated verbatim in the closing History entry (this is the whole point of the ticket and the stored check only runs it twice). No product code is touched: the diff is confined to tests/live/claims.live.test.ts and tests/live/parity.ts, and the other eleven live files are byte-identical and green.

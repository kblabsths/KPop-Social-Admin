# claims.live stops racing the scraper: one snapshot instant for the identity proofs, whileStill for the page-vs-database ones

## Description
**Modules:** `tests/live/claims.live.test.ts` (every case in it that compares two reads) and `tests/live/parity.ts`. Test tier only — **no product code changes in this ticket**, and no other live file is touched.

**Why this file exists at all.** `npm run test:live -- tests/live/claims.live.test.ts` reddened on a DIFFERENT case each run for builder-250 and was green for the next lane an hour later: every failure is two live reads of staging disagreeing with each other while the scraper writes between them. This file is a stored check on TASK-0066, TASK-0067, TASK-0070 and BUG-0167, so the tax is every M3 lane, and the first thing it teaches a bounced builder is to distrust a red live suite.

## Reopened after attempt 1 — what stands, and what bounced

**Landed and VERIFIED by QA on e21e990; not up for re-litigation, keep all of it:** `snapshotAsOf` exported from `parity.ts` with the settle-margin docstring; the identity proof (`the windowed claims read and the id-list join select the same claims`) bounded by ONE `asOf` on both legs; no `Date.now()`/`new Date()` left composing a read bound in this file; both cap guards verbatim; non-vacuity (877 claims in the window); no tolerance anywhere; the diff confined to two files.

**Bounced on criterion 6.** The file was run **13 times across two independent checkouts and reddened 3 times**, every red on a case this ticket changed:
- ×2 — both bucket-count cases: `the database changed under this comparison on all 3 attempts (117 then 117 bytes)`, thrown by `whileStill` at `parity.ts:913`;
- ×1 — `AssertionError: expected 878 to be 877` at `claims.live.test.ts:334` (`gradeWindow`), on `draws the view's longest-waiting window`, a case attempt 1 deliberately scoped out.

**Why `whileStill` did not stop the race — the measurement that rules this ticket.** The device's protection decays with the DURATION of the shape it holds still: it reads, makes, reads again, and needs the two reads to agree. `bucketCounts()` is **six sequential count round trips**, so each attempt holds a ~4 s comparison window open and three attempts hold it open three times over; a scraper cycle writes through every one of them, and the intermittent wrong-count red simply became an intermittent attempts-exhausted red on the same trigger. `cycles.live` and `dashboard.live` hold one small read, which is the only reason the same device works there.

## The ruling (architect, 2026-09-10 — DECISIONS.md corollary of the same date; the 2026-09-10 live-proof ruling itself stands UNCHANGED)

1. **Every page-vs-database and page-vs-page comparison in this file goes through `whileStill`, and the shape held still is ONE ROUND TRIP.** One `select` over the view, tallied or projected in TypeScript; the count that decides a surface's kind is that read's own `length`, never a second `countRows`; `gradeSurface`'s `counted` is handed a NUMBER, not a thunk that reads again. No held shape issues two queries. This is the remedy — not a higher attempts count, not a tolerance, not a skip.
2. **The snapshot cannot bound a page render and must not be made to.** `/claims` takes no upper-edge parameter, giving it one would be product code written to suit a test, and bounding only the TEST's leg is worse than useless: it freezes the detector while the page keeps racing, converting an intermittent disagreement into a deterministic red that reads like a product defect. `asOf` stays exactly where it is — the identity proof, where the test writes every query — and goes nowhere near a page comparison.
3. **The single read is bounded and REFUSES above its bound.** Staging holds 877 pending claims (TASK-0074's census; QA measured 877 then 878 on 2026-09-10) and PostgREST stops at 1,000 rows, so an unguarded `.limit()` truncates silently and the tally becomes a statement about the cap. Bound the read explicitly and throw — naming the cap and the number — when it comes back at or above the lesser of its own bound and 1,000, the way the identity proof's two cap guards already do.
4. **`attempts`:** `whileStill`'s default stays 3 in `parity.ts`. A call site may raise it, to at most 5, only ALONGSIDE the one-read shape and only with a comment stating what it buys: more independent still windows, never a widened comparison. This is legal where a `--retry` flag is not, because `whileStill` retries the PRECONDITION (did the database hold still) and never an assertion outcome — every attempt makes the same exact comparison and exhaustion throws.
5. **Never a tolerance** (DECISIONS 2026-09-10 rule 3, unchanged): no `toBeCloseTo`, no `±`, no `--retry`, no `it.skip`/`it.todo`, no widened assertion anywhere under `tests/live`.

## Scope widened to the whole class IN THIS FILE (architect, 2026-09-10)

QA deliberately filed no third lane here because BUG-0167 already collides on this file; BUG-0167 `depends_on` this ticket, so the widening lands HERE and BUG-0167 inherits it. The file is not race-free until all five cases are covered:

One read: `whole` is that read's own length, and the whole thing is held still around the render.
- **`renders the standing tab as the window of exactly that bucket's subset`** — the same shape over the standing bucket. Its EMPTY branch races too (the page and `claimsFromDatabase("standing")` disagree the instant staging gains a standing claim), so it is held still the same way; `windowLine`'s `held: 0` is graded inside that same still window.
- **`narrows the same way for every spelling of one source id`** — page against PAGE: `renderedCount(asked, …)` vs `renderedCount(canonical, …)` and `claimIds(asked)` vs `claimIds(canonical)` are two renders at two instants. Hold the database still around a `make` that renders the pair (or the whole spelling set) together, so every render compared is inside one window in which nothing moved. The `held < whole` guard in that case is two more test counts — derive both from one read.

# Queues item page: an address that is not a review-item id is reported as a failed database read, not as no such item

## Description
Found by QA attacking BUG-0068 (2026-09-04): the PATCH route and the record
page now both settle a malformed id BEFORE any read; the queues detail page is
the third and last address-taking surface, and it still does not.

**Expected**, by this app's own settled answer on the two surfaces beside it:
`review_items.review_item_id` is a `uuid` (scraper migration
`20260901000002_the_review_item_opens_once_per_subject.sql`, line 39), so a URL
segment that is not a uuid can equal no key in that table. "No such item" is
knowable with certainty and without a database — which is exactly what
`isRecordId` (`src/lib/db/records.ts`) carries, why BUG-0065 put it BEFORE the
record page's read, and why BUG-0068 put it before the PATCH route's write.

**Found**: `src/app/queues/[reviewItemId]/page.tsx:398-399` takes the segment
off `params` and hands it straight to `readReviewItem`, which builds
`.eq("review_item_id", <segment>)`. Postgres refuses the comparison with
`22P02 invalid input syntax for type uuid`, the data layer classifies that
(correctly, for a read it did make) as an arbitrary failure, and the page
renders the FAILED-READ state — the one whose recovery line is "reload".
Reloading re-sends the same segment forever, so that advice can never work: the
operator is stranded on unactionable advice, which is the same harm BUG-0065
was filed to remove one surface over.

**Measured** (2026-09-04, run/admin-window @ 2bbe138, offline tier with the
stub client scripted to answer `invalidUuidSyntax`):
  - reads issued: `[ { table: 'review_items' } ]` — expected none;
  - rendered states: `[ 'error' ]` — expected anything but the failed-read one.

**Reach**: an operator's own address bar, and the app invites it — the queues
empty state says "check the id in the address bar", and the review-item id is
hand-carried between surfaces. That is a wider path than BUG-0068's (which had
no UI path at all), which is why this is P2 and not P3.

**The fix**, if the architect agrees with the two rulings above: ask the id
question BEFORE the read and answer it with this page's own no-such-row state
(the `Empty` card it already renders for `item.data === null`), not with a new
sentence. Do NOT write a second id grammar: `isRecordId` is the one grammar in
this repo (ARCHITECTURE §9.1 item 9, DECISIONS 2026-09-04) and it takes the raw
segment and no config, so it applies to a `review_item_id` unchanged. The
error branch itself stays exactly as it is — a read that really happened and
really failed still reports what the database said (LOOK_AND_FEEL).

**Where it is pinned**: `tests/offline/review-item/page.test.ts`, describe "a
queues address that is not a review-item id". QA left it as a STRICT `it.fails`
pin naming this ticket, so it is green only while the divergence is live; the
fix must flip it back to a plain `it()` in the same commit (the convention this
repo already uses for admin-window/BUG-0013). Watched RED as a plain `it()` on
2bbe138, both halves, one at a time:
  "a segment that can be no review_item_id needs no read: expected
   [ { table: 'review_items', ... } ] to have a length of +0 but got 1"
  "the answer to a bad address is not a failed read: expected [ 'error' ] to
   not include 'error'"

## Acceptance criteria
A /queues/{reviewItemId} address whose segment is not a review-item id renders the page's own no-such-item state, having issued NO database read (observable as zero recorded calls on the stub client in tests/offline/review-item/page.test.ts), and the rendered surface carries no data-state="error" card. The page asks isRecordId from src/lib/db/records.ts — the same function the record page and the PATCH route ask; no second id grammar, regex or per-table key shape is written anywhere (ARCHITECTURE 9.1 item 9). Every other answer this page gives is unchanged: the database's own words for a read that really happened and failed, the not-provisioned state for an absent table, the no-such-row state for a well-formed id that matches nothing, and the item itself when it is there. The strict it.fails pin naming this ticket is flipped back to a plain it() by the fix.

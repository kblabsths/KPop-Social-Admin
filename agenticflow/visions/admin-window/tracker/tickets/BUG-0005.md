# Credential guard still misses destructured and optional-chained env reads, so the one-reader criterion holds for some spellings only

## Description
Expected (TASK-0002 acceptance criterion, restated by BUG-0003): 'src/lib/db/client.ts is the only file under src/ reading SUPABASE_SERVICE_ROLE_KEY', proved structurally by tests/offline/db/layering.test.ts.

Found: envReadOf() at tests/offline/db/layering.test.ts:101-109 requires the character after 'process.env' to be '.' or '['. Four spellings that name the credential just as plainly are therefore invisible to both real rules ('reads the service-role key in the db client alone' :142, 'reads no other SUPABASE_ credential outside the db client' :148):

  1. const { SUPABASE_SERVICE_ROLE_KEY } = process.env;   (ordinary Node/Next code)
  2. process.env?.SUPABASE_SERVICE_ROLE_KEY               (habitual optional chaining)
  3. process.env?.["SUPABASE_SERVICE_ROLE_KEY"]
  4. process.env["SUPABASE_" + "SERVICE_ROLE_KEY"]        (a dynamic bracket read -- the family the doc comment at :94-99 claims is counted 'by construction' because a text scan cannot resolve it; the concatenated form starts with a quote, so it escapes the bracket-identifier alternative and the rule's own stated rationale does not hold for it)

Exact repro (repo root, run/admin-window @ d212ecc):
  1. printf 'const { SUPABASE_SERVICE_ROLE_KEY } = process.env;\nexport const key = SUPABASE_SERVICE_ROLE_KEY;\n' > src/__probe.ts
  2. ./node_modules/.bin/vitest run tests/offline/db/layering.test.ts
  3. Observed: the two credential rules stay green -- the new reader is not reported. Repeat with each spelling above for the same result.
  4. rm src/__probe.ts
Control: the dot, bracket-string-literal and bracket-constant forms ARE reported (13 tests green at d212ecc), so the widening BUG-0003 asked for works; these are the spellings it did not name.

No file under src/ uses any of these forms today (grep -rnE 'process.env' src, 2026-09-02: only src/lib/supabase.ts:3-4 and src/lib/db/client.ts:38-39, both dot form), so this is a latent hole in the ratchet, not a live leak -- hence P2, not P1. Impact is the same class BUG-0003 was filed for: STACK.md's trust boundary names 'service-role material leaking into a client bundle' in scope, every remaining M1 ticket adds files under src/, and a page that destructures the key ships with the layering suite green.

Pinned at tests/offline/db/layering.test.ts, describe 'the credential guard itself', test 'detects a reader that destructures or optionally chains process.env', as it.fails (vitest strict xfail; watched red first as a plain assertion: 'expected [ src/lib/db/client.ts ] to include src/__credential_guard_probe__.ts').

Fix: extend envReadOf() (or add a sibling rule) to cover destructuring from process.env, optional-chained member and bracket access, and a bracket read whose key is not a resolvable non-credential literal; keep the existing three forms and the negative control (process.env["NODE_ENV"] / ["PORT"] must stay unreported). Then DROP the '.fails' from that test so it asserts normally. Do not touch DEPRECATED_UNTIL_TASK_0005 -- verified unchanged at d212ecc. Note tests/offline/db is also TASK-0002's touch scope (claimed by builder-6 at 07:02:54Z); expect to rebase on it.

# /claims: ?domain= narrows every figure on the page and no rendered word says so

## Description
Found on the scoped re-look of `/claims` after BUG-0138 landed (designer, 2026-09-10; production build, my own instance on port 8783 against staging; evidence `agenticflow/tracker/evidence/M2/designer/claims-domain-events-unnamed.png`).

**Measured on staging, `/claims?domain=events`:**

- the bucket table renders `awaiting_row` **741** (unnarrowed: 769) and the gauge card renders **849** / "1 source, **1 domain**" (unnarrowed: 877 / "2 domains") — so the domain narrowing really is applied to every count, exactly as A2 ruled;
- the window line reads "**849 claims match these filters**; the 50 longest-waiting are below";
- the bucket caption switches to its narrowed arm: "…with the claims in it **under the filters above**";
- and the filter bar above renders **`bucket: all`** and **`source_id: all`**, both accent-filled as active. The list's h2 says **ALL CLAIMS**.

The words "domain" and "events" do not occur anywhere in the rendered page. Every visible control says the page is unnarrowed; every figure on it is narrowed. An operator looking at 741 beside 769 from yesterday has no on-screen way to learn why, and the bookmarked breakfast link cannot be read back from the screen it draws.

Two clauses are actively false in that state: "under the filters above" (the narrowing is not above — A2 removed the domain chip row) and "match these filters" (`NARROWED_BY_FILTERS`, `src/components/ui/window-line.tsx:260`, is folded into the scope for a facet the page renders no control for, so the sentence points at two chip rows that both read `all`).

This is BUG-0138's own criterion 7 — "named in the window line's scope and in the bucket caption's narrowed arm" — unbuilt for the domain half. The bucket and source narrowings are fine: their chips show which one is set.

Provenance checked before filing: `git log` on `src/app/claims/page.tsx`, `src/components/ui/window-line.tsx` and `src/components/claims/filter-bar.tsx` returns ticket-bearing commits only (5f08227 BUG-0138, c84e7a7 BUG-0155, c9f4e5b BUG-0049). No human-lane divergence — this is a violation, not a reconciliation.

## Acceptance criteria
1. **A narrowing the page applied is named on the page in the app's own words.** With `?domain=<value>` set, the rendered text of `/claims` names the domain facet and its value — in the window line's scope clause and in the bucket caption's narrowed arm — in every state that arm renders: the filled window, the did-not-fill window, and the `NOTHING_MATCHED` card. Spelling is the builder's, subject to copy bar 5 (sentence case, the value verbatim in mono) and the glossary.

2. **"these filters" and "the filters above" may only refer to narrowings the page renders a control for.** Where the only narrowing in the scope is one with no rendered control, those two phrases do not appear — the sentence names the narrowing instead. Where both kinds are set, the sentence is true of both.

3. **The bucket caption and the window line agree** about what narrowed the figures they sit under, as `claimsNarrowed` already guarantees for the two chip facets.

4. LOOK_AND_FEEL bar 13 ("every windowed list states its window on screen — which read produced the rows") and bar 11 ("state lives in the URL … the breakfast view is a link") both hold for `?domain=` as they do for `?bucket=` and `?source_id=`.

5. Nothing else on the page moves: the bucket-table columns, the chip rows, the list order, the four state primitives and every `data-*` attribute stay as BUG-0138 left them.

**Human-check (human-checkable):** open `/claims?domain=events` at 1440x900 and read only the screen — the page says a domain narrowing is in force and names `events`, and no sentence claims a filter above is set when both chip rows read `all`.

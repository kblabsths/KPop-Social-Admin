# a percent-encoded spelling of a struck table serves the client-rendered error shell, not the app's framed 404

## Description
**Expected** (admin-window/TASK-0040 criterion 3, and admin-window/BUG-0017's whole reason): a record URL whose table the edit map does not carry answers with the app's OWN framed 404 — the routed miss — "never a `notFound()` thrown from the dynamic segment". `next.config.ts`'s own doc comment and `tests/http/auth.http.test.ts` block 1c both state the governing fact: a percent-encoded table segment is the SAME URI as the plain one (RFC 3986 §6.2.2.2), which is why the suite pins `/records/ev%65nts/<id>` as a working record surface.

**Found**: for the two tables Ben struck on 2026-09-08, the percent-encoded spelling is NOT the same answer as the plain one. It falls through `next.config.ts`'s `UNMAPPED_TABLE` pattern (`[^/%]+` deliberately excludes `%`), reaches `src/app/records/[table]/[id]/page.tsx`, and is refused by the `notFound()` throw — the client-rendered error shell BUG-0017 exists to eliminate.

**Repro, measured 2026-09-08 on a production build of run/admin-window @ fcc47c8** (own `next build` + `next start --port 8779` from a detached worktree, staging env, minted `authjs.session-token`, real staging uuids):

    GET /records/groups/259e2030-00bd-4200-8730-4669e46a0c04
      -> 404, len 9728, framed: <h1> present, six nav links, no id="__next_error__"
         (byte-shape identical to /analytics, the routed-miss control)
    GET /records/gro%75ps/259e2030-00bd-4200-8730-4669e46a0c04     <-- same URI
      -> 404, len 8006, id="__next_error__" present, NO <h1>, NO navigation
    GET /records/idols/0a3443a6-4f54-483a-988e-4f639761254a   -> 404, len 9728, framed
    GET /records/idol%73/0a3443a6-4f54-483a-988e-4f639761254a -> 404, len 8004, error shell

    control, a table that IS on the map:
    GET /records/ev%65nts/01a03c9b-1d28-707d-9873-f73ab3add10c -> 200, len 20301, framed

**What changed and why it is filed now.** Before TASK-0040 this URL served a real record page (200; `next.config.ts` records len 13487). The strike moved `groups`/`idols` from the mapped set into the rewrite's known `%` gap, so the same URI went from a working page to an unstyled, un-navigable document. The gap itself is pre-existing and documented as deliberate; what is new is that two formerly-working record URLs now land in it. TASK-0040 was told to leave `next.config.ts` alone, so this is not a bounce of that ticket — its criterion 3 names the rewrite "already derived from `EDITABLE_TABLES`" and that rewrite is exactly what shipped.

**Not a security finding, measured**: the gate is untouched on every spelling — anonymous `GET /records/gro%75ps/<uuid>` answers 307 to `/login?callbackUrl=...`, as do the plain and case-variant spellings, so nothing discloses which record surfaces exist. `PATCH /api/admin/records/gro%75ps/<id>` is refused 404 `{"error":"groups is not an editable table"}` like every other spelling; no write path is involved.

**P3 because the reach is a hand-crafted URL**: no browser produces `%75` for `u`, so the operator impact is a degraded 404 document on a URL essentially nobody types. Raise it if the architect judges the BUG-0017 class worth closing whole.

**Direction is the architect's, not prescribed here.** The obvious move (claim `%` segments too) is the one `next.config.ts` argues against, because it would 404 the working `/records/ev%65nts/<id>`; matching a DECODED segment, or deciding the miss before the render shell, are the other two shapes. A wider character class alone would break a URL that works today.

**The pin is a strict xfail.** `tests/http/auth.http.test.ts`, in the `a record URL for a table the edit map does not carry` describe: `it.fails("BUG-XXXX: serves the framed 404 for a percent-encoded spelling of a struck table")` — green while the divergence stands, RED the day it is closed. **The fix flips it back to a plain `it(...)`**, and the check below then proves it. Watched red as a plain `it()` before filing, on this exact tree: `AssertionError: /records/gro%75ps/2f0bc11e: expected '<!DOCTYPE html><html id="__next_error…' to match /<h1[\s>]/`. The status assertion runs before the shape assertion and passes today, so a harness that could not start the server does not satisfy the pin quietly.

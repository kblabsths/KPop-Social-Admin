# Claims: the window read takes an explicit offset, and the row shaping becomes an importable leaf

## Description
**Modules:** `src/lib/db/claims.ts` (the window read gains an explicit offset) and a NEW pure leaf `src/lib/claims/lines.ts` (the row shaping the page owns today moves out so a route handler can call the SAME one). `src/app/claims/page.tsx` and `src/components/claims/claim-list.tsx` change by IMPORT only.

**Nothing rendered changes in this ticket.** `/claims` must render byte-identically on the same fixtures before and after: same rows, same window line, same figures, same order.

**Why the shaping moves.** `claimLines()` lives in `src/app/claims/page.tsx` and `ClaimLine` lives in `src/components/claims/claim-list.tsx`. TASK-0066's route handler must return rows shaped exactly as the first screen's, and a second copy of that mapping is the class LESSONS 5 names (a shared spelling gets imported, never retyped) and common violation 9's shape. It is a pure function over rows plus a name map — no client, no env, no table name — so by common violations row 17 it belongs in the leaf layer wherever its first caller happened to live.

**Interface contract:**

```ts
// src/lib/claims/lines.ts   (LEAF: imports lib/sources/names, lib/records/routes,
//                            lib/claims/filters — leaf-to-leaf is a DAG, §4 rule 7)
export interface ClaimLine { /* moved VERBATIM from claim-list.tsx, docstrings included */ }

/** One claim as the list renders it, in the order the database returned them. */
export function claimLines(
  claims: readonly ClaimRow[],
  names: ReadonlyMap<string, string>,
): ClaimLine[];
```

`ClaimRow` is declared in `lib/db/claims.ts` today. A leaf may not import `lib/db/**`, **not even a type** (§4 rule 7, first paragraph). So the row shape this leaf reasons over is declared IN THE LEAF and `lib/db/claims.ts` imports it back — exactly what `ReviewItemRow` in `lib/review/shapes.ts` already does. Move `PendingClaimRow` / `ClaimRow` (and only those two interfaces) into `src/lib/claims/lines.ts`, re-export them from `lib/db/claims.ts` so no other caller changes, and keep every docstring.

`src/components/claims/claim-list.tsx` imports `ClaimLine` from the leaf and re-exports the type for existing importers. It renders exactly what it renders today.

```ts
// src/lib/db/claims.ts
export function readClaimWindow(
  options: { filter?: ClaimsFilter; limit: number; offset?: number },
  db?: SupabaseClient,
): Promise<DbResult<ClaimRow[]>>;
```

**The offset is a `.range()`, and the order does not move.** The chain keeps `.order("observed_at", { ascending: true, nullsFirst: false })` then `.order("observation_id", { ascending: true })` — the total order that makes window membership deterministic — and ends in `.range(offset, offset + limit - 1)` in place of `.limit(limit)`. `offset` defaults to 0, so every existing caller is unchanged in behaviour. `ClaimQuery` gains a `range(from: number, to: number): ClaimQuery` member (the chain is written out as a shape in this file on purpose — read its docstring before you touch it). The offline stubs that record `.limit(...)` for this read are updated in the same ticket; what may NOT change is the rendered output on a fixture.

**The unconditional exclusion is a property of `narrowed()` and stays there** (§6 trap 4): a paged read is the same narrowing at a different offset, and `selectClaims` still runs over what comes back. A paged read that skipped either would leak the parked `in_window` bucket into a rendering.

**Brief (common violations row 19 caveat):** this ticket adds no read. It changes the bound of one existing read and moves one pure function.

## Acceptance criteria
readClaimWindow accepts an optional offset, defaults it to 0, and issues one request whose chain is observed_at asc nullsFirst:false, then observation_id asc, then range(offset, offset + limit - 1) — asserted against the offline stub for offset 0 and for offset 50, including that the parked in_window bucket is excluded at both. claimLines and the ClaimLine, ClaimRow and PendingClaimRow interfaces live in src/lib/claims/lines.ts with their docstrings intact; src/app/claims/page.tsx declares neither and imports both; src/components/claims/claim-list.tsx imports the type rather than declaring it; grep shows exactly one declaration of claimLines and one of ClaimLine in src. The leaf imports nothing that can reach a database and tests/offline/db/layering.test.ts is green over it. /claims renders byte-identically to the pre-ticket tree on the offline suite's fixtures — same rows, same order, same window line, same figures — and its live parity suite is green.

# The six gauges as server-side queries with pure TypeScript aggregation

## Description
Module: `src/lib/gauges/` — six files, one per gauge, no UI. Authority: spec section 5 (the table of six and its 'one glance shows' column, and **'the gauges are server-side queries in the Admin app, not database views ... this build adds queries and charts, never tables'**); `contracts/resolver.md` section 12 (the knobs); SPEC F6; M1 EC8; acceptance test 11; ARCHITECTURE section 8.

One file each, each exporting a `fetch...` returning `DbResult<Rows>` and a **pure** `aggregate...` the offline tests exercise directly:

- `cycle-health.ts` — recent `resolution_runs`: duration vs the 15-minute cadence, `facts_examined` vs writes, outcome counts, errors.
- `resolution-latency.ts` — `observations.observed_at` to outcome latency percentiles, per domain, from `field_provenance.applied_at`.
- `pending-claims.ts` — the `pending_claims` buckets with counts and age percentiles, filterable by source and domain, plus the per-source `awaiting_row` trend.
- `queue-health.ts` — per queue: open count, age distribution, opens vs settles per week, fold rates (`folded_count`).
- `standing-disagreements.ts` — live contradictions with age and per-source split.
- `settled-values.ts` — per-source re-reject counts over time, from the rejection stamps (`observations.rejected_at` / `rejected_by`, migration `20260901000003`).

**The implementation rule, and the reason for it:** PostgREST cannot aggregate beyond `count`, and this campaign may add neither a database view nor a SQL-executing route (spec section 5; acceptance doc ground rules). So each gauge **fetches a bounded, time-windowed row set and aggregates in TypeScript**. Every query carries an explicit `limit` and an explicit window; an unbounded fetch is a defect. Keep the aggregation pure and separate from the fetch — that is what makes it testable offline and replaceable later.

Joins are two-step: fetch ids, fetch the related rows with `.in(...)`, join in code (ARCHITECTURE section 4.2). `pending_claims` carries **no age and no value** — age comes from `observations.observed_at` by `observation_id`. **`in_window` never leaves the data layer.**

**The per-source `awaiting_row` threshold line is NOT built here.** The dial (`resolver.stuck_pattern`) lives only in scraper registry YAML; where Admin reads it is a blocked question (spec section 10: a flagged gap, not a silent copy). Ship the trend without the threshold overlay and leave a named seam for it. **Hand-copying the value is not an answer.**

Out of scope: any component or page (TASK-0008 and the page tickets); any migration or database view; any RPC.

## Acceptance criteria
[test 11; EC8] Six gauge modules exist, one per row of spec section 5, each exporting a pure aggregate function that offline tests exercise against the fixture builders — including the empty case and the not-provisioned case. Every gauge query has an explicit limit and window. No migration is added (`supabase/migrations` still holds exactly two files) and no database view, RPC or SQL string is created. `in_window` appears in no gauge output. The per-source threshold overlay is absent and its seam is named in code.

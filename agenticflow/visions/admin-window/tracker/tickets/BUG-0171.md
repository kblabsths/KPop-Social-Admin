# The claims rows route answers gated admin data with no Cache-Control, while every gated page carries one

## Description
**Module:** `src/app/api/admin/claims/rows/route.ts` only — one import and one `headers` option, plus the assertions that pin it.

**Found** (QA, admin-window/TASK-0066 close, residual (a)): every dynamically rendered page in this app answers `Cache-Control: private, no-cache, no-store, max-age=0, must-revalidate` because Next sets it on the response (`node_modules/next/dist/server/base-server.js:1251,1649`). A Route Handler is given no such header: `GET /api/admin/claims/rows` answers 200 with NO `Cache-Control` at all. So the one answer in this app that carries gated admin ROWS across the wire is also the only one that says nothing about being stored, and `/claims` and its own continuation are a single surface under two different cache policies.

**Ruled in scope** (architect, 2026-09-10). QA filed it conditionally — 'a ticket only if a shared cache/CDN is put in front of Railway' — and that condition is the wrong test: the browser's own store, a corporate forward proxy, and any future edge are all reached by the same omission, the header is the app's own statement about its data rather than a deployment detail, and the fix is one line against a constant that already has to exist for the browse route. What it is NOT: a security claim (the gate is unchanged and `requireAdmin()` still runs on every request) and not a rewrite — no arm of the answer changes shape.

**Not a second string.** `PAGE_ANSWER_CACHE_CONTROL` is declared by admin-window/TASK-0068 in `src/lib/paging/bounds.ts`, beside `PAGE_ROUTES` and `OFFSET_PARAM`, spelled exactly as Next spells it. This ticket IMPORTS it. That is also why it is chained behind TASK-0068 rather than racing it: the constant does not exist yet, and TASK-0068 is already landing in this same route file to lift the search-param adapter out of it — two tickets writing one file is a merge collision, not parallelism.

## Acceptance criteria
Every answer GET /api/admin/claims/rows emits carries Cache-Control: private, no-cache, no-store, max-age=0, must-revalidate — the ok page, not_provisioned, error and the 400 refused arm alike — and the value is the PAGE_ANSWER_CACHE_CONTROL constant imported from src/lib/paging/bounds.ts, never a string typed into this file: the literal 'private, no-cache, no-store' appears in exactly one file under src/ and it is bounds.ts. Asserted offline on all four arms through response.headers.get("cache-control") in tests/offline/paging/claims-route.test.ts, and over HTTP against the built app in tests/http/paging.http.test.ts on a signed-in GET and on a refused bound, so the header is proved on the real response Next serves and not only on the Response object the handler returned. Nothing else about the route changes: the four arms keep their shapes and their statuses, isPageAnswer still accepts every body, the bound path and the facet derivation are untouched, and tests/offline/paging is green with no case rewritten. The header matches what a page on the same surface answers, checked against /claims' own response in the same http run rather than against a string this ticket invented.

# The claims paging route handler: gated like a page, bound-checked out loud, one page per request

## Description
**Module:** a NEW route handler `src/app/api/admin/claims/rows/route.ts` — the second read route in the app and the first that serves rows. `PAGE_ROUTES.claims` in `src/lib/paging/bounds.ts` (TASK-0063) is its ONE spelling; this file does not re-spell its own path, and neither does the client.

**Read first:** `src/app/api/admin/records/[table]/[id]/route.ts`'s header — the order of its guards is the pattern this file copies (the gate first, then the value class, then the work), and ARCHITECTURE §4.3 read kind 3.

**Interface contract:**

```ts
// GET /api/admin/claims/rows?<the page's own facets>&offset=<n>
// -> 200 application/json  PageAnswer<ClaimLine>          (ok | not_provisioned | error)
// -> 400 application/json  PageAnswer<never> kind "refused"  (a bound out of range)
// -> the middleware's redirect, before this module's body runs, when unauthenticated
export async function GET(request: Request): Promise<Response>;
```

**The order of the guards, and each one's answer:**

1. **The gate, first and always.** `requireAdmin()` — the same call the PATCH route makes — and `src/middleware.ts` has already turned away a request with no session before the handler is reached at all (§5's gate bullet: `export { auth as middleware }`, never `auth(handler)`). **Nothing below runs for a visitor who is not an allowlisted admin.** M3 EC6 grades this on every method the route accepts.
2. **The facets, through the page's OWN derivation.** The filter and tab come from `src/lib/claims/filters.ts` — the same functions `src/app/claims/page.tsx` calls, given the same `searchParams` — so what the handler queries is what the page's first screen queried. A second parse here is how a paged row set comes to belong to a different narrowing than the rows above it (common violations row 20: what is SHOWN is what was USED).
3. **The bound**, through `pageBound(url.searchParams.get(OFFSET_PARAM), CLAIM_WINDOW)`. A refusal answers **400** carrying the `refused` answer with the reason and the bound named. **Never clamped, never defaulted** (M3 EC6).
4. **The read**: `readClaimWindow({ filter, limit: CLAIM_WINDOW, offset })`, then the source-name registry for exactly this page's `source_id`s, then `claimLines(rows, names)` — the same leaf the first screen uses (TASK-0065). A registry that refuses does not refuse the rows: `sourceLabel` already renders the id verbatim when the registry names nothing, which is what the first screen does today.
5. **The answer**: `pageAnswerOf(result, offset, CLAIM_WINDOW)` — `ok` with the shaped rows and `exhausted` when the page came back short, `not_provisioned` / `error` mapped across unchanged so the client's refusal names the same object the page's own card would name.

**GET only.** No POST, no PATCH, no DELETE — this route reads. Next answers any other method 405.

**No service-role material crosses to the client** (M3 EC6, acceptance test): the handler returns shaped rows and nothing else — no client, no URL, no key, no env name, and no raw PostgREST error object beyond the `message` §4.1 already renders on the page today.

**Absence is a normal answer, not an error.** Against a database answering `PGRST205` the handler answers 200 with `{ kind: "not_provisioned", missing: "pending_claims" }`; it is the page that decides what a not-provisioned surface looks like, and by then the affordance is not drawn at all (TASK-0067).

**Tests.** Offline: drive `GET` directly with a stub client and a stub request for the gate — bound refusals, the ok page, exhaustion, `not_provisioned`, `error`, and the facet pass-through. HTTP (`tests/http/paging.http.test.ts`, new): an unauthenticated GET redirects to `/login` before the body runs, on the built app; the client-bundle scan finds no `SERVICE_ROLE`, no `service_role`, no `STAGING_SUPABASE` and no staging URL (extend the existing scan to cover the new route's bundle rather than writing a second scanner — §10, one owner per structural guard).

## Acceptance criteria
GET /api/admin/claims/rows answers a PageAnswer<ClaimLine> as JSON: ok with exactly the rows readClaimWindow returned at that offset, and exhausted derived from THAT read as the biconditional the driver now enforces — exhausted === rows.length < CLAIM_WINDOW, so the handler answers either a full page that continues or a page of at most CLAIM_WINDOW rows that says the set is exhausted, and NEVER a short page with exhausted false or a page longer than the window (admin-window/BUG-0168's ruling, ARCHITECTURE §4.3 'full-or-exhausted, on BOTH sides of the wire'; requestPage refuses any other combination out loud, so a route that emits one turns every press on /claims into a refusal). Both edges are driven offline against a stub: a read returning CLAIM_WINDOW rows answers exhausted false, a read returning fewer — including zero — answers exhausted true, and the handler never reports a row count the read did not return; not_provisioned naming pending_claims against a PGRST205 stub; error carrying the database's own message. A bound that is absent, non-canonical, not a multiple of CLAIM_WINDOW, below CLAIM_WINDOW or above MAX_PAGE_OFFSET answers 400 with kind "refused" naming the reason and the bound, and no read is issued — proved on two fixtures, one bound that must be refused and one that must not.

THE URL's OFFSET REACHES NOTHING BUT pageBound, AND A REFUSED BOUND REACHES NO READ. The handler imports pageBound and OFFSET_PARAM from src/lib/paging/bounds.ts and does its own arithmetic on the raw parameter nowhere: the route file contains no Number(, no parseInt and no parseFloat, and the only value that reaches readClaimWindow's offset is the number pageBound returned on its ok arm. Driven offline against a stub that RECORDS every read it is asked for, the whole refusal table answers HTTP 400 with kind "refused" naming the reason and the bound AS SENT, and leaves the recorder empty — no offset param at all, "" , "abc", " 50", "+50", "050", "50.0", "1e2", "-50", "49", "51", "100050" — while the one canonical bound in the same table ("50") is served and DOES record exactly one read, so the table cannot pass by refusing everything. This is the measured failure it exists to stop (QA, TASK-0065 close): Number("abc") is NaN, .range(NaN, NaN) is answered by staging with an ok page of zero rows, and a zero-row ok page is exhaustion — a malformed URL would render to the operator as a set that has ended rather than as a refusal.

THE ROUTE OWNS THE SHAPE OF WHAT IT SERVES. isPageAnswer is a cheap gate on the CLIENT — it checks the discriminant and each arm's own fields and cannot see inside a row — so the row type is established here: the handler's declared return is its own PageAnswer<ClaimLine> (rows: ClaimLine[], offset: number, exhausted: boolean) written on the answer rather than inferred, its rows are claimLines' output and nothing re-shaped beside it, and its offset ECHOES the bound the request carried — asserted on every ok fixture to equal the offset the request sent and the offset the read was given, never the read's own or a number recomputed from rows.length. Every body the handler emits on all four arms (ok, not_provisioned, error, refused) is fed back through isPageAnswer in the offline suite and accepted, so the answer this app serves is one its own client can read.

requireAdmin() is the first statement of the handler body and an unauthenticated request never reaches the body: asserted over HTTP against the built app for GET, and the same assertion the pages already carry. The route accepts GET only. The facets are parsed by lib/claims/filters.ts and by nothing written in this file — grep shows no second facet parse in src/app/api. The client-bundle scan finds no SERVICE_ROLE, no service_role, no STAGING_SUPABASE and no staging URL anywhere in the built client bundles. src/app gains no page route: exactly nine page.tsx files remain.

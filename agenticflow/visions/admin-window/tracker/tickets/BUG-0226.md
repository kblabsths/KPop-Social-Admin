# Both paged pages answer HTTP 500: a function prop cannot cross the client boundary

## Description
EXPECTED (admin-window/BUG-0222 criterion 4): the first server-rendered screen of /claims and /browse is unchanged — same window line, same figures, same row set.

FOUND on the landed tree (feb21a66), measured 2026-09-14 against staging on a production build (`npm run build && npm run start -- --port 8781`, STACK.md step 1's two-command block, minted walk cookie):

    GET /  -> 200
    GET /claims -> 500
    GET /browse -> 500
    GET /sources -> 200
    GET /records/walk_sandbox/…0001 -> 200

Server log, verbatim:

    Error: Functions cannot be passed directly to Client Components unless you
    explicitly expose it by marking it with "use server". Or maybe you meant to
    call this function rather than return it.
      {route: ..., params: "", size: 50, id: function Z}
                                             ^^^^^^^^^^
      digest: '3992294335'

In a browser (playwright, same instance) /claims renders Next's error shell — "This page couldn't load / A server error occurred" — and ZERO rows: `[data-claim]` count 0, no paging control, no window line.

MECHANISM. `src/app/claims/page.tsx:1854` and `src/app/browse/page.tsx:1380` hand `PagingProvider` — a `"use client"` component — `deps={{ route, params, size, id: observationId }}`, where `id` is a FUNCTION (`const observationId = (claim: ClaimLine) => claim.observationId`, claims/page.tsx:358; `const eventId = (row: BrowseRow) => row.event_id`, browse/page.tsx:124). Next serializes every prop a server component writes on a client element into the flight payload; a function is not serializable, so the whole page throws before any markup is produced. Both props were added by BUG-0222.

WHY NOTHING IN THE FACTORY SAW IT (LESSONS 10, and the twin of BUG-0094). The offline tier renders `renderToStaticMarkup(await Page(props))` — ordinary SSR with no client boundary, so the function is simply carried and every markup assertion still passes (457/457 green). `tsc` sees a well-typed function; `npm run lint` sees a property; `npm run build` compiles it. The http tier points the app at a dead database, so `pageable` is false, `PagingProvider` is never rendered, and the error cannot fire there either. The live tier drives `lib/db` and the route handler, never the page over HTTP. Only a REQUEST to a built server serializes the tree.

PIN, committed at 04d3ef6a: `tests/offline/claims/page.test.ts` and `tests/offline/browse/page.test.ts` each carry `it.fails("hands the client provider DATA only, so the server can serialize it")`, grading the value the page actually handed across (`tests/fixtures/client-props.ts`, `functionPaths`). Watched RED with the marker flipped to `it`: `AssertionError: expected [ 'deps.id' ] to deeply equal []`, on both files.

THE FIX FLIPS BOTH MARKERS to `it` (check 2 below refuses the close while either stands). What crosses the boundary must be DATA: e.g. the page names the id FIELD (`idKey: "observationId"`) and the driver reads `row[idKey]`, or the client component composes `deps.id` on its own side from a name the page sent. The interface contract of BUG-0222 is unchanged by either — the drop still happens on the append, the bound still advances by the route's row count.

WORTH CONSIDERING, not required by these criteria: nothing in the suite can see this class today. An http-tier stub that serves ROWS (tests/http/postgrest-stub.ts answers only "absent"/"denied") would render both paged surfaces past `pageable` and catch every future instance at the tier that owns it.

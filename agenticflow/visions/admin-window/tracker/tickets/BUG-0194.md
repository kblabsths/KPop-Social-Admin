# /sources' settled-values figures are narrowed to one source and no word on the page says so

## Description
**Found by QA attacking the landed TASK-0073 tree (a13df7d3), on `/sources`' Settled values section.**

TASK-0073 is correct about the LINE: `readRejectionStampGauge()` takes no filter (`src/lib/gauges/settled-values.ts:249-253`; `GaugeOptions` in `src/lib/gauges/gauge.ts:66-75` carries only `since`/`days`/`limit`/`now`), so the fleet-wide scan's window line rightly names no narrowing, and naming one there would put the fleet's 1,000-row cap and its truncation verdict over one source's rows (BUG-0114 with halves swapped). **That half is not in question and must not be "fixed" by naming the facet in that line.**

The defect is the other half, which no criterion of TASK-0073 graded: `RejectionSection` narrows the ROWS it reports (`reported`, `src/components/sources/trends.tsx:283-294`) so both cards under that line carry ONE SOURCE's figures, while every word in that head — the window line and both card labels — is byte-identical to the fleet's rendering. The reader is handed a narrowed number under an unnarrowed sentence (LESSONS 2; ARCHITECTURE §4.3). It is NOT a regression from TASK-0073 — that commit only renamed the local `scope` to `reported` — but it is precisely the finding TASK-0073's own description ordered filed rather than patched ("If a figure on this page still disagrees with the line above it after both, that is a new finding: file it, do not patch it here").

**Repro (offline fixture, deterministic, no staging data needed):**
1. `./node_modules/.bin/vitest run --project=offline tests/offline/sources/page.test.ts -t "says nothing about the narrowing"` — passes only because it is pinned `it.fails`; flip it to `it(` and it reds on the last assertion.
2. Or render the page directly: bare `/sources` vs `/sources?source_id=<ticketmaster>` on `healthyScript()`.

**Measured, bare vs narrowed (offline fixture, `tests/offline/sources/population.ts`), Settled values head:**
- bare: `Claims adjudicated since <instant>, read to <instant> — a window of at most 1,000 rows, not the whole table.` / card `Re-rejected claims in this window` = **3** / card `Sources re-pushing adjudicated values` = **2**, sub `of 2 with any claim adjudicated in this window`
- `?source_id=<ticketmaster>`: the line is **byte-identical** (instants masked) / same card = **2** / same card = **1**, sub `of 1 with any claim adjudicated in this window`

**Expected:** a figure states the scope its rows had — when the section reports one source's rows, some word in that head says so (ARCHITECTURE §4.3, LESSONS 2).
**Found:** the figures move 3 → 2 and 2 → 1 between the two URLs while the sentence and both labels over them are identical, at `src/components/sources/trends.tsx:296-322` (the `WindowLine` and the two `GaugeCard`s) fed by `reported` at `trends.tsx:283-294`.

The second card is the sharper one: it counts SOURCES. Narrowed, it can only ever read "1 of 1" or "0 of 0" while calling that "sources re-pushing adjudicated values ... in this window", where the line above defines the window as the whole table's. Staging hides it today — the 90-day rejection window holds 0 rows on `ubfjjqlvnpnoborczbdb` under every URL (measured 2026-09-11 in a browser, `data-window-held="0"`), so this is latent, not visible to an operator yet. It becomes visible the day a verdict is recorded.

**Fix is the architect's choice and the pin is deliberately agnostic between them:** narrow the read at the query (gives the line a narrowing honestly, but MOVES FIGURES and changes what the cap means — probably a design call), or scope the two card labels / add the section's own scope statement. The pin only requires that SOME word in the line-and-cards head change when the figures change. **Whoever fixes it flips `it.fails(` back to `it(` on that case** — check 2 below is what forces that.

Not in scope here: the awaiting-row line (correct), TASK-0060's source-name renderers, and BUG-0192's `/claims` work.

## Acceptance criteria
The settled-values scan carries the narrowing its own figures carry: readRejectionStamps applies the source facet AT THE QUERY (mirroring readPendingObservations(bounds, filter, db?)), fetchRejectionStamps / readRejectionStampGauge take it the way fetchPendingClaims does, and /sources hands that read the same filter expression it hands scopeOf — one expression, so the words and the rows cannot come to disagree (TASK-0073's rule). Proved at the query on two fixtures (LESSONS 8), off the stub's recorded steps in tests/offline/gauges/settled-values.test.ts: under a narrowed call the observations rejection scan's steps carry an eq on the source column with the filter's value, under a bare call they carry none — and the aggregate's window still states the bounds that scan used. No new facet type and no second narrowing phrase are declared: unchippedPhrase and SOURCES_NARROWING_FACETS are each declared exactly once in src, both outside this section's files, and src/components/sources/trends.tsx, src/lib/gauges/settled-values.ts and src/lib/db/gauges.ts spell no narrowing sentence of their own.

The line and the figures agree in kind under every URL, asserted on rendered HTML. Bare: the head names no narrowing and, with digits masked, is byte-identical to the head this page renders today. Narrowed to a source with rejections: the head names that facet, the figures under it are that read's rows, and the two differ from bare in the same test — tests/offline/sources/page.test.ts's pinned case is unpinned (it.fails becomes it, its title no longer says the page is silent, it keeps its [BUG-0194] marker) and passes on its own terms, non-vacuous in both directions. Narrowing accepted but matching nothing (a well-formed source_id with no rows in the window): the line STILL names its narrowing and the cards render real zeros with their own sub-line - a narrowed scan that returned nothing is still a window (ARCHITECTURE 4.3). A facet this page dropped narrows nothing, appears in no scope, and renders byte-identical to bare.

The cap, the truncation verdict and the floor the cards wear belong to the population the figures are over - never the fleet's cap over one source's rows, never one source's over the fleet's (BUG-0114, both halves): every figure this section reports comes from the single gauge result whose window line it renders, and no second read feeds it. RejectionSection keeps re-applying the filter to the rows it was handed (the returned set is narrowed at the query AND selected again here, the idiom selectPendingClaims uses), so BUG-0022's two landed cases stay green unedited: a stranger source's rejection moves no figure of a narrowed rendering, and the narrowed source's own unnamed-registry count stays 1 when two unregistered strangers are added.

The new fact costs no round trip: the page still issues one rejection scan per render and the same number of recorded database calls at the bare and the narrowed URL. Nothing else on /sources moves: the awaiting-row line still names its own read's narrowing in every URL and names it in no line whose read did not carry it, which empty card the surface draws is unchanged, no surface or control is added, the sidebar still holds exactly six links, and /sources' offline and live parity suites are green with a narrowed and an unnarrowed URL graded by state kind first.

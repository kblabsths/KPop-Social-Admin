# ASK: what does a resolver-owned record page DISPLAY in M1? events/venues currently render their id and nothing else

## Description
**Contract silence, not a build defect.** Spec section 8 describes the resolver-owned edit surface only in its M2 form (override through the gate, provenance stamped admin_locked). It says nothing about what such a record DISPLAYS in M1, when there is no override path yet. TASK-0018's criteria are silent too, so this is filed as an ASK rather than a bounce of that ticket.

Expected (the operator's path): Browse renders a live link on every event row (src/components/browse/browse-table.tsx:35 -> eventRecordHref, src/lib/browse/rows.ts:83), so /records/events/<id> is the primary navigation target from the app's main list screen.

Found: that page shows exactly one field line — event_id — plus the regime sentence. Measured on the landed tree (run/admin-window c4160a4) by rendering the page against a stubbed read: lines = [{name: 'event_id', editable: false}]. Same for venues (venue_id). The operator clicks through from Browse and learns nothing they did not already have in the row they clicked.

Cause, at file:line: src/lib/db/records.ts:41-43, recordColumns() returns [config.pk, ...config.editable].join(', '), and a resolver_owned table's editable list is empty by design (src/lib/edit/config.ts:120-121). So the read asks for the pk alone.

Not fixable in the page: the page renders whatever the read hands it — verified by scripting title/starts_at/name/city onto an events row, which rendered as four read-only lines with zero interactive controls. Inventing a display list inside the page would be the second allowlist ARCHITECTURE section 9 forbids.

The decision needed: does the one map gain a DISPLAY set distinct from its EDITABLE set (so a resolver-owned table can show its columns read-only while editing none), or does an events/venues record page legitimately show only its identity until the M2 verdict slice lands? Either answer is an entry in src/lib/edit/config.ts plus recordColumns(); neither is a page change. The architect should rule and amend or split a ticket accordingly.

## Acceptance criteria
(human-checkable) The architect rules: the one map either carries a display set for resolver-owned tables, or the ruling is recorded that an id-only record page is correct for M1 and Browse's link is amended or accepted. Structural proxy: whatever the ruling, no second allowlist appears outside src/lib/edit/config.ts and the edit surface still renders zero controls for events/venues — pinned by tests/offline/edit/config.test.ts and tests/offline/records/page.test.ts, which the check below runs.

# ASK: what does a resolver-owned record page DISPLAY in M1? events/venues currently render their id and nothing else

## Description
**Contract silence, not a build defect.** Spec section 8 describes the resolver-owned edit surface only in its M2 form (override through the gate, provenance stamped admin_locked). It says nothing about what such a record DISPLAYS in M1, when there is no override path yet. TASK-0018's criteria are silent too, so this is filed as an ASK rather than a bounce of that ticket.

Expected (the operator's path): Browse renders a live link on every event row (src/components/browse/browse-table.tsx:35 -> eventRecordHref, src/lib/browse/rows.ts:83), so /records/events/<id> is the primary navigation target from the app's main list screen.

Found: that page shows exactly one field line — event_id — plus the regime sentence. Measured on the landed tree (run/admin-window c4160a4) by rendering the page against a stubbed read: lines = [{name: 'event_id', editable: false}]. Same for venues (venue_id). The operator clicks through from Browse and learns nothing they did not already have in the row they clicked.

Cause, at file:line: src/lib/db/records.ts:41-43, recordColumns() returns [config.pk, ...config.editable].join(', '), and a resolver_owned table's editable list is empty by design (src/lib/edit/config.ts:120-121). So the read asks for the pk alone.

Not fixable in the page: the page renders whatever the read hands it — verified by scripting title/starts_at/name/city onto an events row, which rendered as four read-only lines with zero interactive controls. Inventing a display list inside the page would be the second allowlist ARCHITECTURE section 9 forbids.

The decision needed: does the one map gain a DISPLAY set distinct from its EDITABLE set (so a resolver-owned table can show its columns read-only while editing none), or does an events/venues record page legitimately show only its identity until the M2 verdict slice lands? Either answer is an entry in src/lib/edit/config.ts plus recordColumns(); neither is a page change. The architect should rule and amend or split a ticket accordingly.

## Acceptance criteria
**Ben's ruling, 2026-09-02:** a resolver-owned record page shows the columns an operator came to see, read-only, with per-field provenance beside each. The list lives in the SAME map as `editable` — there is no second allowlist anywhere in this repo (spec §8, the acceptance doc's ground rule, ARCHITECTURE §9).

1. **`TableEditConfig` gains `display: readonly string[]`** in `src/lib/edit/config.ts`, carrying Ben's columns verbatim: `events` -> title, description, poster, starts_at, venue; `venues` -> name, city, country, address. `groups` and `idols` carry an empty `display` — their columns are already on screen through `editable`. Every name is asserted to be a real column of that table in the scraper's schema (the map's existing test idiom: names checked against `T`/the migration snapshot, so a typo is one red test away).
2. **`display` is READ-ONLY and cannot become writable by being listed.** `decideEdit` is unchanged and still answers the write question from `regime` + `editable` alone; a column in `display` and not in `editable` gets `widget: "read_only"`, and a PATCH naming it is refused server-side by the existing path with the row unchanged. No new branch in the route, no `resolver_owned` write path, no scaffold toward one (M1 EC10, acceptance test 7).
3. **The read asks for the displayed columns.** `recordColumns` becomes pk + editable + display, de-duplicated and stable in that order, so `readRecord` returns them and the surface renders whatever the read hands it. The existing ordering rule in `src/components/records/fields.ts` (pk, then the map's columns in declared order, then anything else read-only) is what draws them — do not add a second ordering rule.
4. **Per-field provenance beside each displayed field**, one short line in the app's voice: the source that applied it and the age ("ticketmaster, applied 3d ago"), with the absolute instant in the title attribute (LOOK_AND_FEEL: relative age, absolute on hover; the source name in mono as the machine's word). Read from `field_provenance` for `(entity_type = the table, entity_id = this row, field)`, current row only — **do not re-derive "latest per fact"**: reuse the landed pure helper `currentDecisions` in `src/lib/browse/rows.ts` (already generic in its row type) and ARCHITECTURE §6 trap 7's rule. A field with no provenance row renders the app's absence, not a blank and not a zero.
5. **All four states, per read.** The provenance leg is its OWN read and reports separately (`ErrorLine` with `reading` naming `field_provenance`): a refused provenance read must not blank the record's values, and an absent `field_provenance` renders the gray not-provisioned card in the provenance column while the values still render. Values and provenance are two reads and two answers, as Browse already does it.
6. **Pre-cutover tables keep their landed line** — "no provenance recorded (pre-cutover table)" (Ben's ruling on TASK-0025, same date), so the provenance slot is filled with a reason on every table, never left blank.
7. **Tokens and primitives only**, no raw values; machine identifiers (column names, source names) in mono, verbatim; the record page stays server-rendered with the page function as its only async boundary.
8. **The write surface is unchanged and still pinned**: `.update(` only in `src/lib/db/records.ts`, no insert/upsert/rpc anywhere, and `admin_locked` is not in any `editable` list. (`admin_locked` may be READ here for the admin-stickiness line once admin-window/BUG-0028 narrows the guard — this ticket depends on it. If BUG-0028 has not landed, ship criterion 4 without the stickiness line rather than weakening the guard.)

# Event record page: a whole PROVENANCE column of dashes with no line saying what a dash means, while the pre-cutover page explains its own

## Description
Found INDEPENDENTLY by both document-blind user-sims (2026-09-03) — the only finding of the M1 endgame that two strangers reached from opposite goals. Confirmed live on :8771.

**Feel bar 5:** "Provenance shows at the fact, on review-item detail, claim detail and every editable field." **The Look, the evidence pair:** "The order and the anatomy never change between screens." **Voice register:** "the pipeline's engineer reading you its own logbook — plain, specific."

`/records/events/<id>` renders a FIELD / VALUE / PROVENANCE table. For an event whose fields carry no `field_provenance` row, every cell of the PROVENANCE column is `—`, and **nothing on the page says what that dash means**. The regime note above the table reads only:

    events is resolver-owned and read-only from Admin: its values change through
    the resolution pipeline, not by a direct edit.

Confirmed live, `/records/events/01a06573-e943-7f4e-8db9-db7a5742560e`: six rows, six dashes in PROVENANCE, no explanatory line.

**The asymmetry is the sharp part.** The pre-cutover branch of the same function DOES explain its dashes — `regimeNote()` in `src/app/records/[table]/[id]/page.tsx:82-89` says for `groups`/`idols`: "No field provenance is recorded for it, so no source is shown beside a value." The resolver-owned branch, which is the ONLY branch where a dash could mean several different things, says nothing. So the app explains the case that needs no explaining and stays silent on the case that does.

Tomas (`tomas.md`): "In a tool whose whole argument is that every fact is traceable, a record where nothing is traceable should say so out loud... I only worked it out by opening a second event where three of six fields say 'ticketmaster, applied 1d ago'. So the dash means 'this value has no recorded provenance', not 'provenance isn't wired up yet' — but I had to discover that by comparison, on a site that elsewhere goes out of its way to spell such things out." His stated condition for trusting the tool: "I'd treat **the record pages** as unverified until the blank provenance column says what it means."

Priya (`priya.md`): "A row of dashes under a column called PROVENANCE reads as 'we lost the data', not as 'nothing has been decided yet'."

Priya also names the true cause she had to leave the app to find: that event's performer claims are all sitting in `awaiting_link`, so nothing has been adjudicated onto it. The record page never says that.

**This is NOT a four-state violation.** The field table is in its OK state — it has rows. A `—` is the Look's mandated null rendering ("A null renders as `—` in disabled-gray — never blank, never `null`, `N/A` or `none`"), and the `empty:{holds,filledBy}` contract governs a surface with no rows, not a null cell inside a populated one. **Do not turn this table into an empty state.** The dashes are right; the missing thing is one sentence of the page's own voice, said once per record exactly as the pre-cutover note is (Ben's ruling on admin-window/TASK-0025: say it once, not on every line).

Evidence: `agenticflow/tracker/evidence/user-sim-m1/tomas-13-record-no-provenance.png` (all dashes), `tomas-11-record-provenance.png` (the contrast case, three of six fields sourced), `03-event-record.png`.

Related but distinct: BUG-0052 is the same file and also copy, but it is the EMPTY state's false pointer to Browse on a pre-cutover table; this is the OK state's unexplained null column on a resolver-owned table. Different branch, different bar.

## Acceptance criteria
A resolver-owned record page (`/records/events/<id>`, `/records/venues/<id>`) states, once per record and in the app's voice, what an empty PROVENANCE cell means: that no `field_provenance` row stands behind that value — distinguished from the page's existing not-provisioned and error states for the provenance leg, which keep their current renderings.

The sentence is said once, above the table, beside the regime note — never repeated per row, and never in place of the `—`.

The `—` in the PROVENANCE column is unchanged: still the disabled-gray em dash, never blank, never "N/A", and the field table never renders as an empty state while it has rows.

A record where SOME fields carry provenance and some do not reads correctly too — the sentence must not claim the whole record is unprovenanced when three of six fields are sourced (`tomas-11-record-provenance.png` is that case).

`tests/offline/records/page.test.ts` asserts, for a resolver-owned record with zero provenance rows, that the rendered page contains the explanatory sentence; and asserts for a partially-provenanced record that the rendering is not contradicted.

Human-check: open an event with an all-dash PROVENANCE column and read the page cold — it says what the dashes mean without opening a second event to compare. (human-checkable)

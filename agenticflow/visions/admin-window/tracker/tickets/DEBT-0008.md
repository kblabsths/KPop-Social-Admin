# /sources and /claims decide the four states from the URL alone: BUG-0133's two-fact rule has one owner and two surfaces never got it

## Description
M2 structure walk finding (architect, 2026-09-09), measured on run/admin-window.

BUG-0129/0131/0133 settled a STRUCTURAL rule for the four states — 'a table with no rows' and 'a filter that matched nothing' never share a rendering. It needs TWO facts, and `isBlockNarrowed` in `src/lib/review/queue-filters.ts:346-356` is the only place in the tree that holds both:

    isNarrowed(filter, within) && block.rendered !== block.population

Fact 1 is structural (can a facet of this URL remove a row of this kind at all). Fact 2 is the block's own population (if the set is empty with no facet, no filter emptied it). The docstring above it is the campaign's clearest statement of the rule.

Two other surfaces answer the same question from fact 1 alone:

- `src/app/claims/page.tsx:647` — `const emptyWords = isNarrowed(filter) ? NOTHING_MATCHED : ...`, and again at :232 (the bucket caption, `NARROWED_BY_FILTERS`) and :681 (`BUCKET_CAPTION.narrowed`). `isNarrowed` in `src/lib/claims/filters.ts:132` is `CLAIM_FACETS.some(f => filter[f] !== undefined)` — the URL, and nothing else. So `/claims?bucket=X` over a view holding zero rows says 'nothing matched' and tells the operator to widen a filter that removed nothing. The ledger records staging holds 0 standing disagreements, so `/claims?tab=standing` with any facet is in that state today.
- `src/app/sources/page.tsx:200` — `data-empty={filter.source_id === undefined ? 'registry' : 'narrowing'}`. Same one-fact shape: an EMPTY registry read under `?source_id=X` renders 'nothing matched' rather than 'the registry holds nothing'.

This is the class ARCHITECTURE.md Common violations row 14 parked at count 1 and BUG-0133 fixed at its instance. The walk found two more surfaces, so it is being promoted to a rule in §4.3 by the same amendment that files this ticket.

The second fact is available on both pages without a new read: `/claims` already reads the whole claim population every request (BUG-0138 measured ~14 round trips over it), and `/sources` reads the registry whole before it narrows (page.tsx:162, 'the registry, whole'). Neither fix is a new query.

Dependency: BUG-0141 (in flight, builder-208) writes `src/app/claims/page.tsx` and `src/lib/claims/filters.ts`. This lands after it — consolidation-shaped work is serial at its destination.

## Acceptance criteria
1. `/claims` and `/sources` each decide their empty-state arm from TWO facts — the URL's structural narrowing AND whether the surface's own unnarrowed population is empty — so a facet over an empty set never renders the 'nothing matched' arm. The decision is made by a shared predicate, not by a third hand-written copy of the rule: either `isBlockNarrowed` moves to a place all three surfaces can import (it is pure and imports only `./shapes`), or each page's leaf gains the same two-fact signature and one test grades all three.
2. `/claims?bucket=<any>&tab=standing` over a population of 0 renders the 'holds nothing' arm, names what fills the surface, and does not tell the operator to widen a filter. Same for `/sources?source_id=<well-formed id>` over an empty registry (`data-empty="registry"`, not `"narrowing"`).
3. Every case BUG-0123/0129/0131/0133 already pinned still holds: a facet over a NON-empty population still names its scope; `?kind=decision` on the decision block is still never named; the dropped-parameter line is unchanged.
4. The rule is graded once for all three surfaces in `tests/offline/absence/pages.test.ts` (the file that already generalises absence rules across surfaces), on two fixtures per surface — one population that must take the narrowing arm and one that must not. A test that only ever saw the empty fixture passes vacuously (LESSONS 8).
5. Neither page issues a query it did not issue before: the population fact comes from a read already on the page.

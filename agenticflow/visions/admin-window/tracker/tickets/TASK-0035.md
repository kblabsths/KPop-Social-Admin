# The walk sandbox in the one map: an EDIT_CONFIG entry that renders not-provisioned wherever the table is absent

## Description
The Admin half of the walk sandbox (Ben's inbox note, 2026-09-03), and
deliberately the *whole* Admin half: **one entry in the one map, and nothing
else.** No route change, no new surface, no nav entry, no Browse change — the
sandbox is reachable only at `/records/<table>/<key>`, which is exactly how a
walker should reach it and exactly how the operator never trips over it.

**Blocked on TASK-0034** for the table's name, its columns, its `Regime` and
its very existence. Do not guess any of them; the entry's column names must be
the names the database spells or the read comes back `not_provisioned` and the
map is a lie.

## What to write

One `TableEditConfig` in `ENTRIES` (`src/lib/edit/config.ts`), in the file's
own idiom: `table`, `pk`, `regime` (TASK-0034's ruling), `editable` listing one
column of each edit type, `display: []`, `reference: null`. The point of the
column set is the *write path's coercion* — text, integer, boolean, date, and
one nullable column so the em-dash absence-then-fill path is walkable. Add a
docstring saying in one sentence what this table is and that it exists only on
staging.

`src/lib/db/tables.ts` gains the name too: `tests/offline/edit/config.test.ts`
asserts every mapped table is spelled in `TABLE_NAMES` ("so a typo here is one
red test away"), which is the pin that makes ARCHITECTURE §4 rule 4 survive
the edit-config leaf not importing it.

## The tests that will go red, and what each one wants

- `tests/offline/edit/config.test.ts:45` asserts `EDITABLE_TABLES` equals
  exactly `["groups","idols","events","venues"]`. It becomes five, and the new
  table gets its own `it(...)` in the manner of the pre-cutover and
  resolver-owned blocks: its regime, its pk, its exact editable list.
- `tests/offline/records/page.test.ts` (two loops), `tests/http/auth.http.test.ts:598`
  and `tests/live/residue.live.test.ts` all iterate `EDITABLE_TABLES`. They
  should pass with a fifth table; if one does not, the loop was carrying an
  assumption about catalog tables that is worth naming rather than special-casing.
- `residue.live.test.ts` now sweeps the sandbox for the `admin-window` marker,
  which is the coverage we want — and it fails if the seed fixture (TASK-0036)
  carries that string. If you see it fail that way, the fixture is wrong, not
  the test.

## The two states this must render honestly

1. **Table absent** — production, forever, and any staging project that has
   not been seeded: the record page shows the not-provisioned card naming the
   table (`src/app/records/[table]/[id]/page.tsx`, the `not_provisioned`
   branch, acceptance test 9's shape). Nothing crashes, nothing is hidden.
2. **Table present** — staging after TASK-0036's reset: every mapped column
   draws a line, empty columns draw the em dash and are still editable, and
   the key line is read-only.

Note for whoever walks it afterwards: a save still 403s for the walker
identity until Ben answers the `admin_allowed_emails` question on
TASK-0034's for-human note. That is not a defect in this entry.

# /queues ignores the source_id the Sources page links it with: another source's item renders as that source's review items

## Description
Walked 2026-09-09 on the walk instance (http://localhost:8771, STAGING, branch run/admin-window), cookie-authed, bundled chromium 151.

Steps from a clean start:
1. GET /sources. The registry row for **test_harness** carries a LINKS cell whose anchor `review items` points at `/queues?source_id=01a01808-8c6f-78aa-b7a7-b07ddb3b057a` (emitted by `queueItemsHref`, src/lib/sources/routes.ts:56).
2. Click it. URL becomes /queues?source_id=01a01808-8c6f-78aa-b7a7-b07ddb3b057a.
3. Observed: SIGNAL QUEUE renders `OPEN SIGNALS 1 / 1 high, 0 low / oldest 7d ago` and one row, "ticketmaster: records keep missing the creation bar at the stuck-record threshold", linking to /queues/01a06287-5b67-7d1f-b4a5-d90aa93cb01a. That item's review_items.source_id is 01a05782-8e7f-752c-ae60-3ce4c51962f6 (ticketmaster), not the test_harness id in the URL. Read directly on staging the same minute: review_items holds exactly 1 row (queue entity_link, status open, source_id 01a05782-...).
4. /queues?source_id=not-a-uuid renders the identical page: same single item, same counts.
5. Nothing says the parameter was dropped: zero elements carry data-empty, and the string "did not apply" occurs 0 times in the rendered text.

Expected: the queue narrows to the source the URL names (review_items.source_id exists and is populated), or the page states the parameter it did not apply, as /claims already does. Measured contrast on the same instance and minute: /claims?bucket=in_window renders "The URL carries bucket, which this page did not apply: nothing below is narrowed by it.", and /claims?source_id=01a05782-... narrows to "877 claims match these filters".

Observed effect: a source's own "review items" link presents another source's item as that source's. Spec F5 ("A source links to its review items and its runs") and spec section 4's entity-crossing navigation are the clauses at stake.

Deliberate at code level, not at operator level: queueItemsHref's docstring says "Queues does not offer this facet yet (its vocabulary is kind / queue / shape / status), and an unrecognised parameter there narrows nothing rather than erroring, so the link lands on the queues rather than anywhere broken until that facet is added (admin-window/TASK-0013's handoff)". The same class of problem on /cycles?source= was fixed by TASK-0016 with one sentence beside the table; the honest minimum here is the same sentence. Whether to add the facet or the line is the architect's call.

Evidence: agenticflow/tracker/evidence/M2/verifier/30-queues-source-not-narrowed.png and 27-queues-source-facet.png; run log agenticflow/tracker/notes/verify-M2-2026-09-09.md.

## Acceptance criteria
Standing on /sources and clicking a source's 'review items' link, the Queues page either renders only that source's review_items rows or names source_id as a parameter it did not apply; /queues?source_id=<source with no items> never renders another source's item as a match, and /queues?source_id=not-a-uuid behaves the same way. Pinned in tests/offline/queues/page.test.ts.

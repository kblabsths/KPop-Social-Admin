# The standing tab's own bucket is subtracted with the URL's, so the chip clause is decided off the other tab's population

## Description
**Expected** (BUG-0192's own rule and its own named hazard 1): on the standing tab, the family subtraction drops the chip facets the URL carried, NEVER the tab's own bucket — "dropping that would compare this tab's rows against the other tab's population". `withoutChipFacets`' docstring states the same guarantee: "a facet a SURFACE merged in of its own accord survives it."

**Found** at `src/lib/claims/filters.ts:177-188`: the subtraction decides FROM `asked` but deletes FROM `applied`, and for `bucket` those are two different facets on the standing tab. `listFilterOf` merges the tab's own `bucket = standing_disagreement` into the applied filter and the URL's `?bucket=` is dropped; when the URL carried a `?bucket=` anyway, `asked.bucket !== undefined` is true, so `delete widened.bucket` removes the TAB's bucket. The widened count is then a count of the whole view, not of this tab's subset, and the attribution answer is decided off the wrong set.

```ts
// src/lib/claims/filters.ts:177
export function withoutChipFacets(applied: ClaimsFilter, asked: ClaimsFilter): ClaimsFilter {
  const widened: ClaimsFilter = { ...applied };
  for (const facet of CHIP_FACETS) {
    if (asked[facet] !== undefined) delete widened[facet];   // deletes the TAB's bucket too
  }
  return widened;
}
```

**Repro (exact), offline, on this landed tree:**

1. `/claims?bucket=escalated&source_id=<SOURCE.third>&domain=groups` (the buckets tab; all three facets applied, dropped-parameter line empty).
2. Click the tab "Standing disagreements". Its href is written by `tabLinks`/`claimsQuery` off `filter`, which on the buckets tab still carries `bucket`, so the click lands on `/claims?bucket=escalated&source_id=<SOURCE.third>&domain=groups&tab=standing`. The state is ONE CLICK away, not a hand-typed URL.
3. On that tab the source chip removes NOT ONE row: the standing subset in `domain=groups` is exactly claim `…909` whether or not `source_id=SOURCE.third` is set (measured on `tests/offline/claims/population.ts`).

Expected (the ticket's rule): no clause points at the chip bar, and the sentence is the one the same page renders without the parameter it dropped.
Actual, measured 2026-09-11 by rendering the page (`tests/offline/claims/page.test.ts`):

```
without ?bucket=  : "… so it holds all the claims in the standing_disagreement bucket, in the groups domain the read found."
with    ?bucket=  : "… so it holds all the claims in the standing_disagreement bucket, in the groups domain, matching these filters the read found."
```

The recorded stub calls name the cause — the widened `head:true` count issued for the `?bucket=` render is

```
select("*",{head:true,count:"exact"}).neq("bucket","in_window").eq("domain","groups")
```

with the tab's `eq("bucket","standing_disagreement")` gone, against `…eq("bucket","standing_disagreement").eq("domain","groups")` on the render without `?bucket=`. It is a count of the OTHER tab's population, and every other count this tab issues carries the tab's bucket.

**Blast radius:** the list's window line, the empty card (`NOTHING_MATCHED.filters`) and — on a URL whose source chip also survives into `filter` — the bucket caption's `underTheFilters`, i.e. exactly the clauses BUG-0192 landed. The gauge leg is NOT affected: `gaugeWithoutChipFilter` spreads `populationFilter` first (`src/app/claims/page.tsx:1178`), so the tab's bucket is put back; the list leg has no such repair.

**Not reachable on staging TODAY, and why it is still a bug:** staging holds 0 standing_disagreement claims (measured 2026-09-11 on a production build at `/claims?tab=standing`: "the read happened and found no claims in the standing_disagreement bucket at all"), so the standing surface's population is 0 and `isSurfaceNarrowed` answers false in every state, hiding this. The first standing disagreement the resolver produces arms it.

**A fix must not simply subtract from `asked`**: the widened filter has to stay the APPLIED read with only the facets the URL CONTRIBUTED removed — i.e. drop a chip facet only where `applied[facet] === asked[facet]` (or hand the surface's own facets in), so the tab's bucket survives and the count stays inside this tab's subset.

**The pin** is already on the branch as a strict xfail: `tests/offline/claims/page.test.ts`, `it.fails("claims no filter above on the standing tab when the chip set removed no row of it")`, inside `describe("a narrowing with no chip row")`. It reaches the state by FOLLOWING the tab link off the markup, asserts the read (every `head:true` count of the standing tab carries the tab's bucket), asserts the sentence (no `NARROWED_BY_FILTERS`, and byte-equal to the line without the dropped parameter), and is non-vacuous the other way (a source that really removes a standing row still earns the clause). Watched red as a plain `it(...)` on this tree, twice — once failing on the sentence, once on the read shape. **The fixing builder flips `it.fails` back to `it`** (this repo's own convention, e.g. `tests/offline/claims/page.test.ts:734`), which is what the check below then grades.

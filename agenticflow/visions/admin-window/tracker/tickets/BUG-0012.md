# Resolution latency counts a verdict unset as an apply the join lost

## Description
`ProvenanceApplyRow` types `field_provenance`'s two nullable keys as non-null, and the latency aggregate then reports every verdict unset as a broken join.

**Authority.** Scraper migration `20260901000005` §1 drops NOT NULL on both columns and states the reader contract in the column comments: `source_id` — 'null on a verdict unset, the one row shape whose authority is a human verdict rather than a winning observation'; `observation_id` — 'null on a verdict unset. A reader takes a null here as "no applied observation"'. `contracts/data-model.md`, Per-field provenance, says the same. `src/lib/gauges/resolution-latency.ts:74-79` documents `unmatchedApplies` as 'applies whose observation was not in the second fetch ... a large value means the join, not the resolver, is what the reader is looking at'.

**Found — the type.** `src/lib/db/gauges.ts:167-168`: `source_id: string; observation_id: string;` against columns that admit null. `readProvenanceApplies` (same file, 331-346) filters on `applied_at` alone, so verdict-unset rows are in the window's row set like any other and the type is a lie about rows the read really returns. Compare `src/lib/browse/rows.ts:60`, which types the same column `string | null` after admin-window/BUG-0010.

**Found — the aggregate.** `src/lib/gauges/resolution-latency.ts:121-127`: `observedAt.get(row.observation_id)` misses for a null key, so `unmatchedApplies += 1`. Measured with one measurable apply (600s) plus one verdict unset (both keys null):
- Expected: `unmatchedApplies` 0 — no observation was lost; the unset never named one.
- Found: `unmatchedApplies` 1, and the unset is also counted in `applies` (2) and `byDomain[0].applies` (2), i.e. inside the population the doc calls 'exactly the population of measurable latencies'.
The latency percentiles themselves are unaffected (`overall.count` 1, `unmeasurable` 1).

**Repro.** `tests/offline/gauges/resolution-latency.test.ts` > 'a verdict unset in the apply window' > 'is not counted as an apply whose observation the join lost' — landed as `it.fails` (strict pin, admin-window/this ticket). Flip it back to `it(` as part of the fix; with the pin left as `it.fails` a correct fix turns it red, which is the signal working, not a second bug. Watched red before pinning: `AssertionError: expected 1 to be +0` at line 286.

**Impact.** The gauge is not yet on a page — `src/app/cycles/page.tsx` is still the placeholder Empty and nothing in `src/` calls `readResolutionLatency` — so the defect reaches an operator the day the Cycles page wires gauge 2, and every verdict unset in the window then reads as a join failure the operator is invited to investigate. That is why it is P2 and not P1.

**Note for the fix.** Scope is the nullability, not the gauge's design: type both columns `string | null`, and decide the unset's place explicitly — either keep it out of the apply population at the read (`.not("observation_id", "is", null)`, which also keeps `applies` honest) or count it as its own kind. It must not land in `unmatchedApplies`. `tests/fixtures/rows.ts` `FieldProvenanceRow` types both columns non-null too and is the reason the pin needs a cast; widening it is part of this fix.

# The exhausted sentence tells the operator every claim is shown while the window line beside it says the count found 827 more — /claims

## Description
**Module:** `src/components/ui/paging.tsx` — `PageMore`'s exhausted arm (`[data-paging="exhausted"]`, "All {holds} in this view are shown."), read against the window line `PagedWindowLine` draws from the SAME paging state three lines above it.

**Expected** (admin-window/BUG-0174 acceptance criterion 5, one element down; LESSONS 11 "one row, one verdict — derive the state once"; ARCHITECTURE §4.3 "a concatenation is still not a total"): where `/claims`' count read and its row reads DISAGREE, no sentence on the page asserts a relationship between them that no single read established. BUG-0174 made the window line obey this: in that state it renders the two-reads sentence and deliberately declines to call the set complete.

**Found:** the sentence under the table asserts exactly the completeness the line just declined to assert, in words identical to the state where completeness IS established. Measured on run/admin-window at 03a247c (the landed BUG-0174 tree), offline through the REAL driver from the real deps `/claims` handed it:

- state A (the reads DIVERGE — count 877, the press ends the set having appended nothing): 50 claim rows drawn, `data-window-held="877"`, `data-window-truncated="false"`, driver status `exhausted`.
  - window line: "… A count of claims answered 877; the reads returned the 50 below, and the read found no more." (honest — no completeness claim)
  - sentence under the table: `<p data-paging="exhausted">All claims in this view are shown.</p>`  ← 827 claims the page's own count read found are not on screen, and the operator is told the view is complete.
- state B (the reads AGREE — count 130, pressed to 130): 130 rows drawn, `data-window-held="130"`.
  - sentence under the table: byte-identical to state A's.

The two states render the same sentence, so the one element an operator actually acts on (it is what REPLACES the control — there is nothing left to press) is the one that makes the false-totality claim. The line is right; the control's sentence is the one that misleads.

**Repro (exact), offline through the real driver:**
1. `./node_modules/.bin/vitest run --project=offline tests/offline/claims/page.test.ts -t "does not tell the operator every claim is shown"`
2. The case (added by QA at BUG-0174's close, `tests/offline/claims/page.test.ts`, in `describe("the affordance that continues the claim list")`) builds both states from `pagedScript(877)` / `pagedScript(130)` and compares the two renders' `[data-paging]` markup AGAINST EACH OTHER — it pins no word of either sentence, so a rewording moves it. Watched RED on 03a247c: `expected '<p data-paging="exhausted" …' not to be '<p data-paging="exhausted" …'`, with every non-vacuity assertion green (50 rows under held=877, 130 rows under held=130, driver `exhausted` in both).
3. It is landed as a strict `it.fails` pin (this repo's QA convention), so the suite is green today and turns RED the moment the divergence disappears.

**Reachability on live data — not a fixture artifact.** `/claims`' count and its rows are TWO reads (`readClaimCount` + the paged row reads), and BUG-0174's own ruling records staging's count moving 877 -> 878 mid-campaign. A claim resolved between the count read and the last press ends the set short of the count, which is this state. The same shape exists on the ceiling path and on `/browse` only where a count is read beside the rows — `/browse` has no second read, so it cannot reach it.

**NOT IN SCOPE:** the window line and every one of BUG-0174's twelve criteria (graded green on this tree — the line's behaviour in this state is CORRECT and must not move); the `[data-paging="limit"]` arm's words (admin-window/BUG-0178 owns them); the refusal's face and colour (BUG-0175/0176); the control's width (BUG-0177); the hooks — `data-paging`'s arm names are the live oracle's and no attribute is added or renamed. The WORDS are the designer's jurisdiction; what is graded here is that the two states do not draw one sentence.

**The fix a builder takes also flips the pin**: `it.fails(...)` back to a plain `it(...)` in the same file (the convention this repo already carries in `tests/offline/cycles/page.test.ts`), which is what the second check below measures.

## Acceptance criteria
1. On /claims, the sentence that replaces the control when the read has ended is NOT the same rendering in both of these states, asserted on rendered markup through the real driver from the real deps the page handed it: (a) the reads AGREE — every claim the count found is drawn — and (b) the reads DIVERGE — the press ended the set with fewer rows on screen than the count the page publishes in data-window-held. Compared against each other, so no word of either sentence is pinned.
2. In the diverged state (b) the page asserts no completeness it did not establish: no element of the paged surface states that the view holds nothing more while the page's own count read published a larger number beside it. The window line in that state is UNCHANGED from the landed BUG-0174 tree, to the byte, on the same fixture.
3. In the agreeing state (a) the page renders exactly what it renders today, to the byte — the control's five press states, both end-of-the-road arms and BUG-0174's twelve criteria are untouched. /browse, which reads no count beside its rows, renders byte-identical markup in every state.
4. The QA pin lands as a plain it(...) rather than it.fails(...), and the case's own non-vacuity assertions stand: 50 rows under a published held of 877, 130 rows under a published held of 130, the driver reporting exhausted in both.
5. No data-paging or data-window attribute is added, removed or renamed: the arm names the live oracles read are the ones they read today.
6. Lint is clean and a PRODUCTION build is green.

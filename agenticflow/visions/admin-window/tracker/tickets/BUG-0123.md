# Claims says '877 claims match these filters' over a read nothing narrowed, and drops a hand-typed parameter in silence

## Description
Filed from the M2 user-sim walk of Priya (`agenticflow/tracker/for-human/M2-usersim-priya.md` §6), 2026-09-09:

> "There is **no way to filter claims by record**. Since the filters are plain links, I did what any data engineer does and typed `?record_id=<my event id>` into the address bar. The page returned 200 and cheerfully told me '877 claims match these filters' — the same 877 as before. An unknown filter silently ignored, with a sentence actively asserting it was applied. If I hadn't known the count by heart I'd have believed it."

The same sim, and Devin, both named the window lines as the reason they trusted every number in this app ("I went looking for a lie and found arithmetic"). This is the one sentence that is not true.

**Expected** — LOOK_AND_FEEL bar 13: a window line states the read that produced the rows, and the doc's own clause for a deep link that landed nowhere — "Where no mark is drawn the same line says why … and **no screen claims a mark it did not draw**." A line may not assert a narrowing the page did not apply.

**Found — two sentences on `/claims`, both asserting filters over an unnarrowed read.** Reproduced on the walk instance (127.0.0.1:8771, staging, 2026-09-09) by fetching `/claims` and `/claims?record_id=01a03f78-a122-7baf-acf7-6f997a030048` and diffing the rendered text: **byte-identical**, both carrying

- the list's window line: "A window of at most 50 rows, not the whole view. **877 claims match these filters**; the 50 longest-waiting are below — narrow with the filters above to reach the rest." (`src/components/ui/window-line.tsx:442-467`, the `matched` arm's truncated clause; the phrase is unconditional and fires with an empty chip bar), and
- the bucket table's caption: "Every bucket the classification view can hold, with the claims in it **under the filters above**." (`src/app/claims/page.tsx:580-584`) — with no filters above.

The page already knows the answer: `isNarrowed(filter)` decides the empty card's words two blocks below (`src/app/claims/page.tsx:548-553`), and `filterFrom(params, options)` (`src/lib/claims/filters.ts`) is where a parameter that narrows nothing is dropped — silently, with nothing carried to the screen.

The count itself is right and the window's cap is stated: this is the sentence around the number, not the number.

Provenance checked before filing: `git log src/components/ui/window-line.tsx src/app/claims/page.tsx` returns ticket-bearing commits only (BUG-0118, BUG-0114, BUG-0109, BUG-0108, TASK-0055). Not a human-lane divergence.

Scope note: `/queues` renders a filter bar of the same shape and its own "items matching these filters" words (`src/app/queues/page.tsx:187`). It is **deliberately out of this ticket's scope** — one page proven first, and no sim walked a hand-typed parameter there. If the fix generalises cleanly in `window-line.tsx`, taking `/queues` with it is welcome, not required.

## Acceptance criteria
1. On an **unnarrowed** read — no facet chip set — neither the list's window line nor the bucket table's caption asserts a filter. The count keeps its noun and its window ("877 claims in all; the 50 longest-waiting are below — narrow with the filters above to reach the rest." or equivalent in the app's voice), and the cap sentence is unchanged.
2. When one or more facets ARE set, the filter phrasing is exactly what it is today, to the byte, including the standing tab's bucket clause (admin-window/BUG-0118 does not regress).
3. **A parameter the page did not apply is named as not applied.** When the URL carries a query parameter that is not one of the page's facets (`record_id`), or a facet value the read holds no rows for and no chip offers (`bucket=in_window`), one line beside the filter bar says so in the app's voice, naming the parameter verbatim in mono and stating that the rows below are not narrowed by it. `tab` and any parameter the page really consumes are not named.
4. `in_window` still never reaches the visible text of any page (bar 3): a value the app may not render is reported as "the URL asked for a filter this page does not apply" without echoing the value, or is echoed only if it is not `in_window` — the builder picks, and the offline `in-window` guard stays green.
5. No change to the rows shown, the counts, the chips' hrefs, the sort statement, the window's `data-window-*` hooks, or the three empty renderings.
6. Human-check (human-checkable): on the walk instance, `/claims` and `/claims?record_id=<any uuid>` no longer read identically, and neither claims a filter that is not set.
7. `npm run lint` and `tsc --noEmit` clean; the offline suite green.

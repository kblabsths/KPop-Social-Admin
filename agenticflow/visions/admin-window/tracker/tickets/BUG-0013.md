# PATCH with a non-finite number (1e999) NULLs a catalog column and answers 200

## Description
BUG-0011's harm through a different door in the same function, on the same route. Found on the LANDED run branch (run/admin-window @ 8ff70f7) while re-checking BUG-0011's fix. It is NOT a regression from that fix: the scalar-type gate below is byte-identical at ac2738d (pre-fix) and at 8ff70f7 (`git show ac2738d:'src/app/api/admin/records/[table]/[id]/route.ts'` lines 77-86) — the hole predates the bounce and survived it untouched.

Expected (the route's own contract, `src/app/api/admin/records/[table]/[id]/route.ts:31`): "only an explicit `null` or `\"\"` clears a column"; and :27 "The request body carries a SCALAR value or null".

Found: a request that asks to SET a value silently NULLs the column and is answered 200 `{"ok":true}`.

  PATCH /api/admin/records/groups/2f0bc11e-0000-4000-8000-000000000001
  content-type: application/json
  {"field":"bio","value":1e999}

  STATUS: 200
  BODY:   {"ok":true,"record":{...}}
  WRITER CALLED: 1
  PostgREST PAYLOAD ON THE WIRE: {"bio":null}

Same for `-1e999`, and for any editable column (`member_count`, `name`, ...).

The chain, each link measured 2026-09-02 on 8ff70f7:
1. `1e999` is valid JSON. `JSON.parse('1e999')` === `Infinity`, `typeof` === `"number"`.
2. `parseBody`'s scalar gate (route.ts:98-107) admits any `typeof value === "number"`, so `Infinity` is accepted as a legitimate scalar and `parseBody` returns `{ok:true, field:"bio", value:Infinity}`. The BUG-0011 guard at :87 does not fire — the `value` key IS present.
3. `updateRecordField` (`src/lib/db/records.ts:105`) builds `.update({ bio: Infinity })`.
4. supabase-js/postgrest-js serialises the update body with `JSON.stringify`, which renders a non-finite number as `null` (ECMA-262: `JSON.stringify(Infinity)` === `"null"`). The bytes PostgREST receives are `{"bio":null}` — byte-identical to an explicit clear.
5. The column is set to NULL and the route answers 200 `{"ok":true}` with the row as stored.

Step 4 measured directly, offline, with a real `createClient` whose `global.fetch` is captured (no socket opened):
  value "hello"  -> payload {"bio":"hello"}
  value null     -> payload {"bio":null}
  value Infinity -> payload {"bio":null}     <-- indistinguishable from the clear
  value -Infinity-> payload {"bio":null}
  value 5        -> payload {"bio":5}

Impact is BUG-0011's, unchanged: this is the app's only write path, it runs with the service-role key (RLS bypassed), and it reaches the vetted catalog. Nine of `groups`'s ten editable columns are nullable in the scraper snapshot (only `name` is NOT NULL), so a malformed request destroys a vetted value and is reported as a success. AGENTS.md's data-ownership rule makes Admin's job corrections; a silent null-out answered `{"ok":true}` is the opposite. Trigger is more exotic than BUG-0011's (a numeric literal over ~1.8e308 rather than a dropped `undefined`), which is why this is P2 and not P1 — but the trust boundary in STACK.md names forged edit requests from a caller past the admin gate as exactly this route's adversary model, and a 200 that reports data loss as success is not something the caller can detect.

Not a security escalation — the caller must already be past `requireAdmin()`.

Fix (suggested): reject a non-finite number in `parseBody`, beside the existing scalar gate — e.g. refuse when `typeof value === "number" && !Number.isFinite(value)` with 400 naming the value. The explicit `null`/`""` clearing paths and the BUG-0011 guard must stay untouched (`tests/offline/edit/route.test.ts` > "still clears a column on an explicit null or an emptied input" and > "refuses a body that omits `value` instead of clearing the column" pin those and must stay green).

The pin: `tests/offline/edit/route.test.ts` > "refuses a non-finite number instead of nulling the column" is marked `it.fails` — a strict pin, green only while the divergence is live. Fixing the route turns it RED; the fix therefore also flips `it.fails` back to `it` in that file. It was watched failing as a plain `it()` against 8ff70f7 before this ticket was filed (AssertionError: {"field":"bio","value":1e999}: expected 200 to be greater than or equal to 400).

Note the bodies in that test are RAW STRINGS on purpose: `JSON.stringify({value: Infinity})` produces `{"value":null}`, so an object body cannot express this request — a test that builds its body as an object silently tests the explicit-clear path instead and passes for the wrong reason.

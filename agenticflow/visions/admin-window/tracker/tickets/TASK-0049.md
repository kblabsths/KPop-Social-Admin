# The close slot: the settle route, the shared frame, the absent-function state and the note field

## Description
**SPEC F10, the frame.** M1 rendered the close slot's SPACE and settled nothing. This ticket builds the slot, its route, its absent state and its note field — and **seeds the three shape modules the next three tickets fill**, so those can be built in parallel without landing in one file (ARCHITECTURE §13.9: consolidation-shaped work is chained at its destination).

**The route**: `POST /api/admin/review-items/[reviewItemId]/settle`. `requireAdmin()` first, exactly as the record PATCH route does; then the body is parsed into a `VerdictDecision`; then `decisionRefusals` — a refused decision is a 400 naming the refusal and never reaches the database; then the ONE call, `settleReviewItem` from `src/lib/db/verdict.ts`. No second write path, no `"use server"` action, no direct write to `review_items` or `verdicts` anywhere. The route is `POST`-only; Next answers every other method 405.

**The frame**: `src/components/review/close/slot.tsx` — a pure synchronous component (§5: the page is the only `async` boundary) taking plain props: the item, the readiness result from `readSettlementReadiness`, and the shape's action list. It renders:
- `not_provisioned` — the graded normal case — as `data-state="not_provisioned"` naming the missing object, with **zero** action controls;
- the note field beside the actions, optional everywhere except `wont_fix`;
- **nothing at all in the recommendation slot**: its producer is parked and stays parked; the strings `recommend`/`recommendation` occur zero times in the rendered detail HTML.

**The three shape modules**, seeded here with an empty action list each and filled by their own tickets: `conflict-actions.tsx` (`data_conflict`), `link-actions.tsx` (`entity_link` fact), `signal-actions.tsx` (the source-pattern signal). They are **not placeholders**: with the function absent, no shape offers an action, so an empty list is the truthful state until each ticket lands. `actions.ts` holds the shared `ActionSpec` type — a label, an action name from `VERDICT_ACTIONS`, and how the control builds its `VerdictDecision`.

**Where the kind comes from**: `lib/review/shapes.ts`, which is already the one place a shape becomes a `decision` or a `signal` (§11). Do not re-derive it.

**Data reality, not a defect** (SPEC F10, M2.md): staging holds exactly ONE review item and it is the `entity_link` source-pattern signal. The two fact-shaped items do not exist there. Fact-shaped rendering is graded on fixtures from `tests/fixtures/rows.ts`; "built, not walkable on this data" is the honest grade, and a criterion demanding a fact-shaped row on staging is mis-authored.

**The absence is the normal case and is graded FIRST.** `verdicts` and `settle_review_item` do not exist on staging and will not until Ben installs the handoffs — that is the database `main` deploys against for the whole of M2. Build and grade the not-provisioned path before the happy path, and never offer a control that would call a missing function.

**No Admin-side workaround for the absent function may be written** — spec §10's one forbidden move: no queued write, no pending-overrides table, no retry buffer, no flag-guarded direct write.

## Acceptance criteria
1. With `verdicts` absent (staging today): every review-item detail renders the close slot as `data-state="not_provisioned"` naming the missing object, contains ZERO action controls and zero form elements, the page answers 200, and every other part of the detail renders exactly as M1 shipped it. Graded offline against the absence fixture and by the page's live suite.
2. With `verdicts` present (stub): the slot renders the shape's action list and the note field; a shape with no actions yet renders the note field and no controls, and says nothing misleading about why.
3. The route exists at `POST /api/admin/review-items/[reviewItemId]/settle`, is gated by `requireAdmin()`, answers 405 to GET/PATCH/DELETE, and answers 400 naming the refusal for a decision `decisionRefusals` rejects — with the recording stub proving zero database calls were made for it.
4. The route's only database interaction is `settleReviewItem`; no `.update(`, `.insert(`, `.upsert(`, `.delete(` or second `.rpc(` exists anywhere in `src/` on any path to `review_items` or `verdicts`.
5. The recommendation slot renders nothing: the strings `recommend` and `recommendation` occur zero times in the rendered detail HTML, on every shape and in both states.
6. An unauthenticated request to the new route redirects to login (the http suite derives routes from the app tree, so this is graded by running it, not by a hand-added entry).
7. The three shape modules exist with the shared `ActionSpec` contract and empty action lists; `tests/offline/absence/pages.test.ts` grades the new surface through the shared rule rather than a per-page docstring (the window-line/state rule, ARCHITECTURE §4.3).
8. `npm run lint`, `tsc --noEmit`, the targeted offline files, the review-item live suite and the http suite are green.

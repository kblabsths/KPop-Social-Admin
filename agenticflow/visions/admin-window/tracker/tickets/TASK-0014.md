# Cycles & runs — the resolver's cycles, newest first, with their counts and errors

## Description
Module: `src/app/cycles/page.tsx` + `src/lib/db/cycles.ts` — **the `resolution_runs` half only**. Authority: spec section 4 (Cycles & runs) and section 5; `contracts/resolver.md` section 6 (the `resolution_runs` row and every column's meaning); SPEC F5; acceptance tests 2, 9, 11; LOOK_AND_FEEL taste reference 'GitHub Actions run list — a run diagnosed from its row'.

- `resolution_runs` **newest first**, with the counts as columns: `facts_examined`, `applied`, `held`, `escalated`, `entities_created`, `claims_linked`, `claims_rerejected`, `errors`, and `error_summary` **inline**, verbatim, in mono.
- **A cycle still running (`ended_at` null) and a `skipped` cycle are each legible as such.** `outcome` is null until completion by design, and an old row with a null `ended_at` is a cycle that died — nothing repairs it, so render it as what it is rather than as 'running' forever (migration `20260901000001`'s own words).
- The **cycle-health** and **resolution-latency** gauges (TASK-0007) render on this page.
- **The adapter framework's `runs` are NOT rendered by this ticket.** That half is TASK-0015, which waits on a blocked question. Leave a clearly named seam — a section that renders nothing — and do not guess at its columns.

Standing rules for every page ticket (ARCHITECTURE sections 4, 5, 7): the page function is the only async component on the route and every child is a pure sync component; read only through `src/lib/db/**`; table names live only in `tables.ts`; render all four states from the `ui` primitives (a missing table never throws and never renders as 0); tokens and primitives, never raw values; every filter, sort and tab is a `searchParams` value; ages relative with the absolute in the title attribute, scheduled times absolute UTC with the zone in the column header, machine identifiers verbatim in mono; **nothing settles anything in M1**.

- **Every latency figure on this page is the AGGREGATE's, never `rows.length`.** `ResolutionLatencyRows.applies` is the raw window — applies AND verdict unsets, exactly as the read returned them — while `ResolutionLatency.applies` is a COUNT of the applies among them, with the unsets excluded and reported separately as `verdictUnsets` (`src/lib/gauges/resolution-latency.ts:63-72` and `:90-124`; BUG-0012). The two spellings are deliberately not the same population, so `rows.applies.length` over-counts by exactly the unsets. Render `readResolutionLatency`'s output — `applies`, `verdictUnsets`, `unmatchedApplies`, `overall`, `byDomain` — and never re-derive a figure from a row array. A domain whose window held only unsets is listed with `applies: 0` and a latency of nulls; that zero is a measured count and `verdictUnsets` is what explains it, so show both or the zero reads as a defect in the resolver.
- A count from a truncated window is a floor and says so (`window.truncated` -> `GaugeCard`'s `floor`); it is never presented as a total.

## Acceptance criteria

A live-marked parity test asserts the rendered cycle rows and their newest-first order against a query the test issues itself. The cycle-health and resolution-latency gauges render. The adapter-runs section renders nothing and names no column. The not-provisioned state names `resolution_runs`.

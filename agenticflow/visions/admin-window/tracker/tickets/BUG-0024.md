# Review-item evidence is always empty on staging: the app selects observations.entity_type, a column the schema owner dropped

## Description
LIVE parity pass, 2026-09-02 (first run against staging). The review-item detail page renders ZERO evidence rows for every review item on staging, because the app selects a column the schema owner retired.

## Repro (exact, deterministic — ran twice, identical)

1. From the repo root:
   `./node_modules/.bin/vitest run --project=live tests/live/review-item.live.test.ts`
   -> exit 1, "Tests 2 failed | 2 passed (4)".
   - "resolves exactly the evidence ids the row carries, in its fold order":
     AssertionError: expected [] to deeply equal [ ...(86) ]
   - "renders each claim's own instant, status and source tier":
     expected undefined to be '2026-08-31T17:46:18.139649+00:00'
     (no `[data-evidence=...]` row exists for the claim).

2. Direct PostgREST repro of the read at `src/lib/db/review-item.ts:203-222`
   (`readObservations`), issuing `OBSERVATION_COLUMNS` verbatim against the 86
   distinct ids in staging's single `review_items.evidence` array:
   `observations` -> error `42703: column observations.entity_type does not exist`
   (141ms, 0 rows of 86).

## Expected vs Found

Expected (SPEC F4 / M1 EC7 / acceptance test 5; `readItemEvidence`,
src/lib/db/review-item.ts:407-467): every evidence id that names a real
observation resolves to a claim and renders, in fold order; ids that name none
render as `[data-unresolved]`.

Found: `readObservations` fails with 42703 for every chunk, so
`readItemEvidence` returns non-ok at src/lib/db/review-item.ts:413, and
src/app/queues/[reviewItemId]/page.tsx:442 renders `StateOf` instead of the
evidence table. Zero evidence rows, for every item, always. Staging's one
review item carries 2064 stored / 86 distinct evidence ids, and all 86 exist in
`observations` (the test's own independent read resolved them).

## Anchor

- `src/lib/db/review-item.ts:111` — `"entity_type"` inside `OBSERVATION_COLUMNS`
  (lines 109-121).
- `src/lib/db/review-item.ts:63-64` — `ObservationRow.entity_type: string`, with
  the comment "`observations` spells the canonical table `entity_type` (trap 1)".
  Nothing in `src/` ever READS that field off an observation (grep: the only
  `entity_type` reads are on `field_provenance`), so the column is selected for
  a value the app does not use.
- The schema owner dropped it:
  `kspace Scraper/supabase/migrations/20260819000002_the_domain_is_the_entity_type.sql`
  — "observations.entity_type (the column) is dropped. domain becomes the first
  part of both identities" — while explicitly keeping `field_provenance`'s
  ("field_provenance IS NOT TOUCHED. Its entity_type column stays").
- Staging's real `observations` columns, read 2026-09-02: domain, entity_id,
  external_ref, field, last_confirmed_at, observation_id, observed_at,
  payload_ref, rejected_at, rejected_by, schema_version, source_id, status,
  value.

## Scope of the fix (not a schema change — this repo only)

`src/lib/db/review-item.ts` only. `PROVENANCE_COLUMNS` (line 125) and the
`.eq("entity_type", ...)` at line 263 are on `field_provenance` and are CORRECT;
`src/lib/db/gauges.ts:212` and `src/lib/db/browse.ts:162` are likewise on
`field_provenance` and correct. `src/lib/review/shapes.ts:36` already states the
right rule for `review_items` ("`domain` — not `entity_type`"). ARCHITECTURE.md
§6 trap 1's sentence about `observations` is what led here and should be
corrected with the fix. No migration, no schema change, no sibling edit.

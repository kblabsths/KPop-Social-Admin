# The window line says 50 claims are below it while 37 are on screen — the unpaged arm falls back to the cap

## Description
**Module:** `src/components/ui/window-line.tsx:541` — `onScreen(info) { return info.drawn ?? info.limit; }`, read by the `matched` arm's `holdsBack` clause ("the {N} longest-waiting are below") on the UNPAGED arm of /claims, where `drawn` is absent.

**Expected** (admin-window/BUG-0174's own rule, LESSONS 2, ARCHITECTURE §4.3): the clause that names the rows BELOW the line states the rows that are on screen. BUG-0174 closed exactly this on the PAGED arm — its `onScreen` docstring records the defect as 'the matched arm fell back to `limit` whenever no press had grown the window past it'.

**Found:** the same fallback still fires wherever the window carries no `drawn` — which is every UNPAGED state of /claims — and the clause is NOT gated on the read having filled its cap (`onScreen`'s docstring claims it is: 'The cap keeps its ONE true use, the unpaged window, where the clause is rendered only over a read that filled'). The gate is `info.truncated`, and on /claims `truncated` comes from the COUNT read (`src/app/claims/page.tsx:1163`, `listCount.data > listed.length`), never from the rows filling 50.

Measured on run/admin-window at c35cc33, offline through the page's real render from the real deps, fixture `offGridScript(rows, count)` (the suite's own 'a database this app must survive' fixture, tests/offline/claims/page.test.ts):

- 37 rows drawn, count 900 -> `data-window-held="900"`, `data-window-truncated="true"`, no paging element, line: '… A window of at most 50 rows, not the whole view. 900 claims in all; the 50 longest-waiting are below — the rest are not shown.'
- 10 rows drawn, count 877 -> same clause: 'the 50 longest-waiting are below'.
- 49 rows drawn, count 51 -> same clause: 'the 50 longest-waiting are below'.
- 37 rows drawn, count 37 (the reads AGREE) -> 'The window did not fill — 37 of at most 50 …' (correct; this is the state the fallback is safe in).

So three screens holding 37, 10 and 49 claims all tell the operator that 50 are below the line. The number is the CAP, published as a description of the screen.

**Reachability:** /claims is drawn unpaged whenever `pageBound(String(listed.length), 50)` is off-grid — i.e. whenever the row read comes back with a number of rows that is not a multiple of the window while the count says more exist. That is the same two-reads divergence this campaign has already recorded on live data twice (staging's count moved 877 -> 878 mid-campaign; admin-window/BUG-0174, admin-window/BUG-0180) and the state the suite's own `offGridScript` comment calls 'a database this app must survive'. It was NOT reproduced on staging: staging's count and rows agree today, and the paged arm (BUG-0180's tree) is correct in every state QA drove in a browser.

**Repro (exact), offline:**
1. `./node_modules/.bin/vitest run --project=offline tests/offline/claims/page.test.ts -t "states the rows that are BELOW it"`
2. The case (QA, in `describe("the claim list's window")`) renders two off-grid screens under ONE count — 37 rows and 10 rows, both count 900 — and compares the two LINES against each other. It pins no word of the sentence: a line that states what is below it cannot say the same thing about two screens holding different numbers of claims. Watched RED on c35cc33 with every non-vacuity assertion green (37 and 10 rows drawn, held=900 on both, `pagingOccurrences` 0 on both).
3. Landed as a strict `it.fails` pin (this repo's QA convention), so the suite is green today and turns RED the moment the divergence disappears. **The fix also flips the pin** to a plain `it(...)`, which is what check 2 below measures.

**NOT IN SCOPE:** the PAGED arm and every one of admin-window/BUG-0180's criteria (graded green on this tree, and the paged control's two terminal sentences are correct — do not move them); the `didNotFill` clause, which is the honest reading where the two reads AGREE and must keep rendering exactly what it renders; the hooks (`data-window-*` are the live oracle's; none is added or renamed); whether /claims should offer a control in an off-grid state at all (admin-window/BUG-0172 ruled it may not, and that ruling stands). The WORDS are the designer's; what is graded here is that the number the clause names is the number of rows on screen.

## Acceptance criteria
1. On the UNPAGED /claims arm, the line's below-clause states the rows the page DREW, not the window's cap: two screens rendered from the same count and different row counts (37 and 10 under a count of 900) do not render the same line. Asserted on rendered markup from the page's real render, compared against EACH OTHER, so no word of the sentence is pinned.
2. ONE derivation still: the number comes from onScreen(info) in src/components/ui/window-line.tsx and no call site computes a second one. A window carrying no drawn does not fall back to a number no read established — if the cap is the honest answer in some state, that state is named in a comment and covered by a test.
3. The state where the reads AGREE is untouched: a window that did not fill under a count equal to its rows still renders the didNotFill clause byte-identically to the tree this ticket starts from, and every window line on the PAGED arm (admin-window/BUG-0180's tree, both pages, first screen included) renders byte-identically in every state.
4. The QA pin lands as a plain it(...) rather than it.fails(...), and its own non-vacuity assertions stand: 37 rows and 10 rows drawn, data-window-held 900 on both, and no paging element in either.
5. No data-window attribute is added, removed or renamed, and the first server render of /claims and /browse is unchanged (SPEC F14, admin-window/BUG-0172).
6. Lint is clean and a PRODUCTION build is green.

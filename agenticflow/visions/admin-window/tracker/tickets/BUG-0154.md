# A source whose registry NAME is blank reaches the screen as a blank evidence cell and a link with nothing to read — the third rendering of one row's absence

## Description
Found attacking BUG-0152 (the evidence pair's absence guard) across the review item page it lands on. BUG-0152 is fixed; this is upstream of it — WHICH value the page hands the guard.

Expected (two of this suite's own pinned rules, and they agree):
 1. `tests/offline/review-item/page.test.ts:2512` "renders the app's dash, on every absence the evidence table reaches" — no evidence cell is ever blank (`expect(cells.filter((cell) => cell === "")).toEqual([])`) and every absence draws EM_DASH;
 2. `tests/offline/review-item/page.test.ts:2215` "keeps the id verbatim when the registry named nothing" — "the id is then the only true thing the page can say, so it says it rather than BLANKING THE LINK" (admin-window/BUG-0043; `src/lib/sources/names.ts:16` says the same: "name it, or render the id VERBATIM … a blank or a guess would be worse than a uuid", pinned as "never answers with an empty label", `tests/offline/sources/names.test.ts:63`).

Found (measured offline 2026-09-09, vitest + cheerio, on run/admin-window @ 53081a3, no device, no network): a `sources` row that EXISTS with `source = "   "` takes neither branch — the lookup finds the row, `??` sees a string, and the blank reaches the anchor as its only content.

  `sourceLabel(sourceNamesOf([{ source_id: S, source: "   " }]), S)` -> `"   "` (length 3, `isAbsent` true). The rule test passes vacuously: it asserts `length > 0`, and whitespace has length.

  Review item page (`conflictScript` with `[T.sources]: {data: [sourceRow({source: "   "}), BANDSINTOWN]}`), evidence row of CLAIM_A, cells as the operator reads them:
    ["TWICE 5TH WORLD TOUR", "", "official", "9d ago", "applied", "ticketmaster/…json"]
  against the sibling row of CLAIM_B, whose source IS named:
    ["TWICE World Tour", "bandsintown", "standard", "9d ago", "pending", "b/x.json"]
  i.e. cell 2 is `""` — a BLANK cell, `[aria-label="no value"]` count 0 inside it — and the markup is
    <a href="/sources?source_id=…0101" data-claim-source="   " class="text-accent…">   </a>
  an anchor whose entire visible content is whitespace: the operator's one route to that source (LOOK_AND_FEEL bar 10) has nothing to read and nothing visible to click, while the row beside it reads "bandsintown".

  Same page, same row, same value, two OTHER renderings — both correct: the claim line and the provenance line of the evidence pair draw the app's dash for it (BUG-0152's guard; measured "— · official · 9d ago" and "— · trusted at apply · applied 8d ago"). So one row's absence renders three ways on one page, and the third one announces nothing.

Where it comes from:
 - `sourceLabel` (`src/lib/sources/names.ts:45`) falls back with `??`, which catches null/undefined only, so a present-but-blank name passes through (LESSONS 4: compare on a normalized form — the app already has one, `isAbsent`/`visibleContent`);
 - `canonicalSideOf` (`src/lib/db/review-item.ts:530`) RETYPES that same `??` instead of importing `sourceLabel` (LESSONS 5), so both spellings need the fix or they drift again;
 - the two cells that draw the result put it in an anchor with no guard: `sourceColumn` (`src/components/review/evidence-cells.tsx:204-212`) and `/claims`' source column (`src/components/claims/claim-list.tsx:167-176`). `evidence-cells.tsx:91` states the assumption this falsifies: "A column with no `value` carries nothing nullable (`source`, `observed`, `status`, `fact`) and can never dash."

Reach: one `sources` row whose name is empty or whitespace — the same trigger admin-window/BUG-0152 was filed and priced on, and the registry is the scraper repo's (this repo cannot vet it). Nothing on staging holds one today. P3 for that reach; inside that state the impact is wider than BUG-0152's (every claim of that source on `/claims` and on every review item loses its readable identity and its link's ink), so it is not below P3.

Pin (landed on run/admin-window by qa-0152, strict `it.fails`, watched RED first as a plain `it`: `AssertionError: blank cells: expected [ "" ] to deeply equal []`):
  `tests/offline/review-item/page.test.ts`, "renders no blank cell for a source whose registry name is blank" — inside describe "an evidence cell with nothing in it", beside the fixtures that only ever remove the whole registry read. It carries a non-vacuity assertion (the sibling row reads its own source name). THE FIX FLIPS IT to a plain `it`.

Repro:
  1. cd "kspace Admin"
  2. ./node_modules/.bin/vitest run --project=offline tests/offline/review-item/page.test.ts -t "renders no blank cell"
  3. It passes as an EXPECTED FAILURE. Flip `it.fails` to `it` and it goes red on the blank cell.

Fix shape (not binding): give the label rule the app's own definition of blank — `sourceLabel` answers the id verbatim when `isAbsent(name)`, one place, and `canonicalSideOf` imports it rather than retyping `??`. Then the evidence pair's guard keeps drawing the dash only where the app truly knows nothing, and the two source cells stop needing one of their own. Add the blank-name fixture to `tests/offline/sources/names.test.ts`'s "never answers with an empty label" so that rule stops passing vacuously.

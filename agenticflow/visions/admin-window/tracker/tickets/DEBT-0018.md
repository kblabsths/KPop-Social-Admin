# Two vitest runs in one checkout redden the layering suite: its self-guards write a FIXED probe path and remove the shared parent

## Description
**Modules:** `tests/offline/db/layering.test.ts` (both self-guards) and `tests/isolated/probe-race.isolated.test.ts` (the pin whose docstring names the path). No product code.

**Found** (QA, admin-window/BUG-0170 close, "also noted, not product") and **re-measured by the architect on run/admin-window @ 127a2a0, 2026-09-11**: two runs of that one file, concurrently, in one checkout —

```
./node_modules/.bin/vitest run --project=offline tests/offline/db/layering.test.ts >/dev/null 2>&1 & p1=$!; \
./node_modules/.bin/vitest run --project=offline tests/offline/db/layering.test.ts >/dev/null 2>&1 & p2=$!; \
wait $p1; r1=$?; wait $p2; r2=$?; test $r1 -eq 0 -a $r2 -eq 0
```

fails **3 runs out of 3** (`r1=1 r2=1` each time, 1.7 s a pair). The failures are in `the credential guard itself`: "still reaches the scanner from there, and leaves nothing behind", "reports nothing for a file that reads an unrelated env name", "detects a bracket key it cannot resolve, however that key is written". Alone, the file is green (29/29).

**Why.** Both self-guards write a FIXED path — `src/.probes/__credential_guard_probe__.ts` (line 217) and `src/.probes/__leaf_import_probe__.ts` (line 614) — and each `finally` does `fs.rmSync(probeDir, {recursive: true})` on the **shared parent** `src/.probes`. So two runs in one checkout collide three ways: one run's probe content is read back by the other run's scan at the same path (which is what the three failures above are), one run's `rmSync` deletes the other's probe mid-scan, and the parent removal races a concurrent `mkdirSync` (`ENOTEMPTY`/`ENOENT`). The suite's structural rules also read the UNFILTERED walk by design (`allSourceFiles`, the file's own docstring), so a foreign run's probe — which deliberately contains `process.env.SUPABASE_SERVICE_ROLE_KEY` — is a file the rules can grade as a violation.

**Ruled: a DEBT here, not a proposal to the curator** (architect, 2026-09-11). The defect is in this repo's own test code and only this repo can fix it; the kit has nothing to patch. It is worth a ticket rather than a note because the factory routinely has two vitest runs in one checkout — a QA lane attacking the landed tree while `receipt.py` re-runs a ticket's stored checks, and `npm test` sits in nearly every ticket's check block — and the failure is a FALSE RED in someone else's lane, which is the kind of finding that gets filed as a phantom product bug (admin-window/BUG-0032 and BUG-0033 are the same probe's earlier two).

**Not a one-liner, and that is the ruling's substance.** A per-run temp NAME alone fixes the collision but not the third hazard: a foreign run's probe still sits in the unfiltered walk the rules grade. Both properties below are required, and they are small — the repo already has the idiom (`tests/.probes/admin-locked-${process.pid}` in `tests/offline/edit/config.test.ts`, `source-tree-${process.pid}-${randomUUID()}` in `tests/offline/toolchain.test.ts`). What must NOT change: the probes stay under a dot-hidden segment beneath `src/` (that is what keeps them out of every compiler's program, `toolchain.test.ts` > "reports only what a compiler compiles"), each self-guard still runs the SAME scanner the rule runs, and neither guard becomes vacuous.

## Acceptance criteria
A PROBE PATH IS UNIQUE PER RUN, AND A RUN REMOVES ONLY ITS OWN. Both self-guards in tests/offline/db/layering.test.ts — the credential probe and the leaf-import probe — write beneath a directory whose name carries process.pid (the idiom tests/offline/edit/config.test.ts and tests/offline/toolchain.test.ts already use), and the finally removes THAT directory, never the shared src/.probes parent. The fixed spellings "src/.probes/__credential_guard_probe__.ts" and "src/.probes/__leaf_import_probe__.ts" appear nowhere in the file. The probes stay dot-hidden beneath src/ — the case "hides its probe from every compiler that reads this tree" still asserts a path segment beginning with "." and still passes, because that is what keeps a probe out of tsc's program and out of a next build running beside the suite.

A RUN'S RULES ARE BLIND TO A PROBE THAT IS NOT ITS OWN. The structural rules of this file keep reading the unfiltered walk (they must: the self-guards are the point), but the file list they grade excludes any path under src/.probes/ that is not this run's own probe. A foreign run's probe contains process.env.SUPABASE_SERVICE_ROLE_KEY on purpose, so leaving it visible would let one lane's scan report another lane's probe as a violation of the credential rule.

PROVED BY THE MEASUREMENT THAT FAILS TODAY, NOT BY INSPECTION. The concurrent pair in the description — two runs of tests/offline/db/layering.test.ts started together, both exit 0 — is a stored check. It failed 3 of 3 attempts on run/admin-window @ 127a2a0 before this ticket, so it is not vacuous; it passes after the fix, and it passes repeated (run it at least three times in the lane before handing over, and say the number in the handoff). The file alone stays 29/29, and npm test — which runs the offline project and then the isolated one — stays green.

NEITHER GUARD GOES VACUOUS. Every case of "the credential guard itself" and "the leaf-import guard itself" keeps both of its fixtures, the one it MUST flag and the one it must not (LESSONS 8), and each still calls the same scanner (filesWhereCodeMatches / foreignImports) the real rules call rather than a second predicate written for the test. "still reaches the scanner from there, and leaves nothing behind" keeps asserting that the probe was visible to the walk AND that nothing survives the scan — with "nothing survives" now meaning this run's own directory.

THE PIN THAT QUOTES THE PATH IS UPDATED WITH IT. tests/isolated/probe-race.isolated.test.ts plants a probe at a path it declares as "the path tests/offline/db/layering.test.ts writes its probe to"; after this ticket that sentence is false. It keeps planting its own probe under a dot-hidden directory beneath src/ — its subject is a walker's resilience to a file that appears and vanishes there, which is unchanged — and its declaration says what it now is. Its three cases and the whole-project case stay as they are; the isolated project stays a separate invocation after the offline one, and tests/offline/toolchain.test.ts's assertions about that isolation are untouched.

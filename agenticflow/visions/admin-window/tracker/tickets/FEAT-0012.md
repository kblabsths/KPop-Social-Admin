# The reference field: a picker that links rows, and a reference that renders as a link

## Description
**SPEC F12.** A reference field is a picker, never a text box — and a reference RENDERS as a link to the record it names.

**The edit half (spec §8, acceptance test 8).** A field whose kind is `reference` edits through an **entity picker**. The picker's choice lands as the admin-tier observation **plus its confirmed match**, so the apply produces `venue_id` / `event_performers` ROWS instead of writing text into a column. The picker searches within the referenced entity's own table, offers only rows that exist, and **never creates an entity** — entity creation is the resolver's, not Admin's. Absent `settle_review_item`, the picker does not render at all: the field is read-only with the reason named, like every other override-regime field (FEAT-0011).

**The display half — this is what ends the idol-group islands.** A reference renders as a **link to the record it names**, wherever it is shown. `events.venue_id` already ships this rendering (BUG-0034 replaced a bare uuid with a link; `recordHref` is the one spelling, DEBT-0001). Apply the same rendering to `idols.group_id`, so an idol's record shows its group and reaches it in one click, and a group's record reaches its idols. A user-sim spent a walk discovering that "groups and idols are two islands" and that an idol page "lists stage_name, real_name, korean_name, position, nationality and so on, but not which group the idol belongs to, and it links nowhere".

**Two hard limits on the display half, because it is easy to over-reach here:**
1. **It adds no editable column.** SPEC F8: the map holds "user-facing fields only, never ids, keys, or timestamps". `group_id` is a key. It is DISPLAYED as a link and it is NOT in the map. A ticket that adds a key to the allowlist is wrong.
2. **It is not a door.** A first group is still reachable only by pasting a uuid. Whether the app gets a groups/idols listing or a search is ROADMAP question 1, Ben's alone, and SPEC F7 forbids a second curated view until he answers. Do not build a listing, a search box, or a "browse groups" affordance under cover of this ticket.

**Same absence rule as every M2 surface:** with the function absent, the reference field is read-only and says why; nothing throws; the link rendering still works, because it is a read.

vision_trace: "The edit surface driven by one hand-written map of what is editable: ... a reference field links rows, never text; provenance is visible at the field."

## Acceptance criteria
1. A `kind: reference` field renders an entity picker, never a text input; a structural test asserts no code path submits a reference field's value as a string.
2. The picker's submission payload carries the chosen entity's id AND its confirmed match, asserted against the recording stub; the payload contains no free text for that field.
3. The picker offers only rows that exist in the referenced table and has no create affordance: zero controls in the picker create, insert, or accept an unmatched value.
4. With `settle_review_item` absent, a reference field renders read-only with the reason named; no picker control appears; the page answers 200 and throws nothing.
5. On an `idols` record the group renders as a LINK whose href resolves to that group's record page (200 authed), and from a `groups` record its idols are reachable in one click. Both use the single `recordHref` spelling — no second href helper is introduced.
6. `idols.group_id` (and every other key) is NOT in `EDIT_CONFIG`'s editable columns for any table: the existing config guard still passes, and a forged PATCH naming `group_id` is refused server-side with 403.
7. No listing page, no search input, and no second Browse view is added: the sidebar still holds exactly six links, `src` contains no search control over `groups` or `idols`, and Browse still renders exactly one curated view.
8. `npm run lint`, `tsc --noEmit` and `npm test` green; the record page's live suite green.

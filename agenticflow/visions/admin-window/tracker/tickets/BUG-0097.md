# The entity picker keeps every option clickable while a choice is saving: a second click sends a second override for the same field

## Description
Found by QA attacking TASK-0055 on the landed tree run/admin-window @ d3d217e.

**Expected** — the rule this campaign already paid for once, in the other widget of the same surface: `a status is only ever replaced or retired by the edit that produced it, or by a later one`, and `the button the operator can click again is disabled={status.kind === "saving"}` (src/components/EditableCell.tsx:105-148 and :670, campaign BUG-0069; the measurement that bought it is quoted in tests/offline/ui/editable-cell.test.ts:296-315 — a second edit committed 226ms after the first lost its in-flight statement, and a 403 erased itself). The picker is the same seam with a different widget: its OPTION buttons are the controls that start a write, so they are what has to go busy while one is in flight.

**Found** — src/components/records/entity-picker.tsx:336-362 (`choose`) has no in-flight guard and no edit epoch, and src/components/records/entity-picker.tsx:176-187 (`PickerOptions`) renders every option as an always-enabled button. The widget disables the control that CANNOT write (the `Choose venues` toggle, entity-picker.tsx:377-388, `disabled={status.kind === "saving"}`) and leaves live every control that CAN. Measured: rendering `PickerPanel` with `status={{kind:"saving"}}` and a 3-row window draws 3 enabled `li button` options (0 carry `disabled`) — same count as at rest.

**Repro** (needs `settle_review_item` installed; with it absent no picker renders at all, which is why this is latent rather than live today):
1. Open /records/events/<id> on a database where `verdicts` exists, so the override path is open.
2. Click `Choose venues` on the venue_id line; the panel opens over the window read.
3. Click venue A. The panel stays open, `saving…` appears, PATCH #1 is in flight.
4. Before it answers, click venue B. `choose` runs again with no guard: PATCH #2 goes out.
Result: two `override` decisions are recorded for events.venue for one intent, and because the status/chosen state carries no epoch, whichever response returns LAST wins the display — if A answers after B, the line shows venue A while the last decision written was B. Expected: the second click is not offered at all while the first write is in flight, and no answer to a superseded write may overwrite a newer statement.

**Pin** — tests/offline/records/entity-picker.test.ts, describe `a choice while a choice is still saving`, a strict `it.fails` marker on `offers no option that would start a second write while one is saving`. Its two neighbours (every option live at `idle`; live again at `saved` and `failed`) are plain `it` and green, so the pin is neither vacuous nor a demand for a permanently dead list. Watched red before filing: `expected 3 to be +0`. Flip it back to `it(...)` with the fix.

**Not asserted here**: any word the panel says. Only which controls it still offers.

# Phone (390px): the fixed 192px sidebar takes half the viewport and the content column collapses

## Description
Found on the M1 endgame designer walk (2026-09-03), responsiveness phase — Playwright device emulation, iPhone 13 (390x844), walk instance :8771 against staging.

**LOOK_AND_FEEL.md is silent on viewport.** Its frame rule says "a 192px fixed left sidebar" and nothing about small screens, and desktop is this milestone's stated target — so this is my taste filling a gap, licensed by VISION's "Ben, the ecosystem's operator, **at breakfast**". Filed at P3 deliberately: if the answer is "the window is a desktop tool, and the doc should say so", that is a good answer and I will write it into LOOK_AND_FEEL.md instead. What is not good is the current state being nobody's decision.

Measured at 390px:

- The sidebar keeps its full 192px — **49% of the viewport** — and the content column gets ~198px minus 16px padding on each side.
- On the Dashboard that leaves the attention cards one word per line: "nothing / open / — / no / question / is / waiting / on / a / verdict" reads down nine lines.
- The cycles table is clipped inside its own scroll region after two columns; `STARTED` and `OUTCOME` are all that fit.
- The page itself does not scroll horizontally (`documentElement.scrollWidth` = 390 = `innerWidth` on Dashboard, Queues and Browse), so the containment is correct — it is only the split that is wrong.

Evidence: `agenticflow/tracker/evidence/designer-walk-m1/dashboard-phone.png`, `queues-phone.png`, `browse-phone.png`.

The desktop rendering is unaffected by anything I would ask for here; at 1440 the frame is exactly right.

## Acceptance criteria
Resolved by the doc, not by a build. Ben ruled 2026-09-02 that the window is
desktop-only for now, a phone layout is a later nice-to-have, and both themes
stay required. The either/or in the original criteria is settled on the second
branch: nobody builds a breakpoint in M1; LOOK_AND_FEEL.md states the range.

1. LOOK_AND_FEEL.md's Frame rule carries a `Viewport:` bullet stating the
   supported width range as a number (1280px and up, design target 1440x900),
   that the frame does not respond (no breakpoint, no collapsed or stacked
   sidebar, no phone layout), and that below that floor the app is unsupported
   in M1 — with the reason (desktop tool for "Ben, the ecosystem's operator,
   at breakfast") and Ben's ruling named.
2. The 390px measurements survive in the bullet as recorded behaviour, so a
   future endgame walker with no memory of today does not refile this bug.
3. A phone layout is named as a later milestone's concern, and the bullet says
   its bar is written into LOOK_AND_FEEL.md before it is built.
4. Width is the only axis narrowed: bar 12 (every page renders in light and
   dark) and the containment rule (the page never scrolls horizontally, only a
   table inside its own border) are unchanged and still apply at every
   supported width.
5. No `src/` or `tests/` file changes — so the 1440x900 rendering is identical
   to today's by construction: same 192px sidebar, same 16px content padding,
   same table layout.

Human-check: reading only the Frame rule, a builder who has never seen this
ticket can say what width the app is built for and what to do about phones.
(human-checkable)

# A walker's session cookie: mint it outside src/, prove the app accepts it, write the walk recipe down

## Description
Module: `tests/walk/` (new — walk tooling, outside `src/`), `tests/offline/walk/`, `tests/http/`, and `agenticflow/docs/vision/STACK.md` §5. Authority: Ben's two rulings of 2026-09-03 (recorded in `agenticflow/docs/DECISIONS.md`, same date), ARCHITECTURE §10 (tests own their own credential seams; one owner per structural guard), STACK §3/§5.

## Why this exists

The M1 endgame — designer walk, user-sims, verifier — drives the real app in a headless browser (the kit's Playwright in `agenticflow/.venv-tools`). Two things stood between those walkers and a first screen, and Ben settled both today.

**Ruling 1 — the walk instance's database credentials come from its own process environment, never from `.env`.** `.env` no longer carries `SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY`; production values live only in Railway's production environment. A walk instance is launched with the two names mapped from the staging names on the launching shell's command line:

```
SUPABASE_URL="$STAGING_SUPABASE_URL" SUPABASE_SERVICE_ROLE_KEY="$STAGING_SUPABASE_SERVICE_ROLE_KEY" \
  AUTH_URL="http://localhost:8771" npm run dev -- --port 8771
```

Nothing in code falls back to another name, nothing prints a value, `.env` is not edited by anyone (Ben's own uncommitted `.env.example` edit is his — leave it alone). **This ticket writes no product code and no `.env`; it writes the recipe down.**

**Ruling 2 — a walker gets past the Google-only NextAuth gate with a minted session cookie**, not a new provider, not a dev flag, not a second sign-in path. next-auth v5 already ships the JWT `encode` its own sign-in uses; a helper *outside* `src/` mints a session token for a fixed, clearly-labelled walker identity and prints it as a cookie descriptor a Playwright script can add to its browser context. Ben accepts the resulting blind spot: **the sign-in flow itself is never walked.**

## Where the helper lives, and why that is legal

`tests/walk/session-cookie.mts`, in the test tree — never under `src/`.

The layering guard (`tests/offline/db/layering.test.ts`) scans `src/` alone and forbids a credential read outside `src/lib/db/client.ts`; a test-tree module reading `AUTH_SECRET` is the exact analogue of `tests/live/setup.ts` reading `STAGING_SUPABASE_URL` / `STAGING_SUPABASE_SERVICE_ROLE_KEY` — the one place that name is read, in the test tree, refusing rather than falling back. `src/` gains nothing: it holds zero mentions of `AUTH_SECRET` today and must still hold zero when this lands (a check pins it).

`.mts`, not `.ts`, measured 2026-09-03 on the Node 26.7.0 this repo runs:

- `node tests/walk/session-cookie.mts` runs directly — Node ≥23.6 strips types with no flag, `.mts` is unambiguously ESM, top-level `await` and `import { encode } from "next-auth/jwt"` both work. The same file named `.ts` also runs but prints a `MODULE_TYPELESS_PACKAGE_JSON` warning and re-parses, because this package has no `"type": "module"` — noise on the walker's stderr for nothing.
- A `.ts` test imports it as `"../walk/session-cookie.mjs"` (the `.mjs`→`.mts` spelling): `tsc --noEmit` accepts that and vitest resolves it (both measured). `"./session-cookie.mts"` needs `allowImportingTsExtensions` and `"./session-cookie"` does not resolve — do not use either.
- `tsconfig.json` `include` already covers `**/*.mts`, so the file is type-checked by `npm run typecheck` without touching tsconfig. **No config file changes and no new dependency**: `next-auth` and `dotenv` are already here.

## Interface contract

```ts
// tests/walk/session-cookie.mts

/** The cookie Auth.js sets on plain-http localhost. */
export const SESSION_COOKIE_NAME = "authjs.session-token";

/** The walker. Deliberately not a real person's address. */
export const WALKER_IDENTITY: { sub: string; email: string; name: string };
//   { sub: "endgame-walker", email: "walker@admin-window.local", name: "Endgame Walker" }

export interface CookieDescriptor {
  name: string;      // SESSION_COOKIE_NAME
  value: string;     // the encoded session JWT
  domain: string;    // default "localhost"
  path: string;      // "/"
  httpOnly: boolean; // true
  sameSite: "Lax";   // Playwright's spelling
}

export function mintSessionCookie(params: {
  secret: string;                          // the caller supplies it; this function never reads env
  claims?: Record<string, unknown>;        // default WALKER_IDENTITY
  domain?: string;                         // default "localhost"
  maxAgeSeconds?: number;                  // default 7200
  salt?: string;                           // default SESSION_COOKIE_NAME
}): Promise<CookieDescriptor>;
```

`SESSION_COOKIE_NAME` is measured, not guessed: `@auth/core`'s `defaultCookies()` prefixes `__Secure-` only when the resolved URL is `https:` (`node_modules/next-auth/node_modules/@auth/core/lib/utils/cookie.js:44-49`), and next-auth resolves that URL from `AUTH_URL` (`node_modules/next-auth/lib/env.js`), which is `http://…` for every walk. The cookie name is also the **salt** Auth.js binds into the encryption key (`@auth/core/lib/actions/session.js:23`) — mint it with any other salt and the app refuses the cookie.

### The CLI

```
node tests/walk/session-cookie.mts [--domain <host>] [--max-age <seconds>] [--email <address>]
```

- **stdout carries exactly one line**: the `CookieDescriptor` as JSON. Nothing else, ever — a walker parses it. Diagnostics, warnings and refusals go to stderr.
- Secret resolution, in this order and no other: `process.env.AUTH_SECRET`; else `AUTH_SECRET` from the repo-root `.env` loaded with `dotenv` (`quiet`, never overriding a name already present). That is precisely the precedence `next dev` itself uses via `@next/env`, which is what makes the minted cookie and the running walk instance agree on the secret, and it is the same pattern `tests/live/setup.ts` already uses. It is **not** a fallback to some other name: there is exactly one name.
- A value that is unset, empty, or whitespace-only is **unset**. The CLI then exits non-zero, names `AUTH_SECRET` on stderr, and mints nothing. No default, no generated secret, no "assume dev".
- **The only secret-derived value this program may emit is the session token itself.** `AUTH_SECRET`'s value must never appear on stdout or stderr, on any path, including the refusal path and any error message.
- `--email` exists for one reason (below) and defaults to the walker identity. It is never used to spell a real person's address into a script or a doc.

## The caveat a walker must know: reads are walkable, the PATCH route is not

The middleware gate asks only `!!session?.user` (`src/lib/auth.ts`, `authorized`), so a minted cookie opens **every page**. The edit route is different: `src/app/api/admin/records/[table]/[id]/route.ts` calls `requireAdmin()` (`src/lib/admin.ts`), which looks the session email up in `admin_allowed_emails` **on every request** and 403s on a miss. Staging's allowlist holds exactly one row (`kb.labs.ths@gmail.com`, added by Ben today), so a walker minted as `walker@admin-window.local` will get **403 on save** from `EditableCell` — correct behaviour, and it would read as a broken save to anyone who did not know.

So: the recipe says this in words, and the sign-in-flow blind spot with it. Whether a walk of the edit surface's save path gets an allowlisted identity is **Ben's to decide** — either a labelled row in staging's `admin_allowed_emails`, or `--email` with an address that allowlist already holds. **No agent adds that row and no agent picks an address.**

## What to build

1. `tests/walk/session-cookie.mts` — the module + CLI above. When it is imported (not run as main) it must print nothing and exit nothing; detect main by comparing `process.argv[1]` to `fileURLToPath(import.meta.url)`.
2. `tests/offline/walk/session-cookie.test.ts` — the secret guard, offline, no network. It spawns the CLI as a child process and asserts:
   - with `AUTH_SECRET` set to a recognisable sentinel, stdout is exactly one line of JSON carrying the six descriptor keys, the name is `authjs.session-token`, and **the sentinel appears nowhere in stdout or stderr**;
   - with `AUTH_SECRET` present but **empty** in the child environment, it exits non-zero, stderr names `AUTH_SECRET`, and stdout is empty. Set the name to the empty string rather than deleting it: `dotenv` never overrides a name already present, so an empty value is how the refusal is provoked deterministically even on a machine whose `.env` carries a real secret — the same trick `tests/offline/live-guard.test.ts` uses for the staging names;
   - `mintSessionCookie` round-trips: `decode` from `next-auth/jwt` with the same secret and salt returns the walker's claims; with a different secret it does not.
3. `tests/http/walk-cookie.http.test.ts` — the end-to-end proof, against the real server the http harness starts on 8772 with its placeholder `AUTH_SECRET` (`tests/http/server-harness.ts` exports it). Run the **CLI itself** as a child process with `AUTH_SECRET` set to that placeholder, parse its stdout, and assert:
   - the descriptor's cookie opens gated **pages** — `GET /` and `GET /queues` answer **200**, not a redirect;
   - a descriptor minted by the same CLI under a **different** secret still redirects (3xx to `/login`) on those same pages.
   Assert on pages, not on the API route: with no database behind it, `requireAdmin()` cannot confirm the allowlist and the PATCH route answers 4xx by design (`tests/http/edit.http.test.ts` owns that).
4. **One copy of the mint.** `tests/http/auth.http.test.ts` and `tests/http/edit.http.test.ts` each hand-roll `encode(...)` today; both must call `mintSessionCookie` instead — including the forged-cookie family, which is the same call with a different secret, salt or `maxAge`. After this ticket exactly one file in `tests/` imports `next-auth/jwt`, and a check pins that. Change nothing else in those two files: their assertions, route inventory and forged-cookie set are other guards' business.
5. `agenticflow/docs/vision/STACK.md` §5 — a **walk instance** subsection carrying, verbatim and runnable: the launch line from ruling 1 (including `AUTH_URL="http://localhost:8771"`, so next-auth resolves the walk instance's own origin instead of rewriting redirects to `:3000` — measured in `node_modules/next-auth/lib/env.js`), the mint line, a Python `context.add_cookies([...])` snippet, and the two caveats (sign-in is not walked; the PATCH route 403s for the walker identity). Update §5's existing bullet that says a walk "needs `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` in `.env`" — that is now wrong twice over (the names are gone from `.env`, and the ASK ticket it points at is closed).

## Acceptance criteria
1. **The helper sits outside `src/`.** `tests/walk/session-cookie.mts` exists; `src/` contains no mention of `AUTH_SECRET` and gains no file, no provider, no dev flag, no route. The layering guard (`tests/offline/db/layering.test.ts`) is untouched and still green.
2. **The CLI prints one JSON line and nothing else.** `node tests/walk/session-cookie.mts` with `AUTH_SECRET` set emits a single line of JSON on stdout carrying `name`, `value`, `domain`, `path`, `httpOnly`, `sameSite`, with `name` = `authjs.session-token`, `path` = `/`, `httpOnly` = `true`, `sameSite` = `Lax`, `domain` = `localhost` unless `--domain` says otherwise. Diagnostics go to stderr.
3. **The only secret-derived value ever emitted is the session token.** With `AUTH_SECRET` set to a sentinel, that sentinel appears nowhere in stdout or stderr — proven by the offline test, on the success path and on every failure path.
4. **An unset secret is a refusal, never a fallback.** With `AUTH_SECRET` empty (or absent, with no `.env` to supply it) the CLI exits non-zero, names `AUTH_SECRET` on stderr, prints nothing on stdout, and mints no cookie. No default value, no generated secret.
5. **The app's own `auth()` accepts the minted cookie.** In `tests/http/walk-cookie.http.test.ts`, against the real server the harness starts on 8772 with its placeholder `AUTH_SECRET`: the cookie the CLI printed makes `GET /` and `GET /queues` answer **200**, and a cookie the same CLI minted under a different secret still redirects (3xx) to `/login` on both.
6. **One mint, one copy.** Exactly one file under `tests/` imports `next-auth/jwt`, and it is `tests/walk/session-cookie.mts`; `tests/http/auth.http.test.ts` and `tests/http/edit.http.test.ts` mint through `mintSessionCookie` and keep every assertion they have today. `npm run test:http` is green.
7. **The walk recipe is written down where the walkers look.** `agenticflow/docs/vision/STACK.md` §5 carries a runnable walk-instance recipe: the launch line mapping `STAGING_SUPABASE_URL` / `STAGING_SUPABASE_SERVICE_ROLE_KEY` onto `SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY` plus `AUTH_URL="http://localhost:8771"` on port 8771, the `node tests/walk/session-cookie.mts` mint line, a Playwright `context.add_cookies([...])` snippet, and both caveats in words — the sign-in flow is not walked, and the PATCH route answers 403 for the walker identity because `requireAdmin()` consults `admin_allowed_emails` per request. §5's stale bullet about a walk needing the two names in `.env` is corrected.
8. **Nothing else moves.** No new dependency (dependency count unchanged at 17), no edit to `package.json`, `tsconfig.json`, `vitest.config.mts`, `eslint.config.mjs`, `.env`, `.env.example`, or any file under `src/`. `./node_modules/.bin/tsc --noEmit` and `npm run lint` are clean.

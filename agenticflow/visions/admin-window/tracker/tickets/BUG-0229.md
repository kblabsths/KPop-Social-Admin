# A count that is a whole number but not a number of ROWS (negative, or beyond exact representation) is published as a figure

## Description
EXPECTED (the bar BUG-0228 folded its count guard in under, stated positively): a count is a number of ROWS — a non-negative integer the machine can represent exactly — or it did not arrive, and an answer that did not arrive refuses through the one rule (unreadableAnswer) naming the object. No body and no header a host can put on the wire may make a surface publish a figure that is not a count of rows.

FOUND on the landed BUG-0228 tree (run/admin-window @ fa41daaf), measured 2026-09-15 by QA over real HTTP against a production build with SUPABASE_URL pointed at a loopback host:

  host answers 200, body [], header 'content-range: */-5'
    /claims -> 200, the Total counts table publishes -5 in EVERY bucket row
               ('standing_disagreement -5', 'awaiting_link -5', 'awaiting_row -5'),
               beside state cards 'empty' and no refusal at all.
  host answers 200, body [], header 'content-range: */99999999999999999999'
    /claims -> 200, the same table publishes '100,000,000,000,000,000,000'.

MECHANISM: supabase-js reaches the count with parseInt over whatever follows the slash in Content-Range, so a host answering a header it made up hands back count: -5 (or 1e20) beside error: null. The guard is Number.isInteger (src/lib/db/result.ts:1153-1154), which is TRUE for both — a negative is a whole number, and 1e20 is an integer-valued double — so readCount (result.ts:1434) returns {kind:'ok', data:-5} and the figure is published. readComplete's truncation arm does not catch it either: -5 > rows.length is false, so the rows pass as a complete set under a negative total.

NOT A REGRESSION: the pre-BUG-0228 predicate (count === null || count === undefined, 7eac5b56^:src/lib/db/result.ts:1310) let the same values through. BUG-0228 narrowed the predicate to close NaN/1.5/Infinity and did close them (verified); this is the same predicate's remaining half, and it is ONE derivation, not an enumeration of header spellings: isInteger -> 'a non-negative integer that is exactly representable'.

NOT THE NAMED RESIDUAL: BUG-0228's handoff names a different open question (rows carrying every declared column with WRONG-TYPED VALUES, which still 500s / and four other routes — QA reproduced it and agrees it is the architect's boundary question, LESSONS 13). This one needs no new predicate and no route boundary: it is one line inside a guard the ticket already owns.

REPRO (exact, offline, no database, no server):
  readCount(T.pendingClaims, (db) => countRead(db, T.pendingClaims),
            stubClient({ [T.pendingClaims]: { data: [], count: -5 } }).asSupabaseClient())
  Expected: {kind:'error'} (unreadableAnswer naming pending_claims). Actual: {kind:'ok', data:-5}.

PIN, watched RED on this tree 2026-09-15 before it was marked: tests/offline/db/result.test.ts, 'refuses a count that is a whole number but not a number of ROWS' — currently marked it.fails (AssertionError: -1: expected 'ok' to be 'error'). THE FIX FLIPS THAT MARKER back to a plain 'it' (check 2 refuses the close while it stands). The test carries its own controls — 0, 1 and Number.MAX_SAFE_INTEGER must still read back as ok — so the guard cannot be tightened into eating a real count.

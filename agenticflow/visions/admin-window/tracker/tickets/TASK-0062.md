# readRowsByIds issues its chunks concurrently, bounded — and refuses exactly as it does today

## Description
**Module:** `src/lib/db/result.ts` — the second leg of a two-step join (ARCHITECTURE §4.2). This is a SHARED surface: `lib/db/claims.ts`, `gauges.ts`, `sources.ts`, `verdict.ts` and `review-item.ts` all call it, so §13.2's exception applies and the offline checks below are wider than one file.

**What changes, and nothing else.** `readRowsByIds`' `for (const chunkIds of chunk(ids))` loop issues its chunks one after another. It becomes a BOUNDED fan-out. No signature change, no caller change, no query change, and NO rendered text changes on `/claims`, `/queues` or the review item (SPEC F16: only the clock).

**Interface contract** (one new export; the function's signature is untouched):

```ts
// src/lib/db/result.ts
/** How many chunk requests may be in flight at once. */
export const CHUNK_FANOUT = 4;

export async function readRowsByIds<Row>(
  missing: string,
  ids: readonly string[],
  run: (db: SupabaseClient, chunkIds: string[]) => PromiseLike<DbResponse<Row[]>>,
  db?: SupabaseClient,
): Promise<DbResult<Row[]>>;
```

**The implementation is ruled, not left open: BATCHES.** `chunk(ids)` as today, then `Promise.all` over at most `CHUNK_FANOUT` chunks per batch, batches in index order, stopping at the first batch that holds a non-`ok`. A promise-pool would also be bounded, but the batch form is what makes the refusal pins below deterministic instead of timing-dependent — and a pin that only usually holds is not a pin.

**The six properties, each on its own fixture (LESSONS 8: one input that must flag and one that must not).** The first three exist today and must survive; the last three are what concurrency can break without any stub noticing:

1. **Zero ids, zero round trips.** `ids.length === 0` returns `{ kind: "ok", data: [] }` and `run` is called ZERO times.
2. **A chunk that errors yields the first non-`ok` result UNCHANGED** — never a half-filled `ok`, and the rows already collected are discarded.
3. **A missing table reaches the PAGE as `not_provisioned` naming that table** (the absence suite, not just the unit).
4. **Order is chunk-index order, never completion order.** Pin it with a stub that settles chunk 2 before chunk 0: the concatenated rows come back in the id set's own order.
5. **The refusal is the LOWEST-INDEX non-`ok`, never whichever rejected first.** Pin it with a stub whose later chunk fails before an earlier one fails.
6. **The fan-out is bounded and is genuinely concurrent.** On an id set spanning at least `CHUNK_FANOUT + 2` chunks, a stub recording issue and settle order shows observed concurrency never above `CHUNK_FANOUT` and at least two requests overlapping (a sequential implementation must fail this test — write it so it does, and say so in the test name). With chunk 0 refusing, the number of requests issued is strictly less than the chunk count: no batch is started after a refusal is known.

**The measurement (M3 EC9's third bullet), in the same session.** Warm server time for `/claims` over HTTP against a PRODUCTION build on port 8771 — the launch block in `agenticflow/docs/STACK.md` §5 verbatim, the env prefix on BOTH commands — recorded as a before/after pair with the exact commands in `agenticflow/tracker/evidence/TASK-0062/warm-times.md`. `/queues` and one review item measured in the same pass; neither regresses. The bar is `/claims` at or under 1.4 s. If the change lands and the bar is missed, record the number and say so — never move the bar, never fall back to the sequential loop quietly.

**Refusal-shaped brief (LESSONS 10, common violations row 19):** count the round trips this function issues per page and put the number in the receipt. The one way this change can be wrong is a refusal that became a partial answer.

# claims.live stops being sized by staging: bounded oracles, a window with headroom, and a walk small enough to hold still

## Description
**Modules:** `tests/live/claims.live.test.ts` and `tests/live/parity.ts` (message-only there, as TASK-0075 left it). **Test tier only — no product code, no other live file.**

## Why now, before it bites

QA's TASK-0075 residual, measured on staging 2026-09-10/11: `pending_claims` holds **877** rows against a **1,000**-row PostgREST ceiling that no `.limit()` raises, and the builder watched the view touch **887** in one burst. Three helpers in this file read the WHOLE view and tally it in TypeScript (`claimsFromDatabase`, `bucketCensus`, `sourceCensus`, each `.limit(VIEW_READ_CAP)` = 5000, guarded by `refuseTruncated` at `min(5000, 1000)`). The day the view crosses 1,000 **every case in this file refuses permanently** — and this file is the stored check of TASK-0066, TASK-0067, TASK-0070, BUG-0167 and everything downstream, so the first thing it will teach a bounced builder is that the product is broken. ~123 rows of headroom is not a margin; it is a countdown.

The guard is right and stays. What is wrong is that the ORACLE's reads are sized by the VIEW instead of by what they compare.

## The ruling (architect, 2026-09-11 — DECISIONS.md of the same date)

**1. No read in this file asks the database for more rows than the assertion compares.** A "whole" figure comes from the database's own exact count, and a row set comes bounded by the assertion.

- **The count rides the SAME request as the rows**: `select(…, { count: "exact" })` returns the true total in the response's own range header, and a count is not subject to the row ceiling. That keeps TASK-0075's one-round-trip shape *and* removes the ceiling in one move — no second `countRows` beside a read, which is the race TASK-0075 killed.
- **`claimsFromDatabase` reads the OLDEST rows the assertion needs, not the view.** The page draws `CLAIM_WINDOW` rows; the oracle needs enough of the page's own order to prove those are exactly the longest-waiting ones, plus a margin. Bound it by that number and take `whole` from the same request's exact count. `refuseTruncated` then guards a bound that means something ("this slice was cut, so it cannot say which claims are oldest") instead of guarding the size of staging.
- **The per-bucket / per-source censuses stop reading rows at all.** Ruled in order, and **measured, never assumed**: (a) first try PostgREST's aggregate form (one request, no ceiling, e.g. a grouped `count()` over the view) and record in the evidence note whether this project enables it; (b) if it is refused, take the per-bucket `head: true, count: "exact"` reads **concurrently in ONE `Promise.all`** — N requests, ONE wait, each immune to the ceiling — and record the still-window duration before and after. **Banned either way:** reading the view's rows to tally them (the shape that dies at 1,000), and sequential counts (the shape TASK-0075 killed, ~4.3 s per attempt).
- **What TASK-0075's "ONE ROUND TRIP" protects is the DURATION of the still window, not the number of requests.** Amended here, in one line: concurrent bounded counts issued in one `Promise.all` are one wait and are permitted where a single read would otherwise have to carry the whole view. Sequential reads inside a held shape stay banned.

**2. The identity proof gets a window with headroom, chosen from a measurement.** `the windowed claims read and the id-list join select the same claims` runs over 90 days against `GAUGE_CAP = 1000` and is at 877. The proof is about the two SHAPES selecting the same claims over the same edges — it holds over any window — so narrow the TEST's day window until the measured set sits at or under **half** the cap, keep both legs on the same `snapshotAsOf` edges (untouched from TASK-0075), and keep it non-vacuous with room. Record the measured set size at the windows you tried (e.g. 7 / 14 / 30 / 90 days) in the evidence note. Add the instruction to the refusal: at or above **80% of the cap** the proof throws naming the day window, the number it got and what to do about it, so the next reader gets an instruction instead of a truncated comparison. State in the comment that 90 days is the GAUGE's bound and this is the TEST's, chosen for headroom.

**3. The paged walk does not need a different device — it needs a smaller shape.** QA and the builder are right that `whileStill` decays with the DURATION of the make, and this case's make is a render + a ~14-request walk + the enumeration, 7–20 s measured, against a ~1 s read; `attempts: 5` buys five long windows and staging churns in bursts (877 → 887 → 879 inside one make). The lever nobody pulled is the SIZE of the walked set:

- **Walk a NARROWING, chosen at runtime, not the whole view.** Take the census this ticket already makes cheap, pick the narrowing with the SMALLEST matching count that is still greater than one window (so the walk is non-vacuous — it must reach past the first window's last row), render `/claims?<that facet>`, walk with the same facet, and enumerate the oracle with the same facet. A 2–3 page walk is a ~2–3 s make, which is the shape `whileStill` was measured to work on everywhere else in the file.
- **No hard-coded source id**: the facet is picked from the census at run time, so the case stays valid as staging grows and as sources come and go. Print which narrowing it chose and its size in the failure message.
- **The unnarrowed page keeps a cheap, still-holdable assertion**: the first screen plus ONE press (two requests), graded the same way. What is given up is the *unnarrowed* completeness claim, which is not a property the page has mid-drain anyway (offset paging over a draining view legitimately skips ids); what is kept is the completeness claim itself, on a set small enough to hold still.
- If the narrowed make still cannot hold still — measure it — the ticket comes back to the architect. **Do not invent a skip, a tolerance or a retry** (DECISIONS 2026-09-10 rule 3 is unchanged: no `toBeCloseTo`, no `±`, no `--retry`, no `it.skip`/`it.todo`, no widened assertion anywhere under `tests/live`).
- **Exhaustion and a defect stop sharing one voice.** QA's residual: "an honest refusal and a product defect share one channel (exit 1)". They still share the exit code — that is the runner's — but not the message: `whileStill`'s exhaustion error opens with a fixed marker (e.g. `STAGING MOVED:`) before the what-moved report it already carries, so whoever meets a red in a downstream lane's stored check can tell in one glance that the database would not hold still. `parity.ts` stays additive-plus-message-only; the pin in `tests/offline/live-guard.test.ts` is extended, not replaced.

**4. The graded exception is ACCEPTED, and recorded so it is not copied.** `names the source_id chips the same way` (and `registryNames()` in the case above it) compares page labels against the sources registry OUTSIDE `whileStill`. QA measured the registry at 3 rows, byte-identical over 20 s, and both sides are keyed on ids the page itself rendered; a new source arrives with a deploy, not with a scraper cycle, and would fail loudly and reproducibly rather than pass quietly. Accepted. Conditions: the case carries a comment stating exactly that reasoning (why it cannot race, and that this is an architect-accepted exception, not a pattern), and it refuses if the registry read comes back larger than a stated small bound — an exception that silently grew is the one nobody re-checks.

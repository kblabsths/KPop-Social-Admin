# ASK BEN: what is installed on staging, and may a live test write fixture rows into resolver-owned tables?

## Description
**Contract silence.** ARCHITECTURE marker `OPEN-FIXTURES`. Folds SPEC named gaps 2 and 5 — they share one answer.

Acceptance tests 2, 3, 5, 10 and 11 assert rendered numbers against real staging rows. Two things could make that vacuous:

1. **The tables may not be there.** Schema truth is the scraper repo's `supabase/migrations/`, and the resolver campaign is still building it — a campaign is running in that repo right now. Every one of the resolver migrations (`20260901000001` `resolution_runs`, `...02` `review_items`, `...03` the rejection stamps, `...04` the `pending_claims` view, `...05` the canonical write path) says in its own header that **'the staging apply is separate and human-gated.'** So: **which of these are actually applied to the staging project today?**
2. **The tables may be empty.** If `review_items` exists with zero rows, 'renders real staging data' is satisfied trivially and every parity test compares 0 to 0.

The question that decides the harness: **may a live test write its own fixture rows into resolver-owned tables** (`observations`, `review_items`, `pending_claims`'s inputs) and sweep them? Acceptance test 13 sanctions a live suite that writes and sweeps; spec section 8 forbids an *app* write path to those domains. Those are not in conflict, but the difference matters and is not written down.

**Recommend:** the app keeps no write path to resolver-owned domains (spec section 8, unchanged), and the **live test suite** may insert a small, tagged fixture population into `observations` / `review_items` **through the service role, only when a table is present and only under the live marker**, sweeping every row in a `finally` (test 13). Tag every fixture row so the residue sweep can find it — a recognisable `external_ref` prefix such as `admincampaign-fixture-`. Without that permission, M1's parity tests can only assert 'the rendered number equals the number the database has', which is still a real bar but proves nothing about rendering a populated queue.

Second half of the answer: **if a column this campaign's SPEC names is missing on staging, that is reported, never invented.** Everything SPEC names was verified present in the scraper repo's migrations on 2026-09-01 — but authored is not applied. Read-only introspection of staging was not possible from here: the `STAGING_SUPABASE_*` names do not exist in `.env` yet, so this ticket's facts come from migrations, not from the live database.

## Acceptance criteria
(human-checkable) Ben states which resolver migrations are applied to staging today, whether the tables hold rows, and whether the live suite may write and sweep tagged fixture rows.

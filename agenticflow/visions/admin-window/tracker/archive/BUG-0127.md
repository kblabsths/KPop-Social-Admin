# Claims' dropped-parameter line spells a hole when the URL's key is blank: 'The URL carries , which this page did not apply'

## Description
Found while attacking admin-window/BUG-0123's new dropped-parameter line, on the LANDED tree (run/admin-window @ c55f764), driven over HTTP against a production build (own port 8793, staging, 2026-09-09).

**Expected** — BUG-0123 criterion 3: a parameter the page did not apply gets "one line beside the filter bar [that] says so in the app's voice, **naming the parameter verbatim in mono** and stating that the rows below are not narrowed by it."

**Found** — a URL whose KEY is empty or blank produces the line with nothing in the mono slot, so the sentence reads with a hole in it:

    $ curl -s -b <session> 'http://localhost:8793/claims?=x'
    200
    <p data-dropped-params="1" class="type-body text-ink-secondary">The URL carries <span data-dropped-param="" class="type-data text-ink"></span>, which this page did not apply: nothing below is narrowed by it.</p>

Visible text: `The URL carries , which this page did not apply: nothing below is narrowed by it.`

Same for a whitespace-only key — `/claims?%20%20=1` renders `data-dropped-param="  "`, which collapses to nothing on screen and reads identically. Both keys really do reach the page: Next hands `?=x` through as `{"": "x"}` and `?%20%20=1` as `{"  ": "1"}` (measured over HTTP, above; reproduced offline through `ClaimsPage`).

**Where** — `droppedParams()` at `src/lib/claims/filters.ts:172-189` skips a parameter whose VALUE is empty (`if (asked === undefined || asked === "") continue;`) but never one whose NAME is empty or blank, so the key goes into `named` and is rendered verbatim by `DroppedParamsLine` at `src/app/claims/page.tsx:382-410`.

The counts, the rows, the chips and the window line are all correct in this state (`877 claims in all`, held=877, no filter asserted) — this is only the sentence naming what it dropped, which is the sentence BUG-0123 exists to make honest. An operator who typed a malformed key is told something was ignored and cannot see what.

**Scale** — P3: the rows and every number stay true, and reaching it takes a hand-typed key that is empty. It is filed rather than fixed in place because the line's own contract is "name it verbatim", and a blank name names nothing.

**Not a bug (checked, for the next reader):** `?record_id=` (empty value) correctly says nothing; `?tab=bogus` correctly says nothing and lands on a real tab; `?<script>alert(1)</script>=1` is escaped by React and renders as text; `in_window` reaches only Next's RSC flight payload (`self.__next_f.push`, which echoes the request URL on `/queues` and `/cycles` too) and never the visible text.

## Acceptance criteria
1. `/claims?=x` and `/claims?%20%20=1` no longer render a sentence with an unfilled name. Either arm is a fix, the builder picks: spell a name an operator can read back, or route a nameless key through the line's existing `withheld` path so it is COUNTED and not claimed to be named ("1 parameter this page may not name").
2. Whatever arm is chosen, the rows, counts, chip hrefs, window line and bucket caption for those URLs are unchanged from today's (877 in all, no filter asserted, no dropped-name span with empty text).
3. Every case BUG-0123 already pinned still holds: `record_id` named verbatim, `bucket` named without echoing its value, `tab` never named, an empty VALUE saying nothing, two dropped names on one line.
4. The strict pin in `tests/offline/claims/page.test.ts` ("spells a name, or none, but never a hole where a name goes") flips from `it.fails` to `it`.
5. `npm run lint` and `tsc --noEmit` clean; the offline suite green.

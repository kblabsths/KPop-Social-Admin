# The http harness must ENFORCE 'no database', not assert it: Next reloads .env over the strip

## Description
Module: `tests/http/server-harness.ts` plus one new offline test. Authority: ARCHITECTURE.md section 10 ("tests/http ... needs no database"); the harness's own docstring: "Every Supabase name is stripped: these routes must answer without a database, and **dropping the names is what proves it rather than asserts it**." Raised by QA on TASK-0001 and confirmed on TASK-0005.

**The defect, measured 2026-09-02 on this tree.** `serverEnv()` deletes every `*SUPABASE*` name from the child env — and then `next start` calls `@next/env`'s `loadEnvConfig` on the repo root and puts them straight back from `.env`. Reproduced directly, no server needed:

```
$ node -e 'const {loadEnvConfig}=require("@next/env");
  for (const k of Object.keys(process.env)) if (k.includes("SUPABASE")) delete process.env[k];
  console.log("before:", Object.keys(process.env).filter(k=>k.includes("SUPABASE")));
  loadEnvConfig(process.cwd(), false);
  console.log("after :", Object.keys(process.env).filter(k=>k.includes("SUPABASE")));'
before: []
after : [ 'SUPABASE_URL', 'SUPABASE_ANON_KEY' ]
```

So the harness's central claim is asserted, not enforced. It is harmless on THIS machine only because the local `.env` happens to carry no `SUPABASE_SERVICE_ROLE_KEY`, so `getDbClient()` still refuses. That is an accident of one developer's untracked file, not a property of the suite.

**Why it must be fixed before TASK-0017, not left as a note.** TASK-0017 adds `tests/http/edit.http.test.ts` — an http test that PATCHes the record route. On any machine whose `.env` carries `SUPABASE_SERVICE_ROLE_KEY` (Railway's shape, or the day Ben adds it locally), that suite would exercise a **write** route against the **real catalog with a service-role key that bypasses RLS**. The harness is the only thing standing between the http suite and production data.

**The mechanism, measured on this tree.** `@next/env` does not override a name that is already present in `process.env`; it only fills absent ones. So the fix is not a bigger delete — deletion is exactly what invites the refill — it is to **set sentinels the reload cannot displace**:

```
$ node -e '... delete every SUPABASE name ...;
  process.env.SUPABASE_URL = "http://127.0.0.1:1/http-suite-sentinel";
  process.env.SUPABASE_ANON_KEY = "sentinel-anon";
  loadEnvConfig(process.cwd(), false);'
SUPABASE_URL = http://127.0.0.1:1/http-suite-sentinel
SUPABASE_ANON_KEY starts: sentinel-
SERVICE_ROLE set? false
```

Build it that way:

- `serverEnv()` keeps the delete pass (it clears staging names and anything else), and then **sets** the two names `src/lib/db/client.ts` actually reads — `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` — to sentinel values that cannot reach a database and cannot be mistaken for credentials. A URL on a closed local port (`http://127.0.0.1:1/http-suite-no-database`) and a key literal that says what it is (`http-suite-not-a-credential`), in the same spirit as the existing `AUTH_SECRET` literal. Comment WHY the values are set rather than deleted, citing the reload; a later reader will otherwise "clean up" the delete-then-set as redundant.
- The result is stronger than the original intent: a DB-reading route under the http suite now reaches `lib/db`, fails to connect, and renders its **error** state. The suite proves the app survives without a database instead of assuming it never asked.

**The enforcement, which is the actual deliverable.** Add `tests/offline/http-harness.test.ts` that imports `serverEnv()` and proves the sentinels SURVIVE the reload — run `loadEnvConfig` over the repo root **in a child process** carrying `serverEnv()` (never in the vitest process; that would mutate the runner's own env), and assert the child reports both names still holding the sentinel values. Assert on NAMES and on the sentinel literals only; never print or assert a real value. That test is what turns "asserted" into "enforced", and it fails loudly the day someone reverts to a bare delete or Next changes its loading rule.

Out of scope: any product file; `.env` / `.env.example` (untracked and human-owned respectively); the http suite's own test files (TASK-0019 owns `tests/http` breadth); pointing the suite at a database (it must not have one).

## Acceptance criteria
serverEnv() sets SUPABASE_URL and SUPABASE_SERVICE_ROLE_KEY to sentinel values after stripping every SUPABASE name, and the sentinels are self-describing literals that cannot connect and cannot be mistaken for credentials. A new offline test proves the property end to end: given serverEnv(), running Next's own env loading over the repo root in a child process leaves both names holding the sentinels — the test fails if the harness reverts to a bare delete. No real credential value is read, printed or asserted anywhere. tests/http still starts and stops the server and the existing http suite passes unchanged. No file under src/ is touched.

# The claim list's FILLED window counts one bucket and calls it 'these filters': /claims?tab=standing states its held count over a narrowing the sentence never names

## Description
Found while re-checking admin-window/BUG-0109 (attempt 2) and admin-window/BUG-0114 on the landed run branch, 2026-09-09. Same class as BUG-0114, on the one clause the BUG-0114 fix deliberately routed AROUND `population()`.

**Expected** — ARCHITECTURE.md §4.3 / LOOK_AND_FEEL bar 13: a window line states what the READ was, and every clause that names the rows names the population the read covered. `DrawnWindow.scope` was made REQUIRED for exactly that (`src/components/ui/window-line.tsx:92-112`), and one `population()` helper feeds every clause — every clause except one.

**Found** — the `matched` arm's TRUNCATED clause is the exception, by design: `src/components/ui/window-line.tsx:390-400` skips `population()` with the reason "this arm's own words already name the narrowing ('match these filters')". That reason holds only when the narrowing IS the chips. On `/claims?tab=standing` the narrowing is the TAB — `listScope` (`src/app/claims/page.tsx:183-188`) returns `in the standing_disagreement bucket` with no chip set, and the FilterBar above shows nothing selected — so the sentence attributes a count of ONE BUCKET to filters that are not applied.

Measured offline, `renderClaims(standingCrowd(73), { tab: "standing" })`, `data-window-held="73"`, `data-window-truncated="true"`:

  "…A window of at most 50 rows, not the whole view. 73 claims match these filters; the 50 longest-waiting are below — narrow with the filters above to reach the rest."

Nothing in that sentence says the 73 are standing disagreements. The unfiltered buckets tab, over 877 claims of every bucket, renders the SAME sentence shape with a different number (measured on staging, 2026-09-09: `/claims` held=877 truncated=true → "877 claims match these filters; the 50 longest-waiting are below…"), so the two populations are indistinguishable from the line.

**The same window contradicts itself.** Its other two arms, on the same page and the same read, DO name the bucket:
- not-filled (measured, `standingCrowd(4)`): "…so it holds all the claims in the standing_disagreement bucket, matching these filters the read found."
- zero (measured on staging, `/claims?tab=standing`, held=0): "The window did not fill: the read happened and found no claims in the standing_disagreement bucket at all."
So one sentence names the narrowing when the window is empty or short, and drops it at the exact moment the window fills and the number gets large.

   `AssertionError: expected 'Oldest first — the longest-waiting cl…' to contain 'standing_disagreement'` at tests/offline/claims/page.test.ts:793. The two assertions ABOVE it pass, which is the contradiction: the same window's unfilled arm does contain `standing_disagreement`.

**Repro (in the app)**
1. Sign in; open `/claims`, click the standing-disagreements tab (`?tab=standing`).
2. With more than `CLAIM_WINDOW` (50) claims in `standing_disagreement`, read the line above the list.
3. It states the bucket's count as a count "match[ing] these filters" while the filter bar has nothing selected.

**Reachability today** — staging holds 877 pending claims, 769 `awaiting_row` + 108 `awaiting_link`, and ZERO `standing_disagreement` (counted independently 2026-09-09 through `pending_claims`), so the standing tab is empty today and takes its (correct) zero arm. It becomes wrong the first time the resolver files 51 standing disagreements — the bucket the tab exists for. Same reachability profile BUG-0114 had.

**Not the other arms** — checked on this tree: `newest` (`/cycles` runs, `/queues`, both Dashboard panels), `alphabetical` (entity picker) and `catalog` (`/browse`) all pass their `scope` through `population()` in BOTH directions; sabotaging `runsScope` to `null` reddens 3 tests and sabotaging `listScope` to `null` reddens 1, so only this clause is unpinned.

**Fix shape (not prescriptive)** — either the `matched` truncated clause takes `population()` like every other clause and the arm's own "match these filters" gives way to the window's phrase, or `listScope` stops being the only carrier and the arm's words are built from it. What it may not do is count one bucket and name a different narrowing.

2. An UNNARROWED filled window (the buckets tab, no chips) keeps the sentence it renders today, to the byte — no narrowing phrase appears where there is no narrowing.
3. The narrowing is never stated twice in one clause (the arm's own words and the window's phrase do not both render).
4. The pin at tests/offline/claims/page.test.ts (`it.fails`, admin-window/BUG-0114's sibling) is flipped back to `it(` in the same commit; that flip is how the stored check tells fixed from unfixed.

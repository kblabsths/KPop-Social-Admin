# The http tier's storable assertion passes on the gate's 403, so it grades nothing the handler answered — make the vacuity visible

## Description
**Module:** `tests/http/paging.http.test.ts`, the `a gated answer is never storable` describe. No product code, no other tier.

**Found** (QA, admin-window/BUG-0171 close, stated as a residual for the architect rather than a bug): the case `answers a signed-in GET and a refused bound with nothing a store may keep` labels its four asks "the browse route, a signed-in GET" / "a refused bound", but on this tier every one of them is answered **403** by `requireAdmin()` — the harness has no database and no `admin_allowed_emails`, so no cookie can be vouched for (STACK.md §4, and the suite's own docstring says so). A 403 carries no `cache-control` at all, `isStorable(null)` is `false`, and the case therefore passes **without ever reaching the handler**. QA reproduced it on its own second server with the harness's sentinels: the header defect BUG-0171 fixed would have left this case GREEN.

**Ruled: make the vacuity visible, do not try to remove it** (architect, 2026-09-11). The tier cannot be given an allowlist or a database — that is STACK.md §4's design and a harness change, not a fix — so the positive claim stays where it already is (the arm tables in `tests/offline/paging/claims-route.test.ts` and `browse-route.test.ts`, plus QA's staging-wire measurement recorded in BUG-0171's History). What is wrong here is only that the case's own text claims more than it grades, and that a future harness gaining a database would silently change what it proves without reddening anything. The general rule this instance produced is written into `ARCHITECTURE.md` §10 ("What the http tier can prove, and what it cannot") so no future decomposition authors the unsatisfiable clause again; this ticket is the one-file consequence.

## Acceptance criteria
THE CASE ASSERTS THE STATUS IT ACTUALLY GRADED. Every ask in the `a gated answer is never storable` describe's route case asserts its exact response status against a NAMED constant in that file (spelled GATE_STATUS, value 403 — the fail-closed answer requireAdmin() gives on a tier with no allowlist), beside the existing isStorable assertion and with the ask's label in the failure message. So the day the harness gains a database or an allowlist, the case goes RED and is re-authored deliberately, instead of silently starting to grade something else.

NO LABEL CLAIMS A HANDLER ANSWER THIS TIER CANNOT REACH. The phrase "a signed-in GET" appears nowhere in tests/http/paging.http.test.ts as the name of something this tier grades: the four asks and the case name say what they are — the gate's answer to a signed-in caller, and the gate's answer to a refused bound — so a reader of the suite cannot mistake it for proof about the handler's four arms. Nothing about the docstring's existing "what this tier cannot prove, and where it is proved instead" paragraph is weakened; it gains the one fact QA measured, that a 403 carries no cache-control at all and therefore satisfies isStorable vacuously, and names the offline arm tables as the positive proof.

NOTHING ELSE IN THE TIER CHANGES. The page case (`is spelled exactly as the built server spells it on a gated page`) is untouched — it grades a real 200 from /browse and /claims and is this suite's only positive claim about the directives. The isStorable predicate and its four MUST-flag fixtures are untouched. The other four describes of the file, and every other file under tests/http, are untouched. npm run test:http is green (26 cases, ~23 s including the build, measured 2026-09-11) and npm run lint is clean.

# pageUrl appends the bound instead of overriding one the facets already spell, so a stale offset is the one the handler reads

## Description
Expected (src/lib/paging/machine.ts:82-87, pageUrl's own doc contract): "The bound is appended LAST and under OFFSET_PARAM, so the parameter the handler reads is the one this module wrote even if a surface's serialized facets carry a stale one."

Found: appending is not overriding. pageUrl builds the query by string concatenation (src/lib/paging/machine.ts:88-92) and never removes an existing OFFSET_PARAM from deps.params, so a facet string that already spells one produces a URL carrying the parameter TWICE — and a route handler reading it with URLSearchParams.get() (the web-platform answer this repo already relies on, src/lib/claims/filters.ts:197) gets the FIRST occurrence, i.e. the stale one, not the bound this press holds.

Exact repro (offline, no server needed):

  ./node_modules/.bin/vitest run --project=offline tests/offline/paging/machine.test.ts

with the pin below un-marked, or directly:

  pageUrl({ route: PAGE_ROUTES.claims, params: 'offset=99', size: 50, fetchJson }, 4)
    -> '/api/admin/claims/rows?offset=99&offset=4'
  new URL(that, 'https://x').searchParams.get('offset')  ->  '99'   (expected '4')
  ... .searchParams.getAll('offset')                     ->  ['99','4']

Measured 2026-09-10 on run/admin-window at 731cf91; the assertion failed with: AssertionError: offset=99: expected '99' to be '4'. The same holds for params 'tab=standing&offset=99'.

Consequence when a consumer arrives: requestPage sends held=4, the server honours 99, and the answer's own offset is deliberately not read back into state (machine.ts:150-160), so the surface appends rows from a window it never asked for and grows held past them — a 'more' press that repeats or skips rows with nothing anywhere to notice. If the stale bound is out of range the surface instead refuses every press forever at a bound the operator cannot see, since PageRefusal drops the server's bound string by design.

Not reachable today: TASK-0063 ships no caller. The trigger is TASK-0064/TASK-0065 handing a surface's serialized search params (rather than a fixed facet allowlist like claimsHref) into PageDeps.params — which is precisely the case the doc comment above claims is already handled, and which the shipped tests never drive (tests/offline/paging/machine.test.ts:90-100 iterates only '', '?tab=standing', 'tab=standing&', '&tab=standing').

Fix direction (builder's call, not QA's): compose the query with URLSearchParams and set() rather than string concatenation, so the last writer wins and the parameter appears once — or, if appending is intended to stay, delete the false guarantee from the doc comment and state the caller's obligation instead. Either way the pin below must go green as a plain 'it'.

The pin: tests/offline/paging/machine.test.ts, 'carries THIS press's bound even when the surface's facets already spell one', currently marked it.fails so the branch stays green. Fixing this makes it XPASS -> the marker must be dropped back to a plain it() in the same commit.

## Acceptance criteria
pageUrl produces a URL whose query carries the OFFSET_PARAM exactly once, and the occurrence is THIS press's bound: for deps.params of "offset=99", "tab=standing&offset=99", "?offset=99" and "offset=99&offset=7", new URL(pageUrl(deps, 4), "https://x").searchParams.getAll("offset") is ["4"] and .get("offset") is "4". Every case the shipped tests already cover is unchanged: "", "?tab=standing", "tab=standing&" and "&tab=standing" still produce the same URL they produce today, the surface's own facets survive in the order the caller wrote them, and the route path is still PAGE_ROUTES' one spelling. The pin in tests/offline/paging/machine.test.ts, "carries THIS press's bound even when the surface's facets already spell one", is a plain it() in the same commit as the fix — no it.fails marker remains in that file. machine.ts stays a pure leaf (it imports bounds.ts and nothing else) and tests/offline/db/layering.test.ts is green over it; requestPage's own behaviour is unchanged — one press one request, a refusal still leaves rows, order and held untouched.

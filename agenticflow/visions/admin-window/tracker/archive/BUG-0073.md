# The record page h1 uppercases the table identifier: WALK_SANDBOX RECORD, GROUPS RECORD

## Description
Found attacking admin-window/BUG-0049 (which fixed the same bug class in the `micro` eyebrow) on the landed run branch da1687d. Measured in a real browser, my own dev instance on :8783 against staging, 1440x900 Chromium, LIGHT and DARK, 2026-09-03.

Expected (LOOK_AND_FEEL Voice copy bar 5): "Machine identifiers (`data_conflict`, `admin_locked`, `event_performers`, `wont_fix`) render verbatim in mono and are never prettified into Title Case prose." LESSONS 5 restates it: uppercasing `data_conflict` prettifies it wrongly.

Found: `/records/[table]/[id]` builds its page h1 by concatenating the TABLE NAME with English — `RecordFrame`, `src/app/records/[table]/[id]/page.tsx:276`: `<Page title={\`${config.table} record\`}>`. `Page` renders that in `type-title` (`src/components/ui/page.tsx:20`), and `type-title` is `font-family: var(--font-sans)` + `text-transform: uppercase` (`src/app/globals.css:131-139`). So the identifier is rewritten on screen.

Real-render measurement, http://localhost:8783/records/walk_sandbox/00000000-0000-4000-8000-000000000001, both schemes, console clean:
  h1 textContent = 'walk_sandbox record'
  h1 innerText   = 'WALK_SANDBOX RECORD'      <- what the operator reads
  computed: text-transform uppercase, font-family Geist (SANS), 14px, letter-spacing 0.7px
Every mapped table has the same shape: groups -> 'GROUPS RECORD', idols -> 'IDOLS RECORD', events, venues.

Three feet lower on the same screen the same page renders the row id in `type-data` mono at text-transform none, and `/queues` renders `data_conflict` verbatim — so the window shows two spellings of one identifier class, which is the exact complaint BUG-0049 was filed for. `walk_sandbox` is the address STACK.md §5 sends every walker to, so this is on a walked path, not a corner.

Why BUG-0049's guard did not catch it: `uppercasedIdentifiers` (`tests/offline/ui/markup.ts:43`) inspects `type-micro` elements only; the h1 is `type-title`. The builder named this residual in BUG-0049's handoff and declined to guess the remedy, correctly — fixing it means ruling whether a page h1 may mix mono and sans, which is a design call, not a build choice.

Repro (exact):
1. Launch the walk instance per STACK.md §5 step 1 (any free port).
2. Mint a cookie: `node tests/walk/session-cookie.mts`; add it to the browser context.
3. Open `/records/walk_sandbox/00000000-0000-4000-8000-000000000001` (any `/records/<table>/<id>` shows it).
4. Read the h1. Expected `walk_sandbox record` with the identifier verbatim in mono; found `WALK_SANDBOX RECORD` in uppercase sans.

Offline repro, no browser: the pin QA left in `tests/offline/records/page.test.ts` ("keeps the table identifier out of the uppercasing h1"), a strict `it.fails` xfail. It asserts the STRUCTURAL property BUG-0049 established for the eyebrow — no `type-title` element carries the table identifier — plus that the identifier is still on the page, so the guard cannot be satisfied by deleting the word. Watched red against this code before it was pinned: `AssertionError: groups: expected [ 'groups record' ] to deeply equal []`. Flip it back to a plain `it(...)` when the fix lands; strict xfail reddens the suite if it starts passing without the flip.

Not decided here (for the designer/architect): whether the h1 becomes an identifier span in mono beside the sans word `record`, the way `ui/micro-label.tsx` solved the eyebrow, or whether the table name leaves the h1 for a line under it. Either satisfies the pin.

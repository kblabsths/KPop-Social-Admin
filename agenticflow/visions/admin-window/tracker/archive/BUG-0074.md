# Dashboard calls a dead cycle 'still running' — the same row /cycles calls 'died'

## Description
Found attacking BUG-0055 (one word per cycle state on /cycles). /cycles now reads every no-outcome cycle through cycleState() — running / died / unrecorded — on BOTH the rows and the health panel. The Dashboard reads the SAME resolution_runs rows and classifies them by ended_at ALONE, so it has no died state at all.

Expected (LOOK_AND_FEEL 'The Voice' glossary, 'one name per concept, everywhere … two builders who never meet must write the same labels'; src/lib/db/cycles.ts:205-217 quoting migration 20260901000001, 'a null older than one cadence is how a crash stays visible'; src/app/cycles/page.tsx:324-327, 'rendering it as running would leave a months-old failure reading as work in progress'): a cycle with NULL ended_at and NULL outcome that started longer ago than one resolver cadence (900s) reads as died on every surface that shows it.

Found (src/app/page.tsx:167-205, outcomeCell(outcome, endedAt)): the only test is 'endedAt === null' -> data-outcome="running", 'still running'. Age is never consulted and RESOLVER_CADENCE_SECONDS/cycleState are never imported. The Dashboard therefore renders a cycle that died in March as 'still running', while /cycles renders the identical row as died.

Repro (offline, deterministic, no database):
1. tests/offline/dashboard/page.test.ts, describe 'a cycle with no end recorded' (added by QA, currently marked it.fails as the pin for THIS ticket).
2. The population is two no-outcome, no-ended_at cycles built off the wall clock: one started 60s ago, one started 30 days ago.
3. cycleState(the 30-day row, {now, cadenceSeconds: RESOLVER_CADENCE_SECONDS}).kind === 'died' — the classification /cycles renders.
4. The Dashboard's own state hook for that row is 'running'.
   Expected: outcomesOf(markup,'cycles')[1] === 'died'. Actual: 'running'.
   Watched red before filing: 'expected running to be died // Object.is equality' (vitest, 2026-09-04).
   The control case in the same describe passes and must keep passing: the 60s-old row IS running on both surfaces.

Why it reaches an operator, measured on staging (ubfjjqlvnpnoborczbdb, dev server on 8783, 2026-09-04): /cycles delivers 69 cycles, 4 of them died — the newest at index 14, 23h old, so today the Dashboard's 6-row window happens to hold none of them and the contradiction is not on screen right now. It arrives the moment a cycle dies: the dead cycle IS the newest, and the Dashboard's window is the newest 6 (DASHBOARD_WINDOW, src/lib/db/dashboard.ts:53). At the 15-min cadence it sits at the top of the Dashboard for ~90 minutes; if the crash also stopped the cron, it stays there forever and the page whose job is 'did anything happen last night' answers 'a cycle is running' about a resolver that is down.

Fix shape (builder's call): the Dashboard's cycle rows go through cycleState() with one render clock, the way /cycles does, and take their word from the same place. The adapter-runs table is a DIFFERENT producer (runs, not resolution_runs) with no cadence of its own — leave it alone; this ticket is the cycles table only.

The pin: tests/offline/dashboard/page.test.ts's 'does not read a cycle older than one cadence as running' is it.fails (vitest's strict xfail — it goes red the day the divergence disappears). Remove the .fails when you fix it.

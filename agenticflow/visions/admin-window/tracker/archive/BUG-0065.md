# Record page: a mistyped id renders the failed-read state, whose only advice is to reload

## Description
Found by QA attacking BUG-0052's landed fix on run/admin-window (70beeb0), on a production build of the landed tree against staging, port 8783, 2026-09-03. Not caused by that fix — the failed-read branch predates it — but BUG-0052 makes this the path the app now sends a pre-cutover operator down.

BUG-0052 made the pre-cutover empty state say: 'Admin has no groups listing: such a record is reached by its id alone. Check the id in the address bar, or take one from the catalog database.' Hand-carrying an id is therefore the sanctioned way to reach a groups/idols record in M1, so mistyping one is the operator error that path invites — and it is what an operator pasting an id out of a SQL client actually does.

Expected (LOOK_AND_FEEL Voice copy bar 3: 'Every error names what failed, then what to do'): a state whose 'what to do' is something the operator can do — the id in the address bar is not an id, fix it.

Found: the generic READ-FAILED state, over recovery advice that cannot ever work. Measured, all HTTP 200, on the landed tree's production build:

  GET /records/groups/not-a-uuid
    data-state="error" | 'groups — invalid input syntax for type uuid: "not-a-uuid" (22P02)' | 'Reload to try the read again.'
  GET /records/groups/00000000-0000-0000-0000-00000000000   (one char short)
    same state, message quotes the truncated id
  GET /records/groups/00000000-0000-0000-0000-000000000000%20   (trailing space, as a browser encodes it)
    same state, message quotes the id with the %20
  GET /records/idols/not-a-uuid — same
  GET /records/events/not-a-uuid, /records/venues/not-a-uuid — same, TWICE (the field_provenance leg and the table leg each report it)

Reloading a malformed id reproduces the identical error forever, so the state strands the operator in the exact moment BUG-0052 set out to rescue (user-sim Priya's tab-closing moment, agenticflow/tracker/evidence/user-sim-m1/priya.md Leg 2). A well-formed id that simply has no row answers correctly with the empty state — verified in the same pass — so the divergence is only the malformed spelling.

At source: src/app/records/[table]/[id]/page.tsx:183-190 renders ErrorLine for every result.kind === 'error', and src/lib/db/records.ts passes the URL segment straight to the query, so a value that is not a uuid is decided by Postgres rather than by the request. A malformed id is a bad REQUEST and is decidable without a database.

Pinned RED, then held as a strict-xfail (vitest it.fails) so the suite stays green until this is fixed: tests/offline/records/page.test.ts, 'does not report a mistyped id as a failed database read' — it asserts a state renders and that it is not the failed-read state, and says nothing about which words replace it. Watched failing against the current code (1 failed) before it was marked. The fixing builder REMOVES the .fails marker; the test then reddens if the behaviour comes back.

Scope note: the fix may live in the page or in lib/db/records.ts — QA takes no view on which. Whatever answers a malformed id must not be the state that means 'the database failed'.

## Acceptance criteria
A record-page URL whose id is not a uuid renders a state that is not the failed-read state, and whose recovery advice is an action the operator can take (a reload is not one for this cause).

A well-formed id with no matching row still renders the unknown-id empty state BUG-0052 wrote — unchanged, both regimes.

tests/offline/records/page.test.ts's 'does not report a mistyped id as a failed database read' passes with the it.fails marker REMOVED.

The behaviour holds on every table in EDIT_CONFIG, and on the resolver-owned pair it is one answer, not one per read leg.

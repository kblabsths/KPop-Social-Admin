# Claims: BUG-0041's 50-row window broke the page's live parity oracle (claims.live is red on the run branch)

## Description
BUG-0041 (landed on run/admin-window as e5cf327, commit 9012ef5) windowed the claims list to CLAIM_WINDOW = 50 (src/components/claims/claim-list.tsx:71, :90-93). Its live parity oracle was not updated with it, so the live suite is RED on the run branch.

Expected: 'tests/live/claims.live.test.ts:200-210' ('lists every claim the view holds - a complete read, nothing dropped') grades the claims list surface and then asserts 'expect(rendered).toHaveLength(whole)' at :209, where 'whole' is countRows() over the entire pending_claims view.

Found: the page renders 50 rows and staging's view holds 877, so the assertion fails:
  AssertionError: expected [ ...(50) ] to have a length of 877 but got 50
  at tests/live/claims.live.test.ts:209

Repro (repo root, staging names in .env; the live setup loads them):
  npm run test:live -- tests/live/claims.live.test.ts
  => Test Files 1 failed (1); Tests 1 failed | 8 passed. Watched red 2026-09-03 15:53 and 16:02 on 193fe57.

Causation is pinned, not inferred: the same command on a detached worktree at f85b43e (the run branch immediately BEFORE BUG-0056 landed, i.e. WITH BUG-0041 and WITHOUT BUG-0056) fails with the identical message. So this is BUG-0041's, and BUG-0056 is not culpable - its own Section change is byte-identical wherever the 'surface' prop is omitted (md5 dbbf6f06bae0bfff49cee4b0ac69ae85 on the rendered markup at f85b43e and at HEAD; only src/app/cycles/page.tsx passes the prop).

Same defect class as BUG-0056, one commit earlier: a page's behaviour changed, its live oracle did not, and nothing offline could see it - run.yaml ci_command runs 'npm test' (offline + isolated projects only) and BUG-0041 pinned its window OFFLINE only (tests/offline/claims/page.test.ts, +184 lines). The live half of that ticket's certification has been failing since it landed.

Fix direction is the builder's call. BUG-0041's own commit message says 'the read stays complete and the bucket table still counts the whole view: no figure on the page became a window aggregate' - so if that holds, the LIST is windowed by design and the oracle's :209 assertion is the stale half: it should assert the rendered rows are the first CLAIM_WINDOW of the view in the view's own order (a prefix, no dropped or duplicated ids), and that the counts the page states are still the whole view's. Do NOT weaken it to 'renders some rows'; the completeness property is what this oracle exists for.

Not in scope, separately red on the same suite and predating BUG-0056 too (identical message at f85b43e): tests/live/queues.live.test.ts:325 and tests/live/residue.live.test.ts:112.

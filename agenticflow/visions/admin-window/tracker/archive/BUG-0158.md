# Three surfaces still label a source with a hand-rolled `?? id`, so a registry row that exists with a blank name reaches the screen as nothing

## Description
Found attacking BUG-0156 on the landed tree (run/admin-window @ 886dd1a, offline vitest, no device, no network, 2026-09-09); named as a residual in that ticket's own builder note and confirmed here by measurement.

Expected (`src/lib/sources/names.ts`, "The one owner of this rule: every surface that labels a source id calls here… A retyped `?? sourceId` beside it is the defect this ticket removed", BUG-0154/BUG-0043): what a source is CALLED is `sourceLabel`'s one rule, and "the registry names nothing" is decided by INK, not by `null` — `??` catches only `null`/`undefined`, so a registry row that EXISTS with a blank name takes neither branch and the blank reaches the screen.

Found — three call sites still spell the fallback by hand:
 1. `src/lib/browse/rows.ts:222` — `nameOf.get(sourceId) ?? sourceId`. MEASURED through `joinBrowseRows` (offline, no db): `sources: [{source_id:"s1", source:""}]` -> `rows[0].sources === [""]`, while `sourceLabel` answers `"s1"`; same for `"   "` and `"​"`. So the browse table's source list reads as nothing for that row while every row beside it names its source — BUG-0154's harm on a second surface.
 2. `src/components/sources/trends.tsx:46` — `{name ?? sourceId}` inside the trend's anchor: an `<a data-trend-source=…>` with nothing to read and nothing visible to click for the same registry row (BUG-0154's exact rendering).
 3. `src/app/claims/page.tsx:487` — `{split.source ?? split.sourceId}` inside the split's anchor, same shape.
Sites 2 and 3 are read from source and are the identical expression; only site 1 is pinned below, because it is the one reachable from a pure function offline.

Reach: `sources.source` is `NOT NULL` with `CHECK (source ~ '^[a-z0-9_]+$')` in the scraper repo, so a blank name needs a producer-side breach; staging has none (verified while attacking BUG-0154/BUG-0156). P3 for that reach — the same price its siblings carried. The value of fixing it is that the rule stops having four owners (LESSONS 5): each of these is a place the next label change will not reach.

Pin (landed on run/admin-window by qa-0156, `it.fails` while the divergence stands — THE FIX FLIPS IT TO A PLAIN `it`), watched RED first as a plain `it` on this exact tree: `tests/offline/browse/views.test.ts`, describe "the join", "says what the label rule says for a registry row that names nothing readable" — red with `AssertionError: "": expected [ '' ] to deeply equal [ 's1' ]`. Non-vacuous: the neighbouring "keeps a source id whose sources row never arrived" pins the case both spellings already agree on.

Repro (site 1):

 2. ./node_modules/.bin/vitest run --project=offline tests/offline/browse/views.test.ts -t "names nothing readable"

Fix shape (not binding): the three call sites ask `sourceLabel(sourceNamesOf(rows), id)` — the map each of them already builds by hand — so the ink rule has one owner. `lib/browse/rows.ts` builds `nameOf` two lines above the fallback; `trends.tsx` and `claims/page.tsx` receive a `name`/`source` already looked up, so their read is the site that should hand over the label the rule answered rather than a raw registry string. A hand-rolled ink test at any of the three would be a fifth owner and is the drift this ticket exists to remove.

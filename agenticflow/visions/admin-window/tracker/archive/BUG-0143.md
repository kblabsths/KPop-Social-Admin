# /cycles?cycle=<a real cycle id in any spelling but the database's> tells the operator the cycle is not in a window it is rendering

## Description
Found while attacking admin-window/BUG-0142, which canonicalised the page's OTHER id facet. Measured offline on run/admin-window at e124cc1 (renderToStaticMarkup of the real page function against the cycles fixture population; tests/offline/cycles/page.test.ts).

Repro (offline, exact):
  cd '/Users/ben-m4/Desktop/Coding/KPOP/kspace Admin'
  ./node_modules/.bin/vitest run --project=offline tests/offline/cycles/page.test.ts -t 'non-canonical spelling'
That case is currently an it.fails pin, so it reports PASS while the defect stands; flip its 'it.fails(' to 'it(' to watch it red. Over HTTP the same repro is: open /cycles?cycle=<the run_id of any cycle in the window>, uppercased (or with its hyphens removed).

Expected: the same answer the page gives for the canonical spelling of the same id, and the same answer its ?run= twin gives for a non-canonical one — data-cycle-found='true', one tr[data-row-marked='true'], aria-current on that row (LESSONS 4: compare on a normalized form; admin-window/BUG-0140 settled this for /sources; canonicalRecordId in src/lib/db/records.ts is the app's one uuid grammar and is already imported by this very file).

Found: with cycle=0192F0C1-0000-7000-8000-00000000000B (the uppercase spelling of fixture cycle FAILED, whose row the page renders), data-cycle-found='false', tr[data-row-marked] count 0, and the page states in prose: 'Cycle 0192F0C1-0000-7000-8000-00000000000B is not among the 200 newest cycles, so it is not in this window - it ran earlier, or no cycle carries that id.' Directly above it the same page's window line says 'The window did not fill - 6 of at most 200 - so it holds all the cycles the read found', and [data-cycle='0192f0c1-0000-7000-8000-00000000000b'] is present in the markup. The page therefore denies a row it is rendering. The unhyphenated spelling 0192f0c100007000800000000000000b behaves the same.

At src/app/cycles/page.tsx line 183: 'const askedFor = firstValue(params[CYCLE_FACET]);' - the raw value goes straight to the row predicate and to AskedCycle. Line 188-189, added by BUG-0142 for the other facet, is the shape this one needs: 'const askedRun = firstValue(params[RUN_FACET]); const markedRun = askedRun === undefined ? null : canonicalRecordId(askedRun);' Measured contrast in one render pass: ?run=<uppercase real run id> marks its row and names it in the canonical spelling (1 marked row); ?cycle=<uppercase real cycle id> marks nothing.

Note for whoever takes it: canonicalising askedFor must NOT change what the dropped-parameter line does with a ?cycle= that is not an id at all - today such a value still earns AskedCycle's absent sentence (the page's own walked behaviour, quoted in BUG-0142's body), while ?run= routes it to DroppedParamsLine instead. Whether the two facets should also converge THERE is a design question, not part of this fix; keep the existing ?cycle= tests green either way.

## Acceptance criteria
On /cycles, a ?cycle= value that canonicalRecordId reduces to the run_id of a cycle in the rendered window is answered as that cycle: data-cycle-found='true', exactly one tr[data-row-marked='true'] and that row's aria-current, in every spelling of the id the database itself would have matched (uppercase and unhyphenated included) - and the id the sentence prints is the canonical one. A value that is not a record id at all keeps whatever the page does with it today. Pinned by flipping the it.fails pin 'marks the cycle a non-canonical spelling of a real id names [admin-window/BUG-0143]' in tests/offline/cycles/page.test.ts back to a plain it(...), with every other case in that file still green.

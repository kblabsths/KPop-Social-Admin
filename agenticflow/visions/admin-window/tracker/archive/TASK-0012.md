# Claims — the classification buckets, the standing-disagreements tab, and no in_window

## Description
Module: `src/app/claims/page.tsx` + `src/lib/db/claims.ts`. Authority: spec section 4 (Claims); `contracts/resolver.md` section 7 (the classification view and its six buckets) and section 4 (mutability classes / standing disagreements); SPEC F5; M1 EC5; acceptance tests 3, 2, 9; LOOK_AND_FEEL 'Key screens — Claims' and quality bar 3.

- The pending-claims classification view (`public.pending_claims`) renders as **buckets with counts and age**, filterable by **source, domain and bucket**. Rendered bucket counts equal the view's counts, per bucket **and per source filter**.
- **`in_window` appears nowhere in the UI** — not as a bucket row, not as an empty bucket, not as a filter option, not as a zero. It is a real string in the view (empty by rule while corroboration windows stay parked) and it is filtered out **once, in `lib/db/claims.ts`**, not page by page.
- **The standing-disagreements subset is its own tab** — `bucket = 'standing_disagreement'`. There is no separate database view for it (resolver section 7: 'the standing-disagreements view is this view filtered to contradictions'); do not go looking for a missing object.
- **A claim links to its source and to its fact's provenance.**
- The view carries `observation_id, domain, entity_id, field, source_id, bucket, unmet_requirement` and **no age and no value** — age comes from `observations.observed_at` joined by `observation_id` in TypeScript (ARCHITECTURE section 4.2). An `awaiting_row` row always names its `unmet_requirement`; render it, never a bare bucket name.
- The **pending-claims gauge** and the **standing-disagreements gauge** (TASK-0007) render on this page, the second on the standing tab. The per-source `awaiting_row` threshold line is not built (blocked question) and the per-source trend itself lives on Sources.

Standing rules for every page ticket (ARCHITECTURE sections 4, 5, 7): the page function is the only async component on the route and every child is a pure sync component; read only through `src/lib/db/**`; table names live only in `tables.ts`; render all four states from the `ui` primitives (a missing table never throws and never renders as 0); tokens and primitives, never raw values; every filter, sort and tab is a `searchParams` value; ages relative with the absolute in the title attribute, scheduled times absolute UTC with the zone in the column header, machine identifiers verbatim in mono; **nothing settles anything in M1**.

## Acceptance criteria
[tests 3, 2, 9; EC5] Offline tests over fixtures covering every bucket prove: rendered bucket counts equal the fixture counts per bucket and per source filter; `in_window` rows are absent from every rendering including the filter options; the standing tab renders exactly the `standing_disagreement` rows; an `awaiting_row` row shows its `unmet_requirement`. A live-marked parity test asserts per-bucket and per-source-filter counts against counts the test issues itself. A rendered-markup scan of this page finds zero occurrences of `in_window`. Each claim links to its source and to its fact's provenance. Not-provisioned and empty states render without throwing.

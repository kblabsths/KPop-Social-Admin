# A queue block blames the kind filter for an emptiness that filter did not cause

## Description
Found attacking BUG-0125 (QA, 2026-09-09), on the seam between the Dashboard's zero attention card and the page it links to. BUG-0125's own criteria are met; this is pre-existing `/queues` behaviour (`git log -L 295,295:src/app/queues/page.tsx` predates it) and is filed rather than folded in — but BUG-0125 is what makes it cost something: the sentence saying what fills a decision queue is exactly what disappears one click later, replaced by a wrong reason.

**Expected** — LOOK_AND_FEEL, the four states ("a table with no rows and a filter that matched nothing are different states and never share a rendering") and its scoped-zero rule ("a filtered 0 names its scope, so it never reads as a whole-queue 0" — the claim is about a filter that actually narrowed THIS block). A block whose rendered set is identical with and without a URL facet may not tell the reader that facet is why it is empty, nor scope its open figure by it.

**Found** — `src/app/queues/page.tsx:286-305`. Each block is ALREADY narrowed to its own kind (`const items = selectItems(result.data, { kind })`, line 286), but `narrowed` is the whole-URL predicate `isNarrowed(filter)` (line 287, `src/lib/review/queue-filters.ts:176`), which counts the `kind` facet. So on `/queues?kind=decision` — the URL the Dashboard's own zero decision card links to (`queueHref`, `src/app/page.tsx`) — the decision block is told a filter emptied it, when that facet removed not one row from it. Both faces, measured:

WALK, production build of run/admin-window (commit 5eb7d67) on port 8795 (own, bind-probed; killed after), staging, cookie-minted, 1440x900, BOTH themes — identical in light (body bg rgb(243,244,246)) and dark (rgb(3,7,18)):
1. Dashboard renders `OPEN DECISIONS | 0 | No open decisions. The resolver files one when sources disagree about a fact, or when a record cannot link.`
2. Click that card (href `/queues?kind=decision`).
3. The DECISION block, `data-state="empty"`, renders:
   - rows region: `No items matching these filters  Widen a filter above; the 'all' chip on any row shows everything again.`
   - open sub-line: `nothing open in this filtered view`
   Staging holds zero decision items of any status, so widening the filter adds nothing; the signal block's identical wording on the same page IS correct (kind=decision really did exclude its 1 open signal).

Offline, no database, in `tests/offline/queues/page.test.ts` with the pin's `it.fails` removed:
- `?kind=decision` vs no params, same `healthyScript()` population: the decision block renders the SAME 7 item ids in the same order, and its open sub-line differs — `AssertionError: decision sub-line: expected '1 high, 4 low in this filtered view…' to be '1 high, 4 lowoldest 30d ago'`.
- `?kind=decision` vs no params on an empty table: the decision block's rows region is `No items matching these filters…` where it is `No decisions waiting / The resolver files one when sources disagree about a fact, or when a record cannot link.` unfiltered.

The suite pins only the TRUE half of the rule today ("a zero that a filter produced > names its scope" drives `?kind=signal` against the DECISION block, where the scope claim is honest), and `states a real 0 when the Dashboard's decision link opens a quiet decision queue` renders this exact URL but asserts only counts and states — which is why it was never seen.

The pin is landed strict: `it.fails("does not scope a block by the one facet that cannot narrow it (BUG-0129)")` in `tests/offline/queues/page.test.ts`, inside `describe("a zero that a filter produced")`. Fix the scoping and it turns red — that is the signal to drop `.fails` and keep the test as the passing rule.

# The signal's evidence table calls a fact a record, and no row says which record it is about

## Description
Filed from the two M2 user-sim walks (2026-09-09). Both strangers stopped at the same table, and it is the app's central investigation surface.

**Priya** (`agenticflow/tracker/for-human/M2-usersim-priya.md` §2, and her "Where I'd have given up" list, item 1): "the RECORD column says `events.venue`, which is a *field name*, not a record. Nothing in that row tells me **which event**. There is no id, no title, no link. I have twenty-odd venue claims in front of me and I cannot get from any one of them to the event it belongs to. … That was the first place I would have closed the tab — a table of evidence where every row is a dead end except the one column that is identical on all 91 rows."

**Devin** (`M2-usersim-devin.md` §2, §7): read the whole table, could not assess the signal from it, and named "on a stuck record, the unlinked performer string next to the catalogue candidates" as one of the four things that would have let him act.

**Expected** — LOOK_AND_FEEL bar 10: "The investigation never leaves the app: from any review item you can reach its claims, from a claim its source and the fact's provenance, from an event its edit surface — each in one click, each a real URL." And the Look's consistency rule, stated for the evidence pair and true of the whole app: an anatomy does not change between screens, and the Voice's glossary is one name per concept. `/claims` already renders these two facts as two separate columns and names both correctly — `fact` = `domain.field`, `record` = the entity id drawn as a link to its record page (`src/components/claims/claim-list.tsx:139-164`).

**Found** — on `/queues/<id>`'s source-pattern view the first column is labelled **`record`** and its cell is `factKey(domain, field)`: `factColumn` in `src/components/review/evidence-cells.tsx:141-152`, used by `PatternEvidence` (`src/components/review/shape-views.tsx:405-418`). The record identity is dropped entirely. So the word `record` names two different things on two screens, and the review item's is the wrong one.

Measured on the walk instance (127.0.0.1:8771, staging, 2026-09-09), item `01a06287-5b67-7d1f-b4a5-d90aa93cb01a`, 91 rows, six columns:

| column | what 91 rows carry |
| --- | --- |
| record | `events.performers` on 88 rows, `events.venue`, `venues.timezone`, `events.ticket_url`, `events.starts_at`, `events.poster_url` — a fact, never a record |
| value | the source's raw JSON |
| source | `ticketmaster`, 91 identical links to one page |
| tier now | `official` on all 91 |
| observed | `8d ago` / `6d ago` |
| payload | one `sha256/…` shared by whole groups of rows |

Two rows are **byte-identical across all six columns** (`events.performers | [{"ids":{"spotify":"4Kxlr1PRlDKEB0ekOCyHgX",…},"ref":"K8vZ917GQmV","name":"BIGBANG"}] | ticketmaster | official | 8d ago | sha256/7b/7b50…`) while being two different stuck events. Nothing on the row distinguishes them.

**The identity is already in hand.** This page's own read selects `observations.external_ref` (`src/lib/db/review-item.ts:85`, `OBSERVATION_COLUMNS`) and drops it before render. Read-only against staging, `observations` where `domain=events, field=venue`: `external_ref` is populated and distinct per source record (`1AvZZ_8GkDIyaGr`, `vvG1IZ_eJSfUoL`, `k7vGF_oRKjGkH`, `17uYv0G6G9kXn2M`, `vvG1IZ_eJl2ADs`), and `entity_id` is non-null on the claims whose canonical row exists — the same value `/claims` links by. So the fix reads nothing new.

Provenance checked before filing: `git log` on `evidence-cells.tsx`, `shape-views.tsx` and `queues/[reviewItemId]/page.tsx` returns ticket-bearing commits only (BUG-0099, TASK-0011, DEBT-0006, BUG-0042, BUG-0096, BUG-0121…). Not a human-lane divergence.

## Acceptance criteria
1. The column that carries `domain.field` is labelled **`fact`** — the word `/claims` uses for the same value — on every evidence view that draws it. No other column is renamed.
2. Every evidence row **identifies the record it is about**, in a column labelled `record`: where `entity_id` is present, the id drawn as a link to `/records/<domain>/<id>` in the app's one link spelling (accent ink + underline at rest, `IN_PAGE_LINK`) — the rendering `factColumn` carries today; where `entity_id` is null (the row does not exist yet, which is why the claim is stuck), the source's own reference for that record, `observations.external_ref`, verbatim in mono and not a link (this app links nothing whose address it does not hold). A row carrying neither renders the table's dash.
3. No two evidence rows about two different source records render byte-identical. Concretely, on item `01a06287-5b67-7d1f-b4a5-d90aa93cb01a` the two `BIGBANG` rows differ in their `record` cell.
4. Anatomy unchanged otherwise: the same column order pattern (record, fact, value, source, tier now, observed, payload), the same type steps, no new colour, no badge, no chip inside an anchor, and the table still scrolls inside its own border at 1280 and 1440 (the page does not).
5. The two per-fact views (`ConflictEvidence`, `StuckFactEvidence`) are unchanged: they are about one record, which the item header already names.
6. Human-check (human-checkable): on the walk instance at 1440x900, light and dark, open `/queues/01a06287-5b67-7d1f-b4a5-d90aa93cb01a`; the first two columns read as a record and a fact, the two BIGBANG rows are told apart at a glance, and every record cell that is a link reaches a record page that 200s.
7. `npm run lint` and `tsc --noEmit` clean; the offline suite green.

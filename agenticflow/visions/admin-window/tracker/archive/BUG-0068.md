# PATCH record route: a malformed id answers 500 with the raw Postgres message, where the page already answers 'no record at this address'

## Description
Found by QA attacking BUG-0065 (2026-09-03), ruled a defect by the architect
2026-09-04.

**Expected**, and it is this app's own settled answer one file away: a URL
segment that is not a record id can equal no uuid primary key in any table, so
"no record at this address" is knowable with certainty and without a database.
The record PAGE asks `isRecordId` (`src/lib/db/records.ts`) BEFORE any read and
says exactly that — the placement is BUG-0065's fix, not an optimisation, and
its docstring carries why: the alternative is telling an operator "the read
failed, reload", advice that can never work because the reload re-sends the same
malformed segment forever.

**Found**: the PATCH route makes the same comparison with no gate at all.
`updateRecordField` hands the segment to PostgREST, Postgres refuses it with
`22P02 invalid input syntax for type uuid`, the data layer classifies that
(correctly, for a read it did make) as an arbitrary failure, and
`src/app/api/admin/records/[table]/[id]/route.ts` answers **HTTP 500 carrying
the database's own words**. Two things are wrong and one of them is mild: the
status says the app broke when the request was malformed, and the body hands raw
Postgres syntax text back to the caller who supplied the bad input.

**Reach, stated plainly, because it sets the priority.** No UI path produces it:
an edit cell exists only on a record page that has already gated the id, and the
browser half (`components/records/submit.ts`) sends the id the page was rendered
for. It takes a hand-crafted request from a caller who is already past NextAuth
and the `admin_allowed_emails` allowlist — inside the trust boundary STACK.md
declares, on the app's one mutating route. That is why this is P3 and not
higher, and why it is not nothing.

**The fix is one call and no new words.** Ask `isRecordId(id)` and answer the
404 this route ALREADY answers when a well-formed id matches no row (`no
<table> record with that id`) — the same sentence, the same status, one more way
to reach it. Do not invent a second id grammar (ARCHITECTURE §9.1 item 9,
DECISIONS 2026-09-04: one gate, one grammar, for the map and the route alike),
do not add a message that spells uuid rules at an HTTP caller, and do not touch
the 500 branch's rule — a read that really happened and really failed still
answers with the database's own words, which is LOOK_AND_FEEL's rule and stays.

Where the gate goes: AFTER `decideEdit`, so every refusal the map owns keeps the
status it has today (404 unknown table, 403 resolver-owned and non-editable
column) and this adds exactly one new answer.

**Where it is proved**: `tests/offline/edit/route.test.ts` — the tier that
exists for this question. It drives the handler with the gate stubbed open and
`updateRecordField` SPIED, so "no database call was even attempted" is
observable as "the writer was never called", which is the load-bearing half.
`tests/http/edit.http.test.ts` cannot reach it: under the DB sentinels
`requireAdmin()` fails closed there and every PATCH is refused by the gate
before the handler decides anything.

No live check is carried, deliberately: the 2026-09-03 decision binds a ticket
whose scope includes a PAGE under `src/app/**` or a shared primitive under
`src/components/ui/**`, and this is a route handler whose change happens before
any database call — no live parity oracle can observe it, and
`tests/live/edit.live.test.ts` writes staging rows for a path this ticket does
not alter.

## Acceptance criteria
A PATCH to /api/admin/records/{table}/{id} whose id is not a record id is refused 404 with the route's existing no-such-record wording, having made NO database call (the writer is never invoked, observable in tests/offline/edit/route.test.ts where it is spied), and its body carries no Postgres text — no '22P02', no 'invalid input syntax', no column or type names from the database. The route asks isRecordId from src/lib/db/records.ts, the same function the record page asks; no second id grammar, regex or per-table key shape is written anywhere (ARCHITECTURE 9.1 item 9). Every other answer this route gives is unchanged and pinned: 400 for a malformed body, an absent 'value' key or a non-finite number; 404 for an unknown table; 403 for a resolver-owned table and for a column outside the map; 503 for not_provisioned; 500 with the database's own words for a read or write that actually happened and failed; 200 with the record for an allowed edit — including a WELL-FORMED id that matches no row, which still answers 404 exactly as it does today. The id gate runs after decideEdit, so the map's refusals keep their current statuses.

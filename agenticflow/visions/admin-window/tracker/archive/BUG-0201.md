# /sources swallows a source_id it cannot use and answers with the whole registry, saying nothing

## Description
Filed from the M3 user-sim walk of Tomas Berg (`agenticflow/tracker/for-human/M3-usersim-tomas.md`), 2026-09-11, the section "Typing rubbish into the address bar: three pages, three different manners":

> "On **Sources** it is worse, and this is the one that actually cost the tool trust. I asked for a single source with `?source_id=deadbeef` — a value that is obviously not an id — and the page returned **the full registry, all three sources**, with no notice of any kind. The gauges below it dropped the 'from source_id …' phrasing and quietly went back to reporting all sources. If I had glanced at that screen believing I had narrowed to one source, I would have read three sources' rows as one source's story and had no way to know."

and his closing line: *"What would lose me: the silent parameter handling on Sources and Browse … on those two pages the prose goes quiet at exactly the moment it should speak."*

**Expected** — this campaign already holds the rule and owns one module for it. `src/lib/url/dropped-params.ts` exists precisely so no route re-derives it: *"a parameter outside a page's facets, and a facet value outside the offered vocabulary, both narrow nothing by design … Dropping it is right; dropping it SILENTLY is not."* It was `/claims`' alone (BUG-0123), moved whole to serve every route (BUG-0141), and `/cycles` carries it too (TASK-0016's precedent). LOOK_AND_FEEL bar 13 (a window line states the read that produced the rows) and the Look's *"no screen claims a mark it did not draw"* are the bars; BUG-0141's ruling is the campaign's own restatement: *"a `source_id` this page CANNOT use (`not-a-uuid`) must be named rather than swallowed"*.

**Found** — three of six pages say it and `/sources` is one of the two that do not. `grep -rn "DroppedParamsLine\|droppedParams" src` returns `src/app/cycles/page.tsx`, `src/app/queues/page.tsx`, `src/app/claims/page.tsx` and no other route. On `/sources`, `filterFrom` (`src/app/sources/page.tsx:161-165`) reduces an uncanonicalisable `source_id` to `{}` and the page reads the whole registry with nothing on screen saying so; every other key (`?q=`, `?table=`, `?limit=`) is never looked at at all. The page's own docstring already states the honest half of this — *"a facet this page dropped … never reaches a filter and so appears in no scope"* — which is right for the window lines and is exactly why a second sentence is needed: the scope phrases go quiet, and silence is what the operator reads as "no narrowing was asked for".

The counterpart it is measured against, from the same walk: `/claims?bucket=banana`, `?source_id=not-a-uuid`, `?limit=-1` and `?bucket=ESCALATED` each returned *"The URL carries `<name>`, which this page did not apply: nothing below is narrowed by it."* — "I could act on every one of those."

Provenance checked before filing: `git log src/app/sources/page.tsx` returns ticket-bearing commits only (BUG-0194, TASK-0073, BUG-0163, DEBT-0008 …). Not a human-lane divergence.

Sibling: the `/browse` half of the same finding is filed separately; the files are disjoint (`src/app/browse/page.tsx`), so the two can run in parallel or go to one builder.

## Acceptance criteria
1. `/sources` names a parameter it did not apply, in the app's one sentence for it: the page calls `droppedParams` from `@/lib/url/dropped-params` and renders `DroppedParamsLine` (`src/components/ui/dropped-params.tsx`). No second definition of that sentence is written anywhere — four bugs have landed on the shared one and a copy would be born with none of them.
2. The `applied` narrowing handed to the rule is **the filter the reads actually carried** (`filterFrom`'s output), never the raw URL: `?source_id=deadbeef` is named because no read carried it; `?source_id=<a canonical id>` is not named, whether or not the registry holds a row for it (that id really did narrow, and `data-empty="narrowing"` already says what came back).
3. A key the page consumes elsewhere, a key carrying no value, a nameless value, and a key outside the renderable allowlist all behave exactly as the module already defines them — this ticket adds a caller, not a rule.
4. Nothing else on the page moves. The registry table, both gauges, every window line and every scope phrase render byte-identically to today in the unnarrowed case and in the canonical-`source_id` case; `/sources` with no parameters is byte-identical to what it renders now.
5. The offline suite grades the new arm at the surface: a test named `names a source_id it could not use as a parameter it did not apply` (that string, so the check below can find it) asserts the line is present for `?source_id=deadbeef` and absent for a canonical id and for a bare `/sources`.
6. Human-check: at 1440x900, `/sources?source_id=deadbeef` reads as a page that did not narrow — the line names `source_id` in mono and says nothing below is narrowed by it — while `/sources?source_id=<real id>` is unchanged. **(human-checkable)**

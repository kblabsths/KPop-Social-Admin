# Links inside data tables announce themselves only under the pointer — the defect BUG-0054 fixed on /cycles, still shipping on three M2 surfaces

## Description
Measured on the M2 early walk, 2026-09-08, walk instance on 127.0.0.1:8771 against staging, bundled Chromium, 1440x900, computed styles at rest (after the 120ms transition settles — the reading is racy before that).

**Expected** — LOOK_AND_FEEL says this app draws a link at rest as accent ink plus an underline, twice, and both times as a statement of fact about the app: the asked-for-row rule ("carries that id as an in-page link **drawn as a link at rest** (accent ink, underlined)") and the resting edit affordance ("Hairline rather than accent is what keeps it apart from a link, **which this app draws as accent ink plus underline**"). `src/components/cycles/links.ts` is that spelling, `IN_PAGE_LINK = "text-accent underline"`, and its docstring records why BUG-0054 earned it: links that were `text-ink hover:text-accent` made "the one thing on screen that would have carried the reader to the row they asked for announce itself only under the pointer", and the M1 user-sim scanned uuids by eye instead of finding it.

**Found** — the app has two link renderings, and three of the M2 slice's surfaces use the rejected one. Measured `color` / `text-decoration-line` at rest inside `main`:

| surface | link | at rest |
| --- | --- | --- |
| `/records/events/<id>`, the `venue_id` reference | "The Theater at Bill Graham Civic Auditorium" | `rgb(30,41,57)` (primary ink), `none`, class `type-body transition-colors hover:text-accent` |
| `/queues`, the row's "what happened" | the item title | `rgb(30,41,57)`, `none`, class `transition-colors hover:text-accent` |
| `/queues/<id>`, the evidence table's `source` column (x91) | "ticketmaster" | `rgb(30,41,57)`, `none`, class `transition-colors hover:text-accent` |
| `/queues/<id>` header, "Its claims" / "Its source" | | `rgb(152,16,250)` accent, `underline` — correct |
| `/cycles`, the cycle id and the runs-window lead | | `rgb(152,16,250)` accent, `underline` — correct |

The record page is where it costs most. Every value in that table is mono primary ink; the editable ones carry a 1px hairline underline (TASK-0053, so a value that can be changed says so at rest). The one value that NAVIGATES — the reference to the venue, F12's display half and the whole of "from an event its edit surface … each in one click" (bar 10) — is the only interactive thing on the page with no resting affordance at all, and it is drawn exactly like the inert `event_id` above it.

Provenance checked before filing: `git log` on all three files returns ticket-bearing commits only (TASK-0055, BUG-0086, TASK-0040 / TASK-0011 / the queues work) — no human-lane divergence, so this is a violation and not a reconciliation.

Scope, honestly: `hover:text-accent` occurs in ten files under `src`, including the Dashboard, Claims, Browse and Sources tables which this early walk did not cover. This ticket grades the three surfaces measured above; the rest is the endgame walk's sweep unless the fix generalises, which it should — one spelling of a link, in one place, is what `cycles/links.ts` already demonstrates.

## Acceptance criteria
1. On the three surfaces named — the `venue_id` reference on an `events` record, the "what happened" link on a `/queues` row, and the `source` link in a review item's evidence table — every anchor renders at rest as this app spells a link: accent ink plus an underline, no hover required.
2. There is ONE spelling of a link in `src`, shared, not re-typed per component (`cycles/links.ts`'s `IN_PAGE_LINK` is the existing one and is the natural home); the three files above stop carrying their own.
3. A link stays distinguishable in both themes and keeps its contrast: accent measures >= 4.5:1 on `surface` and on `chrome` in light and dark (bar 12), including on a hovered row (whose fill is chrome).
4. The resting edit affordance stays distinct from a link: an editable value keeps its hairline underline in primary ink, a link is accent — the two are not confusable on the record page, which draws both.
5. No new colour, no change to row height, table density or cell padding: this changes ink, decoration and face only.
6. Human-check: on `/records/events/01a03f78-8bba-755c-8298-58f0549d9817` at 1440x900, without moving the mouse, the venue name is visibly the one thing on the page that goes somewhere. (human-checkable)
7. **The reference label is mono**, in one face whether or not a name resolved. `ReferenceValue` (`src/components/records/record-fields.tsx:77-90`) renders the venue's name in `type-body` sans and falls back to `type-data` mono when no name was read, so one line renders in two faces depending on the data. `venues.name` is a value the database produced, and LOOK_AND_FEEL's typographic split is that mono carries every such value while sans carries the words the app wrote — the id beside it is already mono for exactly that reason. Visible in `evidence/M2/designer/event-light-1440.png`: the `venue_id` row is the only value on that page that reads as prose.
8. `npm run lint` and `tsc --noEmit` clean; the targeted offline files green.

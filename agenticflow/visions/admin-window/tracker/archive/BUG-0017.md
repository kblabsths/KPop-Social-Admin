# A notFound() from a dynamic route serves an empty document: the 404 page only appears after hydration

## Description
Found attacking BUG-0014 on the landed run branch (122c3c1), production build, next start, cookie-authed.

REPRO (exact):
1. npm run build
2. Start the built app: node_modules/.bin/next start -p 8774 -H 127.0.0.1 (AUTH_SECRET set; no DB needed)
3. Mint a session cookie for that secret and GET http://127.0.0.1:8774/records/no-such-table/2f0bc11e with it, redirect: manual.
   'no-such-table' is any table EDIT_CONFIG does not carry, so src/app/records/[table]/[id]/page.tsx:83 runs notFound().

Expected (BUG-0014 criterion 1: the not-found surface 'inherits the Frame, the page padding and the token layer like every other route'; criterion 3: measured document.body background is the page token): the served document carries the same framed surface an unmatched URL serves — measured on /analytics, len 9727, <body class="flex min-h-full flex-col">, <link rel="stylesheet" data-precedence="next">, one <h1>, the sidebar, and href="/".

Found: the served document is len 7914, <html id="__next_error__">, <body> with NO class, body content is exactly <div hidden=""><!--$--><!--/$--></div>, the CSS arrives only as <link rel="preload" as="style"> (never a stylesheet), and the flight payload ends with 6:E{"digest":"NEXT_HTTP_ERROR_FALLBACK;404"}. The whole root layout is absent from the SSR output. The not-found tree exists in the flight payload only ('notFound':[...h1 'Page not found'...]) and is painted client-side.
Status is correct (404) on both paths.

MEASURED CONSEQUENCE (Chromium 1280x900, playwright, light and dark):
- JS enabled: after hydration both paths are identical and correct — body bg rgb(243,244,246) light / rgb(3,7,18) dark, ink rgb(30,41,57) / rgb(229,231,235), one h1 'Page not found', sidebar present, link back to / navigates. So the operator's damage is a blank first paint, for as long as the JS chunk takes.
- JS disabled: /analytics renders the full framed 404 (body innerText 300 chars, 7 links, bodyBg rgb(243,244,246)); /records/no-such-table/x renders document.body.innerText === '' (empty string), document.body.className === '' and getComputedStyle(document.body).backgroundColor === 'rgba(0, 0, 0, 0)' — a blank, unstyled page with no way back.

Every other route in the app server-renders its markup, including this same dynamic route when the read succeeds (/records/groups/<id>, 200, len 11438, <main> and sidebar present) and when the read FAILS (its error state SSRs fine). The notFound() path is the only one that serves an empty document.

WHY IT IS FILED RATHER THAN LEFT: it is reachable by a typed URL or a stale bookmark — the same operator behaviour BUG-0014 was opened for — and it is structural, not local: the next dynamic route that calls notFound() (a /queues/[id] detail, which the gate suite already probes) inherits the same empty document. Not a defect of src/app/not-found.tsx: that file is correct and its surface is measurably right on every unmatched URL. The fix is in how the dynamic segment renders — it is Next 16 streaming behaviour aborting the SSR render on the thrown error — so it belongs to the route, not to the 404 page.

PIN: tests/http/auth.http.test.ts, describe('a notFound() thrown inside a dynamic route'), marked it.fails — the run-branch pin, so the suite stays green while the divergence stands. It was watched RED as a plain it() first: 'expected <!DOCTYPE html><html id="__next_error…' to match /<h1[\s>]/'. When the served document carries the surface again the test XPASSes and turns red; the fix must ALSO drop the .fails.

NOT IN SCOPE OF A FIX: do not weaken the assertion; do not adopt experimental global-not-found.js (it bypasses the layout, which is the defect BUG-0014 removed).

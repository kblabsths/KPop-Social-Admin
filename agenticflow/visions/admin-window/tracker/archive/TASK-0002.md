# The staging data layer: the client seam, DbResult, and the table-name constants

## Description
Module: `src/lib/db/` — the foundation every page reads through. Authority: spec section 3 ('server-side reads reach the internal tables'), section 4; acceptance doc ground rules and test 9; SPEC F2; ARCHITECTURE sections 4, 4.1, 4.2, 6.

Ships three files and their offline tests. **No page, no component, no query for a specific surface** — those are the page tickets'.

Interface contract (later tickets code against this without reading your work):

```ts
// src/lib/db/result.ts
export type DbResult<T> =
  | { kind: "ok"; data: T }
  | { kind: "not_provisioned"; missing: string }
  | { kind: "error"; message: string };
export function classify(error: unknown, missing: string): DbResult<never>;

// src/lib/db/client.ts
export function getDbClient(): SupabaseClient;   // the ONE reader of process.env credentials

// src/lib/db/tables.ts
export const T = { reviewItems: "review_items", observations: "observations",
  fieldProvenance: "field_provenance", pendingClaims: "pending_claims",
  sources: "sources", resolutionRuns: "resolution_runs", runs: "runs",
  events: "events", eventListings: "event_listings", venues: "venues",
  groups: "groups", idols: "idols", eventPerformers: "event_performers",
  verdicts: "verdicts" } as const;
```

Rules that are the point of this ticket:

- **Every exported read in `lib/db/**` returns `Promise<DbResult<T>>` and never throws.** That is how acceptance test 9 becomes structural instead of per-page discipline.
- `classify` maps PostgREST/Postgres codes `PGRST205`, `PGRST204`, `42P01`, `42703` to `not_provisioned` (carrying the name from `tables.ts`); every other error becomes `error` carrying **the database's own message**, never a generic one (LOOK_AND_FEEL, Interaction principles: 'the app shows what the database said').
- `client.ts` is the only file in `src/` that reads database credentials from `process.env`. It reads `SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY` — **the deployed app's existing names, unchanged**, because the Railway service is never repointed by this campaign. It must never mention a `STAGING_` name (that belongs to `tests/live/setup.ts`, TASK-0003). If the answer to the env ASK ticket changes this, it changes this file and nothing else.
- `tables.ts` is the only place a table or view name is spelled. A page containing the literal `"review_items"` is a defect.
- Seed `tests/fixtures/` with the shared builders later tests import instead of hand-rolling rows: a review item in each of the three shapes, a pending claim in each bucket, a `resolution_runs` row, a `runs` row, a `sources` row, an observation, a `field_provenance` row, and a stub client that returns a scripted PostgREST response (including the table-not-in-schema-cache error shape). Columns are the ones ARCHITECTURE section 6 lists — verified against the scraper repo's migrations; do not invent one.

Out of scope: page queries, gauges, anything under `src/app/`, anything that talks to a real database (that is TASK-0003).

## Acceptance criteria
[test 9] Offline tests prove: a read whose error carries `PGRST205` / `42P01` returns `{kind:'not_provisioned', missing:<the table name>}`; a column-missing code returns not_provisioned naming the column; an arbitrary failure returns `{kind:'error'}` carrying the database's own message verbatim; a success returns `{kind:'ok'}`. No exported read throws for any of those inputs. `src/lib/db/client.ts` is the only file under `src/` reading `SUPABASE_SERVICE_ROLE_KEY`, and no file under `src/` mentions `STAGING_`. The fixture builders exist and are what the tests use.

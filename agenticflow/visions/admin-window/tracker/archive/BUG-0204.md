# The pending-claims gauge ignores the bucket facet and is the one caption on /claims that does not say so

## Description
Filed from the M3 user-sim walk of Marisa (`agenticflow/tracker/for-human/M3-usersim-marisa.md`), 2026-09-11, the section "Counts above vs. what I'm looking at":

> "The exception is the **PENDING CLAIMS GAUGE** at the bottom. Its caption only mentions its time window; it says nothing about the filters. And it ignores the bucket filter. So with `bucket=awaiting_link` I get: table: **'108 claims match these filters'**; gauge, one screen lower: **'CLAIMS IN THIS WINDOW — 877 — 1 source, 2 domains'**. And with `bucket=escalated` the table says **'the read happened and found no claims matching these filters at all'** while the gauge underneath still says **877**. Two numbers about the same thing on the same screen, and the one page element that's been scrupulously captioning its own scope everywhere else goes quiet exactly where I need it to speak up. … this is the one I'd have quoted wrong in a message to somebody."

She had just finished verifying, by hand, that every other caption on the page tells the truth about its own scope — *"that's a level of care I don't see often"* — which is what makes the one silent caption expensive.

**Expected** — LOOK_AND_FEEL bar 13 (a windowed list states the read that produced it) and the campaign's own ruling of 2026-09-11 on the surface two Sections up. The bucket table has the identical property — `bucketStats` drops the bucket facet on purpose, so its counts do not move when a bucket chip is active — and it was ruled a defect and fixed, in `src/app/claims/page.tsx:290-318`:

> *"What was wrong is that the page said 'nothing above narrows these counts' with the bucket chip standing active above it: the page denying a facet it had applied. So this clause states what this TABLE answers for, and nothing else."*

giving the shipped clause `" — these counts answer for every bucket; the bucket filter above does not narrow them"`.

**Found** — the gauge has the same property and no clause. `gaugeFilter` (`src/app/claims/page.tsx:1774-1780`) keeps `source_id` and `domain` and drops `bucket`, correctly: the gauges scan `observations`, which has no bucket column. Its `WindowLine` is handed `scope={narrowing.scope}`, which carries the source/domain narrowing and, by construction, can never carry the bucket. The page's own comment at :1150-1152 records the silence as intended — *"`?bucket=` alone narrows this section's figures not at all, **and its sentence says so by saying nothing**"* — and that is the sentence this ticket overturns: saying nothing is not how this page says anything else, and the one number a stranger would have quoted wrong is the one that said nothing.

Same read, same figures, a sentence. The figures are right and must not move.

Provenance checked before filing: `git log src/app/claims/page.tsx` returns ticket-bearing commits only (TASK-0071, BUG-0193, BUG-0186, BUG-0163 …). Not a human-lane divergence.

## Acceptance criteria
1. Where a **bucket** facet is in force on `/claims`, the pending-claims gauge's window line states what that gauge answers for — that the bucket filter above does not narrow these figures — in the same shape as the bucket table's shipped clause (`src/app/claims/page.tsx:318`), so one page gives one answer to "did my bucket chip reach this number".
2. The clause states scope and nothing more: it never names a bucket value, never claims the bucket narrowed anything (nothing did), never takes the blaming arm a real narrowing takes, and says nothing about the list above or about why that list is empty (LESSONS 2 and 3, and the 2026-09-11 ruling on the table's clause).
3. Where a source or domain facet is ALSO in force, the existing scope phrases are unchanged and the new clause is added to them, exactly as the table's clause is added to its blaming arm rather than replacing it.
4. The unnarrowed page, the source-narrowed page and the domain-narrowed page render byte-identically to today: only the arm where a bucket facet is in force gains a clause.
5. **No figure changes.** The gauge still reads `observations` by source and domain and knows nothing of buckets; `gaugeFilter` is untouched; no new read, no new leg, no new bound.
6. The standing tab's gauge is out of scope: that tab owns its bucket rather than carrying it as a URL facet, and its line already says what it says.
7. The comment at `src/app/claims/page.tsx:1150-1152` recording the old intent ("its sentence says so by saying nothing") is replaced by what the page now does — the check below fails while it stands.
8. The offline suite grades it at the surface: a test named `says the bucket filter does not narrow the gauge` (that string, so the check below can find it) asserts the clause is present for `?bucket=awaiting_link` and `?bucket=escalated`, absent for a bare `/claims`, and present alongside the source phrase for `?bucket=…&source_id=…`.
9. Human-check: at 1440x900, `/claims?bucket=escalated` reads as one page — the list says the read found no claims matching these filters, the gauge says 877 in its window, and the gauge's own line says the bucket filter did not narrow it. **(human-checkable)**

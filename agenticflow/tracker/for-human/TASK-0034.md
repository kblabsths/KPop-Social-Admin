## 1. The walker cannot save, and a sandbox table does not fix that

STACK.md §5 records it already: the PATCH route calls `requireAdmin()`, which
looks the session email up in `admin_allowed_emails` on every request. Staging's
allowlist does not hold `walker@admin-window.local`, so every save from a walk
gets a 403 — correctly. STACK also records that this row is **your call and no
agent adds it**, so the sandbox buys read-and-render walks only until you
answer. Two ways:

```sql
-- either: give the walker identity its own labelled row on STAGING only
insert into public.admin_allowed_emails (email)
values ('walker@admin-window.local')
on conflict do nothing;
```

or, no database write at all: tell the walkers to mint the cookie with
`--email <an address the allowlist already holds>`
(`node tests/walk/session-cookie.mts --email …`). That reuses a real admin
identity, which is honest for a walk and leaves no extra row behind — but the
walk's writes then appear under your name.

## 2. The table, if you would rather not wait

The architect (TASK-0034) is ruling between: **A** you create it once by hand
and the tooling only truncates/reseeds (no new dependency, and the standing
rule that nothing in `src/` or `tests/` reads `STAGING_SUPABASE_DB_URL` stays
intact), or **B/C** the tooling creates it itself over that DB URL with a
Postgres driver (a new dependency through the supply gate, plus a DSN-shaped
credential in the repo). If you want A now, this is the paste — **staging
project only, never production**:

```sql
create table if not exists public.walk_sandbox (
  sandbox_id  text primary key,
  label       text not null,
  note        text,
  tally       integer not null default 0,
  is_flagged  boolean not null default false,
  observed_on date,
  updated_at  timestamptz not null default now()
);
alter table public.walk_sandbox enable row level security;  -- service role only; no policy

insert into public.walk_sandbox (sandbox_id, label, note, tally, is_flagged, observed_on) values
  ('walk-1', 'First sandbox row', 'A note a walker may rewrite.', 7,  false, '2026-01-15'),
  ('walk-2', 'Second sandbox row', null,                          0,  true,  null),
  ('walk-3', 'Third sandbox row', 'Leave this one alone.',        42, false, '2026-02-29')
on conflict (sandbox_id) do nothing;
```

One column per edit type — text, nullable text, integer, boolean, date — because
the widget is a single text cell and all the type work happens on the way into
PostgREST. `walk-2`'s empty `note` is the em-dash absence a walker fills in.
Tell TASK-0034 you did it and the ruling collapses to option A.
